# Day 2 - 비용 관리 도구: 얼마 썼는지 보고, 새기 전에 막는다

## 📌 핵심 정리

- **Cost Explorer** = **가계부**. 지난 비용을 그래프로 들여다보고, 이 추세면 앞으로 얼마 나올지 예측한다.
- **AWS Budgets** = **카드 사용 알림**. 한도를 미리 정해두면 가까워지거나 넘을 때 먼저 알려준다.
- **CUR(Cost and Usage Report)** = **거래 명세 원본**. 가장 상세한 라인 아이템을 S3로 내보내 맞춤 분석에 쓴다.
- **비용 할당 태그** = **지출 항목 라벨**. 태그를 붙이고 **활성화**까지 해야 팀·프로젝트별로 비용이 갈린다.
- 흐름 한 줄: **본다(Cost Explorer) → 막는다(Budgets) → 깊이 판다(CUR) → 누구 것인지 가른다(태그).**

어제 우리는 같은 자원도 구매 방식에 따라 값이 달라진다는 걸 배웠다. 그런데 아무리 잘 골라도 **얼마를 어디에 쓰고 있는지 보이지 않으면** 최적화도, 통제도 불가능하다. 오늘은 비용을 들여다보고(분석), 미리 막고(예산 경고), 자세히 뜯어보고(상세 보고서), 누가 무엇에 썼는지 구분(태그)하는 네 가지 도구를 정리한다.

핵심 질문은 셋이다: "지난 비용은 어떻게 생겼나?", "예산을 넘기 전에 알 수 있나?", "이 비용이 어느 팀·프로젝트 것인가?"

## 왜 클라우드에 와서야 "비용 관리 도구"가 필요해졌나

이 도구들이 왜 생겼는지는 **도구가 없던 시절**을 떠올려 보면 단번에 이해된다.

온프레미스 시절에는 비용 질문이 이미 끝나 있었다. 서버를 사는 순간 값이 정해졌고, 그다음 몇 년은 전기 요금 정도만 오갔다. "이번 달에 우리 팀이 얼마 썼지?"라는 질문 자체가 잘 나오지 않았다. **이미 나간 돈**이었기 때문이다.

클라우드는 정반대다. 세 가지가 한꺼번에 바뀌었다.

1. **비용이 매 순간 발생한다** — 켜둔 시간이 곧 돈이다. 어제 잠깐 켜본 서버를 끄지 않으면 오늘도, 내일도 요금이 붙는다.
2. **누구나 자원을 켤 수 있다** — 클라우드의 장점인 "주문형 셀프서비스"가 비용 측면에서는 위험이 된다. 결재 없이 클릭 몇 번이면 자원이 생기고, 켠 사람이 잊으면 아무도 모른다.
3. **항목이 잘게 쪼개진다** — 청구서 한 장에 수백 줄이 찍힌다. 눈으로 훑어서는 무엇이 늘었는지 알 수 없다.

그래서 도구가 없는 조직의 클라우드 청구서는 **"월말에 열어보고 놀라는 편지"**가 되기 쉽다. 테스트하려고 잠깐 띄운 서버 한 대, 지우는 걸 잊은 디스크 스냅샷 — 각각은 작지만 한 달을 곱하면 무시할 수 없는 금액이 된다. 더 나쁜 건 **월말에야 알게 된다**는 점이다.

```
[도구가 없는 조직]
자원 생성 ──── 한 달 내내 아무도 모름 ──── 월말 청구서 (놀람)

[도구를 쓰는 조직]
자원 생성 ─ 태그로 라벨 ─ Budgets 경고 ─ Cost Explorer 점검 ─ 예상했던 청구서
             (누구 것)     (한도 임박)      (어디가 늘었나)
```

오늘 배우는 네 도구는 이 그림의 아래쪽 줄을 만드는 부품들이다. **비용을 사고가 난 뒤에 확인하는 것에서, 나기 전에 다루는 것으로** 바꾸는 게 목표다.

> 📚 **사례**: 직원 열 명 남짓한 어느 스타트업이 클라우드로 옮긴 첫 달을 상상해 보자. 예산은 넉넉히 잡았는데 청구서가 그 두 배로 나왔다. 원인은 신입 개발자가 성능 테스트용으로 띄운 큰 서버들을 하나만 끄고 나머지를 잊은 것이었다. 잘못한 사람을 찾는 게 요점이 아니다. **그 조직에는 "누가 무엇을 켰는지"를 보여주는 장치도, "예산의 절반을 넘었다"고 알려주는 장치도 없었다**는 게 진짜 문제다.

> 💡 **개념**: "클라우드 비용을 지속적으로 보고, 배분하고, 최적화하는 일을 조직의 습관으로 만드는 것"을 클라우드 재무 관리(Cloud Financial Management)라고 부른다. AWS Well-Architected Framework의 **비용 최적화(Cost Optimization)** 기둥과 같은 이야기다.

## AWS Cost Explorer: 비용을 보고 예측한다

**AWS Cost Explorer**는 **과거 비용·사용량을 시각화하고 미래를 예측**하는 분석 도구다. 그래프와 표로 "지난 6개월 동안 어떤 서비스에 얼마를 썼는지", "이 추세면 다음 달은 얼마쯤 나올지"를 보여준다. 서비스별·리전별·태그별로 쪼개 볼 수도 있다.

쓰임은 명확하다. 어떤 서비스가 비용을 잡아먹는지 찾아내고, RI나 Savings Plans 추천도 받아 최적화 기회를 발견한다. 한마디로 **"과거를 분석하고 미래를 내다보는"** 도구다.

**비유하자면 가계부다.** 가계부를 쓰는 이유는 돈을 안 쓰기 위해서가 아니라 **어디로 새는지 알기 위해서**다. 총액만 보면 "이번 달은 많이 썼네" 이상을 알 수 없지만, 식비·교통비·구독료로 쪼개면 "구독료가 조용히 늘고 있었구나"가 드러난다. Cost Explorer가 하는 일이 정확히 이것이다.

Cost Explorer가 비용을 쪼개는 기준은 여러 가지다.

| 쪼개는 기준 | 이런 질문에 답한다 |
|-------------|--------------------|
| 서비스별 | "우리 비용의 절반은 어느 서비스에서 나오나?" |
| 기간별(일·월) | "언제부터 늘기 시작했나?" |
| 리전별·계정별 | "안 쓰는 줄 알았던 곳에서 요금이 나오나?" |
| 태그별 | "어느 팀·프로젝트의 비용인가?" (태그 활성화 필요) |

실무에서 Cost Explorer를 여는 순간은 청구서가 늘었을 때 **"어디가 늘었는지"**를 찾기 위해서다. **총액 → 서비스 → 리전 → 자원**으로 좁혀 가는 것이 비용 조사의 기본 동선이다. 예측 기능도 같은 맥락으로, "지금 속도면 예산을 넘긴다"는 판단을 **월 중간에** 내릴 수 있게 해준다.

> 📚 **사례**: 어느 온라인 교육 서비스의 청구서가 갑자기 크게 늘었다. 총액만 봐서는 원인을 알 수 없었지만 Cost Explorer에서 서비스별로 쪼개니 데이터 전송 비용만 유독 튀어 있었다. 파고들어 보니 새로 올린 고화질 강의 영상이 CDN 없이 매번 원본 스토리지에서 직접 나가고 있었다. 서비스가 느려진 것도, 장애가 난 것도 아니어서 **비용 그래프를 보기 전에는 아무도 이상을 눈치채지 못했다**. 비용 가시성이 곧 아키텍처 문제의 조기 경보가 되는 전형적인 장면이다.

> 💡 **관련 이론**: "비용 추이 시각화", "서비스별 분석", "향후 비용 예측"이 보이면 Cost Explorer다. 분석·예측이 핵심이지, 한도 경고를 보내는 도구는 아니다(그건 Budgets).

> ⚠️ **함정**: Cost Explorer는 **사람이 열어봐야 보이는** 도구다. 알아서 문자나 메일을 보내주지 않는다. 시험 문항에 "**자동으로 알림을 받아**", "**한도에 도달하면 통보**" 같은 표현이 섞여 있으면 정답은 Cost Explorer가 아니라 **Budgets**다. 반대로 "그래프로 확인", "추세 분석", "예측"이라면 Cost Explorer다. 이 두 도구를 가르는 단어는 결국 **"보러 간다" vs "알려준다"**이다.

## AWS Budgets: 예산을 정하고 넘기 전에 알린다

**AWS Budgets**는 **비용·사용량 예산을 설정하고, 그 한도에 가까워지거나 초과하면 알림(이메일/SNS)을 보내는** 도구다. 예를 들어 "월 $500"으로 예산을 잡고 "80%(=$400)에 도달하면 알려줘"라고 설정하면, 청구서가 폭탄이 되기 전에 미리 손쓸 수 있다.

Cost Explorer와 자주 헷갈리지만 역할이 다르다. Cost Explorer는 "이미 쓴 비용을 분석", Budgets는 "앞으로 새지 않도록 미리 경고"다. 둘은 보완 관계다.

| 항목 | Cost Explorer | AWS Budgets |
|------|---------------|-------------|
| 초점 | 과거 비용 분석·미래 예측 | 예산 설정·임계치 알림 |
| 주된 동작 | 시각화/리포트 조회 | 한도 도달 시 사전 경고 |
| 언제 | "얼마 썼는지 보고 싶다" | "예산 넘기 전에 알고 싶다" |

**비유하자면 카드 사용 알림 문자다.** 문자가 오는 이유는 명세서를 볼 줄 몰라서가 아니라 **명세서는 한 달 뒤에 오고 그때는 이미 늦기 때문**이다. Budgets는 클라우드 요금에 이 알림을 붙여준다. 콘솔에 들어가 보지 않아도 알림이 먼저 찾아온다.

예산은 금액(비용 예산)뿐 아니라 **사용량 자체**를 기준으로도 잡을 수 있고, 예약 인스턴스·Savings Plans를 사두고 잘 쓰고 있는지(활용률·커버리지)를 감시하는 용도로도 쓸 수 있다.

알림을 거는 기준은 두 가지다. **실제(actual) 기준**은 이미 쓴 금액이 임계치에 닿았을 때 울리고, **예측(forecasted) 기준**은 "이 추세면 넘겠다" 싶을 때 미리 울린다. 앞은 확실하지만 늦고, 뒤는 빠르지만 추정이다. 그래서 보통 둘을 함께 걸어둔다.

> 📚 **사례**: 한 소규모 게임 스튜디오가 신작 테스트 서버를 올리며 개발용 계정에 별도 예산을 걸어두었다. 곧 "이 추세면 이번 달 예산을 넘길 것으로 보인다"는 예측 알림이 왔고, 확인해 보니 부하 테스트 스크립트가 종료 처리에 실패해 매번 서버를 새로 만들고만 있었다. **월말 청구서로 알았다면 한 달 치를 다 물었을 일을, 알림 덕분에 며칠 치로 끊었다.**

> 💡 **관련 이론**: "예산 설정", "임계치 초과 시 알림", "비용 폭탄 예방"이 보이면 Budgets다. "분석/예측"이면 Cost Explorer.

> ⚠️ **함정**: Budgets는 기본적으로 **알려주는** 도구다. 예산을 넘겼다고 해서 AWS가 알아서 서비스를 끄거나 계정을 잠그지 않는다. 시험 보기에 "**예산을 초과하면 자동으로 리소스가 중지된다**"처럼 적혀 있으면 오답 신호로 보자. 자동 조치가 필요하면 알림에 별도의 조치를 연결해 **직접 설계해야** 한다. 클라우드의 기본 태도는 "고객의 워크로드를 마음대로 멈추지 않는다"이며, 통제는 고객 책임이라는 공동 책임 모델과도 결이 같다.

## AWS Cost and Usage Report(CUR): 가장 상세한 청구 데이터

**AWS Cost and Usage Report(CUR)**는 AWS가 제공하는 **가장 상세한 비용·사용량 데이터**다. 모든 사용 라인 아이템을 시간 단위까지 쪼개 S3 버킷으로 내보내며, Athena·QuickSight 같은 분석 도구와 연결해 깊이 파고들 수 있다.

Cost Explorer가 "대시보드 수준의 시각화"라면, CUR은 "원천 데이터(raw data) 그 자체"다. 회계팀이 정밀하게 비용을 배분하거나, 대규모 조직이 맞춤 분석을 해야 할 때 쓴다.

**비유하자면 은행 거래 명세 원본이다.** 은행 앱의 "카테고리별 지출" 요약 화면이 Cost Explorer라면, 세무사에게 넘기는 **모든 거래가 한 줄씩 찍힌 원본 파일**이 CUR이다. 원본은 보기 불편하지만, 요약 화면이 답해 주지 못하는 질문까지 답할 수 있다.

언제 원본이 필요할까. 부서별 정산이 소수점까지 맞아야 할 때, 그리고 **"고객 한 명당 인프라 비용"처럼 AWS가 미리 만들어 두지 않은 각도**로 보고 싶을 때다.

```
[CUR이 지나가는 길]
AWS 청구 데이터 ──> S3 버킷에 파일로 적재 ──> 분석 도구(Athena/QuickSight 등)
   (라인 아이템)        (내가 소유한 저장소)        (내가 원하는 질문)
```

정리하면 **Cost Explorer는 "AWS가 만들어 준 화면을 본다", CUR은 "내가 원하는 화면을 직접 만든다"**는 차이다. 데이터를 다룰 사람과 도구가 있는 조직에서 진가를 발휘하며, 소규모 팀이라면 Cost Explorer만으로도 대체로 충분하다.

> 💡 **관련 이론**: "가장 상세한", "라인 아이템 수준", "S3로 내보내 맞춤 분석"이 보이면 CUR이다. 가벼운 조회·예측은 Cost Explorer, 정밀 원천 데이터는 CUR로 구분하자.

> ⚠️ **함정**: CUR을 켰다고 해서 콘솔에 새 그래프가 생기지 않는다. CUR이 하는 일은 **파일을 내 S3 버킷에 떨어뜨려 주는 것까지**이고, 그 뒤로 무엇을 할지는 고객 몫이다. 시험 보기에서 "가장 상세한", "raw", "내보내기", "맞춤 분석"이라는 단어가 함께 나오면 CUR, "바로 보기 좋은 그래프"라면 Cost Explorer라고 갈라두자.

## 비용 할당 태그(Cost Allocation Tags): 누구의 비용인지 가른다

**비용 할당 태그**는 리소스에 붙인 태그(키-값, 예: `Project=alpha`, `Team=marketing`)를 **청구 데이터에서 비용 구분 기준으로 활성화**하는 기능이다. 그러면 Cost Explorer나 CUR에서 "마케팅팀이 쓴 비용", "alpha 프로젝트 비용"처럼 **태그별로 비용을 쪼개** 볼 수 있다.

태그 없이는 모든 비용이 한 덩어리로 보여 "이게 누구 비용이냐"를 따질 수 없다. 그래서 부서별 비용 청구(쇼백/차지백)나 프로젝트 단위 정산에 필수다.

```
[태그가 비용 가시성을 만든다]
태그 없음 → 전체 비용 한 덩어리, 책임 소재 불분명
태그 있음 → Team/Project/Env 별로 비용 분리, 정확한 배분
```

**비유하자면 영수증에 붙이는 지출 항목 라벨이다.** 서랍에 영수증을 몽땅 넣어두면 총액은 알아도 "이번 출장에 얼마 썼나"는 알 수 없다. 영수증마다 '출장', '회식', '비품'이라고 적어 두면 그때부터 분류가 가능해진다. 클라우드에서 그 라벨 역할을 하는 게 태그다.

태그가 실제로 비용 리포트에 나타나려면 **두 단계**를 다 밟아야 한다. ① 리소스에 `Team=marketing` 같은 키-값을 붙이고, ② 청구 화면에서 그 태그를 **비용 할당 태그로 활성화**한다. ②를 잊으면 태그는 붙어 있는데 리포트에는 아무 변화가 없다. "태그를 다 달았는데 왜 안 보이죠?"의 답은 대부분 여기에 있다.

태그는 고객이 직접 정하는 **사용자 정의 태그**(`Team`, `Project`, `Env`, `CostCenter` 등)와 AWS가 자동으로 붙여주는 **AWS 생성 태그**로 나뉜다. 비용 배분에 실제로 쓰이는 건 대부분 앞쪽이다.

그리고 조직이 먼저 정해야 할 게 하나 있다 — **이름 규칙**이다. 태그 키는 대소문자를 구분해서 `Team`, `team`, `TEAM`이 **서로 다른 태그**로 취급된다. 사람마다 다르게 적으면 비용이 세 갈래로 흩어져 아무것도 집계되지 않는다. 그래서 성숙한 조직은 태그를 **표준 목록으로 관리**한다.

이렇게 갈라 놓은 비용은 **쇼백(showback)** — "당신 팀은 이만큼 썼습니다"라고 보여만 주기 — 이나 **차지백(chargeback)** — 그 금액을 실제로 팀 예산에서 차감하기 — 으로 쓰인다. 둘 다 태그 없이는 시작조차 할 수 없다. **"태그는 비용 관리의 전제 조건"**이라고 외워도 좋다.

> 📚 **사례**: 사업부 세 곳이 하나의 계정을 함께 쓰던 회사를 떠올려 보자. 청구서는 한 장으로 오고 그 금액은 통째로 정보시스템팀 예산에서 나갔다. 결과는 예상대로였다 — 자원을 만드는 건 사업부, 돈을 무는 건 정보시스템팀. 아무도 아끼지 않았다. 이 회사가 한 일은 요금제를 바꾸는 것도, 서버를 줄이는 것도 아니었다. **태그 규칙을 정하고, 태그를 켜고, 매달 사업부별 비용을 공유하기 시작한 것**이 전부였다. 그것만으로 안 쓰는 자원이 눈에 띄게 정리됐다. 비용은 보이는 순간부터 관리되기 시작한다.

> 💡 **관련 이론**: "부서·프로젝트별 비용 구분", "비용을 팀에 배분", "태그 기준으로 청구"가 보이면 비용 할당 태그다. 분석 도구(Cost Explorer/CUR)는 태그가 켜져 있어야 태그별로 비용을 보여줄 수 있다.

> ⚠️ **함정**: 태그를 나중에 활성화하면 **활성화한 시점 이후의 데이터부터** 태그별로 갈린다. 지난달 청구서가 소급해서 예쁘게 나뉘지는 않는다. 그래서 태그 규칙은 계정을 늘리기 전, 자원이 많아지기 전에 **먼저** 정해두는 편이 압도적으로 편하다.

## 헷갈리는 넷을 한 번에 구분하기

시험에서 이 네 가지(+ 청구 대시보드)는 늘 같은 보기 안에 함께 등장한다.

| 도구 | 한 줄 정체 | 시점 | 사람이 해야 하는 일 |
|------|-----------|------|---------------------|
| 청구 대시보드 | 이번 달 현재까지의 요금 요약 첫 화면 | 지금 | 열어본다 |
| Cost Explorer | 비용을 쪼개 보고 추세를 예측하는 분석 화면 | 사후 | 열어보고 파고든다 |
| AWS Budgets | 한도를 정해두고 넘기 전에 알려주는 경고 장치 | 사전 경고 | 한 번 설정해두면 알림이 온다 |
| CUR | 가장 상세한 청구 원본 데이터를 S3로 내보내기 | 사후(정밀) | 분석 도구로 직접 가공한다 |
| 비용 할당 태그 | 비용을 팀·프로젝트로 가르는 라벨 | 전제 조건 | 태그를 달고 활성화한다 |

**태그가 없으면 나눌 수 없고, Cost Explorer가 없으면 볼 수 없고, Budgets가 없으면 늦게 알고, CUR이 없으면 깊이 팔 수 없다.** 네 가지는 서로를 대체하지 않는다.

## 시험에 이렇게 나온다

문항에 아래 표현이 보이면 답이 정해진다. 반대로 흔한 함정 선택지도 함께 적어 둔다.

| 문항에 이런 표현이 나오면 | 정답은 | 자주 나오는 함정 선택지 |
|---------------------------|--------|-------------------------|
| "그래프로 시각화", "추세 분석", "다음 달 예측" | Cost Explorer | Budgets(알림 도구라 성격이 다름) |
| "임계치에 도달하면 알림", "초과 전에 통보" | AWS Budgets | Cost Explorer(자동 알림 없음) |
| "가장 상세한", "라인 아이템", "S3로 내보내 맞춤 분석" | CUR | Cost Explorer(요약 수준) |
| "부서별로 비용을 나눠 정산", "프로젝트별 비용 구분" | 비용 할당 태그 | Budgets(나누는 기능이 아님) |
| "배포하기 전에 예상 비용을 계산" | Pricing Calculator(Day 4) | Cost Explorer(이미 쓴 비용용) |
| "누가 어떤 API를 호출했는지 추적" | CloudTrail(비용 도구 아님) | Cost Explorer |

마지막 줄이 특히 중요하다. **CloudTrail은 비용 도구가 아니라 감사(누가 무엇을 했는가) 도구**다. 비용 문항의 보기에 슬쩍 섞여 드는 단골 오답이다.

## 한 장으로 정리

| 신호(키워드) | 도구 |
|--------------|------|
| 과거 비용 시각화·서비스별 분석·미래 예측 | Cost Explorer |
| 예산 설정, 임계치 초과 시 알림 | AWS Budgets |
| 가장 상세한 라인 아이템, S3 내보내기, 맞춤 분석 | Cost and Usage Report(CUR) |
| 팀·프로젝트별 비용 구분/배분 | 비용 할당 태그 |

## 정리하며

오늘의 한 문장: **본다(Cost Explorer) → 막는다(Budgets) → 깊이 판다(CUR) → 누구 것인지 가른다(태그).** 이 네 도구는 따로 노는 게 아니라 하나의 비용 관리 흐름을 이룬다. 비용을 시각화해 새는 곳을 찾고, 예산 알림으로 폭탄을 예방하고, 상세 보고서로 정밀 분석하며, 태그로 책임 소재를 분명히 한다.

한 가지만 더. 이 도구들은 **켜두는 것만으로는 아무 일도 하지 않는다.** 그래프는 누군가 열어봐야 하고, 예산 알림은 누군가 받아 조치해야 한다. 비용 관리는 기술보다 **습관과 책임의 문제**에 가깝다.

다음 글에서는 문제가 생겼을 때 AWS가 우리를 어떻게 돕는지 — 지원 플랜과 Trusted Advisor — 를 살펴본다.

## 📖 용어

- **AWS Cost Explorer** : 지난 비용을 그래프로 쪼개 보고 앞으로의 비용을 예측하는 분석 화면. 가계부에 해당한다.
- **AWS Budgets** : 비용·사용량 한도를 정해두고 가까워지거나 넘으면 알려주는 경고 장치. 카드 사용 알림에 해당한다.
- **실제(actual) / 예측(forecasted) 기준 알림** : 이미 쓴 금액이 닿았을 때 울리는 알림 / 이 추세면 넘겠다 싶을 때 미리 울리는 알림.
- **CUR(Cost and Usage Report)** : 가장 상세한 청구 원본 데이터를 내 S3 버킷으로 내보내는 기능. 거래 명세 원본에 해당한다.
- **라인 아이템** : 청구 데이터에서 사용 내역 한 줄. CUR이 다루는 가장 작은 단위다.
- **비용 할당 태그** : 리소스에 붙인 키-값 라벨을 청구 데이터의 구분 기준으로 쓰는 기능. 활성화해야 적용된다.
- **쇼백 / 차지백** : 팀별 사용 비용을 알려만 주기 / 실제로 그 팀 예산에서 차감하기.
- **청구 대시보드** : 이번 달 현재까지의 누적 요금과 서비스별 요약을 보여주는 첫 화면.
- **클라우드 재무 관리** : 클라우드 비용을 지속적으로 보고, 배분하고, 줄여 나가는 조직의 운영 습관.

## 📝 연습 문제

**문제 1.** 지난 몇 달간 어떤 서비스에 비용이 가장 많이 들었는지 그래프로 분석하고, 향후 비용을 예측하려 한다. 가장 적합한 도구는?

A) AWS Budgets  
B) AWS Cost Explorer  
C) 비용 할당 태그  
D) AWS CloudTrail  

**정답: B**  
해설: Cost Explorer는 과거 비용·사용량을 시각화하고 미래 비용을 예측하는 분석 도구다. Budgets는 예산 초과 알림용이고, 비용 할당 태그는 비용 구분 기준일 뿐 분석·예측 자체를 하지 않으며, CloudTrail은 API 감사 로그라 비용 분석 도구가 아니다.

---

**문제 2.** 월 예산을 정해두고, 실제 비용이 그 한도의 일정 비율에 도달하면 자동으로 알림을 받아 초과를 예방하려 한다. 가장 적합한 도구는?

A) AWS Cost Explorer  
B) AWS Cost and Usage Report  
C) AWS Budgets  
D) AWS Pricing Calculator  

**정답: C**  
해설: AWS Budgets는 비용·사용량 예산을 설정하고 임계치 도달·초과 시 알림을 보내 비용 폭탄을 예방한다. Cost Explorer는 사후 분석, CUR은 상세 데이터 내보내기, Pricing Calculator는 사전 비용 견적용이라 임계치 알림 기능이 핵심이 아니다.

---

**문제 3.** 회계팀이 시간 단위까지 쪼개진 가장 상세한 라인 아이템 청구 데이터를 S3로 내보내 Athena로 맞춤 분석하려 한다. 가장 적합한 것은?

A) AWS Budgets  
B) AWS Cost and Usage Report(CUR)  
C) AWS Cost Explorer  
D) 비용 할당 태그  

**정답: B**  
해설: CUR은 AWS가 제공하는 가장 상세한 비용·사용량 데이터로, S3로 내보내 Athena·QuickSight와 연계한 맞춤 분석에 적합하다. Cost Explorer는 대시보드 수준 시각화, Budgets는 예산 알림, 태그는 비용 구분 기준이라 원천 데이터 분석 용도와 다르다.

---

**문제 4.** 여러 팀이 같은 계정을 쓰는데, 각 팀이 발생시킨 비용을 분리해 부서별로 정산하려 한다. 가장 먼저 활용해야 할 기능은?

A) 비용 할당 태그  
B) 스팟 인스턴스  
C) AWS Budgets  
D) 프리 티어  

**정답: A**  
해설: 비용 할당 태그를 활성화하면 Team·Project 같은 태그 기준으로 비용을 쪼개 부서별로 배분·정산할 수 있다. Budgets는 예산 알림이고, 스팟·프리 티어는 요금 모델/무료 한도라 비용을 팀별로 구분하는 기능과 무관하다.

**문제 5.** Cost Explorer와 AWS Budgets의 핵심 차이를 가장 정확히 설명한 것은?

A) Cost Explorer는 예산 알림, Budgets는 비용 시각화를 한다  
B) Cost Explorer는 과거 분석·예측, Budgets는 예산 설정·초과 알림을 한다  
C) 둘 다 동일하며 이름만 다르다  
D) Cost Explorer는 무료 한도 관리, Budgets는 태그 관리를 한다  

**정답: B**  
해설: Cost Explorer는 과거 비용을 분석하고 미래를 예측하는 도구이고, Budgets는 예산을 정해 임계치 초과 시 알림을 보내는 도구다. 둘은 역할이 다른 보완 관계이며, 무료 한도 관리나 태그 관리가 본래 역할은 아니다.
