# Day 1 - 도메인 복습 1: 클라우드 개념 + 클라우드 기술 및 서비스 핵심 총정리

## 📌 핵심 정리

- 오늘 다루는 두 영역(Domain 1 + Domain 3)만으로 전체의 **58%**입니다.
- Domain 1은 **"왜 클라우드인가"**, Domain 3은 **"그래서 무엇을 쓰는가"**입니다.
- 개념에서 자주 갈리는 축은 **확장성 vs 탄력성**, **가용성 vs 내구성**, **리전 vs AZ vs 엣지** 셋입니다.
- 서비스는 이름이 아니라 **"어떤 상황이면 이것"**이라는 조건을 외웁니다. 문항은 언제나 상황을 묘사합니다.
- 스토리지 3형제(S3·EBS·EFS)와 DB 3형제(RDS·DynamoDB·Redshift)는 매 회차 나온다고 보고 준비하세요.
- 오늘의 목표는 읽는 것이 아니라 **가리고 말해 보는 것(인출 연습)**입니다.

마지막 한 주가 시작됐습니다. 이번 주는 새로운 지식을 더 쌓기보다 **이미 배운 것을 시험에서 꺼낼 수 있도록 정리**하는 데 집중합니다. 오늘은 CLF-C02 4개 시험 영역 중 비중이 가장 큰 두 영역인 **Domain 1 (클라우드 개념, 24%)** 과 **Domain 3 (클라우드 기술 및 서비스, 34%)** 을 한 번에 훑어봅니다.

### 복습 회차는 이렇게 쓰는 게 좋습니다

지금부터는 **새로 읽는 시간**이 아니라 **꺼내는 시간**입니다. 눈으로 훑으면 "안다"고 착각하기 쉽지만, 시험장에서 필요한 것은 아무것도 안 보이는 상태에서 **끄집어내는 능력**입니다. 그래서 오늘 문서는 표가 많습니다. 표를 볼 때마다 오른쪽(정답 열)을 가리고, 왼쪽만 보고 **소리 내어** 답한 뒤, 막힌 항목만 표시해 원래 회차로 돌아가세요.

> 💡 **개념**: 이렇게 답을 먼저 떠올린 뒤 확인하는 방식을 **인출 연습(retrieval practice)**이라고 합니다. 같은 시간을 써도 여러 번 다시 읽는 것보다 기억에 오래 남습니다. 시험이 요구하는 동작 자체가 '인출'이므로, 연습도 같은 동작으로 해야 효과가 큽니다.

## Domain 1 핵심 — 클라우드 개념

### 클라우드의 6가지 이점 (꼭 외우기)

| 이점 | 핵심 의미 |
|------|-----------|
| 선행 비용을 가변 비용으로 | 데이터센터 선투자 대신 사용한 만큼 지불 |
| 규모의 경제 이점 | AWS 전체 사용량 덕분에 단가 인하 |
| 용량 추정 불필요 | 필요할 때 늘리고 줄임 (탄력성) |
| 속도와 민첩성 향상 | 클릭 몇 번으로 리소스 확보 |
| 데이터센터 운영·유지 비용 절감 | 인프라 관리 부담 제거 |
| 몇 분 만에 전 세계 배포 | 리전 선택으로 글로벌 확장 |

이 여섯 가지가 왜 '이점'인지는 **클라우드가 없던 시절**을 떠올리면 바로 이해됩니다. 예전에는 사람이 몇 명 올지를 개발 전에 숫자로 정하고, 그에 맞춰 장비를 주문하고, 배송·설치·전력·냉방까지 준비한 뒤에야 코드를 올릴 수 있었습니다. 그런데 그 예측은 어차피 틀립니다. 많이 사면 놀리는 장비에 돈이 묶이고, 적게 사면 사람이 몰리는 바로 그 순간에 서비스가 멈춥니다. 클라우드는 **"미리 맞힐 필요"를 없애서** 이 딜레마를 지웠고, 나머지 이점은 대부분 여기서 파생됩니다.

### 헷갈리기 쉬운 개념 짝

개념 영역에서 실제로 점수가 갈리는 곳은 아래 네 짝입니다. 이름이 비슷해서 대충 넘기기 쉬운데, 문항은 정확히 이 차이를 노립니다.

| 짝 | 차이 | 한 줄 기억법 |
|----|------|--------------|
| 확장성(Scalability) vs 탄력성(Elasticity) | 늘릴 수 **있는가** vs 수요에 맞춰 **자동으로** 늘고 주는가 | 능력이냐, 자동이냐 |
| 고가용성(High Availability) vs 내결함성(Fault Tolerance) | 장애가 나도 **금방 회복** vs 장애가 나도 **끊김 없이 계속** | 빨리 복구냐, 아예 안 멈추냐 |
| 가용성 vs 내구성(Durability) | 지금 **접근 가능한가** vs 데이터가 **사라지지 않는가** | 열리느냐, 남아 있느냐 |
| 민첩성(Agility) vs 확장성 | 새로 **시작하는 속도** vs 커지는 **능력** | 빨리 해보기냐, 크게 키우기냐 |

> ⚠️ **함정**: "수요가 늘면 서버를 추가한다"는 문장만 보고 무조건 **탄력성**을 고르면 위험합니다. 사람이 손으로 추가한다면 그것은 **확장성**입니다. 탄력성이라는 단어가 정답이 되려면 "**자동으로**", "**수요에 따라 자동 조절**" 같은 표현이 함께 있어야 합니다. 반대로 "수동으로 크기를 조정할 수 있다"는 문장에 탄력성을 고르면 틀립니다.

### 클라우드 컴퓨팅 모델 / 배포 모델

| 구분 | 종류 | 핵심 |
|------|------|------|
| 컴퓨팅 모델 | IaaS / PaaS / SaaS | 통제권 ↔ 관리 부담의 균형 |
| 배포 모델 | 클라우드 / 하이브리드 / 온프레미스 | 데이터·워크로드 위치 |

> 💡 **관련 이론**: IaaS는 사용자가 OS까지 관리(EC2), PaaS는 코드만 관리(Elastic Beanstalk), SaaS는 사용만 함(즉시 사용 가능한 완제품). "운영체제를 직접 패치한다"는 키워드가 나오면 IaaS입니다.

세 모델이 아직 손에 안 잡힌다면 **식사 준비**로 바꿔 생각해 보세요. 재료와 주방을 빌려 직접 요리하면 IaaS, 주방장이 있는 부엌에 레시피(코드)만 건네면 PaaS, 완성된 음식을 사 먹으면 SaaS입니다. 위로 갈수록 편하지만 **내가 손댈 수 있는 범위는 줄어듭니다.** 문항이 "통제권을 최대한 갖고 싶다"고 하면 아래쪽(IaaS), "관리 부담을 최소화하고 싶다"고 하면 위쪽(PaaS/SaaS)입니다.

### AWS 글로벌 인프라

- **리전(Region)**: 지리적으로 떨어진 영역. 데이터 주권/지연 시간/요금이 다름
- **가용 영역(AZ)**: 한 리전 안의 물리적으로 분리된 데이터센터 묶음. **고가용성의 기본 단위**
- **엣지 로케이션(Edge Location)**: CloudFront 콘텐츠 캐싱 지점

셋의 관계는 포함 구조로 보면 한 번에 정리됩니다.

```
 [ 리전 (예: 서울) ]
    ├── 가용 영역 A   ← 물리적으로 떨어진 데이터센터 묶음
    ├── 가용 영역 B   ← 여기에 나눠 배치 = 고가용성
    └── 가용 영역 C
 [ 엣지 로케이션 ]  ← 리전 밖, 사용자와 가까운 곳에 다수
                     콘텐츠를 캐싱해 응답을 빠르게 (CloudFront)
```

그래서 문항이 무엇을 묻는지에 따라 답이 이렇게 갈립니다.

| 문항이 요구하는 것 | 답 |
|--------------------|----|
| 한 리전 안에서 장애에 견디는 구성 | 여러 **가용 영역**에 분산 |
| 재해 복구, 국가 단위 분산, 데이터 주권 | 여러 **리전** 사용 |
| 전 세계 사용자에게 콘텐츠를 빠르게 | **엣지 로케이션**(CloudFront) |
| 법적으로 데이터를 특정 국가 안에 둬야 함 | **리전** 선택 |

> ⚠️ **함정**: "지연 시간을 줄이고 싶다"는 표현 하나로 답이 결정되지 않습니다. **정적 콘텐츠(이미지·영상·파일)를 전 세계에 빠르게** 전달하는 것이면 엣지 로케이션(CloudFront)이지만, **사용자와 가까운 곳에서 애플리케이션 자체를 돌리고 싶다**면 그 지역의 리전을 고르는 것이 답입니다. 또한 엣지 로케이션은 캐싱 지점일 뿐 **가용 영역을 대신하는 고가용성 수단이 아닙니다.**

## Domain 3 핵심 — 클라우드 기술 및 서비스

### 컴퓨팅

| 서비스 | 한 줄 정의 |
|--------|-----------|
| EC2 | 가상 서버(IaaS), OS까지 사용자가 관리 |
| Lambda | 서버리스 함수, 코드 실행 시간만큼 과금 |
| Elastic Beanstalk | 코드 업로드 시 인프라 자동 구성(PaaS) |
| ECS / EKS | 컨테이너 오케스트레이션(ECS=AWS 자체, EKS=쿠버네티스) |
| Fargate | 서버리스 컨테이너 실행(EC2 관리 불필요) |

컴퓨팅은 **"내가 어디까지 관리할 것인가"** 하나의 사다리로 보면 외울 것이 확 줄어듭니다. 관리할 것이 많은 쪽부터 **EC2(OS까지 내가) → ECS/EKS(컨테이너 관리) → Fargate(서버 없음) → Lambda(코드만)** 순입니다.

| 상황 묘사 | 답 |
|-----------|----|
| OS를 직접 골라 패치하고 소프트웨어를 설치해야 한다 | EC2 |
| 이벤트가 올 때만 잠깐 실행되는 짧은 코드 | Lambda |
| 코드만 올리면 알아서 인프라를 구성해 주면 좋겠다 | Elastic Beanstalk |
| 컨테이너로 만든 앱을 여러 대에 걸쳐 돌리고 싶다 | ECS 또는 EKS |
| 컨테이너는 쓰고 싶지만 서버는 관리하기 싫다 | Fargate |
| 이미 쿠버네티스를 쓰고 있어 그대로 옮기고 싶다 | EKS |

> ⚠️ **함정**: "서버리스"라는 단어를 보면 무조건 Lambda를 고르는 실수가 잦습니다. AWS에서 서버리스는 Lambda만의 성질이 아닙니다. **Fargate(컨테이너), DynamoDB(데이터베이스), S3(스토리지)**도 사용자가 서버를 관리하지 않습니다. 문항이 **"컨테이너"**를 함께 말하면 Fargate, **"NoSQL 데이터베이스"**를 말하면 DynamoDB 쪽으로 갈라야 합니다.

### 스토리지

| 서비스 | 유형 | 핵심 키워드 |
|--------|------|-------------|
| S3 | 객체 스토리지 | 정적 파일, 백업, 무제한 확장 |
| EBS | 블록 스토리지 | EC2에 붙는 디스크 |
| EFS | 파일 스토리지 | 여러 EC2가 공유하는 파일시스템 |
| S3 Glacier | 아카이브 | 장기 보관, 저렴, 검색 지연 허용 |

스토리지 3형제는 **집 안의 저장 공간**으로 바꿔 보면 절대 안 헷갈립니다.

| 서비스 | 일상 비유 | 결정적 신호 |
|--------|-----------|-------------|
| S3 | 물건마다 이름표를 붙여 넣어 두는 **창고** | 파일 업로드/다운로드, 정적 웹사이트, 백업 |
| EBS | 컴퓨터 한 대에 꽂는 **외장 하드** | EC2에 붙는 디스크, 한 인스턴스 전용 |
| EFS | 여러 사람이 동시에 여는 **공유 폴더** | 여러 EC2가 **동시에 마운트** |
| S3 Glacier | 지하 창고에 넣어 둔 **오래된 서류 상자** | 몇 년 보관, 꺼낼 일은 거의 없음 |

> 📚 **사례**: 사진 공유 서비스를 만든다고 해봅시다. 사용자가 올린 사진은 제한 없이 쌓이고 웹에서 바로 내려받아야 하니 **S3**에 둡니다. 사진을 처리하는 EC2에는 OS와 프로그램이 깔린 디스크가 필요하니 **EBS**가 붙습니다. 처리 서버를 여러 대로 늘렸는데 모두 같은 작업 폴더를 봐야 한다면 **EFS**를 붙입니다. 3년이 지나 아무도 안 보는 원본은 **S3 Glacier**로 옮깁니다. 한 서비스 안에서 넷이 각자 다른 자리를 맡는다는 점이 핵심입니다.

> ⚠️ **함정**: "여러 서버가 같은 데이터를 봐야 한다"에 반사적으로 EBS를 고르면 틀립니다. 여러 EC2가 **동시에 마운트해 공유**하는 요구는 **EFS**입니다. 또 **인스턴스 스토어**는 EC2에 붙은 임시 디스크라 중지하면 데이터가 사라집니다. "영구 보관" 문항에서는 항상 오답입니다.

### 네트워킹

| 서비스 | 핵심 키워드 |
|--------|-------------|
| VPC | 격리된 가상 네트워크 |
| Route 53 | DNS 서비스 |
| CloudFront | CDN, 엣지 캐싱 |
| Direct Connect | 온프레미스↔AWS 전용 회선 |
| API Gateway | API 게시·관리 |

네트워킹도 도시 비유로 잡아 두면 편합니다. **VPC는 내가 분양받은 부지에 친 담장**이고, **Route 53은 주소를 알려주는 전화번호부**이며, **CloudFront는 동네마다 둔 물류 거점**, **Direct Connect는 우리 회사와 AWS를 잇는 전용 도로**입니다. 인터넷이라는 공용 도로를 쓰지 않고 따로 낸 길이라 속도와 대역폭이 안정적입니다.

여기에 **ELB와 Auto Scaling**이 자주 함께 나옵니다. 이름이 비슷해 보이지만 하는 일이 다릅니다. **ELB는 들어온 요청을 여러 서버에 나눠 주는 은행 창구 안내원**이고, **Auto Scaling은 손님이 몰리면 창구를 더 여는 지점장**입니다.

> 💡 **관련 이론**: 둘은 경쟁 관계가 아니라 **짝**입니다. Auto Scaling이 대수를 조절하고 ELB가 그 대수에 맞춰 요청을 배분해야 비로소 "수요에 따라 자동으로 늘고 주는" 탄력성이 완성됩니다. 문항이 "요청을 고르게 분산"이면 ELB, "부하에 따라 인스턴스 수를 자동 조절"이면 Auto Scaling으로 갈라 읽으세요.

### 데이터베이스

| 서비스 | 유형 |
|--------|------|
| RDS | 관계형 DB(관리형) |
| Aurora | 고성능 관계형(MySQL/PostgreSQL 호환) |
| DynamoDB | 서버리스 NoSQL |
| Redshift | 데이터 웨어하우스(분석) |
| ElastiCache | 인메모리 캐시(Redis/Memcached) |

> 💡 **관련 이론**: "관계형 + 관리형"이면 RDS, "NoSQL + 서버리스"면 DynamoDB, "대규모 분석/웨어하우스"면 Redshift입니다. 이 세 가지 매핑만 확실해도 DB 문제 다수를 맞출 수 있습니다.

데이터베이스도 상황 묘사로 갈라 두면 훨씬 빨리 답이 나옵니다.

| 상황 묘사 | 답 |
|-----------|----|
| 표와 관계, SQL, 기존 MySQL·PostgreSQL을 옮김 | RDS |
| 같은 관계형인데 **더 높은 성능**이 필요 | Aurora |
| 키-값, 스키마가 유연함, 서버 관리 없음, 대규모 트래픽 | DynamoDB |
| 수년치 데이터를 모아 리포트·분석 쿼리 | Redshift |
| 같은 조회가 반복돼 **응답을 빠르게** 하고 싶음 | ElastiCache |

> ⚠️ **함정**: 관계형과 비관계형의 구분을 "무엇을 저장하느냐"로 외우면 흔들립니다. 기준은 **구조**입니다. 행과 열이 정해져 있고 표끼리 관계를 맺으면 관계형(RDS·Aurora), 항목마다 담기는 속성이 달라도 되는 유연한 구조면 NoSQL(DynamoDB)입니다. 또한 **ElastiCache는 데이터베이스를 대체하는 것이 아니라 앞에 두는 캐시**입니다. "원본 데이터를 보관"하는 용도로 고르면 오답입니다.

## 키워드 → 서비스 번역표

시험 문항은 서비스 이름을 알려주지 않고 **상황을 묘사**합니다. 결국 하는 일은 한국어 표현을 서비스 이름으로 번역하는 것입니다. 왼쪽을 가리고 오른쪽을 맞혀 보고, 다시 오른쪽을 가리고 왼쪽을 떠올려 보세요.

| 문항에 나오는 표현 | 떠올릴 답 |
|--------------------|-----------|
| 운영체제를 직접 패치, 통제권 최대 | EC2 (IaaS) |
| 코드만 올리면 인프라 자동 구성 | Elastic Beanstalk (PaaS) |
| 이벤트로 잠깐 실행, 실행 시간만 과금 | Lambda |
| 컨테이너는 쓰되 서버 관리는 싫다 | Fargate |
| 정적 파일, 백업, 사실상 무제한 확장 | S3 |
| 여러 서버가 동시에 마운트하는 파일 공유 | EFS |
| 몇 년 보관, 꺼낼 일 거의 없음, 저렴 | S3 Glacier |
| 전 세계 사용자에게 콘텐츠를 빠르게, 캐싱 | CloudFront (엣지 로케이션) |
| 온프레미스와 AWS를 잇는 전용 회선 | Direct Connect |
| 요청을 여러 서버에 고르게 나눔 | ELB |
| 부하에 따라 인스턴스 수 자동 조절 | Auto Scaling |
| 한 리전 안에서 장애에 견디게 | 여러 가용 영역(AZ)에 분산 |
| 키-값, 서버리스, 유연한 스키마 | DynamoDB |
| 대량 데이터 분석, 웨어하우스 | Redshift |
| 반복 조회를 빠르게, 인메모리 | ElastiCache |

## 자주 틀리는 함정 목록

틀리는 데에는 이유가 있습니다. 이유까지 알아야 다음에 안 틀립니다.

1. **탄력성과 확장성을 섞습니다** — "자동으로"라는 말이 없으면 탄력성이 아닙니다.
2. **엣지 로케이션을 고가용성 수단으로 봅니다** — 엣지는 캐싱 지점, 장애 대비의 기본 단위는 가용 영역입니다.
3. **"서버리스" 한 단어로 Lambda를 찍습니다** — Fargate·DynamoDB·S3도 서버를 관리하지 않습니다.
4. **파일 공유 요구에 EBS를 고릅니다** — 여러 EC2가 동시에 쓰는 공유는 EFS입니다.
5. **영구 보관에 인스턴스 스토어를 고릅니다** — 중지하면 사라지는 임시 저장소입니다.
6. **ElastiCache를 데이터베이스 자리에 넣습니다** — 원본이 아니라 앞에 두는 캐시입니다.
7. **IaaS/PaaS/SaaS를 서비스 이름으로만 외웁니다** — 시험은 "누가 어디까지 관리하느냐"로 묻습니다.
8. **"지연 시간"만 보고 CloudFront를 찍습니다** — 콘텐츠 전달이면 CloudFront, 앱 자체를 가까이 두는 것이면 리전 선택입니다.

## 한 문장 요약 카드

오른쪽을 가리고 말해 보는 용도입니다.

| 카드 | 한 줄 |
|------|-------|
| EC2 / Lambda | OS까지 내가 관리 / 이벤트 때만 도는 코드 |
| Beanstalk / Fargate | 코드만 주면 인프라 자동 / 서버 없이 컨테이너 |
| S3 / EBS / EFS | 무제한 창고 / 한 대에 꽂는 외장 하드 / 공유 폴더 |
| VPC / CloudFront | 격리된 담장 / 가까운 곳에 캐싱하는 CDN |
| ELB / Auto Scaling | 나눠 주는 안내원 / 창구를 더 여는 지점장 |
| RDS / DynamoDB / Redshift | 관계형 / 서버리스 NoSQL / 분석용 웨어하우스 |
| 리전 / AZ / 엣지 | 지역 / 지역 안의 분리된 데이터센터 / 캐싱 지점 |

## 자가 점검 체크리스트

설명할 수 있으면 통과입니다. 막히는 항목이 있으면 해당 회차로 돌아가세요.

- [ ] 클라우드의 6가지 이점을 보지 않고 다섯 개 이상 말할 수 있다
- [ ] 확장성과 탄력성, 고가용성과 내결함성의 차이를 각각 한 문장으로 구분할 수 있다
- [ ] IaaS·PaaS·SaaS를 **관리 범위** 기준으로 배열할 수 있다
- [ ] 리전·가용 영역·엣지 로케이션의 포함 관계를 그릴 수 있다
- [ ] "고가용성 구성"이라는 요구에 무엇을 답해야 하는지 안다
- [ ] EC2·Lambda·Beanstalk·Fargate를 관리 부담 순으로 늘어놓을 수 있다
- [ ] S3·EBS·EFS를 각각 언제 쓰는지 상황으로 구분할 수 있다
- [ ] ELB와 Auto Scaling의 역할을 섞지 않고 말할 수 있다
- [ ] RDS·DynamoDB·Redshift·ElastiCache를 상황으로 갈라 고를 수 있다

## 오늘의 마무리

오늘은 가장 비중이 큰 두 영역을 압축해서 봤습니다. 표에 나온 서비스의 **한 줄 정의와 대표 키워드**를 입으로 말할 수 있는지 점검하세요. 내일은 보안과 청구 영역을 정리합니다.

## 한 줄 요약

**Domain 1은 개념 짝(확장성/탄력성, 가용성/내구성, 리전/AZ/엣지)을 정확히 구분하는 일이고, Domain 3는 "이 상황이면 이 서비스"라는 번역표를 몸에 익히는 일입니다.** 이름 대신 상황 묘사를 외우면 34%가 걸린 영역이 훨씬 가벼워집니다.

## 📖 용어

- **확장성(Scalability)** : 자원을 늘릴 수 있는 능력 자체. 자동일 필요는 없습니다.
- **탄력성(Elasticity)** : 수요에 맞춰 자원이 **자동으로** 늘고 주는 성질.
- **고가용성(High Availability)** : 일부에 장애가 나도 서비스가 빠르게 정상으로 돌아오는 성질.
- **내결함성(Fault Tolerance)** : 장애가 생겨도 아예 멈추지 않고 계속 동작하는 성질.
- **리전(Region)** : 지리적으로 떨어진 AWS 인프라 영역. 데이터 위치·지연 시간·요금이 달라집니다.
- **가용 영역(AZ)** : 한 리전 안에서 물리적으로 분리된 데이터센터 묶음. 고가용성의 기본 단위입니다.
- **엣지 로케이션** : 사용자와 가까운 위치에서 콘텐츠를 캐싱하는 지점. CloudFront가 사용합니다.
- **IaaS · PaaS · SaaS** : 인프라만 / 실행 환경까지 / 완제품까지 빌려주는 3단계. 위로 갈수록 관리 부담이 줄어듭니다.
- **서버리스** : 사용자가 서버를 직접 준비·관리하지 않는 방식. Lambda·Fargate·DynamoDB 등이 해당합니다.
- **객체 스토리지** : 파일을 이름표와 함께 통째로 저장하는 방식. S3가 대표입니다.
- **블록 스토리지** : 서버에 디스크처럼 붙여 쓰는 저장 방식. EBS가 대표입니다.
- **ELB(Elastic Load Balancing)** : 들어온 요청을 여러 서버에 나눠 보내는 부하 분산 서비스.
- **Auto Scaling** : 부하에 따라 인스턴스 대수를 자동으로 늘리고 줄이는 기능.
- **인메모리 캐시** : 자주 쓰는 데이터를 메모리에 두어 응답을 빠르게 하는 계층. ElastiCache가 대표입니다.

## 📝 연습 문제

**문제 1.** 사용자가 운영체제 패치와 미들웨어 설치까지 직접 책임지길 원할 때 가장 적합한 클라우드 컴퓨팅 모델은 무엇인가?

A) SaaS  
B) IaaS  
C) PaaS  
D) FaaS  

**정답: B**  
해설: IaaS는 가상 서버 같은 기본 인프라만 제공하고 OS와 미들웨어는 사용자가 관리하므로 통제권이 가장 큽니다. SaaS는 완제품 소프트웨어만 사용하고, PaaS는 코드만 관리하며 OS는 제공자가 책임지므로 직접 패치할 필요가 없습니다. FaaS는 함수 단위 서버리스로 인프라 관리가 더욱 추상화됩니다.

---

**문제 2.** 단일 리전 내에서 고가용성 아키텍처를 구성하기 위한 가장 기본적인 단위는 무엇인가?

A) 엣지 로케이션  
B) 여러 가용 영역(AZ)에 분산 배치  
C) 여러 리전에 분산 배치  
D) 하나의 대형 인스턴스  

**정답: B**  
해설: 가용 영역은 한 리전 안에서 물리적으로 분리된 데이터센터 묶음으로, 여러 AZ에 분산하면 한 곳 장애 시에도 서비스가 유지됩니다. 엣지 로케이션은 콘텐츠 캐싱용입니다. 여러 리전 분산은 재해 복구 범위로 더 광범위하며 질문이 요구한 단일 리전 내 구성이 아닙니다. 단일 대형 인스턴스는 단일 장애 지점이 됩니다.

---

**문제 3.** 여러 EC2 인스턴스가 동시에 마운트하여 파일을 공유해야 한다. 가장 적합한 스토리지 서비스는?

A) Amazon EBS  
B) Amazon S3 Glacier  
C) Amazon EFS  
D) 인스턴스 스토어  

**정답: C**  
해설: EFS는 여러 EC2 인스턴스가 동시에 마운트할 수 있는 공유 파일 스토리지입니다. EBS는 일반적으로 하나의 인스턴스에 연결되는 블록 스토리지입니다. S3 Glacier는 장기 아카이브용으로 즉시 공유 마운트 용도가 아닙니다. 인스턴스 스토어는 인스턴스 중지 시 데이터가 사라지는 임시 저장소입니다.

---

**문제 4.** 클라우드 컴퓨팅의 이점 중 "선행 비용을 가변 비용으로 전환한다"는 것이 의미하는 바로 옳은 것은?

A) 사용량과 무관하게 매달 고정 요금을 낸다  
B) 데이터센터를 미리 구축하는 대신 사용한 만큼만 지불한다  
C) 모든 서비스가 무료로 제공된다  
D) 1년치 비용을 반드시 선결제해야 한다  

**정답: B**  
해설: 가변 비용 모델은 대규모 선투자 없이 실제 사용한 리소스에 대해서만 지불하는 것을 뜻합니다. 고정 요금이나 의무 선결제는 이 개념과 반대이며, 클라우드가 무료인 것도 아닙니다.

---

**문제 5.** 정적 웹사이트 파일과 대용량 백업을 저장하기 위한 무제한 확장 객체 스토리지로 가장 적합한 서비스는?

A) Amazon RDS  
B) Amazon EBS  
C) Amazon S3  
D) Amazon Redshift  

**정답: C**  
해설: S3는 객체 스토리지로 정적 파일과 백업 저장에 적합하며 사실상 무제한으로 확장됩니다. RDS는 관계형 데이터베이스, EBS는 EC2용 블록 스토리지, Redshift는 분석용 데이터 웨어하우스로 객체 저장 용도가 아닙니다.
