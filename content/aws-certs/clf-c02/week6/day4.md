# Day 4 - 자주 틀리는 함정·키워드: "키워드→서비스" 번역표

CLF-C02 문제는 대부분 **상황을 묘사하는 키워드**를 던지고 "가장 적합한 서비스"를 묻습니다. 그래서 시험은 사실상 **키워드를 서비스로 번역하는 게임**입니다. 오늘은 그 번역표를 정리하고, 비슷해서 헷갈리는 서비스 쌍을 비교합니다.

## 📌 핵심 정리

- CLF-C02는 사실상 **키워드 번역 시험**입니다. 지문 속 한두 단어가 정답 서비스를 결정합니다.
- 서비스 이름만 외우면 헷갈립니다. 이름 옆에 **"무엇을 위한 것"** 을 항상 붙여서 기억하세요.
- 오답은 대부분 **같은 카테고리의 이웃 서비스**입니다. 그래서 "짝 비교"가 가장 효율적인 복습법입니다.
- 절대 표현("항상", "무제한", "100%")이 들어간 보기는 대체로 오답입니다.

## 핵심 "키워드 → 서비스" 번역표

| 문제 속 키워드 | 정답 서비스 |
|----------------|-------------|
| CDN / 엣지 캐싱 / 콘텐츠 전송 | CloudFront |
| 서버리스 함수 / 이벤트 기반 코드 실행 | Lambda |
| DNS / 도메인 라우팅 | Route 53 |
| 객체 스토리지 / 정적 파일 / 백업 | S3 |
| 장기 아카이브 / 거의 안 꺼냄 / 저렴 | S3 Glacier |
| 관계형 데이터베이스 / 관리형 SQL | RDS |
| NoSQL / 서버리스 / 밀리초 | DynamoDB |
| 데이터 웨어하우스 / 대규모 분석 | Redshift |
| 인메모리 캐시 / 초고속 읽기 | ElastiCache |
| DDoS 방어 | Shield |
| 웹 방화벽 / SQL 인젝션·XSS 차단 | WAF |
| 위협 탐지 / 지능형 모니터링 | GuardDuty |
| API 호출 감사 / 누가 무엇을 했나 | CloudTrail |
| 리소스 구성 추적 / 규정 준수 상태 | Config |
| 지표·로그 모니터링 / 알람 | CloudWatch |
| 전용 네트워크 회선 / 온프레미스 연결 | Direct Connect |
| 비용 견적(사전) | Pricing Calculator |
| 비용 추세 분석(사후) | Cost Explorer |
| 예산 초과 알림 | Budgets |
| 규정 준수 보고서 다운로드 | Artifact |
| 모범 사례 점검(비용·보안·성능) | Trusted Advisor |

> 💡 **관련 이론**: 시험에서 정확한 서비스 이름이 떠오르지 않더라도, 위 키워드 매핑을 거꾸로 추적하면 오답을 빠르게 지울 수 있습니다. 키워드 하나가 정답을 결정하는 "신호어"라고 생각하세요.

## 카테고리별 확장 번역표

위 표는 압축판이고, 여기서부터는 카테고리별로 나눠서 봅니다. **카테고리를 먼저 정하고 그 안에서 고르는 것**이 가장 빠른 경로입니다. 지문을 읽고 "이건 스토리지 문제다"까지만 정해도 보기 절반이 날아갑니다.

### 컴퓨팅

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 가상 서버 / OS를 내가 직접 고르고 관리 | EC2 |
| 이벤트가 있을 때만 코드 실행 / 서버 없음 | Lambda |
| 코드만 올리면 인프라는 알아서 (PaaS) | Elastic Beanstalk |
| 컨테이너 오케스트레이션 | ECS / EKS(쿠버네티스) |
| 컨테이너를 서버 관리 없이 실행 | Fargate |
| 부하에 따라 인스턴스 수를 자동 증감 | EC2 Auto Scaling |

### 스토리지

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 객체 저장 / 정적 웹 파일 / 백업 / 무한히 늘어나는 파일 | S3 |
| 거의 안 꺼내는 장기 아카이브 | S3 Glacier 계열 |
| EC2 한 대에 붙이는 디스크 | EBS |
| 여러 EC2가 동시에 마운트하는 공유 파일 시스템 | EFS |
| 온프레미스와 클라우드 스토리지를 이어 주는 다리 | Storage Gateway |
| 네트워크로 옮기기엔 너무 큰 데이터를 물리 장치로 | Snow 제품군 |

### 네트워킹 · 콘텐츠 전송

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 내 전용 가상 네트워크 / 서브넷 격리 | VPC |
| 도메인 이름 등록·라우팅 | Route 53 |
| 엣지 캐싱 / 전 세계 사용자에게 빠른 전달 | CloudFront |
| 데이터센터와 AWS를 잇는 **전용 회선** | Direct Connect |
| 인터넷을 통한 암호화 터널 연결 | Site-to-Site VPN |
| 인스턴스 단위 방화벽 / 서브넷 단위 방화벽 | 보안 그룹 / 네트워크 ACL |

### 데이터베이스

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 관리형 관계형 DB / 기존 MySQL·PostgreSQL 이전 | RDS |
| AWS가 만든 고성능 관계형 DB | Aurora |
| 키-값 / NoSQL / 서버리스 / 한 자릿수 밀리초 | DynamoDB |
| 데이터 웨어하우스 / 수년치 데이터 복합 분석 | Redshift |
| 인메모리 캐시 / 반복 조회 속도 개선 | ElastiCache |

### 보안 · 자격 증명

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 누가 무엇을 할 수 있는지 / 사용자·그룹·역할·정책 | IAM |
| 자격 증명을 코드에 넣지 않고 서비스에 권한 | IAM 역할 |
| 여러 계정을 묶어 정책·결제를 중앙 관리 | Organizations |
| 암호화 키 생성·관리 | KMS |
| SQL 인젝션·XSS 같은 웹 공격 차단 | WAF |
| 대량 트래픽 DDoS 방어 | Shield |
| 계정·네트워크에서 수상한 활동 **탐지** | GuardDuty |
| EC2·컨테이너의 **취약점 점검** | Inspector |
| S3 속 **민감 정보(개인정보) 발견** | Macie |

### 모니터링 · 관리 · 거버넌스

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 지표·로그·알람 / 임계치를 넘으면 알림 | CloudWatch |
| 누가 언제 어떤 API를 호출했나 (감사) | CloudTrail |
| 리소스 설정이 규칙을 지키는가 / 변경 이력 | Config |
| 비용·보안·성능 모범 사례 점검 | Trusted Advisor |

### 비용 · 요금 · 지원

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| 아직 쓰지 않은 구성의 **예상 비용 계산** | Pricing Calculator |
| **이미 쓴** 비용의 추세·분해 분석 | Cost Explorer |
| 정해둔 금액을 넘으면 **알림** | Budgets |
| 여러 계정 청구를 하나로 + 사용량 합산 | Organizations 통합 결제 |
| 24/7 기술 지원 / 전담 TAM | Support 플랜 (Business / Enterprise) |

### 마이그레이션 · 분석 · 통합

| 문제 속 키워드 | 정답 방향 |
|----------------|----------|
| DB를 최소 중단으로 이전 | DMS |
| S3에 있는 데이터를 SQL로 바로 조회 | Athena |
| 알림 발송(이메일·문자·구독형) | SNS |
| 작업을 큐에 넣어 서로 느슨하게 연결 | SQS |

> 📚 **사례**: "백업 테이프를 창고에 보관해 왔는데 클라우드로 옮기고 싶습니다. 다만 기존 백업 소프트웨어는 그대로 쓰고 싶습니다." 카테고리는 **스토리지**이고, 신호어 "기존 소프트웨어를 그대로"는 온프레미스 장비가 클라우드 스토리지를 로컬 저장소처럼 보게 해 주는 **다리 역할**을 요구하므로 Storage Gateway로 좁혀집니다. 반대로 "수십 테라바이트를 한 번에 옮기고 끝"이었다면 Snow 제품군입니다. **같은 "백업"이라도 뒤에 붙은 조건이 답을 바꿉니다.**

## 자주 틀리는 헷갈림 쌍

### CloudTrail vs Config vs CloudWatch

| 서비스 | 답하는 질문 |
|--------|-------------|
| CloudTrail | "누가 언제 무슨 API를 호출했나?" (감사) |
| Config | "리소스 구성이 규칙을 지키나? 어떻게 바뀌었나?" |
| CloudWatch | "성능·지표가 정상인가? 임계치를 넘었나?" (모니터링) |

### S3 vs EBS vs EFS

| 서비스 | 유형 | 신호어 |
|--------|------|--------|
| S3 | 객체 | 정적 파일, 무제한, 웹 |
| EBS | 블록 | EC2에 붙는 디스크(1:1) |
| EFS | 파일 | 여러 EC2 공유 마운트 |

### Shield vs WAF vs GuardDuty

| 서비스 | 막는 것 |
|--------|---------|
| Shield | DDoS(대량 트래픽 공격) |
| WAF | 계층 7 웹 공격(SQL 인젝션, XSS) |
| GuardDuty | 비정상 활동·위협 탐지(예방이 아닌 탐지) |

### IAM 사용자 vs 그룹 vs 역할

| 요소 | 핵심 |
|------|------|
| 사용자 | 사람/앱 1개의 영구 자격 증명 |
| 그룹 | 사용자 묶음에 권한 일괄 부여 |
| 역할 | **임시 권한 위임** (EC2가 S3 접근, 계정 간 접근, 페더레이션) |

> 💡 **관련 이론**: "EC2 인스턴스가 S3에 접근해야 한다"처럼 자격 증명을 코드에 저장하지 않고 서비스에 권한을 주는 상황이면 거의 항상 **IAM 역할**이 정답입니다.

### RDS vs DynamoDB vs Redshift vs ElastiCache

| 서비스 | 한 줄 정체 | 신호어 |
|--------|-----------|--------|
| RDS | 관리형 관계형(SQL) 데이터베이스 | 테이블·조인, 기존 MySQL/PostgreSQL 이전 |
| DynamoDB | 서버리스 NoSQL 키-값 저장소 | 밀리초, 키-값, 서버 관리 없음, 초대형 확장 |
| Redshift | 분석용 데이터 웨어하우스 | 수년치 데이터, 리포트, 복잡한 집계 쿼리 |
| ElastiCache | 인메모리 캐시 | 같은 조회가 반복됨, 응답을 더 빠르게 |

기억 장치: **"업무 처리는 RDS/DynamoDB, 분석은 Redshift, 속도 보조는 ElastiCache"**입니다.

### EC2 vs Elastic Beanstalk vs Fargate vs Lambda

관리 부담 순으로 늘어놓으면 관계가 한눈에 보입니다.

```
   내가 관리할 것이 많다 ←──────────────────→ 적다
   EC2  >  Elastic Beanstalk  >  Fargate  >  Lambda
   (OS까지)   (앱만 올리면)     (컨테이너만)  (함수 코드만)
```

- "완전한 제어", "특정 OS 필요" → **EC2**
- "코드만 올리면", "빠르게 배포" → **Elastic Beanstalk**
- "컨테이너인데 서버는 관리 안 함" → **Fargate**
- "이벤트 발생 시에만", "운영 부담 최소" → **Lambda**

### ELB vs Auto Scaling — "나누기"와 "늘리기"

둘은 경쟁 관계가 아니라 **짝꿍**입니다.

| 구분 | Elastic Load Balancing | EC2 Auto Scaling |
|------|------------------------|------------------|
| 하는 일 | 들어온 트래픽을 여러 서버에 **나눠 줌** | 서버 대수를 **늘리고 줄임** |
| 없으면 생기는 일 | 한 서버에만 트래픽이 몰림 | 트래픽이 늘어도 서버 수는 그대로 |
| 대응 관계 | 고가용성(살아 있는 대상에만 전달) | 탄력성(수요에 맞춘 증감) |

식당으로 비유하면 **ELB는 손님을 빈 테이블로 안내하는 직원**, **Auto Scaling은 손님이 늘면 테이블을 더 놓는 결정**입니다. 문항이 "트래픽을 분산"이라고 하면 ELB, "서버 대수를 조절"이라고 하면 Auto Scaling입니다.

### 확장성 vs 탄력성

| 개념 | 뜻 | 구분 포인트 |
|------|----|------------|
| 확장성(Scalability) | 필요하면 자원을 **늘릴 수 있는 능력** | 자동일 필요 없음, "늘릴 수 있다"에 방점 |
| 탄력성(Elasticity) | 수요에 따라 **자동으로 늘고 줄어드는** 성질 | 줄어드는 것까지 포함, 자동이 핵심 |

**수직 확장**은 한 대의 사양을 키우기, **수평 확장**은 대수를 늘리기입니다.

### 고가용성 vs 내결함성 vs 재해 복구

셋 다 "장애 대비"지만 **어느 규모의 장애를 견디느냐**가 다릅니다.

| 개념 | 대비하는 장애 | 대표 답 |
|------|--------------|---------|
| 고가용성(High Availability) | 서버 한 대·한 AZ 장애에도 서비스 계속 | 여러 **AZ**에 분산 |
| 내결함성(Fault Tolerance) | 고장이 나도 성능 저하 없이 그대로 동작 | 이중화·중복 구성 |
| 재해 복구(Disaster Recovery) | 지역 전체 마비 같은 큰 사고 후 복구 | 여러 **리전** |

> ⚠️ **함정**: "고가용성"에 여러 리전을 고르고 "재해 복구"에 여러 AZ를 고르는 실수가 가장 흔합니다. 판별 기준은 지문에 **지역·지리적 범위를 뜻하는 표현이 있는지**입니다. "데이터센터 한 곳이 정전되어도" → AZ, "지역 전체 장애에 대비" → 리전입니다.

### 리전 vs 가용 영역(AZ) vs 엣지 로케이션

| 구분 | 무엇인가 | 왜 고르나 |
|------|---------|----------|
| 리전(Region) | 지리적으로 떨어진 큰 지역 단위 | 법·규제 준수, 사용자와의 거리, 재해 복구 |
| 가용 영역(AZ) | 한 리전 안의 물리적으로 분리된 데이터센터 묶음 | 고가용성, 한 곳이 죽어도 계속 |
| 엣지 로케이션(Edge Location) | 사용자 가까이에 있는 캐시 지점 | 콘텐츠 전달 지연 시간 단축 |

기억 장치: **리전은 "어느 나라", AZ는 "그 안의 건물", 엣지는 "동네 편의점"**입니다.

### GuardDuty vs Inspector vs Macie

| 서비스 | 무엇을 보나 | 한 단어 |
|--------|-----------|--------|
| GuardDuty | 계정·네트워크의 수상한 **활동** | 위협 탐지 |
| Inspector | EC2·컨테이너의 **취약점** | 취약점 점검 |
| Macie | S3에 든 **민감 정보** | 데이터 발견 |

**"행동은 GuardDuty, 구멍은 Inspector, 개인정보는 Macie"**로 외웁니다.

### WAF vs Shield — 둘 다 막지만 층이 다릅니다

| 서비스 | 막는 것 | 비유 |
|--------|--------|------|
| Shield | 대량 트래픽으로 밀어붙이는 DDoS | 문 앞에 몰려든 인파를 막는 방벽 |
| WAF | 요청 내용 자체가 악의적인 웹 공격 | 들어오는 사람의 가방을 검사하는 보안 요원 |

### Artifact vs Config vs Trusted Advisor

- **Artifact** — "AWS가 받은 인증 보고서를 어디서 받나?" (문서 다운로드)
- **Config** — "내 리소스 설정이 규칙을 지키고 있나?"
- **Trusted Advisor** — "비용·보안·성능 면에서 개선할 점이 무엇인가?"

### 요금 모델 — 온디맨드 vs 예약 인스턴스 vs Savings Plans vs 스팟

| 모델 | 언제 고르나 | 절대 고르면 안 되는 상황 |
|------|------------|------------------------|
| 온디맨드 | 사용량 예측 불가, 단기·실험, 약정 부담 회피 | "장기간 꾸준히 쓰며 최대 절감" |
| 예약 인스턴스(RI) | 1~3년 꾸준히 쓸 것이 확실함 | "언제 끝날지 모르는 단기 작업" |
| Savings Plans | 장기 약정하되 구성 변경 유연성도 필요 | "단기·일회성 작업" |
| 스팟 | 중단되어도 되는 배치·분석·렌더링 작업 | "중단되면 안 되는 기간계 서비스" |

> ⚠️ **함정**: "가장 비용 효율적"이라는 말만 보고 무조건 스팟을 고르면 틀립니다. 스팟은 **중단될 수 있다**는 전제를 받아들이는 대가로 저렴한 것이라, 지문에 "항상 실행되어야 한다", "중단되면 안 된다" 같은 표현이 있으면 후보에서 빠집니다.

### Organizations vs 통합 결제

이 둘은 대등한 두 서비스가 아닙니다. **통합 결제는 Organizations가 제공하는 기능 중 하나**입니다.

| 항목 | 설명 |
|------|------|
| Organizations | 여러 AWS 계정을 묶어 중앙에서 관리하는 상위 개념 |
| 통합 결제(Consolidated Billing) | 그중 청구를 하나로 합치고 사용량을 합산하는 기능 |
| SCP(서비스 제어 정책) | 계정·조직 단위로 허용 가능한 작업 범위를 제한하는 기능 |

"청구서를 하나로"면 통합 결제, "특정 서비스를 못 쓰게 막고 싶다"면 SCP입니다.

### 비용 도구 — Pricing Calculator vs Cost Explorer vs Budgets

가장 단순한 구분은 **시간축**이며, **"계산기는 미래, 탐색기는 과거, 예산은 현재"**로 외웁니다.

| 도구 | 시점 | 설명 |
|------|------|------|
| Pricing Calculator | 쓰기 **전** | 아직 만들지 않은 구성의 예상 비용 계산 |
| Cost Explorer | 쓴 **후** | 이미 발생한 비용의 추세·구성 분석 |
| Budgets | 쓰는 **중** | 정한 금액·사용량을 넘으면 알림 |

### Direct Connect vs Site-to-Site VPN

**Direct Connect**는 인터넷을 거치지 않는 전용 회선("일관된 성능"), **Site-to-Site VPN**은 인터넷 위의 암호화 터널입니다.

## 함정 표현 주의

- **"비용 효율적인(most cost-effective)"** → 보통 스팟/예약/Glacier/Savings Plans 쪽으로 답이 기운다
- **"운영 부담 최소(least operational overhead)"** → 서버리스(Lambda, Fargate, DynamoDB)나 관리형 서비스가 정답
- **"고가용성"** → 여러 AZ 분산
- **"재해 복구/지역 장애 대비"** → 여러 리전

- **"완전한 제어가 필요하다"** → EC2처럼 직접 관리하는 쪽
- **"지연 시간을 줄여야 한다"** → 엣지·CDN 또는 사용자와 가까운 리전
- **"자격 증명을 저장하지 않고"** → IAM 역할
- **"중단되면 안 되는"** → 스팟 제외

> 💡 **개념**: 이런 수식어를 **제약 조건(constraint)** 이라고 생각하면 편합니다. 제약이 하나 늘어날 때마다 후보가 절반으로 줄어듭니다. 조건이 많은 긴 지문이 오히려 답을 좁히기 쉬운 이유가 여기에 있으니, 지문이 길다고 겁먹지 말고 **조건을 하나씩 세어 보세요.**

## 오답 함정 목록 — 왜 틀리는지까지

"왜 끌리는가"를 알아야 다음번에 안 끌립니다.

| 함정 | 왜 끌리는가 | 실제 판별법 |
|------|------------|------------|
| DDoS 문제에 WAF를 고름 | 둘 다 "공격 차단"이라서 | 양으로 밀어붙이면 Shield, 요청 내용이 악의적이면 WAF |
| 감사 문제에 CloudWatch를 고름 | 둘 다 "로그"라서 | "누가 무엇을 했나"면 CloudTrail |
| 아카이브 문제에 S3 Standard를 고름 | S3가 익숙해서 | "거의 안 꺼낸다"면 Glacier 계열 |
| 공유 파일 문제에 EBS를 고름 | 디스크라는 말 때문에 | "여러 EC2가 동시에"면 EFS |
| 분석 문제에 RDS를 고름 | SQL이라는 말 때문에 | "수년치 데이터 집계·리포트"면 Redshift |
| 서버리스 문제에 Beanstalk를 고름 | "자동 관리"라는 말 때문에 | Beanstalk도 하부에 EC2가 있습니다 |
| 견적 문제에 Cost Explorer를 고름 | 비용 도구라서 | 아직 안 쓴 것이면 Pricing Calculator |
| 관리형 DB의 OS 패치를 고객 책임으로 고름 | "OS=고객"만 외워서 | 관리형 서비스는 기반 OS를 AWS가 맡습니다 |
| "무제한", "항상 무료" 보기를 고름 | 매력적으로 들려서 | 절대 표현은 거의 항상 오답입니다 |

> ⚠️ **함정**: 이름이 비슷한 서비스를 **이름만으로** 외우면 시험장에서 흔들립니다. "Inspector는 검사관이니까 로그를 검사하겠지" 같은 어림짐작이 출제자가 노리는 지점입니다. 서비스는 이름이 아니라 **"어떤 질문에 답하는 도구인가"** 로 기억하세요.

## 📖 용어

- **신호어** : 지문 안에서 정답 서비스를 가리키는 결정적 단어. "밀리초", "장기 보관" 같은 것들입니다.
- **제약 조건** : "비용 최소", "중단 불가"처럼 후보를 좁히는 지문 속 조건. 많을수록 답이 좁혀집니다.
- **카테고리 먼저 좁히기** : 서비스 이름을 떠올리기 전에 컴퓨팅·스토리지 같은 분류부터 정하는 풀이법.
- **객체 스토리지** : 파일을 통째로 저장하는 방식. S3가 대표이며 무한히 늘어납니다.
- **블록 스토리지** : 서버에 디스크처럼 붙이는 저장 방식. EBS가 대표입니다.
- **파일 스토리지** : 여러 서버가 동시에 마운트해 쓰는 저장 방식. EFS가 대표입니다.
- **서버리스** : 서버를 직접 준비·운영하지 않는 방식. Lambda, Fargate, DynamoDB가 대표입니다.
- **관리형 서비스** : 운영의 상당 부분을 AWS가 대신 맡아 주는 서비스.
- **수직 확장 / 수평 확장** : 한 대의 사양을 키우기 / 대수를 늘리기.
- **아카이브 계층** : 꺼내는 데 시간이 걸리는 대신 보관 비용이 낮은 스토리지 등급.
- **통합 결제** : Organizations에서 여러 계정의 청구를 하나로 합치고 사용량을 합산하는 기능.
- **절대 표현** : "항상", "무제한", "100% 보장" 등. 보기에 있으면 오답 신호로 봅니다.

## 📝 연습 문제

**문제 1.** "EC2 인스턴스가 자격 증명을 코드에 저장하지 않고 S3 버킷에 접근하도록 안전하게 권한을 부여"하려면 무엇을 사용해야 하는가?

A) IAM 사용자에 액세스 키 발급  
B) IAM 역할  
C) 루트 사용자 자격 증명  
D) S3 버킷 정책에 비밀번호 저장  

**정답: B**  
해설: IAM 역할은 임시 자격 증명을 통해 서비스에 권한을 위임하므로 액세스 키를 코드에 하드코딩할 필요가 없습니다. IAM 사용자 키 발급은 키 유출 위험이 있고, 루트 사용자는 절대 사용하면 안 되며, 비밀번호를 버킷 정책에 저장하는 것은 보안에 어긋납니다.

---

**문제 2.** "리소스 구성이 내부 규정을 계속 준수하는지 추적하고 변경 이력을 보고 싶다." 가장 적합한 서비스는?

A) AWS CloudTrail  
B) Amazon CloudWatch  
C) AWS Config  
D) AWS WAF  

**정답: C**  
해설: AWS Config는 리소스 구성 상태와 변경 이력을 추적하고 규정 준수 여부를 평가합니다. CloudTrail은 API 호출 감사, CloudWatch는 지표·로그 모니터링, WAF는 웹 방화벽입니다.

---

**문제 3.** "거의 조회하지 않는 데이터를 가장 저렴하게 장기 보관"하려면 어떤 스토리지가 적합한가?

A) Amazon S3 Standard  
B) Amazon EBS  
C) Amazon S3 Glacier  
D) Amazon EFS  

**정답: C**  
해설: S3 Glacier는 검색 지연을 허용하는 대신 매우 저렴한 장기 아카이브 스토리지입니다. S3 Standard는 자주 접근하는 데이터용으로 더 비싸고, EBS는 EC2용 블록 스토리지, EFS는 공유 파일 스토리지로 장기 아카이브 용도가 아닙니다.

---

**문제 4.** "운영 부담을 최소화하면서 이벤트가 발생할 때만 코드를 실행"하고 싶다. 가장 적합한 서비스는?

A) Amazon EC2  
B) AWS Lambda  
C) AWS Elastic Beanstalk  
D) Amazon EC2 Auto Scaling  

**정답: B**  
해설: Lambda는 서버를 관리하지 않고 이벤트 발생 시에만 코드를 실행하는 서버리스 서비스로 운영 부담이 가장 적습니다. EC2와 Auto Scaling은 서버 관리가 필요하고, Elastic Beanstalk도 하부에 EC2를 운영하므로 Lambda보다 부담이 큽니다.

---

**문제 5.** "대량 트래픽을 동원한 DDoS 공격으로부터 애플리케이션을 보호"하려면 어떤 서비스를 사용해야 하는가?

A) AWS WAF  
B) AWS Shield  
C) Amazon GuardDuty  
D) AWS KMS  

**정답: B**  
해설: AWS Shield는 DDoS 공격 방어에 특화된 서비스입니다. WAF는 SQL 인젝션·XSS 같은 계층 7 웹 공격 필터링, GuardDuty는 위협 탐지, KMS는 암호화 키 관리로 DDoS 방어가 주목적이 아닙니다.
