# Day 2 - 도메인 복습 2: 보안 및 규정 준수 + 청구·요금·지원 핵심 총정리

## 📌 핵심 정리

- 오늘의 두 영역은 합쳐 **42%**입니다. 어제의 58%와 더하면 시험 전체가 됩니다.
- Domain 2의 모든 문항은 결국 **"이건 AWS가 해주나, 내가 해야 하나"** 한 질문으로 되돌아옵니다. 그 답을 정하는 것이 공동 책임 모델입니다.
- **데이터와 접근 권한은 어떤 서비스를 쓰든 항상 고객 책임**입니다. 이 한 줄이 보안 문항의 절반을 풀어 줍니다.
- 보안 서비스는 이름을 외우지 말고 **"무엇을 막거나 찾아내는가"**로 묶으세요. 막는 것(WAF·Shield), 찾아내는 것(GuardDuty·Inspector·Macie), 기록하는 것(CloudTrail·Config)으로 갈립니다.
- Domain 4는 **시점(사전/사후)**, **주체(사람/도구)**, **목적(분석/알림/제한)** 세 축만 잡으면 대부분 정리됩니다.
- 오늘도 목표는 읽는 것이 아니라 **가리고 말해 보는 것**입니다.

어제는 클라우드 개념과 기술·서비스를 정리했습니다. 오늘은 나머지 두 영역, **Domain 2 (보안 및 규정 준수, 30%)** 와 **Domain 4 (청구·요금·지원, 12%)** 를 총정리합니다. Domain 2는 비중이 두 번째로 큰 만큼 출제가 많고, Domain 4는 작지만 IAM·요금 도구처럼 헷갈리기 쉬운 포인트가 모여 있습니다.

## Domain 2 핵심 — 보안 및 규정 준수

### 공동 책임 모델 (Shared Responsibility Model)

가장 중요한 개념입니다. "클라우드의 보안 vs 클라우드 내부의 보안"으로 구분합니다.

| 책임 주체 | 담당 영역 | 예시 |
|-----------|-----------|------|
| AWS (of the Cloud) | 인프라 보안 | 물리적 시설, 하드웨어, 네트워크, 하이퍼바이저 |
| 고객 (in the Cloud) | 데이터·구성 보안 | 데이터 암호화, IAM 설정, OS 패치, 보안 그룹 |

> 💡 **관련 이론**: "고객 데이터 암호화", "IAM 사용자 관리", "EC2 게스트 OS 패치"는 항상 **고객 책임**입니다. 반대로 "데이터센터 물리 보안", "하드웨어 폐기"는 **AWS 책임**입니다. 단, 관리형 서비스(RDS 등)는 OS 패치를 AWS가 담당하는 점에 주의하세요.

이 모델이 왜 필요한지는 **클라우드 이전과 비교**하면 분명해집니다. 서버를 직접 사서 전산실에 두던 시절에는 경계선을 그릴 일이 없었습니다. 건물 출입 통제부터 디스크 폐기, 백업, 방화벽 설정까지 **전부 우리 회사 몫**이었으니까요. 클라우드로 옮기면 그 일 중 상당수를 AWS가 대신 해 주는데, 문제는 **"어디까지"**가 눈에 보이지 않는다는 것입니다. 그래서 AWS는 경계선을 문서로 명확히 그어 두었고, 그것이 공동 책임 모델입니다.

세입자와 건물주로 바꿔 생각하면 쉽습니다. 건물의 골조·엘리베이터·소방 설비·현관 출입 통제는 **건물주(AWS)** 몫입니다. 하지만 **우리 집 현관문을 잠그는 것, 누구에게 열쇠를 복사해 줄지 정하는 것, 집 안의 귀중품을 금고에 넣을지 말지**는 세입자(고객) 몫입니다. 건물이 아무리 안전해도 내가 문을 열어 두면 소용이 없습니다. **S3 버킷을 공개로 열어 두어 생기는 사고가 정확히 이 경우**입니다.

책임 경계는 서비스 유형에 따라 움직입니다. 이 이동을 그림으로 잡아 두세요.

```
 관리형 정도 낮음 ───────────────────────────→ 높음
   EC2 (IaaS)          RDS               Lambda / S3
 OS 패치 = 고객      OS 패치 = AWS      실행 환경 = AWS
 ──────────────────────────────────────────────────
 데이터 · 접근 권한 · 암호화 설정 = 언제나 고객
```

> ⚠️ **함정**: "관리형 서비스를 쓰면 보안은 AWS가 다 알아서 한다"는 보기는 항상 오답입니다. 관리형으로 갈수록 **운영 작업**이 AWS로 넘어갈 뿐, **데이터 자체와 누가 접근할 수 있는지**는 끝까지 고객 책임입니다. 문항에 "데이터", "권한", "접근 제어", "암호화 활성화"라는 말이 있으면 답은 거의 고객 쪽입니다.

### IAM (Identity and Access Management)

| 요소 | 핵심 |
|------|------|
| 사용자(User) | 개별 사람/애플리케이션 자격 증명 |
| 그룹(Group) | 사용자 묶음, 권한 일괄 부여 |
| 역할(Role) | 임시 권한 위임(서비스 간, 페더레이션) |
| 정책(Policy) | JSON 권한 문서, 최소 권한 원칙 적용 |

- **루트 사용자**: 절대 일상 작업에 쓰지 말고 **MFA 활성화** 후 잠가둔다
- **최소 권한 원칙**: 꼭 필요한 권한만 부여

네 가지를 회사 출입 관리로 바꾸면 이렇습니다.

| IAM 요소 | 일상 비유 | 결정적 신호 |
|----------|-----------|-------------|
| 사용자 | 직원 개인에게 발급한 **사원증** | 사람 한 명, 로그인 |
| 그룹 | 사원증에 찍힌 **부서** | 여러 사람에게 같은 권한을 일괄로 |
| 역할 | 잠깐 빌려주는 **방문증** | 서비스가 다른 서비스에 접근, 임시 권한 |
| 정책 | 어느 문을 열 수 있는지 적은 **규정집** | 허용/거부를 정의하는 문서 |

> ⚠️ **함정**: "EC2에서 도는 애플리케이션이 S3에 접근해야 한다"는 상황에서 액세스 키를 코드에 적어 두는 보기를 고르면 틀립니다. 정답은 거의 언제나 **IAM 역할(Role)**입니다. 키를 코드에 넣으면 소스가 유출되는 순간 계정도 함께 털리고, 키를 바꿀 때마다 배포를 다시 해야 합니다. 역할은 임시 자격 증명을 자동으로 주고받으므로 이 두 문제가 모두 사라집니다.

> 💡 **개념**: **최소 권한 원칙**은 "일단 넓게 주고 나중에 줄이자"의 반대입니다. 좁게 시작해 필요할 때 넓히는 방향으로 갑니다. 넓게 준 권한은 아무도 불편해하지 않기 때문에 **줄일 계기가 영원히 오지 않는다**는 것이 이 원칙이 존재하는 실무적 이유입니다. 보기에 "모든 사용자에게 관리자 권한", "전체 접근 허용" 같은 표현이 보이면 대개 오답 신호입니다.

### 주요 보안 서비스

| 서비스 | 역할 |
|--------|------|
| IAM | 인증·인가 |
| AWS Shield | DDoS 방어 |
| AWS WAF | 웹 애플리케이션 방화벽(SQL 인젝션, XSS 차단) |
| GuardDuty | 위협 탐지(지능형 모니터링) |
| Amazon Inspector | 취약점 자동 평가 |
| KMS | 암호화 키 관리 |
| Secrets Manager | 비밀번호·키 보관 및 자동 교체 |
| AWS Config | 리소스 구성 추적·규정 준수 |
| CloudTrail | API 호출 감사 로그 |

> 💡 **관련 이론**: "누가 무엇을 했는지(API 감사)"는 **CloudTrail**, "리소스가 규정을 지키는지 추적"은 **Config**, "성능/지표 모니터링"은 **CloudWatch**입니다. 이 셋의 구분이 단골 함정입니다.

#### 역할별로 묶어서 외우기

이름이 많아 보이지만, **하는 일의 성격**으로 묶으면 세 덩어리뿐입니다.

| 묶음 | 하는 일 | 해당 서비스 |
|------|---------|-------------|
| 막는다 | 공격이 들어오는 길목을 차단 | WAF, Shield, 보안 그룹 |
| 찾아낸다 | 이상 징후·취약점·민감 정보를 탐지 | GuardDuty, Inspector, Macie |
| 기록한다 | 누가 무엇을 했고 무엇이 바뀌었는지 남김 | CloudTrail, Config, CloudWatch |
| 감춘다 | 데이터와 비밀을 안전하게 보관 | KMS, Secrets Manager |

#### 헷갈리는 짝 갈라내기

| 짝 | 갈라내는 기준 |
|----|---------------|
| WAF vs Shield | 웹 요청의 **내용**을 검사(SQL 인젝션·XSS 차단) vs 대량 트래픽 **공격량**을 막음(DDoS) |
| GuardDuty vs Inspector | 계정·네트워크 활동에서 **수상한 움직임** 탐지 vs 워크로드의 **알려진 취약점** 점검 |
| Inspector vs Macie | 소프트웨어 취약점 vs **S3에 담긴 민감 정보**(개인정보 등) 탐지 |
| CloudTrail vs Config | **누가 무엇을 했나**(행위 기록) vs **무엇이 어떻게 설정돼 있나**(구성 상태) |
| CloudTrail vs CloudWatch | 감사 로그 vs **성능 지표·모니터링** |
| KMS vs Secrets Manager | 암호화 **키**를 만들고 관리 vs 비밀번호·API 키를 보관하고 **자동 교체** |

세 기록 서비스는 건물 관리로 비유하면 확실히 갈립니다. **CloudTrail은 출입문 CCTV와 출입 기록부**(누가 언제 들어와 무엇을 했나), **Config는 시설 점검 대장**(소화기가 규정대로 비치돼 있나, 언제 바뀌었나), **CloudWatch는 계기판**(지금 전력 사용량과 온도가 얼마인가)입니다.

> 📚 **사례**: 어느 날 회사의 EC2 인스턴스 하나가 새벽에 갑자기 대량의 외부 통신을 시작했다고 해봅시다. 이 **수상한 행동 자체를 알아채는 것**이 GuardDuty입니다. 조사에 들어가 "그 인스턴스가 언제, 어떤 계정으로 생성됐고 누가 보안 그룹을 열었는지" 확인하는 데 쓰는 것이 **CloudTrail**입니다. "우리 회사 규칙상 열려 있으면 안 되는 포트가 열려 있었다"는 사실을 상시로 감지해 주는 것은 **Config**이고, 그 인스턴스에 오래된 취약점이 남아 있었는지 점검하는 것은 **Inspector**입니다. 하나의 사건에서 네 서비스가 각각 다른 조각을 맡습니다.

### 규정 준수 도구

- **AWS Artifact**: 규정 준수 보고서(SOC, PCI DSS 등) 다운로드
- **AWS Compliance Center / Programs**: 인증 프로그램 정보

> 💡 **관련 이론**: 규정 준수 문항에서 **Artifact는 "보고서를 받는 곳"**이라는 점만 확실히 하면 됩니다. 감사 대응이나 고객사 실사에서 "AWS가 특정 인증을 지키고 있음을 증명하는 문서가 필요하다"는 상황이 나오면 답은 Artifact입니다. 우리 계정이 규칙을 지키는지 확인하는 것(Config)과 혼동하지 마세요. **Artifact는 AWS 쪽 증빙, Config는 우리 쪽 점검**입니다.

## Domain 4 핵심 — 청구·요금·지원

### EC2 요금 모델

| 모델 | 특징 | 적합한 경우 |
|------|------|-------------|
| 온디맨드 | 사용한 만큼, 약정 없음 | 단기·예측 불가 워크로드 |
| 예약 인스턴스(RI) | 1~3년 약정, 큰 할인 | 안정적·지속 워크로드 |
| Savings Plans | 사용량 약정 기반 할인 | 유연한 장기 절감 |
| 스팟 인스턴스 | 최대 90% 할인, 중단 가능 | 내결함성 배치 작업 |

네 가지를 고르는 기준은 결국 **"얼마나 오래, 얼마나 확실히 쓰는가"** 하나입니다. 통신 요금제로 바꾸면 온디맨드는 약정 없는 종량제, RI는 조건까지 못 박은 장기 약정, Savings Plans는 "월 얼마 쓰겠다"만 약속하는 장기 약정, 스팟은 출발 직전 남은 좌석 특가입니다. RI와 Savings Plans가 끝까지 헷갈린다면 **"무엇을 약속했는가"**만 기억하세요 — RI는 **자리**를, Savings Plans는 **금액**을 약속합니다. 그래서 유형이나 리전을 바꿔도 할인이 따라오는 쪽이 Savings Plans입니다.

> ⚠️ **함정**: "비용을 가장 많이 줄이는 방법"이라는 표현만 보고 반사적으로 스팟을 고르면 틀립니다. 스팟은 AWS가 언제든 회수할 수 있어 **중단을 견딜 수 있는 작업에만** 해당합니다. 보기나 지문에 "내결함성", "배치", "재시작 가능", "중단돼도 무방" 같은 표현이 함께 있어야 정답 후보가 됩니다. 상시 서비스되는 웹 서버나 데이터베이스에 스팟을 고르면 오답입니다.

### 비용 관리·청구 도구

| 도구 | 용도 |
|------|------|
| AWS Pricing Calculator | 사전 비용 견적 |
| AWS Cost Explorer | 사용·비용 추세 시각화/분석 |
| AWS Budgets | 예산 설정 및 초과 시 알림 |
| Cost and Usage Report (CUR) | 가장 상세한 청구 데이터 |
| Billing Conductor | 사용자 정의 청구 |

> 💡 **관련 이론**: "예산을 넘으면 알림을 받고 싶다"면 **Budgets**, "과거 비용 추세를 분석"하려면 **Cost Explorer**, "아직 만들지 않은 리소스 견적"은 **Pricing Calculator**입니다.

이 셋은 **서 있는 시점**이 다릅니다. 이 축 하나로 대부분의 비용 도구 문항이 갈립니다.

```
   과거 ────────────── 현재 ────────────── 미래
 Cost Explorer        Budgets         Pricing Calculator
 CUR                (넘기 전 알림)     (아직 안 만든 것)
 (이미 쓴 돈)
```

가계부로 바꾸면 Cost Explorer는 월별 지출 그래프, Budgets는 카드 한도 초과 알림 문자, CUR은 항목이 전부 찍힌 영수증 원본, **비용 할당 태그**는 영수증에 붙이는 '식비/교통비' 스티커입니다.

> ⚠️ **함정**: Cost Explorer에도 앞으로의 비용을 **예측**하는 기능이 있어서 "예측"이라는 단어만 보고 이것을 고르는 실수가 잦습니다. 그 예측은 **이미 쓰고 있는 것의 추세를 늘려 그린 선**입니다. **아직 만들지 않은** 구성의 비용을 구하는 것은 Pricing Calculator입니다. 지문에 "배포 전", "신규 설계", "아직 생성하지 않은"이 있으면 Cost Explorer가 아닙니다.

### AWS Organizations & 통합 결제

- **Organizations**: 여러 계정을 묶어 중앙 관리
- **통합 결제(Consolidated Billing)**: 청구를 하나로 합쳐 **볼륨 할인** 공유
- **SCP(서비스 제어 정책)**: 계정별 허용 작업 제한

가족 결합 요금제를 떠올리면 그대로입니다. 가족 각자의 번호(계정)는 따로 있지만 요금은 한 장으로 나오고(통합 결제), 데이터는 가족끼리 나눠 씁니다(할인 공유). 부모가 자녀 회선에 차단을 걸어 두는 것이 **SCP**입니다.

> ⚠️ **함정**: **SCP는 권한을 '주는' 도구가 아니라 '한도를 정하는' 도구**입니다. SCP가 허용하더라도 계정 안의 IAM 정책이 허용하지 않으면 여전히 못 하고, IAM에서 관리자 권한을 줬어도 SCP가 막아 두었다면 할 수 없습니다. **울타리(SCP) 안에서 열쇠(IAM)를 쥐어 준다**고 기억하세요. 또한 **Organizations는 거버넌스, 통합 결제는 절감**으로 역할이 다릅니다. "권한을 중앙에서 제한"이라는 문장에 통합 결제를 고르면 오답입니다.

### 지원 플랜

| 플랜 | 핵심 |
|------|------|
| Basic | 무료, 문서·포럼 |
| Developer | 업무 시간 이메일 지원 |
| Business | 24/7 기술 지원, 전체 Trusted Advisor |
| Enterprise On-Ramp / Enterprise | TAM(전담 기술 계정 관리자), 가장 빠른 응답 |

> 💡 **관련 이론**: **전담 TAM(Technical Account Manager)** 이 필요하면 **Enterprise** 플랜입니다. 24/7 전화 지원이 처음 제공되는 것은 **Business** 플랜부터입니다.

지원 플랜은 **보험 등급**으로 보면 이해가 빠릅니다. 평소에는 차이를 못 느끼지만 사고가 났을 때 누가 얼마나 빨리 오는지가 달라집니다. 한 계단 올라갈 때 **새로 생기는 것**만 기억하면 표를 통째로 외울 필요가 없습니다.

```
 Basic       문서 · 포럼 · 청구 문의   (기술 케이스 ✕)
   └ + 기술 지원(이메일, 업무 시간)  → Developer
        └ + 24/7 기술 지원, 전체 Trusted Advisor → Business
             └ + TAM(전담 사람), 가장 빠른 응답 → Enterprise
```

> ⚠️ **함정**: "24시간 지원이 필요하다"만 보고 곧장 Enterprise를 고르면 요건을 초과한 오답이 됩니다. 24/7은 **Business**부터 제공됩니다. Enterprise의 결정적 신호는 **TAM**이나 **가장 빠른 응답**입니다. 또한 **TAM은 사람, Trusted Advisor는 도구**입니다. 지문의 "전담", "자문", "담당자"는 사람 쪽이고 "점검", "권고", "자동 검사"는 도구 쪽입니다.

## 자주 틀리는 함정 목록

틀리는 데에는 이유가 있습니다. 이유까지 알아야 다음에 안 틀립니다.

1. **"관리형이니 보안도 AWS 몫"이라고 생각합니다** — 운영은 넘어가도 데이터와 권한은 끝까지 고객 책임입니다.
2. **액세스 키를 코드에 넣는 보기를 고릅니다** — 서비스 간 접근은 언제나 IAM 역할이 정답입니다.
3. **WAF와 Shield를 바꿔 답합니다** — 요청의 **내용**을 보는 것이 WAF, **공격량(DDoS)**을 막는 것이 Shield입니다.
4. **GuardDuty와 Inspector를 섞습니다** — 수상한 **행동**이 GuardDuty, 알려진 **취약점**이 Inspector입니다.
5. **CloudTrail과 Config를 혼동합니다** — **행위 기록**이 CloudTrail, **구성 상태**가 Config입니다.
6. **Artifact와 Config를 섞습니다** — AWS 쪽 증빙 문서가 Artifact, 우리 계정 점검이 Config입니다.
7. **"예측"만 보고 Cost Explorer를 찍습니다** — 아직 만들지 않은 구성은 Pricing Calculator입니다.
8. **"24시간 지원"에서 Enterprise로 뜁니다** — 24/7은 Business부터입니다.
9. **SCP가 권한을 부여한다고 봅니다** — 상한선만 정할 뿐, 실제 허용은 IAM이 합니다.
10. **요건보다 비싼 답이 안전하다고 믿습니다** — 조건을 정확히 만족하는 선택이 정답인 경우가 많습니다.

## 한 줄 요약

**Domain 2는 "이 일의 책임자가 누구인가"와 "이 서비스는 무엇을 막거나 찾아내는가" 두 질문으로 압축되고, Domain 4는 "시점·주체·목적" 세 축으로 압축됩니다.** 서비스 이름을 하나하나 외우는 대신 이 다섯 개의 질문을 손에 쥐고 문항을 읽으면, 보기 네 개 중 둘은 읽자마자 지울 수 있습니다.

## 📖 용어

- **공동 책임 모델** : 클라우드 보안을 AWS와 고객이 나눠 맡는 방식. 클라우드 자체는 AWS, 그 안에 올린 것은 고객 몫입니다.
- **하이퍼바이저** : 물리 서버 한 대 위에 여러 가상 서버를 띄우는 가상화 계층. AWS가 책임집니다.
- **IAM 역할(Role)** : 비밀번호 없이 임시로 권한을 빌려주는 자격 증명. 서비스 간 접근에 씁니다.
- **최소 권한 원칙** : 업무에 꼭 필요한 만큼만 권한을 주는 원칙. 좁게 시작해 필요할 때 넓힙니다.
- **MFA(다중 인증)** : 비밀번호에 더해 두 번째 확인 수단을 요구하는 로그인 방식.
- **AWS WAF** : 웹 요청의 내용을 검사해 SQL 인젝션·XSS 같은 공격을 걸러내는 방화벽.
- **AWS Shield** : 대량 트래픽으로 서비스를 마비시키는 DDoS 공격을 막는 서비스.
- **GuardDuty** : 계정·네트워크 활동을 지켜보며 수상한 움직임을 탐지하는 서비스.
- **Amazon Inspector** : 워크로드에 알려진 취약점이 남아 있는지 자동으로 점검하는 서비스.
- **Amazon Macie** : S3에 담긴 민감 정보를 찾아내는 서비스.
- **KMS** : 암호화 키를 만들고 관리하는 서비스.
- **CloudTrail / AWS Config** : 누가 무엇을 했는지 남기는 감사 기록 / 리소스 구성이 규칙에 맞는지 추적.
- **AWS Artifact** : AWS의 규정 준수 보고서를 내려받는 곳.
- **SCP(서비스 제어 정책)** : 계정이 할 수 있는 일의 상한선을 정하는 정책. 권한 부여가 아니라 한도 설정입니다.

## 📝 연습 문제

**문제 1.** 공동 책임 모델에서 다음 중 항상 고객의 책임에 해당하는 것은?

A) 데이터센터의 물리적 보안  
B) 하이퍼바이저 패치  
C) IAM 사용자 및 권한 구성  
D) 하드웨어의 안전한 폐기  

**정답: C**  
해설: IAM 사용자와 권한 설정은 클라우드 "내부"의 구성으로 항상 고객 책임입니다. 물리적 보안, 하이퍼바이저 패치, 하드웨어 폐기는 모두 클라우드 인프라에 해당하므로 AWS 책임입니다.

---

**문제 2.** 계정에서 발생한 모든 API 호출 기록을 감사 목적으로 추적하려면 어떤 서비스를 사용해야 하는가?

A) Amazon CloudWatch  
B) AWS CloudTrail  
C) AWS Config  
D) Amazon Inspector  

**정답: B**  
해설: CloudTrail은 누가 언제 어떤 API를 호출했는지 기록하는 감사 로그 서비스입니다. CloudWatch는 성능 지표·로그 모니터링, Config는 리소스 구성 변경·규정 준수 추적, Inspector는 취약점 평가용입니다.

---

**문제 3.** 중단되어도 무방한 대규모 배치 처리 작업의 비용을 최대 90%까지 절감하려면 가장 적합한 EC2 요금 모델은?

A) 온디맨드 인스턴스  
B) 예약 인스턴스  
C) 스팟 인스턴스  
D) 전용 호스트  

**정답: C**  
해설: 스팟 인스턴스는 여유 용량을 최대 90% 저렴하게 제공하지만 AWS가 회수할 수 있어 중단에 강한(내결함성) 작업에 적합합니다. 온디맨드는 할인이 없고, 예약 인스턴스는 장기 약정 기반, 전용 호스트는 규정 준수·라이선스 목적입니다.

---

**문제 4.** 전담 기술 계정 관리자(TAM)의 지원이 필요한 대규모 기업에 가장 적합한 AWS Support 플랜은?

A) Basic  
B) Developer  
C) Business  
D) Enterprise  

**정답: D**  
해설: 전담 TAM은 Enterprise(및 Enterprise On-Ramp) 플랜에서 제공됩니다. Basic은 무료 기본 지원, Developer는 업무 시간 이메일, Business는 24/7 기술 지원을 제공하지만 전담 TAM은 포함하지 않습니다.

---

**문제 5.** 월별 비용이 설정한 한도를 초과할 경우 알림을 받고 싶다면 어떤 도구를 사용해야 하는가?

A) AWS Pricing Calculator  
B) AWS Budgets  
C) AWS Cost Explorer  
D) AWS Artifact  

**정답: B**  
해설: AWS Budgets는 예산 한도를 설정하고 초과하거나 예측치가 넘으면 알림을 보내는 도구입니다. Pricing Calculator는 사전 견적, Cost Explorer는 과거 비용 분석, Artifact는 규정 준수 보고서 제공 도구입니다.
