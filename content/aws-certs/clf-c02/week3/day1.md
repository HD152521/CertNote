# Day 1 - 데이터베이스 개요: 같은 "DB"라도 쓰임새가 다르다

애플리케이션은 결국 데이터를 어딘가에 저장한다. 그런데 AWS 콘솔을 열면 데이터베이스 카테고리에만 RDS, Aurora, DynamoDB, ElastiCache, Redshift 같은 이름이 줄줄이 나온다. 처음 보면 "DB는 그냥 하나면 되는 거 아냐?"라고 생각하기 쉽지만, 시험에서도 실무에서도 핵심은 **"이 데이터에는 어떤 DB가 맞느냐"를 고르는 것**이다.

오늘은 다섯 가지 대표 데이터베이스 서비스를 외우는 게 아니라, **각자가 어떤 문제를 풀려고 태어났는지**를 그림으로 잡는다. 그 그림이 잡히면 "고객 주문 데이터", "장바구니 임시 저장", "한 달치 매출 분석" 같은 시나리오에서 답이 자연스럽게 보인다.

## 관리형 데이터베이스란 무엇인가

먼저 큰 틀부터. AWS의 데이터베이스 서비스는 거의 전부 **관리형(managed)**이다. 즉 서버 설치, OS 패치, 백업, 장애 복구 같은 귀찮은 운영 일을 AWS가 대신해준다. 우리가 직접 EC2에 MySQL을 깔 수도 있지만, 그러면 패치도 백업도 전부 내 책임이 된다.

> 💡 **관련 이론**: 이것이 Day별로 반복되는 **공동 책임 모델**의 데이터베이스 버전이다. RDS 같은 관리형 서비스를 쓰면 엔진 패치·백업·복제 같은 "인프라 운영"은 AWS 책임으로 올라가고, 고객은 데이터 모델링·접근 권한·쿼리 같은 "데이터 안의 일"에 집중한다.

| 구분 | 직접 운영(EC2 위 설치) | 관리형(RDS 등) |
|------|------------------------|----------------|
| OS·엔진 패치 | 고객 | AWS |
| 백업·스냅샷 | 고객이 구성 | AWS 자동 |
| 장애 복구 | 고객이 설계 | AWS 자동(Multi-AZ) |
| 세밀한 OS 제어 | 가능 | 제한적 |

## 관계형 데이터베이스: RDS와 Aurora

가장 전통적인 데이터는 **표(table)로 정리된 정형 데이터**다. 고객, 주문, 결제처럼 행과 열이 명확하고 서로 관계(JOIN)가 있는 데이터. 이걸 다루는 게 관계형 데이터베이스(RDBMS)이고, SQL로 질의한다.

**Amazon RDS(Relational Database Service)**는 MySQL, PostgreSQL, MariaDB, Oracle, SQL Server 같은 익숙한 엔진을 관리형으로 제공한다. 기존에 쓰던 DB를 그대로 클라우드로 옮기고 싶을 때 가장 자연스러운 선택이다.

**Amazon Aurora**는 AWS가 클라우드에 맞게 새로 설계한 관계형 DB로, MySQL·PostgreSQL과 호환된다. 같은 MySQL 코드를 쓰면서도 성능이 더 높고(표준 MySQL 대비 수 배), 스토리지가 자동으로 늘어나며, 여러 AZ에 데이터를 자동 복제해 내구성이 높다.

| 항목 | RDS | Aurora |
|------|-----|--------|
| 엔진 | MySQL/PostgreSQL/Oracle/SQL Server 등 | MySQL·PostgreSQL 호환 |
| 성격 | 익숙한 엔진을 그대로 관리형으로 | 클라우드 네이티브로 재설계 |
| 성능 | 표준 수준 | 표준 대비 높음 |
| 스토리지 | 미리 용량 지정 | 자동 확장 |

> 💡 **관련 이론**: "기존 Oracle DB를 최소 변경으로 옮기고 싶다" → RDS. "최고 성능과 자동 확장을 원하고 MySQL/PostgreSQL이면 충분하다" → Aurora. 시험에서 이 두 키워드("기존 엔진 유지" vs "고성능 클라우드 네이티브")가 자주 나온다.

## NoSQL: DynamoDB

표 형태로 깔끔하게 안 떨어지는 데이터도 많다. 사용자 프로필, 게임 상태, IoT 센서 값처럼 구조가 유연하고, **초당 수백만 건의 읽기/쓰기**가 필요한 경우다. 이럴 때 쓰는 게 **Amazon DynamoDB**, 완전 관리형 NoSQL(키-값 / 문서) 데이터베이스다.

DynamoDB의 특징은 "서버를 신경 쓸 필요가 없다"는 점이다. 용량을 미리 잡지 않아도 트래픽에 따라 자동 확장되고(온디맨드 모드), 한 자리 밀리초(single-digit millisecond) 수준의 빠른 응답을 어떤 규모에서도 보장한다.

```
[관계형 RDS/Aurora]              [NoSQL DynamoDB]
 행/열 고정 스키마                유연한 항목(item) 구조
 JOIN으로 관계 표현               단일 키로 초고속 조회
 복잡한 질의에 강함               초대규모 트래픽에 강함
```

> 💡 **관련 이론**: "스키마가 자주 바뀌거나", "예측 불가한 대규모 트래픽", "서버 관리 없이"라는 키워드가 보이면 DynamoDB다. 반대로 "복잡한 JOIN", "트랜잭션 정합성", "기존 SQL 앱"이면 RDS/Aurora 쪽이다.

## 캐시: ElastiCache

DB는 좋지만, 같은 데이터를 1초에 수천 번 읽으면 DB가 힘들어진다. 이때 **자주 쓰는 데이터를 메모리에 잠깐 올려두고 빠르게 꺼내쓰는** 것이 캐시다. **Amazon ElastiCache**는 Redis와 Memcached를 관리형으로 제공하는 인메모리 캐시 서비스다.

대표 용도는 세션 저장, 리더보드, 자주 조회되는 상품 정보 캐싱 등이다. 메모리에서 처리하므로 마이크로초~밀리초 수준으로 매우 빠르다. 단, 메모리는 휘발성이라 **영구 저장소가 아니라 "앞단 가속기"**로 이해해야 한다.

> 💡 **관련 이론**: "DB 부하를 줄여라", "응답 지연을 줄여라", "세션/리더보드"라는 신호가 보이면 ElastiCache. 캐시는 원본 DB를 대체하는 게 아니라 앞에 두는 보조 계층이라는 점이 핵심이다.

## 분석/데이터 웨어하우스: Redshift

마지막은 성격이 완전히 다른 데이터다. "지난 3년치 매출을 지역·상품별로 집계해줘" 같은 **대량의 데이터를 모아 분석**하는 일. 이런 분석 질의는 RDS 같은 운영 DB에 던지면 느리고 운영에 방해가 된다.

**Amazon Redshift**는 이런 분석 전용 **데이터 웨어하우스(Data Warehouse)**다. 페타바이트급 데이터를 열 기반(columnar) 저장으로 빠르게 집계·분석하도록 만들어졌다. 핵심 구분은 OLTP와 OLAP이다.

| 구분 | OLTP (운영) | OLAP (분석) |
|------|-------------|-------------|
| 대표 서비스 | RDS, Aurora, DynamoDB | Redshift |
| 질의 성격 | 짧고 빈번한 읽기/쓰기 | 대량 데이터 집계 |
| 예시 | 주문 처리, 결제 | 매출 리포트, BI 대시보드 |

> 💡 **관련 이론**: "데이터 웨어하우스", "BI", "대량 데이터 분석/집계", "리포팅"이 보이면 Redshift다. 반대로 "실시간 거래/주문 처리"는 OLTP(RDS/Aurora/DynamoDB)다.

## 한 장으로 정리: 어떤 데이터에 어떤 DB

```
정형 + SQL + JOIN          → RDS / Aurora
유연한 구조 + 초대규모      → DynamoDB
빠른 캐시 + DB 부하 감소    → ElastiCache
대량 분석 + 리포팅          → Redshift
```

CLF 시험은 깊은 튜닝이 아니라 **"이 시나리오에 맞는 서비스를 고르는 능력"**을 묻는다. 그래서 각 서비스의 한 줄 정체성을 또렷이 기억하는 게 가장 효과적이다.

## 정리하며

오늘은 다섯 데이터베이스 서비스를 "용도"로 구분했다. 관계형은 RDS/Aurora, NoSQL은 DynamoDB, 캐시는 ElastiCache, 분석은 Redshift. 외우려 하지 말고 "이 데이터의 성격이 무엇인가"를 먼저 묻는 습관을 들이면 된다.

다음 글에서는 이 서비스들을 서로 **느슨하게 연결**해주는 메시징 서비스 — SQS, SNS, EventBridge — 를 본다. 데이터가 어디에 저장되느냐만큼, 시스템 간에 어떻게 메시지를 주고받느냐도 클라우드 설계의 핵심이다.

## 📝 연습 문제

**문제 1.** 한 회사가 기존 온프레미스 Oracle 데이터베이스를 최소한의 변경으로 AWS로 옮기려 한다. 가장 적합한 서비스는?

A) Amazon RDS  
B) Amazon DynamoDB  
C) Amazon Redshift  
D) Amazon ElastiCache  

**정답: A**  
해설: RDS는 Oracle을 포함한 익숙한 관계형 엔진을 관리형으로 제공하므로 기존 DB를 최소 변경으로 이전하기에 적합하다. DynamoDB는 NoSQL이라 스키마/쿼리를 다시 설계해야 하고, Redshift는 분석용 데이터 웨어하우스, ElastiCache는 캐시라서 운영 DB 자체를 대체하지 못한다.

---

**문제 2.** 유연한 데이터 구조와 예측이 어려운 초대규모 트래픽을 처리하며 서버 관리가 필요 없는 NoSQL 데이터베이스는?

A) Amazon Aurora  
B) Amazon RDS  
C) Amazon DynamoDB  
D) Amazon Redshift  

**정답: C**  
해설: DynamoDB는 완전 관리형 NoSQL로 유연한 항목 구조와 자동 확장, 한 자리 밀리초 응답을 제공한다. Aurora와 RDS는 관계형(정형 스키마)이고, Redshift는 대량 데이터 분석용 웨어하우스라 운영 트래픽 처리에는 맞지 않는다.

---

**문제 3.** 데이터베이스의 읽기 부하를 줄이고 자주 조회되는 데이터의 응답 속도를 높이려 한다. 가장 적합한 서비스는?

A) Amazon Redshift  
B) Amazon ElastiCache  
C) Amazon RDS  
D) Amazon DynamoDB  

**정답: B**  
해설: ElastiCache는 Redis/Memcached 기반 인메모리 캐시로, 자주 쓰는 데이터를 메모리에 두어 DB 부하를 줄이고 응답을 가속한다. Redshift는 분석용, RDS/DynamoDB는 원본 저장소이지 캐시 계층이 아니다.

---

**문제 4.** 한 회사가 지난 수년간의 판매 데이터를 모아 대규모 집계 분석과 BI 리포트를 만들려 한다. 가장 적합한 서비스는?

A) Amazon Redshift  
B) Amazon DynamoDB  
C) Amazon ElastiCache  
D) Amazon RDS  

**정답: A**  
해설: Redshift는 대량 데이터의 집계·분석(OLAP)에 최적화된 데이터 웨어하우스다. DynamoDB와 RDS는 짧고 빈번한 운영 질의(OLTP)에 맞고, ElastiCache는 캐시 계층이라 대규모 분석 질의에 적합하지 않다.

---

**문제 5.** MySQL/PostgreSQL과 호환되면서 표준 대비 높은 성능과 스토리지 자동 확장을 제공하는, AWS가 클라우드에 맞게 새로 설계한 관계형 데이터베이스는?

A) Amazon RDS for MySQL  
B) Amazon Aurora  
C) Amazon DynamoDB  
D) Amazon ElastiCache  

**정답: B**  
해설: Aurora는 MySQL·PostgreSQL과 호환되는 클라우드 네이티브 관계형 DB로, 높은 성능과 자동 확장 스토리지가 특징이다. RDS for MySQL은 표준 엔진을 관리형으로 제공할 뿐이고, DynamoDB는 NoSQL, ElastiCache는 캐시다.
