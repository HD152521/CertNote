# Day 1 - 공동 책임 모델 심화와 IAM의 기본기

보안은 시험 비중이 가장 큰 영역(30%)이다. 그런데 여기서 가장 먼저 짚고 넘어가야 할 질문이 있다. "클라우드 보안은 누구의 책임인가?" 답은 "둘 다"다. AWS와 고객이 보안을 **나눠서** 책임진다. 이 경계선을 정확히 긋는 것이 **공동 책임 모델(Shared Responsibility Model)**이고, 오늘은 그 모델을 다시 한번 또렷이 정리한 뒤, 고객이 책임지는 부분의 핵심 도구인 **IAM(자격 증명 및 접근 관리)**으로 들어간다.

이전 주에 공동 책임 모델을 짧게 언급했지만, 보안 영역에서는 이 모델이 모든 답의 출발점이 된다. "이건 AWS가 해주나, 내가 해야 하나?"라는 질문에 답할 수 있으면 시험 문제의 상당수가 풀린다.

## 공동 책임 모델: "of the cloud" vs "in the cloud"

가장 유명한 한 줄 요약이 있다. AWS는 **클라우드 자체(of the cloud)의 보안**을 책임지고, 고객은 **클라우드 안(in the cloud)의 보안**을 책임진다.

- **AWS 책임 (Security OF the Cloud)**: 데이터센터 물리 보안, 서버 하드웨어, 네트워크 인프라, 가상화 계층, 관리형 서비스의 기반 소프트웨어.
- **고객 책임 (Security IN the Cloud)**: 데이터 자체, 데이터 암호화 설정, 운영체제·애플리케이션 패치(EC2의 경우), 네트워크 방화벽 규칙, **IAM을 통한 접근 권한 관리**.

| 항목 | 책임 주체 |
|------|-----------|
| 데이터센터 출입 통제 | AWS |
| EC2 인스턴스의 OS 패치 | 고객 |
| 물리 서버 폐기 시 디스크 파기 | AWS |
| S3 버킷에 올린 데이터의 접근 권한 | 고객 |
| IAM 사용자/비밀번호 정책 | 고객 |
| 하이퍼바이저(가상화 계층) 보안 | AWS |

> 💡 **관련 이론**: 책임 경계는 서비스 유형에 따라 이동한다. EC2(IaaS)는 OS 패치까지 고객 몫이지만, RDS·Lambda 같은 관리형 서비스로 갈수록 AWS가 더 많은 운영을 책임진다. "관리형일수록 AWS 책임이 커진다"가 핵심 패턴이다. 단, **데이터와 접근 권한은 어떤 서비스든 항상 고객 책임**이다.

## IAM이란 무엇인가

고객 책임 중에서도 가장 자주 다루는 것이 "누가 무엇을 할 수 있는가"를 정하는 일이다. 이것을 담당하는 글로벌 서비스가 **AWS IAM(Identity and Access Management)**이다. IAM은 무료이며, 모든 리전에 걸친 **글로벌 서비스**다(리전별로 따로 만들지 않는다).

IAM이 다루는 두 가지 큰 질문:

- **인증(Authentication)**: "당신은 누구인가?" — 사용자가 맞는지 확인.
- **인가(Authorization)**: "당신은 무엇을 할 수 있는가?" — 어떤 작업을 허용할지 결정.

## IAM의 4가지 핵심 구성요소

IAM을 이해하려면 사용자, 그룹, 역할, 정책 네 가지를 구분해야 한다.

**1. 사용자(User)**: 사람 또는 애플리케이션 하나에 대응하는 자격 증명. 로그인 비밀번호나 액세스 키를 가진다.

**2. 그룹(Group)**: 사용자들을 묶는 단위. 예를 들어 "개발자" 그룹에 권한을 부여하면 그 그룹에 속한 모든 사용자가 같은 권한을 갖는다. 권한을 사람마다 일일이 주지 않고 그룹 단위로 관리하면 훨씬 깔끔하다. (그룹은 사용자만 담을 수 있고, 그룹 안에 그룹은 못 넣는다.)

**3. 역할(Role)**: 비밀번호나 액세스 키가 없는 자격 증명으로, **임시 권한을 빌려주는** 용도다. 대표적으로 EC2 인스턴스가 S3에 접근해야 할 때, EC2에 역할을 부여하면 액세스 키를 코드에 박지 않고도 안전하게 권한을 얻는다.

**4. 정책(Policy)**: 권한을 정의하는 JSON 문서. "어떤 작업(Action)을, 어떤 리소스(Resource)에, 허용(Allow)/거부(Deny)할지"를 적는다. 정책을 사용자·그룹·역할에 붙여서 권한을 부여한다.

```
[정책(Policy)]  ── 권한 규칙을 정의 (JSON)
      │ 붙인다
      ▼
[사용자/그룹/역할] ── 실제 자격 증명에 권한 적용
```

> 💡 **관련 이론**: "EC2 인스턴스가 S3에 접근해야 하는데 어떻게 권한을 주는 게 안전한가?"라는 문제가 나오면 답은 거의 항상 **IAM 역할(Role)**이다. 액세스 키를 코드나 인스턴스에 하드코딩하는 것은 보안상 최악의 선택이다.

## 루트 사용자 보호와 MFA

AWS 계정을 처음 만들면 **루트 사용자(Root User)**가 생긴다. 이 계정은 모든 것을 할 수 있는 최고 권한자라서, 탈취되면 재앙이다. 그래서 AWS는 강하게 권고한다.

- 루트 사용자는 일상 작업에 **사용하지 말 것**. 대신 IAM 사용자를 만들어 사용한다.
- 루트 사용자에 **MFA(다중 인증)**를 반드시 활성화한다.
- 루트 액세스 키는 만들지 말고, 있다면 삭제한다.

**MFA(Multi-Factor Authentication)**는 비밀번호(아는 것)에 더해, 휴대폰 앱의 일회용 코드나 보안 키(가진 것)를 추가로 요구하는 방식이다. 비밀번호가 유출돼도 두 번째 요소가 없으면 로그인할 수 없으므로 보안이 크게 강화된다.

> 💡 **관련 이론**: 시험에서 "계정 보안을 강화하는 가장 좋은 첫 단계"를 물으면 거의 항상 **루트 사용자에 MFA 활성화 + 루트 사용 자제 + IAM 사용자 생성**이 정답 묶음이다.

## 최소 권한 원칙(Least Privilege)

IAM 권한 설계의 황금률은 **최소 권한 원칙**이다. 즉 "업무에 꼭 필요한 만큼만" 권한을 준다. 처음부터 넓게 주고 나중에 줄이는 게 아니라, 좁게 시작해 필요할 때 추가하는 방향이 안전하다.

| 나쁜 예 | 좋은 예(최소 권한) |
|---------|--------------------|
| 모든 사용자에게 관리자 권한 | 역할별로 필요한 서비스 권한만 |
| S3 전체 접근 부여 | 특정 버킷의 읽기 권한만 |
| 권한을 사람마다 즉흥적으로 | 그룹/정책으로 표준화 |

> 💡 **관련 이론**: "보안 모범 사례에 맞는 권한 부여 방식"을 묻는 문제의 답은 대부분 최소 권한 원칙이다. "필요 이상으로 넓은 권한"은 항상 오답 신호다.

## 정리하며

오늘은 보안의 출발점인 공동 책임 모델을 다시 정리하고, 고객 책임의 핵심 도구 IAM을 살펴봤다. 사용자·그룹·역할·정책의 역할 구분, 루트 보호와 MFA, 최소 권한 원칙 — 이 네 가지가 IAM 문제의 90%를 커버한다.

다음 글에서는 IAM 너머의 보안 서비스들 — WAF, Shield, GuardDuty, Inspector, Macie, Security Hub — 을 각각 한 줄 정체성으로 정리한다. 이름이 비슷해 헷갈리기 쉬운데, "무슨 위협을 막는가"로 묶으면 쉽게 외워진다.

## 📝 연습 문제

**문제 1.** 공동 책임 모델에서 다음 중 항상 **고객의 책임**에 해당하는 것은?

A) 데이터센터의 물리적 보안  
B) 하이퍼바이저(가상화 계층)의 보안  
C) S3에 저장한 데이터의 접근 권한 설정  
D) 서버 하드웨어의 유지보수  

**정답: C**  
해설: 데이터와 그 접근 권한은 어떤 서비스를 쓰든 항상 고객 책임("in the cloud")이다. 데이터센터 물리 보안, 하이퍼바이저, 하드웨어 유지보수는 모두 AWS가 책임지는 "of the cloud" 영역이다.

---

**문제 2.** EC2 인스턴스에서 실행되는 애플리케이션이 S3 버킷에 접근해야 한다. 가장 안전한 권한 부여 방식은?

A) 액세스 키를 애플리케이션 코드에 하드코딩한다  
B) EC2 인스턴스에 IAM 역할(Role)을 부여한다  
C) 루트 사용자의 자격 증명을 사용한다  
D) 모든 사용자에게 관리자 권한을 준다  

**정답: B**  
해설: IAM 역할은 액세스 키를 노출하지 않고 EC2에 임시 권한을 안전하게 제공한다. 코드에 키를 하드코딩하거나 루트 자격 증명을 쓰는 것은 보안 위험이 크고, 관리자 권한 부여는 최소 권한 원칙에 위배된다.

---

**문제 3.** AWS 계정 보안을 강화하기 위한 모범 사례로 옳지 않은 것은?

A) 루트 사용자에 MFA를 활성화한다  
B) 일상 작업은 루트 대신 IAM 사용자로 수행한다  
C) 루트 사용자의 액세스 키를 만들어 자동화에 사용한다  
D) 최소 권한 원칙에 따라 권한을 부여한다  

**정답: C**  
해설: 루트 액세스 키는 만들지 않는 것이 권장되며, 탈취 시 계정 전체가 위험해진다. MFA 활성화, 루트 사용 자제와 IAM 사용자 활용, 최소 권한 원칙은 모두 올바른 모범 사례다.

---

**문제 4.** 여러 IAM 사용자에게 동일한 권한을 효율적으로 부여하고 관리하려면 가장 적절한 방법은?

A) 사용자마다 정책을 개별적으로 작성한다  
B) IAM 그룹에 정책을 붙이고 사용자를 그룹에 추가한다  
C) 모든 사용자를 루트 사용자로 통합한다  
D) 사용자마다 별도의 역할을 만든다  

**정답: B**  
해설: 그룹에 정책을 부여하면 그룹에 속한 모든 사용자가 같은 권한을 일관되게 갖게 되어 관리가 간편하다. 사용자별 개별 정책은 관리가 번거롭고, 루트 통합은 불가능하며 위험하고, 역할은 임시 권한 위임 용도이지 사용자 권한 표준화 도구가 아니다.

---

**문제 5.** IAM에 대한 설명으로 옳은 것은?

A) IAM은 리전별로 따로 설정해야 하는 리전 서비스다  
B) IAM 사용은 추가 요금이 부과된다  
C) IAM은 글로벌 서비스이며 사용에 추가 요금이 없다  
D) IAM 정책은 허용(Allow)만 정의할 수 있다  

**정답: C**  
해설: IAM은 모든 리전에 걸친 글로벌 서비스이며 사용 자체에 추가 요금이 없다. 리전별 설정이 필요하지 않고, 정책은 허용(Allow)뿐 아니라 명시적 거부(Deny)도 정의할 수 있다.
