# Day 5 - Week 2 종합 — 핵심 서비스 1 복습

이번 주는 AWS의 "내부 인프라"를 한 바퀴 돌았다. 서버(컴퓨팅), 데이터를 담는 그릇(스토리지), 그것들을 잇는 길(네트워킹), 그리고 멀리 있는 사용자에게 빠르게 전달하는 바깥쪽 서비스(엣지)까지. 오늘은 새로운 내용을 더하지 않고, 흩어진 조각들을 한 장의 큰 그림으로 묶어 복습한다.

복습의 핵심은 암기가 아니라 **"언제 무엇을 고르는가"**다. 시험은 거의 항상 상황(시나리오)을 주고 "가장 적합한 서비스는?"을 묻는다. 그래서 오늘은 서비스별 비교표와 선택 기준을 중심으로 정리한다.

## 한눈에 보는 핵심 서비스 1 지도

| 분류 | 대표 서비스 | 한 줄 정의 |
|------|-------------|------------|
| 컴퓨팅 | EC2 | 직접 관리하는 가상 서버 |
| 컴퓨팅 | Lambda | 서버 없이 코드만 실행(서버리스) |
| 컴퓨팅 | ECS/Fargate | 컨테이너 실행 |
| 스토리지 | S3 | 객체 스토리지(파일·이미지·백업) |
| 스토리지 | EBS | EC2에 붙이는 블록 디스크 |
| 스토리지 | EFS | 여러 서버가 공유하는 파일 시스템 |
| 네트워킹 | VPC | 내 전용 가상 네트워크 |
| 엣지 | CloudFront | 콘텐츠를 빠르게 전달하는 CDN |
| 엣지 | Route 53 | 도메인 이름을 주소로 변환하는 DNS |

> 💡 **관련 이론**: 이 표의 분류는 곧 "책임 경계"의 단계이기도 하다. EC2는 OS까지 내가 관리하고, ECS/Fargate는 컨테이너만 신경 쓰며, Lambda는 코드만 올리면 된다. 위로 갈수록 AWS가 더 많이 떠맡는다.

## 컴퓨팅 복습: EC2 vs Lambda vs ECS

세 서비스는 모두 "코드를 실행"하지만, 내가 관리하는 범위와 과금 방식이 다르다.

| 항목 | EC2 | Lambda | ECS/Fargate |
|------|-----|--------|-------------|
| 단위 | 가상 서버 | 함수(이벤트 단위) | 컨테이너 |
| 관리 부담 | 높음(OS·패치) | 거의 없음 | 중간(컨테이너) |
| 과금 | 실행 시간(시간/초) | 실행 횟수·시간(ms) | 실행 리소스 |
| 적합한 경우 | 항상 켜진 서버, 세밀한 제어 | 짧고 간헐적인 작업 | 컨테이너화된 앱 |

> 🎯 **시나리오**: "하루에 몇 번, 파일이 올라올 때만 잠깐 처리하면 된다" → 항상 켜둘 필요가 없으니 Lambda. "OS를 직접 튜닝하고 24시간 도는 레거시 앱을 올린다" → EC2. "이미 도커 컨테이너로 만든 앱을 서버 관리 없이 돌리고 싶다" → Fargate.

> 💡 **관련 이론**: Lambda는 "서버리스"라 불리지만 서버가 없는 게 아니라 **서버를 내가 보지 않는다**는 뜻이다. 사용한 만큼만 내고 자동으로 확장(스케일)된다. 이 점이 "유휴 시간에도 돈이 나가는" EC2와의 결정적 차이다.

## 스토리지 복습: S3 vs EBS vs EFS

세 가지 모두 데이터를 저장하지만 "데이터의 모양"과 "누가 붙는가"가 다르다.

| 항목 | S3 | EBS | EFS |
|------|-----|-----|-----|
| 종류 | 객체 스토리지 | 블록 스토리지 | 파일 스토리지 |
| 연결 대상 | 인터넷(어디서나 접근) | EC2 1대에 부착 | 여러 EC2가 공유 |
| 비유 | 무한한 파일 보관함 | 한 PC의 하드디스크 | 사내 공유 폴더 |
| 적합한 경우 | 백업·정적 파일·이미지 | 서버의 부팅 디스크·DB 데이터 | 다수 서버의 공유 데이터 |

> ⚠️ **함정**: EBS는 기본적으로 **하나의 EC2에만** 붙는 디스크다. "여러 서버가 같은 파일을 동시에 읽고 써야 한다"면 EBS가 아니라 EFS다. "인터넷에서 직접 접근하는 대용량 파일·백업"이면 S3다. 이 구분이 시험 단골이다.

> 💡 **관련 이론**: S3는 객체(Object) 단위로 저장한다. 즉 파일과 그 메타데이터·고유 식별자를 묶어 통째로 다룬다. 그래서 파일 일부만 수정하는 데는 부적합하지만, 사실상 무한히 확장되고 내구성이 매우 높아(99.999999999%) 백업·정적 호스팅에 강하다.

## 네트워킹 복습: VPC 기초

VPC(Virtual Private Cloud)는 AWS 안에 만드는 **내 전용 가상 네트워크**다. 집에 비유하면, AWS라는 거대한 아파트 단지 안에 내가 임대한 한 채의 집이고, 그 안을 방(서브넷)으로 나누고 문(보안 그룹)을 단다.

| 개념 | 의미 |
|------|------|
| 서브넷(Subnet) | VPC를 잘게 나눈 구역(퍼블릭/프라이빗) |
| 퍼블릭 서브넷 | 인터넷과 직접 통신 가능(웹 서버 등) |
| 프라이빗 서브넷 | 인터넷 직접 접근 차단(DB 등 보호) |
| 보안 그룹 | 인스턴스 단위 방화벽(허용 규칙) |
| 인터넷 게이트웨이 | VPC를 인터넷과 연결하는 출입구 |

> 🎯 **시나리오**: "웹 서버는 외부에서 접속해야 하지만, 데이터베이스는 외부에 절대 노출하면 안 된다." → 웹 서버는 퍼블릭 서브넷, DB는 프라이빗 서브넷에 둔다. DB는 인터넷 게이트웨이로 가는 경로가 없으니 외부에서 직접 닿을 수 없다.

> 💡 **관련 이론**: 보안 그룹은 **상태 저장(stateful)** 방화벽이다. 들어오는 요청을 허용하면 그에 대한 응답은 규칙을 따로 만들지 않아도 자동으로 나간다. "허용 규칙만 정의하고 나머지는 기본 차단"이라는 점도 기억해 두자.

## 엣지 복습: CloudFront + Route 53

두 서비스는 거리 문제를 푸는 한 쌍이다. CloudFront는 "빠른 전달", Route 53은 "이름 해석"이다.

| 항목 | CloudFront | Route 53 |
|------|------------|----------|
| 정체 | CDN(콘텐츠 전달망) | DNS(도메인 이름 변환) |
| 하는 일 | 콘텐츠를 엣지에 캐싱해 빠르게 전달 | 도메인 이름을 IP·자원으로 연결 |
| 핵심 키워드 | 캐싱·지연 시간 감소·원본 보호 | 라우팅 정책·상태 확인·도메인 등록 |

> ⚠️ **함정**: "지연 시간을 줄이려 콘텐츠를 캐싱" = CloudFront, "도메인을 가장 가까운 리전으로 라우팅" = Route 53. 둘 다 엣지 인프라를 쓰지만 역할이 다르다는 점을 헷갈리지 말자.

## 정리하며

핵심 서비스 1을 한 줄씩 다시 새기면 이렇다. **컴퓨팅**은 EC2(직접 관리 서버)·Lambda(서버리스)·ECS(컨테이너)로 책임 경계가 위로 올라가고, **스토리지**는 S3(객체)·EBS(단일 서버 블록)·EFS(공유 파일)로 데이터 모양이 다르며, **네트워킹**은 VPC가 전용 네트워크를 만들고 서브넷·보안 그룹으로 나누고 지키며, **엣지**는 CloudFront가 전달하고 Route 53이 안내한다.

시험에서는 항상 "상황 → 가장 적합한 서비스"의 형태로 묻는다는 것을 기억하자. 다음 주에는 데이터베이스·메시징·관리 도구·IaC 같은 핵심 서비스 2를 배운다.

## 📝 연습 문제

**문제 1.** 하루에 몇 차례, 파일이 업로드될 때만 잠깐 실행되는 가벼운 처리 작업을 운영하려 한다. 유휴 시간에는 비용이 들지 않도록 하려면 가장 적합한 컴퓨팅 서비스는?

A) Amazon EC2  
B) AWS Lambda  
C) Amazon EBS  
D) Amazon VPC  

**정답: B**  
해설: Lambda는 이벤트가 발생할 때만 실행되고 사용한 만큼만 과금되는 서버리스 서비스라, 간헐적이고 짧은 작업에 적합하다. EC2는 켜져 있는 동안 계속 과금되어 유휴 비용이 발생하고, EBS는 블록 스토리지, VPC는 네트워크이므로 코드 실행 주체가 아니다.

---

**문제 2.** 여러 대의 EC2 인스턴스가 동일한 파일을 동시에 읽고 쓸 수 있는 공유 파일 시스템이 필요하다. 가장 적합한 스토리지는?

A) Amazon S3  
B) Amazon EBS  
C) Amazon EFS  
D) Amazon CloudFront  

**정답: C**  
해설: EFS는 여러 EC2가 동시에 마운트해 공유할 수 있는 파일 스토리지다. EBS는 기본적으로 하나의 인스턴스에만 붙는 블록 디스크라 동시 공유에 부적합하고, S3는 객체 스토리지, CloudFront는 콘텐츠 전달망이므로 공유 파일 시스템 용도가 아니다.

---

**문제 3.** 데이터베이스 서버를 인터넷에서 직접 접근하지 못하도록 보호하면서, 웹 서버는 외부 접속을 허용하려 한다. VPC에서 가장 적절한 구성은?

A) 웹 서버와 DB를 모두 퍼블릭 서브넷에 둔다  
B) 웹 서버는 퍼블릭 서브넷, DB는 프라이빗 서브넷에 둔다  
C) 웹 서버와 DB를 모두 프라이빗 서브넷에 둔다  
D) 서브넷을 나누지 않고 보안 그룹도 두지 않는다  

**정답: B**  
해설: 외부 접속이 필요한 웹 서버는 퍼블릭 서브넷, 보호가 필요한 DB는 인터넷 경로가 없는 프라이빗 서브넷에 두는 것이 표준 구성이다. 둘 다 퍼블릭에 두면 DB가 노출되고, 둘 다 프라이빗이면 웹 서버가 외부 접속을 받을 수 없으며, 서브넷·보안 그룹을 두지 않으면 보호 자체가 불가능하다.

**문제 4.** S3, EBS, EFS의 차이를 가장 정확하게 구분한 것은?

A) S3는 블록, EBS는 객체, EFS는 파일 스토리지다  
B) S3는 객체, EBS는 단일 서버용 블록, EFS는 공유 파일 스토리지다  
C) 셋 다 EC2 한 대에만 붙는 디스크다  
D) 셋 다 인터넷에서 직접 접근하는 객체 스토리지다  

**정답: B**  
해설: S3는 객체 스토리지, EBS는 보통 하나의 EC2에 부착되는 블록 스토리지, EFS는 여러 서버가 공유하는 파일 스토리지다. 종류가 뒤바뀐 설명이나, 셋 다 단일 서버 디스크라거나 셋 다 객체 스토리지라는 설명은 사실과 다르다.

**문제 5.** 전 세계 사용자에게 정적 콘텐츠를 낮은 지연 시간으로 전달하기 위해 콘텐츠를 사용자 가까운 거점에 캐싱하려 한다. 가장 적합한 서비스는?

A) Amazon Route 53  
B) Amazon CloudFront  
C) Amazon EFS  
D) Amazon EC2  

**정답: B**  
해설: CloudFront는 콘텐츠를 전 세계 엣지 로케이션에 캐싱해 사용자에게 가까운 곳에서 빠르게 전달하는 CDN이다. Route 53은 도메인 이름을 주소로 바꾸는 DNS이고, EFS는 공유 파일 스토리지, EC2는 가상 서버이므로 콘텐츠 캐싱·전달 역할과는 다르다.
