# Day 2 - 스토리지 개요: S3(객체), EBS(블록), EFS·FSx(파일)

어제 컴퓨팅이 데이터를 "처리"하는 자리였다면, 오늘은 그 데이터를 "어디에 두느냐"의 이야기다. AWS의 스토리지는 종류가 많아 보이지만, 사실 데이터를 담는 방식이 세 가지뿐이다 — 객체(Object), 블록(Block), 파일(File). 이 세 가지가 각각 S3, EBS, EFS/FSx로 이어진다. CLF-C02 시험은 "어떤 데이터를 어떤 스토리지에 두는가"를 반복해서 묻는다.

오늘은 세 가지 스토리지 방식이 어떻게 다른지, 그리고 S3의 스토리지 클래스가 "얼마나 자주 꺼내 쓰느냐"에 따라 어떻게 나뉘는지를 정리한다.

## 세 가지 저장 방식: 객체 · 블록 · 파일

먼저 큰 그림이다. 데이터를 담는 방식은 세 가지로 나뉜다.

| 방식 | 비유 | AWS 서비스 | 접근 방법 |
|------|------|-----------|----------|
| 객체(Object) | 거대한 사물함, 물건마다 라벨 | S3 | HTTP API(키로 조회) |
| 블록(Block) | 컴퓨터에 붙이는 하드디스크 | EBS | 서버에 마운트 |
| 파일(File) | 공유 폴더(네트워크 드라이브) | EFS, FSx | 여러 서버가 동시 마운트 |

핵심 차이는 **"무엇에 붙느냐, 누가 접근하느냐"**다. 블록(EBS)은 EC2 한 대에 붙는 디스크이고, 파일(EFS)은 여러 EC2가 동시에 공유하는 폴더이며, 객체(S3)는 인터넷 어디서든 키(이름)로 꺼내는 사물함이다.

> 💡 **관련 이론**: "객체 스토리지"가 전통적인 파일 시스템과 다른 점은 폴더 계층 구조가 없다는 것이다. S3는 사실 폴더가 없고 모든 객체가 평평한 공간에 키(고유 이름)로 저장된다. `photos/2026/img.jpg` 같은 경로처럼 보이는 것도 실은 폴더가 아니라 키 이름의 일부일 뿐이다.

## S3: 사실상 무한한 객체 스토리지

S3(Simple Storage Service)는 AWS에서 가장 널리 쓰이는 스토리지다. 사진, 동영상, 백업, 로그, 정적 웹사이트 파일 등 무엇이든 **객체** 단위로 저장한다. 객체들은 **버킷(Bucket)**이라는 통에 담긴다.

S3의 특징:

- **사실상 무한한 용량**: 용량을 미리 정할 필요가 없다. 넣는 만큼 늘어난다.
- **높은 내구성**: 11 9s(99.999999999%)라는 내구성을 목표로, 데이터를 여러 곳에 자동 복제한다.
- **인터넷 접근**: 각 객체는 고유 URL로 접근할 수 있다(권한 설정에 따라).
- **서버 불필요**: EC2 없이도 그 자체로 존재한다(서버리스 스토리지).

> 💡 **관련 이론**: "내구성(Durability)"과 "가용성(Availability)"은 다른 개념이다. 내구성은 "데이터를 잃어버리지 않을 확률"이고, 가용성은 "지금 당장 접근할 수 있을 확률"이다. S3는 11 9s의 내구성을 자랑하는데, 이는 데이터를 여러 가용 영역(AZ)에 자동 복제하기 때문이다.

> 📚 **사례**: 정적 웹사이트(HTML·CSS·이미지)를 S3 버킷에 올리고 그 자체로 호스팅할 수 있다. 서버를 한 대도 띄우지 않고 웹사이트를 운영하는 것이다. 트래픽이 늘어도 S3가 알아서 감당하므로 확장 걱정이 없다.

## EBS: EC2에 붙이는 블록 스토리지

EBS(Elastic Block Store)는 **EC2 인스턴스에 붙이는 하드디스크**다. 물리 컴퓨터에 SSD를 꽂는 것과 같은 개념이다. OS를 설치하거나, 데이터베이스 파일을 두거나, 빠른 읽기·쓰기가 필요한 곳에 쓴다.

EBS의 핵심 특징:

- **한 인스턴스에 연결**: 기본적으로 EBS 볼륨 하나는 같은 가용 영역(AZ)의 EC2 한 대에 붙는다.
- **수명 분리 가능**: EC2를 종료해도 EBS 볼륨은 남길 수 있어 데이터가 보존된다.
- **스냅샷 백업**: 특정 시점의 볼륨을 S3에 스냅샷으로 백업할 수 있다.

> ⚠️ **함정**: EBS 볼륨은 특정 가용 영역(AZ)에 묶여 있다. 그래서 다른 AZ의 EC2에 그대로 붙일 수 없다. AZ를 넘기려면 스냅샷을 떠서 다른 AZ에 새 볼륨으로 복원해야 한다. 이 "AZ 종속성"이 시험에 종종 나온다.

## EFS와 FSx: 여러 서버가 공유하는 파일 스토리지

EBS가 한 대에 붙는 디스크라면, **EFS(Elastic File System)**는 여러 EC2가 동시에 같이 쓰는 공유 폴더다. 네트워크 드라이브를 떠올리면 된다. 여러 서버가 같은 파일을 읽고 써야 할 때 쓴다.

| 서비스 | 용도 |
|--------|------|
| EFS | Linux 기반 여러 EC2가 공유하는 파일 시스템, 자동 확장 |
| FSx for Windows | Windows 환경용 공유 파일(SMB 프로토콜) |
| FSx for Lustre | 고성능 컴퓨팅(HPC)·머신러닝용 초고속 파일 시스템 |

EFS는 용량을 미리 정할 필요 없이 파일을 넣는 만큼 자동으로 늘어나고, 여러 AZ에 걸쳐 접근할 수 있다는 점에서 EBS와 다르다.

> 💡 **관련 이론**: EBS와 EFS의 결정적 차이는 "동시 접근"이다. EBS는 보통 한 EC2 전용 디스크(1:1), EFS는 여러 EC2가 동시에 마운트하는 공유 폴더(1:다)다. "여러 서버가 같은 파일을 공유해야 한다"는 키워드가 나오면 EFS, "한 서버의 OS·DB 디스크"라면 EBS다.

## S3 스토리지 클래스: 얼마나 자주 꺼내 쓰는가

S3 안에서도 데이터를 "얼마나 자주 접근하느냐"에 따라 가격이 다른 **스토리지 클래스**를 고를 수 있다. 자주 안 꺼낼 데이터일수록 보관료는 싸지만, 꺼낼 때 시간이나 추가 비용이 든다.

| 클래스 | 접근 빈도 | 특징 |
|--------|----------|------|
| S3 Standard | 자주 | 기본값, 즉시 접근, 보관료 가장 높음 |
| S3 Standard-IA | 가끔 | 보관료 저렴, 꺼낼 때 추가 요금 |
| S3 One Zone-IA | 가끔 | 단일 AZ 저장, 더 저렴(내구성 약간 낮음) |
| S3 Glacier Instant Retrieval | 드물게 | 아카이브, 즉시 꺼냄 |
| S3 Glacier Flexible Retrieval | 드물게 | 아카이브, 분~시간 단위로 꺼냄 |
| S3 Glacier Deep Archive | 거의 안 함 | 가장 저렴, 꺼내는 데 수 시간 |
| S3 Intelligent-Tiering | 알 수 없음 | 접근 패턴에 따라 AWS가 자동 이동 |

> 💡 **관련 이론**: 스토리지 클래스 선택의 원리는 "보관료와 인출비의 교환"이다. 자주 꺼내면 Standard, 거의 안 꺼내면 Glacier Deep Archive가 싸다. 접근 패턴을 모르겠다면 Intelligent-Tiering이 알아서 옮겨 준다. 그리고 이 이동을 자동화하는 것이 **수명 주기 정책(Lifecycle Policy)**이다 — 예: "90일 지난 객체는 Glacier로, 1년 지나면 삭제."

> 🎯 **시나리오**: "법적 보관 의무로 7년간 보관해야 하지만 거의 꺼내 볼 일이 없는 감사 로그"를 어디에 둘까? → S3 Glacier Deep Archive. 보관료가 가장 싸고, 꺼내는 데 몇 시간 걸려도 "거의 꺼내지 않는" 조건에 부합하므로 비용 최적이다.

## 정리하며

오늘의 핵심은 세 갈래다. 첫째, 저장 방식은 **객체(S3)·블록(EBS)·파일(EFS·FSx)** 세 가지뿐이고, 각각 "사물함·붙이는 디스크·공유 폴더"로 기억하면 된다. 둘째, EBS는 한 EC2 전용 + AZ 종속, EFS는 여러 EC2 공유라는 점이 둘을 가르는 기준이다. 셋째, S3 스토리지 클래스는 "얼마나 자주 꺼내느냐"에 따라 보관료와 인출비를 교환하는 메뉴이고, 모르면 Intelligent-Tiering, 자동화는 수명 주기 정책이다.

내일은 이 서버와 스토리지가 모여 사는 동네 — VPC와 네트워킹의 기초로 넘어간다.

## 📝 연습 문제

**문제 1.** 여러 EC2 인스턴스가 동시에 같은 파일에 접근하여 읽고 써야 하는 Linux 기반 워크로드가 있다. 가장 적합한 스토리지는?

A) EBS  
B) EFS  
C) S3 Glacier Deep Archive  
D) 인스턴스 스토어  

**정답: B**  
해설: EFS는 여러 EC2가 동시에 마운트해 공유할 수 있는 파일 시스템으로, "여러 서버가 같은 파일을 공유"라는 조건에 정확히 맞는다. EBS는 기본적으로 한 인스턴스 전용 디스크이고, Glacier는 자주 접근하지 않는 아카이브용이라 동시 파일 공유와 무관하다.

**문제 2.** 법적 의무로 7년간 보관해야 하지만 거의 꺼내 볼 일이 없는 대용량 감사 로그를 가장 저렴하게 저장하려고 한다. 적합한 S3 스토리지 클래스는?

A) S3 Standard  
B) S3 Standard-IA  
C) S3 Glacier Deep Archive  
D) S3 Intelligent-Tiering  

**정답: C**  
해설: Glacier Deep Archive는 S3에서 보관료가 가장 저렴한 클래스로, 꺼내는 데 수 시간이 걸리지만 "거의 접근하지 않는 장기 보관"에는 가장 비용 효율적이다. Standard는 자주 접근하는 데이터용이라 비싸고, Standard-IA는 가끔 접근용, Intelligent-Tiering은 접근 패턴을 모를 때 쓰는 자동 계층화 옵션이다.

**문제 3.** S3의 "내구성 11 9s(99.999999999%)"가 의미하는 것으로 가장 정확한 것은?

A) 데이터에 언제나 즉시 접근할 수 있는 확률  
B) 저장한 데이터를 잃어버리지 않을 확률  
C) 데이터 전송 속도  
D) 한 달에 다운타임이 없는 비율  

**정답: B**  
해설: 내구성(Durability)은 "데이터를 손실하지 않을 확률"을 뜻하며, S3는 데이터를 여러 가용 영역에 자동 복제해 이 목표를 달성한다. 접근 가능성은 가용성(Availability)이라는 별개 개념이므로 A·D는 내구성의 정의가 아니고, 전송 속도(C)와도 무관하다.

**문제 4.** EBS 볼륨에 대한 설명으로 옳은 것은?

A) 여러 가용 영역(AZ)의 EC2에 자유롭게 동시 연결할 수 있다  
B) 특정 가용 영역(AZ)에 묶여 있어 그 AZ의 EC2에 연결된다  
C) 서버 없이도 HTTP로 직접 접근하는 객체 스토리지다  
D) 용량을 미리 정할 수 없고 무한히 자동 확장된다  

**정답: B**  
해설: EBS 볼륨은 특정 AZ에 종속되어 같은 AZ의 EC2에 연결되며, 다른 AZ로 옮기려면 스냅샷을 떠서 복원해야 한다. 여러 AZ에 자유롭게 동시 연결된다는 A는 틀렸고, HTTP로 접근하는 객체 스토리지는 S3(C)의 특징이며, 무한 자동 확장은 S3·EFS의 특징이지 EBS가 아니다.

**문제 5.** S3에서 객체의 접근 빈도가 시간이 지나며 줄어들 때, 비용 절감을 위해 더 저렴한 스토리지 클래스로 자동 이동시키는 메커니즘은?

A) 수명 주기 정책(Lifecycle Policy)  
B) 보안 그룹(Security Group)  
C) EBS 스냅샷  
D) 예약 인스턴스  

**정답: A**  
해설: 수명 주기 정책은 "며칠이 지나면 어떤 클래스로 이동하고, 며칠 후 삭제한다" 같은 규칙으로 객체를 자동으로 더 저렴한 클래스로 옮기거나 삭제한다. 보안 그룹은 네트워크 트래픽 제어, EBS 스냅샷은 블록 볼륨 백업, 예약 인스턴스는 EC2 구매 옵션이므로 모두 무관하다.
