# Day 4 - 콘텐츠 전송과 DNS: CloudFront, Route 53, 엣지 서비스

어제까지 서버·스토리지·네트워크라는 "내부 인프라"를 봤다. 오늘은 그 인프라가 만든 콘텐츠를 **전 세계 사용자에게 빠르게 전달하는** 바깥쪽 서비스다. 핵심은 두 가지 질문이다 — "어떻게 하면 멀리 있는 사용자에게도 빠르게 줄까(CloudFront)"와 "사용자가 도메인 이름을 쳤을 때 어디로 보낼까(Route 53)". 이 둘이 함께 "엣지(Edge)" 서비스를 이룬다.

오늘은 CDN의 원리(CloudFront), DNS의 원리(Route 53), 그리고 둘이 어떻게 협력하는지를 입문 수준으로 정리한다.

## 거리의 문제: 왜 엣지가 필요한가

서버가 미국 버지니아에 있고 사용자가 서울에 있다면, 데이터는 태평양을 건너 왕복해야 한다. 빛의 속도에도 한계가 있어 물리적 거리는 곧 지연(latency)이 된다. 매번 이미지·동영상·웹페이지를 지구 반대편에서 가져오면 느리다.

해법은 단순하다 — **콘텐츠를 사용자 가까이 미리 가져다 둔다.** 이를 위해 AWS는 전 세계에 **엣지 로케이션(Edge Location)**이라는 작은 거점을 수백 개 운영한다. 사용자는 멀리 있는 본 서버 대신 가장 가까운 엣지에서 콘텐츠를 받는다.

> 💡 **관련 이론**: 엣지 로케이션은 리전(Region)이나 가용 영역(AZ)과 다른 개념이다. 리전·AZ는 실제 데이터와 연산이 사는 큰 데이터센터 클러스터이고, 엣지 로케이션은 콘텐츠를 캐싱(임시 저장)해 사용자에게 가깝게 전달하는 훨씬 작고 훨씬 많은 거점이다.

## CloudFront: AWS의 CDN

CloudFront는 AWS의 **CDN(Content Delivery Network)**이다. CDN은 콘텐츠를 전 세계 엣지 로케이션에 캐싱해 사용자에게 가까운 곳에서 빠르게 전달하는 서비스다.

동작을 한 흐름으로 보면:

1. 사용자가 콘텐츠(예: 이미지)를 요청한다.
2. 가장 가까운 엣지 로케이션이 그 콘텐츠를 캐시에 가지고 있으면 즉시 준다(캐시 히트).
3. 없으면 엣지가 원본(Origin, 예: S3 버킷이나 EC2)에서 한 번 가져와 사용자에게 주고, 동시에 캐시에 저장해 둔다.
4. 다음 사용자는 엣지의 캐시에서 빠르게 받는다.

| 개념 | 의미 |
|------|------|
| 오리진(Origin) | 콘텐츠의 원본 출처(S3, EC2, ALB 등) |
| 엣지 로케이션 | 콘텐츠를 캐싱해 사용자에게 가까이 전달하는 거점 |
| 캐시 히트/미스 | 엣지에 콘텐츠가 있음/없음 |
| TTL | 캐시를 얼마나 오래 유지할지(Time To Live) |

CloudFront의 이점은 속도만이 아니다. 원본 서버의 부하를 줄여 주고(요청을 엣지가 흡수), HTTPS·DDoS 방어(AWS Shield) 같은 보안 기능도 엣지에서 제공한다.

> 📚 **사례**: 동영상 스트리밍 서비스가 인기 영상을 전 세계에 빠르게 제공하려 한다. 원본 영상은 S3에 두고 CloudFront를 앞에 붙이면, 서울 사용자는 서울 인근 엣지에서, 런던 사용자는 런던 인근 엣지에서 받는다. 원본 S3는 처음 한 번씩만 부담하고, 이후 대부분의 트래픽은 엣지가 흡수한다.

> 💡 **관련 이론**: CloudFront는 **정적 콘텐츠(이미지·동영상·CSS)**뿐 아니라 **동적 콘텐츠**도 전달할 수 있고, AWS Shield(DDoS 방어)·AWS WAF(웹 방화벽)와 결합해 보안 계층 역할도 한다. 입문 수준에서는 "CloudFront = 빠른 전달 + 원본 보호"로 기억하면 된다.

## Route 53: AWS의 DNS

사용자는 `54.239.28.85` 같은 IP 주소가 아니라 `example.com` 같은 이름으로 사이트를 찾는다. 이 **도메인 이름을 실제 IP 주소로 바꿔 주는 전화번호부**가 DNS(Domain Name System)이고, AWS의 DNS 서비스가 **Route 53**이다.

Route 53이 하는 세 가지 큰 일:

| 기능 | 설명 |
|------|------|
| 도메인 등록 | `example.com` 같은 도메인을 직접 구매·등록 |
| DNS 라우팅 | 도메인 이름을 IP나 AWS 자원으로 연결(레코드) |
| 상태 확인(Health Check) | 대상이 살아 있는지 점검하고, 죽으면 다른 곳으로 보냄 |

> 💡 **관련 이론**: "Route 53"이라는 이름의 53은 DNS가 사용하는 표준 포트 번호(53번)에서 왔다. DNS는 인터넷의 가장 기초 인프라 중 하나로, 이름을 주소로 바꾸는 첫 단계다.

### 라우팅 정책 — 어디로 보낼지 정하는 규칙

Route 53은 단순히 이름을 주소로 바꾸는 데 그치지 않고, **"같은 도메인을 상황에 따라 다른 곳으로 보내는"** 정책을 제공한다. 입문 수준에서는 종류가 있다는 것만 알면 된다.

| 라우팅 정책 | 개념 |
|-------------|------|
| 단순(Simple) | 한 도메인을 한 대상으로 |
| 가중치(Weighted) | 트래픽을 비율로 분배(예: 90% A서버, 10% 신버전) |
| 지연 시간(Latency) | 사용자에게 가장 빠른 리전으로 |
| 장애 조치(Failover) | 주 서버가 죽으면 예비 서버로 |
| 지리(Geolocation) | 사용자 위치에 따라 다른 곳으로 |

> 🎯 **시나리오**: "미국과 유럽 양쪽에 서버를 두고, 각 사용자를 가장 빠른 쪽으로 보내고 싶다." → Route 53의 지연 시간(Latency) 기반 라우팅. 사용자에게 응답이 가장 빠른 리전으로 자동 연결한다. "주 서버가 죽으면 예비로 넘기고 싶다"면 장애 조치(Failover) 정책이다.

## CloudFront + Route 53: 함께 일하는 그림

두 서비스는 따로가 아니라 보통 함께 쓰인다. 흐름을 합쳐 보자.

```
[ 사용자가 www.example.com 입력 ]
            │
            ▼
   ┌──────────────────┐
   │  Route 53 (DNS)  │  이름 → CloudFront 주소로 안내
   └──────────────────┘
            │
            ▼
   ┌──────────────────┐
   │   CloudFront     │  가장 가까운 엣지에서 응답
   │   (엣지/CDN)      │  캐시에 있으면 즉시, 없으면 오리진에서
   └──────────────────┘
            │ (캐시 미스 시에만)
            ▼
   ┌──────────────────┐
   │ 오리진 (S3/EC2)  │  콘텐츠 원본
   └──────────────────┘
```

사용자가 도메인을 입력하면 → Route 53이 "이 이름은 CloudFront로 가라"고 안내하고 → CloudFront가 가장 가까운 엣지에서 콘텐츠를 주며 → 엣지에 없을 때만 원본(S3·EC2)을 찾아간다. 이 조합으로 "이름 해석은 Route 53, 빠른 전달은 CloudFront, 원본 보관은 S3"라는 역할 분담이 완성된다.

> ⚠️ **함정**: CloudFront(CDN)와 Route 53(DNS)을 혼동하기 쉽다. CloudFront는 "콘텐츠를 빠르게 전달"하고, Route 53은 "이름을 주소로 변환"한다. 둘 다 엣지 인프라를 쓰지만 하는 일이 다르다. "지연 시간을 줄이려 콘텐츠를 캐싱" = CloudFront, "도메인을 가장 가까운 리전으로 라우팅" = Route 53.

## 정리하며

오늘의 두 주인공은 거리 문제를 푸는 한 쌍이다. CloudFront는 **CDN** — 콘텐츠를 전 세계 엣지 로케이션에 캐싱해 사용자에게 가까운 곳에서 빠르게 전달하고, 동시에 원본 서버를 보호한다. Route 53은 **DNS** — 도메인 이름을 IP·AWS 자원으로 바꿔 주며, 가중치·지연 시간·장애 조치 같은 라우팅 정책으로 트래픽을 똑똑하게 보낸다. 둘은 보통 "Route 53이 안내하고 CloudFront가 전달"하는 형태로 협력한다.

내일은 이번 주에 배운 핵심 서비스 1(컴퓨팅·스토리지·네트워크·엣지)을 한 장의 큰 그림으로 묶어 복습한다.

## 📝 연습 문제

**문제 1.** 전 세계 사용자에게 이미지와 동영상을 낮은 지연 시간으로 전달하기 위해, 콘텐츠를 사용자와 가까운 거점에 캐싱하려고 한다. 가장 적합한 서비스는?

A) Amazon Route 53  
B) Amazon CloudFront  
C) Amazon EBS  
D) AWS Lambda  

**정답: B**  
해설: CloudFront는 AWS의 CDN으로, 콘텐츠를 전 세계 엣지 로케이션에 캐싱해 사용자에게 가까운 곳에서 빠르게 전달한다. Route 53은 DNS(이름→주소 변환) 서비스, EBS는 블록 스토리지, Lambda는 서버리스 컴퓨팅이므로 콘텐츠 캐싱·전달과는 역할이 다르다.

---

**문제 2.** 사용자가 입력한 도메인 이름(`example.com`)을 실제 IP 주소나 AWS 자원으로 연결해 주는 AWS 서비스는?

A) Amazon CloudFront  
B) Amazon S3  
C) Amazon Route 53  
D) Amazon VPC  

**정답: C**  
해설: Route 53은 AWS의 DNS 서비스로, 도메인 이름을 IP 주소나 AWS 자원으로 변환(라우팅)하며 도메인 등록과 상태 확인 기능도 제공한다. CloudFront는 콘텐츠 전달(CDN), S3는 객체 스토리지, VPC는 가상 네트워크이므로 이름-주소 변환의 주체가 아니다.

---

**문제 3.** 미국과 유럽에 각각 서버를 두고, 각 사용자를 응답이 가장 빠른 리전으로 자동 연결하려고 한다. 가장 적합한 Route 53 라우팅 정책은?

A) 단순(Simple) 라우팅  
B) 지연 시간(Latency) 기반 라우팅  
C) 가중치(Weighted) 라우팅  
D) 장애 조치(Failover) 라우팅  

**정답: B**  
해설: 지연 시간 기반 라우팅은 사용자에게 응답이 가장 빠른 리전으로 트래픽을 보내는 정책으로, 다지역 배포에서 지연을 줄이는 데 적합하다. 단순 라우팅은 한 대상으로만 보내고, 가중치는 비율 분배, 장애 조치는 주/예비 전환 용도이므로 "가장 빠른 리전" 조건에는 맞지 않는다.

**문제 4.** 엣지 로케이션(Edge Location)에 대한 설명으로 가장 정확한 것은?

A) 리전·가용 영역과 동일한 대형 데이터센터다  
B) 콘텐츠를 캐싱해 사용자에게 가까이 전달하는, 전 세계에 많이 분산된 거점이다  
C) 데이터베이스를 영구 저장하는 전용 스토리지다  
D) EC2 인스턴스를 실행하는 기본 단위다  

**정답: B**  
해설: 엣지 로케이션은 콘텐츠를 캐싱해 사용자에게 가깝게 전달하기 위한, 리전·AZ보다 훨씬 작고 훨씬 많이 분산된 거점이다. 리전·AZ와 동일한 대형 데이터센터가 아니며(A 오답), 영구 데이터 저장소(C)나 EC2 실행 단위(D)도 아니다.

**문제 5.** CloudFront와 Route 53의 역할 차이를 가장 정확히 구분한 것은?

A) 둘 다 도메인 이름을 IP로 변환한다  
B) CloudFront는 콘텐츠를 캐싱·전달하고, Route 53은 도메인 이름을 주소로 변환한다  
C) CloudFront는 DNS이고, Route 53은 CDN이다  
D) 둘 다 블록 스토리지를 제공한다  

**정답: B**  
해설: CloudFront는 콘텐츠를 엣지에 캐싱해 빠르게 전달하는 CDN이고, Route 53은 도메인 이름을 주소로 변환하는 DNS다. 역할이 반대로 서술된 C는 틀렸고, 둘 다 이름을 IP로 변환한다는 A나 블록 스토리지를 제공한다는 D도 사실이 아니다.
