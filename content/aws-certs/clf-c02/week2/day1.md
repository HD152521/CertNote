# Day 1 - 컴퓨팅 개요: EC2, Lambda, 그리고 컨테이너(ECS/Fargate)

클라우드를 한 문장으로 줄이면 "남의 컴퓨터를 빌려 쓰는 것"이다. 그런데 그 "컴퓨터"를 빌리는 방식이 한 가지가 아니다. 가상 서버 한 대를 통째로 빌릴 수도 있고, 코드 조각만 던져 두고 실행될 때만 빌릴 수도 있으며, 컨테이너 단위로 빌릴 수도 있다. 이 세 가지 방식이 각각 EC2, Lambda, ECS/Fargate다. CLF-C02 시험은 이 셋을 깊게 다루지 않지만, "어떤 상황에 어떤 컴퓨팅을 고르는가"는 반드시 묻는다.

오늘은 세 가지 컴퓨팅 서비스가 어떤 문제를 풀기 위해 태어났는지, 그리고 그것들이 "운영 책임을 얼마나 AWS에 넘기느냐"라는 하나의 축 위에 어떻게 줄지어 있는지를 정리한다.

## EC2: 클라우드의 가상 서버

EC2(Elastic Compute Cloud)는 AWS에서 가장 오래되고 기본이 되는 컴퓨팅 서비스다. 한마디로 **클라우드 위의 가상 서버 한 대**를 빌리는 것이다. 운영체제(Linux, Windows)를 고르고, CPU·메모리 크기를 고르고, 디스크를 붙이면 몇 분 안에 내 서버가 켜진다.

EC2가 주는 것은 "유연성과 통제권"이다. 서버에 SSH로 접속해 원하는 소프트웨어를 깔고, OS 설정을 바꾸고, 무엇이든 할 수 있다. 대신 그만큼 **내가 관리할 책임도 크다** — OS 패치, 보안 업데이트, 용량 조절이 모두 내 몫이다.

> 💡 **관련 이론**: EC2는 IaaS(Infrastructure as a Service)의 대표 사례다. IaaS는 "인프라(서버, 네트워크, 스토리지)만 빌려주고 그 위는 사용자가 알아서"라는 모델이다. 책임 공유 모델(Shared Responsibility Model)에서 EC2는 "AWS는 하드웨어와 하이퍼바이저까지, 사용자는 OS부터 위로"라는 경계를 가진다.

### 인스턴스 유형 — 작업에 맞는 모양 고르기

EC2 인스턴스는 용도에 따라 "유형(instance family)"으로 나뉜다. 시험에서는 패밀리 이름 하나하나를 외울 필요는 없고, **"용도에 맞는 균형이 있다"**는 개념만 알면 된다.

| 유형 | 특징 | 어울리는 작업 |
|------|------|--------------|
| 범용(General Purpose) | CPU·메모리 균형 | 웹 서버, 소규모 DB, 개발 환경 |
| 컴퓨팅 최적화(Compute Optimized) | CPU 비중 높음 | 배치 처리, 게임 서버, 고성능 연산 |
| 메모리 최적화(Memory Optimized) | RAM 비중 높음 | 대형 인메모리 DB, 캐시 |
| 스토리지 최적화(Storage Optimized) | 디스크 I/O 높음 | 대용량 데이터 웨어하우스 |
| 가속 컴퓨팅(Accelerated) | GPU 등 가속기 | 머신러닝, 그래픽 렌더링 |

핵심은 "한 가지 만능 서버는 없다"는 것이다. 메모리를 많이 쓰는 작업에 컴퓨팅 최적화 인스턴스를 쓰면 비싸고 비효율적이다. 작업의 성격에 맞춰 모양을 고르는 것이 비용 최적화의 첫걸음이다.

### 구매 옵션 — 같은 서버, 다른 가격

EC2는 똑같은 서버라도 "어떻게 사느냐"에 따라 가격이 크게 달라진다. 이건 시험에 자주 나온다.

| 구매 옵션 | 개념 | 어울리는 상황 |
|-----------|------|--------------|
| 온디맨드(On-Demand) | 쓰는 만큼 시간당 과금, 약정 없음 | 예측 불가·단기·테스트 워크로드 |
| 예약 인스턴스(Reserved Instance) | 1년/3년 약정으로 최대 ~72% 할인 | 24시간 꾸준히 도는 안정 워크로드 |
| Savings Plans | 약정 사용량($/시간) 기준 할인 | 유연한 장기 사용 |
| 스팟 인스턴스(Spot) | 남는 용량을 최대 ~90% 싸게, 중단 가능 | 중단돼도 괜찮은 배치·내결함성 작업 |
| 전용 호스트(Dedicated Host) | 물리 서버 통째로 점유 | 라이선스·규정 준수 요구 |

> 💡 **관련 이론**: 구매 옵션의 본질은 "예측 가능성과 가격의 교환"이다. 약정을 길게 하고 중단을 감수할수록 싸진다. 온디맨드는 가장 비싸지만 가장 자유롭고, 스팟은 가장 싸지만 AWS가 언제든 회수할 수 있다. 이건 AWS Well-Architected의 비용 최적화(Cost Optimization) 기둥의 핵심 도구다.

> ⚠️ **함정**: 스팟 인스턴스는 "AWS가 용량이 필요하면 2분 통보 후 회수"한다는 점이 핵심이다. 그래서 결제 처리나 상태가 중요한 작업에는 부적합하고, 중단돼도 다시 시작하면 되는 배치·렌더링·CI 빌드 같은 작업에 적합하다.

## Lambda: 서버 없는(서버리스) 컴퓨팅

EC2가 "서버를 빌리는 것"이라면 Lambda는 **"서버를 잊는 것"**이다. 코드(함수)만 올려 두면, 이벤트가 발생할 때마다 AWS가 알아서 실행 환경을 띄워 코드를 돌리고, 끝나면 내린다. 관리할 서버 자체가 없다.

Lambda의 특징을 세 가지로 정리하면:

- **이벤트 기반 실행**: S3에 파일이 올라오거나, API 요청이 들어오거나, 스케줄이 되면 실행된다.
- **사용한 만큼만 과금**: 코드가 실행된 시간(밀리초)과 횟수로만 과금한다. 아무 일도 없으면 비용이 0이다.
- **자동 확장**: 요청이 1건이든 1만 건이든 AWS가 알아서 병렬로 띄운다.

> 💡 **관련 이론**: Lambda는 서버리스(Serverless)의 대표 주자다. "서버리스"는 서버가 없다는 뜻이 아니라, **서버를 사용자가 보거나 관리하지 않는다**는 뜻이다. OS 패치, 용량 계획, 확장이 전부 AWS의 책임으로 넘어간다. 책임 공유 모델에서 사용자가 책임지는 영역이 EC2보다 훨씬 작아진다.

> 📚 **사례**: 하루에 몇 번, 불규칙하게 들어오는 이미지 썸네일 생성 작업을 생각해 보자. EC2로 하면 서버를 24시간 켜 두고 대부분 놀게 된다. Lambda로 하면 이미지가 올라온 그 순간에만 실행되고 비용도 그때만 든다. 이런 "간헐적·이벤트성 작업"이 Lambda의 전형적 무대다.

## ECS와 Fargate: 컨테이너 컴퓨팅

세 번째는 컨테이너다. 컨테이너는 "애플리케이션과 그 실행에 필요한 모든 것을 하나의 표준 상자에 담아 어디서든 똑같이 돌리는" 기술이다(대표 도구가 Docker). AWS에서 컨테이너를 운영하는 대표 서비스가 **ECS(Elastic Container Service)**다.

여기서 한 가지를 더 구분해야 한다 — **컨테이너를 어디서 돌리느냐**다.

| 실행 방식 | 개념 | 관리 부담 |
|-----------|------|----------|
| ECS on EC2 | 내가 빌린 EC2 위에서 컨테이너 실행 | 서버 관리 내 책임 |
| ECS on Fargate | 서버 없이 컨테이너만 실행(서버리스) | 서버 관리 AWS 책임 |

즉 **Fargate는 "컨테이너용 서버리스"**다. EC2를 직접 빌려 그 위에서 컨테이너를 돌릴 수도 있고(통제권 ↑, 관리 부담 ↑), Fargate를 써서 서버를 신경 쓰지 않을 수도 있다(편리함 ↑).

> 💡 **관련 이론**: AWS에는 ECS 외에 **EKS(Elastic Kubernetes Service)**도 있다. EKS는 오픈소스 표준인 Kubernetes를 AWS가 관리형으로 제공하는 것이다. 시험 입문 수준에서는 "ECS는 AWS 고유 방식, EKS는 Kubernetes 표준 방식, 둘 다 Fargate로 서버리스 실행 가능"이라는 정도만 알면 충분하다.

## 하나의 축으로 보는 세 가지 컴퓨팅

세 서비스는 따로따로 외우기보다, **"운영 책임을 얼마나 AWS에 넘기는가"**라는 하나의 축 위에서 보면 명료해진다.

```
[ 통제권 ↔ 편리함의 스펙트럼 ]

  내가 더 관리             AWS가 더 관리
  통제권 큼                관리 부담 작음
  ───────────────────────────────────────►

  EC2  →  ECS on EC2  →  ECS on Fargate  →  Lambda
 (서버 직접)            (컨테이너 서버리스)   (함수 서버리스)
```

왼쪽으로 갈수록 자유롭지만 손이 많이 가고, 오른쪽으로 갈수록 편하지만 통제권은 줄어든다. 시험 시나리오에서 "운영 부담을 최소화하고 싶다"는 키워드가 나오면 오른쪽(Lambda/Fargate)이 정답이고, "OS 수준의 세밀한 통제가 필요하다"면 왼쪽(EC2)이 정답이다.

> 🎯 **시나리오**: "트래픽이 거의 없다가 갑자기 폭증하는 이벤트성 API를, 운영 인력 없이 운영하고 싶다." → Lambda. 자동 확장 + 사용한 만큼 과금 + 서버 관리 불필요라는 세 조건을 모두 만족한다. 반대로 "특정 OS 커널 설정이 필요한 레거시 앱"이라면 EC2다.

## 정리하며

오늘 본 그림은 단순하다. AWS의 컴퓨팅은 **하나의 스펙트럼**이다. EC2(가상 서버) → 컨테이너(ECS/Fargate) → Lambda(함수)로 갈수록 사용자가 관리할 것이 줄고 AWS가 떠맡는 것이 늘어난다. EC2의 인스턴스 유형은 "작업에 맞는 모양", 구매 옵션은 "예측 가능성과 가격의 교환"이라는 두 개념만 잡으면 된다. Lambda와 Fargate의 공통 키워드는 "서버리스 = 서버를 안 보고 안 관리한다"이다.

내일은 컴퓨팅이 만들어 낸 데이터를 어디에 저장하는가 — S3, EBS, EFS로 이어지는 스토리지의 세계를 본다.

## 📝 연습 문제

**문제 1.** 트래픽이 불규칙하고 간헐적으로 발생하는 이벤트성 작업을, 서버를 직접 관리하지 않고 사용한 만큼만 비용을 내며 운영하려고 한다. 가장 적합한 컴퓨팅 서비스는?

A) EC2 온디맨드 인스턴스  
B) EC2 예약 인스턴스  
C) AWS Lambda  
D) 전용 호스트(Dedicated Host)  

**정답: C**  
해설: Lambda는 이벤트가 발생할 때만 실행되고 실행된 시간만큼만 과금하며 서버 관리가 전혀 필요 없다. "불규칙·간헐적·서버 관리 불필요·사용한 만큼 과금"이라는 조건이 모두 Lambda를 가리킨다. EC2 온디맨드/예약은 서버를 띄워 두어야 하므로 놀 때도 비용이 들고, 전용 호스트는 물리 서버를 통째로 점유하는 방식이라 정반대다.

**문제 2.** 중단되어도 다시 시작하면 되는 대규모 배치 처리 작업을 가능한 한 저렴하게 실행하려고 한다. 가장 비용 효율적인 EC2 구매 옵션은?

A) 온디맨드 인스턴스  
B) 스팟 인스턴스  
C) 예약 인스턴스(3년 약정)  
D) 전용 호스트  

**정답: B**  
해설: 스팟 인스턴스는 AWS의 남는 용량을 최대 약 90% 저렴하게 쓰는 옵션이며, 단점은 AWS가 용량이 필요하면 회수할 수 있다는 점이다. 따라서 "중단되어도 괜찮은" 배치·내결함성 작업에 가장 적합하다. 온디맨드는 가장 비싸고, 예약 인스턴스는 24시간 꾸준한 워크로드용이며, 전용 호스트는 라이선스/규정 준수 목적이라 비용 효율과는 거리가 멀다.

**문제 3.** 컨테이너 기반 애플리케이션을 운영하되, 그 컨테이너를 돌리는 서버(EC2)를 직접 프로비저닝하거나 관리하고 싶지 않다. 적합한 조합은?

A) ECS on EC2  
B) ECS on Fargate  
C) EC2 단독  
D) 예약 인스턴스 + EC2  

**정답: B**  
해설: Fargate는 "컨테이너용 서버리스" 실행 방식으로, 컨테이너를 돌릴 기반 서버를 사용자가 프로비저닝·관리하지 않는다. ECS on EC2는 사용자가 EC2를 직접 관리해야 하므로 조건에 어긋나고, EC2 단독이나 예약 인스턴스 조합은 컨테이너 오케스트레이션과 서버 관리를 모두 사용자가 떠안는 방향이다.

**문제 4.** 다음 중 EC2 인스턴스 유형(instance family)을 고르는 기준을 가장 정확히 설명한 것은?

A) 모든 작업에는 범용 인스턴스가 항상 최선이다  
B) 작업의 성격(CPU·메모리·디스크·GPU 비중)에 맞춰 균형이 다른 유형을 고른다  
C) 인스턴스 유형은 가격에만 영향을 주고 성능과는 무관하다  
D) 메모리를 많이 쓰는 작업에는 컴퓨팅 최적화 인스턴스가 적합하다  

**정답: B**  
해설: 인스턴스 유형은 작업의 성격에 맞춰 CPU·메모리·스토리지·가속기의 균형이 다르게 설계되어 있다. 만능 유형은 없으며(A 오답), 유형 선택은 성능과 비용 모두에 영향을 준다(C 오답). 메모리 집약 작업에는 메모리 최적화 인스턴스가 맞고 컴퓨팅 최적화는 CPU 집약 작업용이므로 D는 틀렸다.

**문제 5.** "서버리스(Serverless)"라는 용어의 의미로 가장 정확한 것은?

A) 물리적으로 서버가 전혀 존재하지 않는다  
B) 서버는 존재하지만 사용자가 프로비저닝·관리하지 않으며 AWS가 책임진다  
C) 사용자가 서버를 직접 패치하고 확장해야 한다  
D) EC2만이 서버리스에 해당한다  

**정답: B**  
해설: 서버리스는 서버가 없다는 뜻이 아니라, 서버의 프로비저닝·패치·확장 같은 관리 책임을 사용자가 지지 않고 AWS가 떠맡는다는 뜻이다. 따라서 물리 서버가 없다는 A는 틀렸고, 사용자가 직접 관리한다는 C도 서버리스 정의에 반한다. EC2는 사용자가 서버를 관리하는 IaaS이므로 서버리스가 아니다(D 오답). Lambda와 Fargate가 서버리스의 대표 사례다.
