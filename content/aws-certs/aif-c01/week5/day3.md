# Day 3 - AI 보안: IAM 최소권한, 데이터 암호화, PII 보호, PrivateLink, 책임 공유 모델

어제까지 우리는 "AI가 공정하고 신뢰할 수 있게" 만드는 책임 있는 AI를 봤다. 오늘은 시선을 기술적 방어로 옮긴다. **AI 보안** — 누가 모델과 데이터에 접근할 수 있는가, 데이터는 어떻게 보호되는가, 개인정보는 어떻게 막는가. AIF-C01은 클라우드 자격증답게 보안 기초를 묻는다. AI 전용 보안 기술이 따로 있는 게 아니라, AWS의 표준 보안 원칙을 AI/ML 맥락에 적용하는 것이 핵심이다.

오늘 다룰 다섯 기둥: IAM 최소권한, 데이터 암호화(저장/전송), PII 보호, PrivateLink, 그리고 모든 보안의 전제인 책임 공유 모델이다.

## 책임 공유 모델: 누가 무엇을 책임지나

AWS 보안의 출발점은 **책임 공유 모델(Shared Responsibility Model)**이다. 보안은 AWS와 고객이 나눠서 책임진다.

| 구분 | 책임 주체 | 예시 |
|------|----------|------|
| 클라우드 **자체**의 보안 | **AWS** | 데이터센터, 하드웨어, 글로벌 인프라, 관리형 서비스의 기반 |
| 클라우드 **안**의 보안 | **고객** | 데이터 분류·암호화, IAM 권한 설정, 접근 제어, 네트워크 구성 |

핵심 한 줄: **"AWS는 클라우드의 보안(security OF the cloud), 고객은 클라우드 안에서의 보안(security IN the cloud)을 책임진다."**

> 💡 **관련 이론**: 관리형 서비스(Bedrock, SageMaker 등)를 쓸수록 AWS가 지는 책임이 커진다. 하지만 "데이터를 누구에게 보여줄지(IAM)", "어떤 데이터를 넣을지", "암호화 키를 어떻게 관리할지"는 항상 고객 몫이다. 시험에서 "Bedrock으로 모델을 호출할 때 입력 데이터 접근 권한 관리는 누구 책임?"이라고 물으면 답은 고객이다.

## IAM 최소 권한: 꼭 필요한 만큼만

**IAM(Identity and Access Management)**은 "누가 무엇을 할 수 있는가"를 제어한다. AI/ML에서도 마찬가지로 핵심 원칙은 **최소 권한(Least Privilege)**이다.

- **최소 권한 원칙**: 각 사용자·역할·서비스에 **업무에 꼭 필요한 권한만** 부여한다. "혹시 몰라서" 넓게 주는 것이 가장 흔한 보안 실수다.
- **역할(Role) 기반 접근**: 사람뿐 아니라 서비스도 역할을 통해 권한을 받는다. 예: SageMaker 학습 작업이 S3 데이터에 접근하려면 그에 맞는 IAM 역할이 필요하다.
- **정책(Policy)**: 어떤 리소스에 어떤 액션을 허용/거부할지 JSON으로 명시한다.

예를 들어, 데이터 과학자에게는 학습 데이터가 든 특정 S3 버킷 읽기 권한만 주고, 프로덕션 모델 배포 권한은 주지 않는다.

> ⚠️ **함정**: "관리자 권한(Administrator)을 주면 편하다"는 최악의 안티패턴이다. 또 "한 번 권한을 주면 끝"이 아니라, 주기적으로 검토하고 안 쓰는 권한은 회수해야 한다. 시험에서 "보안을 강화하려면?"에 "모두에게 전체 권한 부여"는 항상 오답이다.

## 데이터 암호화: 저장 중 + 전송 중

데이터는 두 상태에서 보호해야 한다.

| 상태 | 무엇을 막나 | AWS 수단 |
|------|------------|----------|
| 저장 중(at rest) | 디스크·스토리지에 저장된 데이터 탈취 | KMS로 S3·EBS·SageMaker 볼륨 등 암호화 |
| 전송 중(in transit) | 네트워크를 오가는 데이터 도청 | TLS/HTTPS로 암호화된 통신 |

- **AWS KMS(Key Management Service)**: 암호화 키를 안전하게 생성·관리한다. S3에 저장된 학습 데이터, SageMaker 노트북 볼륨, 모델 아티팩트 등을 KMS 키로 암호화한다.
- **전송 중 암호화**: API 호출, 데이터 업로드/다운로드가 모두 TLS로 보호되도록 한다.

AI/ML 파이프라인은 데이터가 여러 서비스를 거치므로(S3 → SageMaker → 엔드포인트), **각 단계마다** 저장·전송 암호화를 빠짐없이 적용하는 것이 중요하다.

> 🔍 **더 깊이**: KMS는 키 자체를 안전하게 보관하면서, "누가 이 키로 복호화할 수 있는가"도 IAM과 연동해 제어한다. 즉 암호화와 접근 제어가 함께 작동한다. 데이터를 암호화해도 키 접근 권한을 아무에게나 주면 의미가 없다 — 암호화는 IAM 최소 권한과 짝을 이뤄야 완성된다.

## PII 보호: 개인정보를 찾아내고 가린다

**PII(개인 식별 정보, Personally Identifiable Information)** — 이름, 주민번호, 전화번호, 카드번호 등 — 는 특히 엄격히 보호해야 한다. AWS는 PII를 자동으로 찾고 보호하는 도구를 제공한다.

| 서비스 | 역할 |
|--------|------|
| Amazon Macie | S3에 저장된 데이터에서 PII·민감정보를 자동 탐지·분류 |
| Amazon Comprehend (PII 탐지) | 텍스트에서 PII를 식별하고 마스킹/제거 |
| Amazon Bedrock Guardrails (PII 필터) | 생성형 AI 입력·출력에서 PII 마스킹 |

- **Amazon Macie**: 머신러닝으로 S3 버킷을 스캔해 "여기 신용카드 번호가 노출돼 있다" 같은 위험을 알린다.
- **Amazon Comprehend**: 자연어 텍스트에서 PII 엔티티를 찾아 마스킹하거나 제거한다. 학습 데이터에서 개인정보를 빼는 전처리에 유용하다.

> 📚 **사례**: 한 보험사가 고객 상담 기록을 학습 데이터로 쓰려 했다. 그대로 쓰면 이름·주소가 모델에 새어 들어갈 위험(프라이버시 침해)이 있었다. 팀은 ① Macie로 어느 S3 버킷에 PII가 있는지 먼저 스캔하고, ② Comprehend PII 탐지로 텍스트에서 개인정보를 마스킹한 뒤 학습에 사용했으며, ③ 배포된 챗봇에는 Bedrock Guardrails의 PII 필터를 걸어 출력에서도 개인정보가 나가지 않게 했다. 데이터 수명주기 전 단계에서 PII를 막은 사례다.

## PrivateLink: 인터넷을 거치지 않는 연결

기본적으로 AWS 서비스 API는 퍼블릭 엔드포인트로 접근한다. 민감한 데이터를 다룰 때는 트래픽이 공용 인터넷을 거치지 않게 하는 것이 안전하다. **AWS PrivateLink**가 이를 해결한다.

- PrivateLink는 VPC(가상 사설 네트워크) 안에서 AWS 서비스(예: Bedrock, SageMaker)로 **프라이빗 연결**을 만든다.
- 트래픽이 AWS 내부 네트워크에만 머물고 **인터넷에 노출되지 않는다**.
- 데이터 유출 위험을 줄이고, 규제가 엄격한 환경(금융·의료)에서 자주 요구된다.

> 🔍 **더 깊이**: "Bedrock을 쓰는데 데이터가 인터넷을 거치지 않게 하고 싶다"는 시나리오의 답이 PrivateLink(VPC 엔드포인트)다. 암호화(데이터 내용 보호)와 PrivateLink(경로 보호)는 다른 층의 방어다. 암호화는 "내용을 못 읽게", PrivateLink는 "애초에 공용 경로로 안 가게" 하는 것이다.

## 보안 다섯 기둥 빠른 복습

- **책임 공유 모델**: AWS는 인프라, 고객은 데이터·접근·구성.
- **IAM 최소 권한**: 꼭 필요한 만큼만, 역할 기반으로.
- **암호화**: 저장 중(KMS) + 전송 중(TLS) 모두.
- **PII 보호**: Macie(탐지)·Comprehend(마스킹)·Guardrails(출력 필터).
- **PrivateLink**: 인터넷을 안 거치는 프라이빗 연결.

## 정리하며

오늘은 AI 보안을 다섯 기둥으로 정리했다. AI 전용 마법이 아니라, AWS의 표준 보안 원칙을 ML 파이프라인에 빠짐없이 적용하는 것이 핵심이다. 모든 것의 전제는 책임 공유 모델 — "고객은 클라우드 안에서의 보안을 책임진다"이고, 그 안에서 IAM·암호화·PII 보호·PrivateLink가 층층이 방어를 이룬다.

내일은 보안에서 한 발 더 나아가 **데이터 거버넌스와 규정 준수** — 데이터 출처·품질, 모델 거버넌스, CloudTrail 감사·로깅, 생성형 AI의 법적·윤리 고려 — 를 본다.

## 📝 연습 문제

**문제 1.** AWS 책임 공유 모델에 따르면, Amazon Bedrock으로 모델을 호출하는 애플리케이션에서 "입력 데이터에 누가 접근할 수 있는지에 대한 IAM 권한 설정"은 누구의 책임인가?

A) AWS  
B) 고객  
C) Bedrock 모델 제공사  
D) 인터넷 서비스 공급자  

**정답: B**  
해설: IAM 권한 설정, 데이터 접근 제어는 "클라우드 안에서의 보안"으로 고객 책임이다. AWS는 데이터센터·하드웨어 등 클라우드 자체의 보안을 책임진다. C·D는 책임 공유 모델의 당사자가 아니다.

**문제 2.** 데이터 과학자에게 학습용 S3 버킷에 대한 접근 권한을 부여할 때 가장 안전한 방식은?

A) 모든 사용자에게 관리자(Administrator) 권한을 준다  
B) 업무에 꼭 필요한 특정 버킷 읽기 권한만 부여한다(최소 권한)  
C) IAM 없이 버킷을 퍼블릭으로 공개한다  
D) 권한을 한 번 주면 다시는 검토하지 않는다  

**정답: B**  
해설: 최소 권한 원칙에 따라 업무에 필요한 만큼만 부여하는 것이 가장 안전하다. A의 전체 관리자 권한, C의 퍼블릭 공개는 과도한 노출이고, D는 권한을 주기적으로 검토·회수해야 한다는 원칙에 어긋난다.

**문제 3.** "저장 중 암호화(at rest)"와 "전송 중 암호화(in transit)"에 대한 설명으로 옳은 것은?

A) 저장 중 암호화는 KMS 등으로 디스크에 저장된 데이터를 보호하고, 전송 중 암호화는 TLS로 네트워크 통신을 보호한다  
B) 둘은 같은 것이며 한쪽만 하면 된다  
C) 전송 중 암호화는 S3 저장 데이터를 보호한다  
D) 저장 중 암호화는 네트워크 도청을 막는다  

**정답: A**  
해설: 저장 중 암호화(KMS 등)는 스토리지의 데이터를, 전송 중 암호화(TLS)는 오가는 통신을 보호하며 둘 다 필요하다. B는 둘을 동일시해 틀렸고, C·D는 두 개념의 역할을 뒤바꿔 틀렸다.

---

**문제 4.** 학습 데이터로 쓸 고객 상담 텍스트에서 이름·주민번호 같은 개인정보(PII)를 자동으로 식별하고 마스킹하려 한다. 가장 적절한 서비스는?

A) AWS PrivateLink  
B) Amazon Comprehend(PII 탐지)  
C) AWS KMS  
D) Amazon EC2  

**정답: B**  
해설: Amazon Comprehend는 텍스트에서 PII 엔티티를 식별하고 마스킹·제거할 수 있다. A의 PrivateLink는 네트워크 경로 보호, C의 KMS는 암호화 키 관리, D의 EC2는 컴퓨팅 서비스로 PII 텍스트 탐지 기능이 아니다.

---

**문제 5.** 규제가 엄격한 금융 기업이 Amazon Bedrock을 사용하면서 트래픽이 공용 인터넷을 거치지 않고 AWS 내부 네트워크에만 머물도록 하려 한다. 가장 적절한 방법은?

A) AWS PrivateLink(VPC 엔드포인트)로 프라이빗 연결을 구성한다  
B) 데이터를 평문으로 전송한다  
C) IAM 권한을 모두 제거한다  
D) Amazon Macie로 PII를 스캔한다  

**정답: A**  
해설: PrivateLink는 VPC 내부에서 AWS 서비스로 프라이빗 연결을 만들어 트래픽이 인터넷에 노출되지 않게 한다. B는 보안을 약화시키고, C는 정상 운영을 막으며, D의 Macie는 PII 탐지 도구로 네트워크 경로 보호와 무관하다.
