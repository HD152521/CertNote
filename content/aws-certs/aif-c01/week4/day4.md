# Day 4 - AWS AI 서비스 (2) + Amazon Q: 챗봇·검색·추천·예측과 생성형 비서

## 📌 핵심 정리

- **Lex** 는 인텐트·슬롯 기반 챗봇/음성봇, **Kendra** 는 사내 문서 자연어 검색, **Personalize** 는 개인화 추천, **Forecast** 는 시계열 예측이다.
- **Amazon Q** 는 완성형 생성형 비서다. 사내 데이터로 답하는 업무용 **Q Business** 와 코딩을 돕는 개발자용 **Q Developer** 로 나뉜다.
- Bedrock 은 직접 조립하는 **빌딩 블록**, Amazon Q 는 바로 쓰는 **완제품 비서**다. Lex 는 정해진 대화 흐름의 봇, 에이전트는 FM 추론으로 움직이는 유연한 다단계 작업이다.
- "찾기"는 Kendra, "분석하기"는 Comprehend. "누구에게 무엇을"은 Personalize, "언제 얼마나"는 Forecast 다.
- 이름과 제공 상태가 바뀌는 중이다. Kendra·Forecast·Q Business 는 신규 고객에게 열려 있지 않고, 후속으로 Bedrock Knowledge Bases·SageMaker Canvas·**Amazon Quick** 이, 코딩 비서 쪽은 **Kiro** 가 안내된다.

## Lex: 대화형 챗봇·음성봇 만들기

어제는 이미지·문서·텍스트·음성을 다루는 6개 AI 서비스를 봤다. 오늘은 나머지 핵심 서비스인 Lex(챗봇), Kendra(검색), Personalize(추천), Forecast(예측)와 AWS 의 생성형 AI 비서 Amazon Q 를 보고, 지금까지 본 모든 서비스를 "무엇을 고를까" 기준으로 묶는다. 핵심은 여전히 **용도 매핑**, 곧 "이 시나리오엔 어떤 서비스인가?"다.

**Amazon Lex** 는 챗봇과 음성봇을 만드는 서비스다. Amazon Alexa 에 쓰인 것과 같은 계열의 대화 기술을 서비스로 내놓은 것으로 소개돼 왔다. Lex 의 두 핵심 개념:

- **인텐트(Intent)**: 사용자가 하려는 의도(예: "항공편 예약하기").
- **슬롯(Slot)**: 그 의도를 채우는 데 필요한 정보(예: 출발지, 도착지, 날짜).

Lex 는 사용자의 말에서 인텐트를 파악하고 부족한 슬롯을 되물으며 대화를 이끈다. 실제 처리(예약 실행)는 Lambda 로 연결한다.

```
사용자: "내일 부산 가는 비행기 예약해줘"
  └ 인텐트 판별 → 항공편 예약
  └ 슬롯 채우기 → 도착지=부산, 날짜=내일, 출발지=(비어 있음)
Lex   : "어디에서 출발하시나요?"          ← 빈 슬롯을 되묻는다
사용자: "서울이요"
  └ 슬롯 완성 → Lambda 호출(예약 실행) → "예약이 완료됐습니다"
```

- 봇을 만드는 사람은 인텐트마다 **예시 문장 몇 개**를 적어 준다. Lex 가 그것으로 언어 모델을 만들어 "부산행 표 끊어줘" 같은 다른 표현도 같은 인텐트로 알아듣는다.
- 음성 입력은 Lex 안의 음성 인식(ASR)이 텍스트로 바꾼 뒤 처리한다. 음성봇을 만들 때 Transcribe 를 따로 붙일 필요가 없다.
- 요금은 처리한 텍스트·음성 **요청 수**에 따라 든다.

> 💡 **관련 이론**: Lex 는 음성/텍스트 입력을 이해하는 **NLU(자연어 이해)** 와 대화 관리를 제공한다. "고객 문의를 처리하는 대화형 봇을 만들고 싶다"는 단서가 Lex 신호다. Bedrock Agents 와 헷갈릴 수 있는데, Lex 는 인텐트/슬롯 기반의 정형화된 대화 봇 구축에, Bedrock Agents 는 FM 의 추론으로 더 유연하게 다단계 작업을 수행하는 데 강하다.

## Kendra: 똑똑한 기업 내부 검색

**Amazon Kendra** 는 머신러닝 기반의 **기업 내부 검색(enterprise search)** 서비스다. 사내 위키, PDF, SharePoint, S3 등에 흩어진 문서를 색인해, 직원이 자연어로 질문하면 정확한 답이 있는 위치를 찾아준다.

단순 키워드 검색이 아니라 "질문의 의미"를 이해해 답을 찾는다. "휴가는 며칠인가요?"라고 물으면 관련 규정 문서의 정확한 문단을 짚어준다.

- 여러 저장소를 **커넥터**로 연결해 하나의 색인으로 모은다.
- 검색 결과에 조직의 **접근 권한**을 반영할 수 있다. 볼 수 없는 문서는 검색에도 나오지 않게 거른다.
- 색인은 프로비저닝하는 순간부터 비어 있어도, 질의가 없어도 과금된다. "쓴 만큼"이 아니라 "띄워 둔 만큼"에 가깝다.
- **현재 상태**: Kendra 는 신규 고객에게 더는 열려 있지 않고(기존 고객은 계속 사용), AWS 는 비슷한 용도로 **Amazon Bedrock Knowledge Bases** 를 안내한다. 최신 시험 가이드의 범위 내 서비스 목록에도 Kendra 는 없다. 다만 "사내 문서 자연어 검색 = Kendra"라는 짝은 기출 유형과 학습 자료에 널리 남아 있으니 알아 둔다.

> 🔍 **더 깊이**: Kendra 는 RAG 의 "검색(retrieval)" 부분을 강력하게 담당할 수 있어, Bedrock 과 결합해 생성형 Q&A 의 백엔드로 쓰인다. "사내 여러 문서를 가로질러 자연어로 검색"이면 Kendra 다. Comprehend(텍스트 의미 분석)와 구분해야 한다 — Kendra 는 "찾기", Comprehend 는 "분석하기"다.

## Personalize & Forecast: 추천과 예측

이 둘은 전통 ML 작업을 관리형으로 제공한다.

- **Amazon Personalize**: 실시간 **추천 시스템**. Amazon닷컴의 추천 기술을 서비스화한 것으로, "이 상품을 본 사람이 좋아할 만한 것"을 추천한다.
- **Amazon Forecast**: **시계열 예측**. 과거 데이터를 바탕으로 미래 수요·판매·재고를 예측한다.

| 서비스 | 작업 | 활용 사례 |
|--------|------|-----------|
| Personalize | 개인화 추천 | 상품·콘텐츠 추천, 맞춤 검색 |
| Forecast | 시계열 예측 | 수요 예측, 재고 계획, 매출 전망 |

둘은 "과거 데이터로 무언가를 내놓는다"는 점이 닮아 헷갈린다. 먹고 사는 데이터와 내놓는 답이 다르다.

| 구분 | Personalize | Forecast |
|------|------|------|
| 주재료 | 사용자가 아이템과 **상호작용한 기록**(클릭, 구매, 시청) | 날짜가 붙은 **과거 수치**(일별 판매량 등) |
| 답의 모양 | 사용자마다 다른 아이템 목록 | 미래 시점의 숫자 |
| 답하는 질문 | "이 사람에게 무엇을 보여 줄까" | "다음 달에 몇 개가 팔릴까" |
| 그 밖의 쓰임 | 비슷한 아이템, 검색 결과 재정렬, 특정 아이템에 반응할 사용자 묶음 뽑기 | 인력·서버 용량·에너지 수요 계획 |

- Personalize 는 CSV 로 올린 과거 기록과 앱에서 들어오는 **실시간 이벤트**를 함께 쓴다. 방금 본 상품이 곧바로 추천에 반영되는 이유다.
- **현재 상태**: Forecast 는 신규 고객에게 더는 열려 있지 않고 AWS 는 **SageMaker Canvas** 의 시계열 예측으로 옮겨 가도록 안내한다. 최신 시험 가이드의 범위 내 서비스 목록에도 없다. "예측(forecasting)"이라는 **작업 유형** 자체는 여전히 시험 범위다.

가상의 사례로, 한 이커머스 기업은 Forecast 로 매장별·상품별 수요를 예측해 재고를 최적화하고, Personalize 로 사용자별 추천을 제공했다. 둘 다 데이터 과학팀 없이 관리형 API 로 구현했다. "미래 수치를 예측"이면 Forecast, "사용자에게 맞춤 추천"이면 Personalize 다.

## Amazon Q: AWS의 생성형 AI 비서

**Amazon Q** 는 생성형 AI 기반의 비서(어시스턴트)다. 용도에 따라 두 갈래로 나뉜다.

| 구분 | Amazon Q Business | Amazon Q Developer |
|------|-------------------|--------------------|
| 대상 | 일반 직원·업무 | 개발자 |
| 하는 일 | 사내 데이터 기반 질문 답변·요약 | 코드 생성·설명·디버깅, AWS 작업 지원 |
| 연결 | 위키·문서·앱 등 사내 시스템 | IDE, AWS 콘솔/CLI |

- **Amazon Q Business**: 사내 데이터에 연결해 직원이 자연어로 질문하면 근거와 함께 답해주는 업무용 비서. (사내 RAG 챗봇을 완제품으로 제공하는 느낌.)
- **Amazon Q Developer**: 코드 작성·설명·디버깅을 돕고 AWS 인프라 관련 질문에 답하는 개발자 비서. (과거 CodeWhisperer 의 후속/확장.)

두 제품 모두 Amazon Bedrock 위에서 만들어졌다. Q Business 의 특징은 셋이다.

- 답에 **출처(인용)** 를 붙인다.
- 질문한 사람이 **볼 권한이 있는 문서만** 근거로 쓴다. 인사 문서를 볼 수 없는 직원에게는 그 내용으로 답하지 않는다.
- 플러그인으로 휴가 신청 같은 **간단한 업무 처리**까지 한다.

Bedrock 과 Amazon Q 는 성격이 다르다. Bedrock 은 "내가 직접 생성형 앱을 만드는 빌딩 블록(API)"이고, Amazon Q 는 "이미 완성된 생성형 비서 제품"이다. 직접 챗봇을 설계·개발할 거면 Bedrock, 곧바로 쓸 수 있는 업무/개발 비서가 필요하면 Amazon Q 다.

## 바뀌는 이름들: Amazon Quick 과 Kiro

이 영역은 제품 이름이 빠르게 바뀐다. 시험 가이드 최신판이 드는 이름과 옛 이름을 함께 알아 둔다.

| 역할 | 익숙한 이름 | 지금 안내되는 이름 | 상태 |
|------|------|------|------|
| 업무용 생성형 비서 | Amazon Q Business | **Amazon Quick** | Q Business 는 신규 고객에게 열려 있지 않음 |
| BI 대시보드 | Amazon QuickSight | Amazon Quick 의 **Quick Sight** 기능 | 이름만 바뀌고 기존 API 는 그대로 |
| 개발자용 코딩 비서 | Amazon Q Developer(옛 CodeWhisperer) | **Kiro** | Q Developer IDE 플러그인은 지원 종료가 공지됨 |
| 다단계 작업 에이전트 | Amazon Bedrock Agents | **Amazon Bedrock AgentCore** | 기존 것은 Agents Classic 이 되어 신규 고객에게 열려 있지 않음 |

- **Amazon Quick**: 자연어 채팅으로 업무 자동화, 데이터 분석, 조사, 간단한 웹 앱 제작을 하는 서비스다. 사내 문서와 데이터 소스를 연결해 답의 근거로 삼는 색인(Quick Index), 반복 업무 자동화(Quick Flows, Quick Automate), 출처가 달린 조사 보고서(Quick Research), 대시보드(Quick Sight)를 한곳에 묶었다.
- **Kiro**: AI 기반 개발 환경이다. IDE 와 CLI 에서 에이전트가 코드를 작성하고, 요구사항 → 설계 → 작업 목록으로 기능을 계획하는 스펙(spec) 방식을 쓴다.
- 최신 시험 가이드는 GenAI 애플리케이션을 만드는 서비스의 예로 Bedrock, SageMaker AI, JumpStart, **Amazon Quick, Kiro**, Strands Agents, Bedrock AgentCore 를 든다. 가이드의 개정 이력은 Amazon Q 도 범위 내 서비스로 적는다. 그러니 옛 이름과 새 이름 어느 쪽이 보기에 나와도 **역할**로 읽으면 된다. "직원용 완성형 비서"와 "개발자용 코딩 비서"라는 두 자리는 그대로다.

## 닮은 서비스 가려내기

**대화형 서비스 셋.** 모두 "챗봇"처럼 보이지만 만드는 방식이 다르다.

| 구분 | Lex | 에이전트(Bedrock) | Amazon Q Business / Quick |
|------|------|------|------|
| 정체 | 봇을 만드는 서비스 | 에이전트를 만드는 빌딩 블록 | 이미 만들어진 비서 |
| 대화를 이끄는 것 | 내가 정의한 인텐트·슬롯 | FM 의 추론과 도구 선택 | 제품에 내장된 동작 |
| 강점 | 예측 가능하고 통제된 흐름, 음성 지원 | 정해 두지 않은 요청에도 유연하게 대응 | 개발 없이 바로 도입 |
| 맞는 단서 | "예약·조회처럼 절차가 정해진 문의", "전화 응대" | "여러 단계를 스스로 판단해 API 호출" | "직원이 사내 자료에 질문", "즉시 도입" |

**검색·지식 서비스 넷.**

| 서비스 | 하는 일 | 결과물 |
|------|------|------|
| Kendra | 사내 문서를 색인해 자연어로 **찾는다** | 관련 문서와 답이 있는 구절 |
| Bedrock Knowledge Bases | 찾은 내용을 FM 에 붙여 **답을 쓴다**(RAG) | 인용이 달린 생성 답변 |
| Q Business / Quick | 위 과정을 **완제품 비서**로 제공 | 직원이 바로 쓰는 채팅 화면 |
| Comprehend | 주어진 글을 **분석한다** | 감정·개체·핵심 구 |

## 서비스 선택 기준: 한 장으로 정리

시험에서 가장 중요한 건 "단서 → 서비스" 연결이다.

| 시나리오 단서 | 정답 서비스 |
|---------------|-------------|
| 여러 FM 을 관리 없이 API 로 | Bedrock |
| 자체 데이터로 커스텀 모델 학습·배포 | SageMaker |
| 이미지/영상 분석 | Rekognition |
| 문서(양식·표)에서 데이터 추출 | Textract |
| 텍스트 감정·개체 분석(NLP) | Comprehend |
| 음성 → 텍스트 / 텍스트 → 음성 | Transcribe / Polly |
| 언어 번역 | Translate |
| 대화형 챗봇·음성봇 | Lex |
| 사내 문서 자연어 검색 | Kendra |
| 개인화 추천 | Personalize |
| 시계열 수요·매출 예측 | Forecast |
| 업무용 생성형 비서(사내 데이터) | Amazon Q Business |
| 개발자용 코딩 비서 | Amazon Q Developer |

이 표가 Week 4 의 결론이자, 시험 점수를 좌우하는 핵심 자산이다. 표의 단서가 살짝 비틀려 나올 때를 대비해 갈림길만 따로 모았다.

| 비틀린 단서 | 정답 | 탈락하는 보기와 이유 |
|------|------|------|
| "전화로 걸려 온 문의를 음성으로 받아 예약까지 처리" | Lex | Transcribe — 받아쓰기만 하고 대화를 이끌지 못한다 |
| "챗봇이 정해진 절차 밖의 요청도 판단해 여러 API 를 호출" | 에이전트 | Lex — 정의한 인텐트 안에서만 움직인다 |
| "직원이 사내 문서에 질문, 개발 인력 없이 이번 달 도입" | Q Business(Amazon Quick) | Bedrock — 직접 만들어야 한다 |
| "사내 문서 검색은 되는데 답을 문장으로 써 주길 원한다" | 검색 + FM(RAG) | Kendra 단독 — 찾아 주기만 한다 |
| "방금 본 상품을 반영해 다음 화면의 추천을 바꾼다" | Personalize | Forecast — 개인별 목록을 만들지 않는다 |
| "다음 분기 지점별 판매량을 숫자로 예측" | Forecast | Personalize — 수치를 예측하지 않는다 |
| "IDE 에서 코드 자동완성과 보안 취약점 점검" | Q Developer(Kiro) | Q Business — 업무용 비서 |
| "리뷰 글에서 자주 언급되는 주제와 감정을 뽑는다" | Comprehend | Kendra — 찾는 서비스지 분석하지 않는다 |

**비용이 드는 지점**도 서비스마다 결이 다르다.

- Lex: 요청 수. 띄워 둘 서버가 없다.
- Kendra: 색인을 띄워 둔 시간과 문서 동기화. 쓰지 않아도 든다.
- Personalize: 데이터 처리량, 모델 학습 시간, 추천 요청 수.
- Forecast: 학습 시간, 저장한 데이터, 생성한 예측 수.
- Q Business: 사용자별 구독료와 색인 용량. 토큰 단위가 아니라 **사람 수** 기준이라는 점이 Bedrock 과 다르다.

내일은 Week 4 전체를 종합 복습한다. 모든 AI/ML 서비스를 용도 매핑표로 한 번에 정리하고, 시험에서 헷갈리기 쉬운 서비스 쌍들을 비교한다.

## 📖 용어

- **인텐트(intent)** : 사용자가 그 말로 하려는 일. "예약하기", "잔액 조회" 같은 의도 단위.
- **슬롯(slot)** : 인텐트를 실행하는 데 필요한 값. 날짜, 장소, 수량 등.
- **NLU(자연어 이해)** : 문장에서 의도와 필요한 정보를 알아내는 기술.
- **기업 내부 검색** : 여러 사내 저장소의 문서를 한 번에 색인해 찾는 검색.
- **커넥터** : SharePoint, S3 같은 외부 저장소를 서비스에 연결해 문서를 가져오는 통로.
- **상호작용 데이터** : 사용자가 아이템을 클릭·구매·시청한 기록. 추천 모델의 주재료다.
- **시계열 데이터** : 시간 순서로 기록된 수치. 일별 판매량, 시간별 트래픽 등.
- **빌딩 블록** : 직접 조립해 제품을 만드는 부품 성격의 서비스. Bedrock 이 대표적이다.
- **Amazon Quick** : 채팅으로 업무 자동화·분석·조사를 하는 서비스. 옛 QuickSight 가 그 안의 기능이 됐다.
- **Kiro** : AWS 가 Q Developer IDE 플러그인의 후속으로 안내하는 AI 개발 환경.

## 📝 연습 문제

**문제 1.** 인텐트와 슬롯 개념을 사용해 고객 문의를 처리하는 대화형 챗봇/음성봇을 만들려 한다. 가장 적합한 서비스는?

A) Amazon Kendra  
B) Amazon Lex  
C) Amazon Forecast  
D) Amazon Polly  

**정답: B**  
해설: Lex는 인텐트(의도)와 슬롯(필요 정보) 기반으로 챗봇·음성봇을 구축하는 서비스다. A는 문서 검색, C는 시계열 예측, D는 음성 합성으로 대화형 봇 구축과는 다르다.

---

**문제 2.** 직원이 사내 위키·PDF·SharePoint에 흩어진 문서를 자연어 질문으로 검색해 정확한 답의 위치를 찾게 하려 한다. 가장 적합한 서비스는?

A) Amazon Comprehend  
B) Amazon Translate  
C) Amazon Kendra  
D) Amazon Personalize  

**정답: C**  
해설: Kendra는 ML 기반 기업 내부 검색으로, 여러 소스에 흩어진 문서를 색인해 자연어 질문에 정확한 답 위치를 제공한다. A는 텍스트 의미 분석, B는 번역, D는 추천으로 검색이 본업이 아니다.

---

**문제 3.** 사용자의 과거 행동을 바탕으로 "좋아할 만한 상품"을 실시간으로 추천하려 한다. 적합한 서비스는?

A) Amazon Forecast  
B) Amazon Personalize  
C) Amazon Lex  
D) Amazon Textract  

**정답: B**  
해설: Personalize는 Amazon닷컴의 추천 기술을 서비스화한 실시간 개인화 추천 시스템이다. A(Forecast)는 시계열 수치 예측이고, C는 챗봇, D는 문서 추출로 추천과 무관하다.

---

**문제 4.** 개발자가 IDE 안에서 코드 생성·설명·디버깅과 AWS 관련 질문에 대한 도움을 즉시 받고 싶다. 가장 적합한 것은?

A) Amazon Q Developer  
B) Amazon Q Business  
C) Amazon Forecast  
D) Amazon Comprehend  

**정답: A**  
해설: Q Developer는 개발자용 생성형 비서로 코드 작성·설명·디버깅과 AWS 작업을 지원한다. B(Q Business)는 사내 데이터 기반 업무용 비서로 대상이 다르다. C는 예측, D는 NLP로 코딩 지원과 무관하다.

**문제 5.** 직접 챗봇을 설계·개발하지 않고, 사내 데이터에 연결해 직원 질문에 근거와 함께 답하는 "완성형 업무용 생성형 비서"를 바로 도입하려 한다. 가장 적합한 것은?

A) Amazon Bedrock  
B) Amazon Q Business  
C) Amazon SageMaker  
D) Amazon Lex
