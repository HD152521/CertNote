# Day 1 - Amazon Bedrock: 파운데이션 모델을 빌려 쓰는 완전관리형 서비스

Week 3에서 우리는 생성형 AI의 원리, 파운데이션 모델(FM), 프롬프트 엔지니어링, RAG의 개념을 배웠다. 이제 그것을 "AWS에서 실제로 어떻게 쓰느냐"로 넘어간다. Week 4는 AIF-C01 시험에서 **가장 비중이 큰** 영역이다. 시험 문제의 상당수가 "이 시나리오에는 어떤 AWS AI 서비스가 적합한가?"를 묻기 때문이다.

그 중심에 **Amazon Bedrock**이 있다. Bedrock은 여러 회사의 거대 파운데이션 모델을 **단일 API**로 빌려 쓰게 해주는 완전관리형 서비스다. 오늘은 Bedrock이 무엇을 해주는지, 모델은 어떻게 고르는지, 그리고 RAG·Guardrails·Agents 같은 핵심 기능을 시험 관점에서 정리한다.

## Amazon Bedrock이란 무엇인가

Bedrock의 핵심 가치는 한 문장으로 요약된다. **"GPU를 사거나 모델을 직접 호스팅하지 않고, API 호출만으로 거대 파운데이션 모델을 쓴다."** 인프라 관리가 전혀 필요 없는 **서버리스(serverless)** 방식이다.

Bedrock은 여러 제공사의 모델을 한곳에 모아둔 "FM 마켓플레이스"다.

| 제공사 | 대표 모델 | 강점 |
|--------|-----------|------|
| Anthropic | Claude | 추론, 긴 문맥, 대화 |
| Amazon | Titan, Nova | 텍스트·이미지·임베딩, 비용 효율 |
| Meta | Llama | 오픈 가중치 계열, 커스터마이징 |
| Mistral AI | Mistral, Mixtral | 경량·고속 |
| Cohere | Command, Embed | 임베딩·검색 |
| Stability AI | Stable Diffusion | 이미지 생성 |

> 💡 **관련 이론**: Bedrock은 "Infrastructure as API"의 생성형 AI 버전이다. 전통적으로 거대 모델을 운영하려면 수천 개 GPU와 운영 인력이 필요했다. Bedrock은 이 모든 것을 추상화해, 개발자는 "어떤 모델에 어떤 프롬프트를 보낼까"만 신경 쓰면 된다. 시험에서 "인프라 관리 없이 여러 FM을 골라 쓰고 싶다"는 시나리오가 나오면 거의 항상 Bedrock이 정답이다.

## 모델을 어떻게 고르는가

여러 모델 중 하나를 고르는 기준은 단순한 "성능 순위"가 아니다. AIF 시험은 **트레이드오프**를 묻는다.

- **정확도/추론 능력**: 복잡한 추론, 코드 생성, 긴 문맥이 필요하면 고성능 모델(예: 큰 Claude 모델).
- **비용**: 토큰당 가격이 모델마다 다르다. 단순 분류·요약이면 저렴한 경량 모델로 충분하다.
- **지연 시간(latency)**: 실시간 챗봇은 빠른 응답이 중요하므로 경량 모델이 유리할 수 있다.
- **모달리티(modality)**: 텍스트만? 이미지 생성? 멀티모달(이미지 이해)? 임베딩? 작업에 맞는 종류를 골라야 한다.
- **컨텍스트 윈도우**: 긴 문서를 한 번에 넣어야 하면 큰 컨텍스트 윈도우 모델.

> 📚 **사례**: 한 고객지원 팀은 처음에 모든 문의를 최고 성능 모델로 처리하다 비용이 폭증했다. 분석해 보니 80%의 문의는 단순 FAQ였다. 이들을 저렴한 경량 모델로 라우팅하고, 복잡한 문의만 고성능 모델로 보내자 비용이 60% 줄면서 품질은 유지됐다. "가장 비싼 모델이 항상 정답은 아니다"가 핵심 교훈이다.

## RAG와 Knowledge Bases: 모델에 우리 회사 데이터 붙이기

파운데이션 모델은 학습 시점까지의 일반 지식만 안다. "우리 회사 내부 규정"이나 "최신 제품 매뉴얼"은 모른다. 이를 해결하는 것이 **RAG(Retrieval-Augmented Generation, 검색 증강 생성)**다.

RAG의 흐름은 이렇다.

```
사용자 질문 → 회사 문서 DB에서 관련 내용 검색 → 검색 결과를 프롬프트에 첨부 → FM이 그 근거로 답변
```

Bedrock에는 이 과정을 자동화해주는 **Knowledge Bases(지식 베이스)** 기능이 있다. 우리가 S3에 문서를 올려두면 Bedrock이 알아서 문서를 잘게 쪼개(chunking) **임베딩**으로 바꾸고, **벡터 데이터베이스**에 저장한다. 사용자가 질문하면 의미가 비슷한 조각을 찾아 모델에 함께 넘긴다.

> 💡 **관련 이론**: RAG는 파인튜닝과 자주 비교된다. **파인튜닝**은 모델 자체를 추가 학습시켜 "능력/말투"를 바꾸는 것이고, **RAG**는 모델은 그대로 두고 "최신 지식/사실"을 외부에서 가져다 붙이는 것이다. 자주 바뀌는 사내 데이터, 출처를 명확히 해야 하는 경우, 환각(hallucination)을 줄이고 싶을 때는 RAG가 유리하다. 시험에서 "최신 정보로 답하게 하고 싶은데 모델을 매번 재학습하긴 부담스럽다"면 RAG/Knowledge Bases가 정답이다.

## Guardrails: 안전 울타리 치기

생성형 AI를 실제 서비스에 붙이면 위험이 따른다. 욕설, 폭력적 콘텐츠, 경쟁사 언급, 개인정보 노출, 엉뚱한 주제로의 일탈 등이다. **Amazon Bedrock Guardrails**는 이런 입출력을 걸러주는 안전장치다.

Guardrails가 막아주는 것들:

| 보호 영역 | 하는 일 |
|-----------|---------|
| 유해 콘텐츠 필터 | 증오·폭력·성적 표현 등 차단 |
| 거부 주제(Denied topics) | 특정 주제(예: 의료 조언)에 답하지 않게 설정 |
| 민감 정보(PII) | 주민번호·이메일 등 개인정보 마스킹·차단 |
| 단어 필터 | 금지어·욕설·경쟁사명 차단 |
| 환각 감지 | 근거 없는 답변(맥락 이탈) 걸러내기 |

핵심은 Guardrails가 **모델과 독립적**이라는 점이다. 한 번 정의한 가드레일을 여러 모델에 일관되게 적용할 수 있다.

## Agents: 모델이 직접 작업을 수행하게 하기

기본 FM은 "글을 생성"할 뿐, 실제 행동(주문 조회, 예약 변경)은 못 한다. **Amazon Bedrock Agents**는 모델이 **여러 단계로 추론하면서 외부 API(Lambda 등)나 Knowledge Base를 호출**해 실제 작업을 완수하게 해준다.

예를 들어 "내 항공편을 내일로 변경해줘"라는 요청에 Agent는 (1) 사용자의 예약 조회 API 호출 → (2) 변경 가능 여부 확인 → (3) 변경 API 호출 → (4) 결과를 자연어로 안내, 이런 다단계 작업을 스스로 계획하고 실행한다.

> 🔍 **더 깊이**: Agent의 핵심은 "추론(reasoning) + 도구 사용(tool use)"이다. 모델이 "지금 무엇을 해야 하는지" 판단하고, 필요한 도구(API)를 골라 호출하고, 그 결과를 보고 다음 행동을 결정한다. Knowledge Bases가 "읽기(검색)"라면 Agents는 "행동(실행)"까지 한다. 시험에서 "모델이 단순 답변을 넘어 여러 단계로 실제 업무를 수행해야 한다"면 Agents가 정답이다.

## 정리하며

오늘의 핵심 그림은 이렇다. **Amazon Bedrock**은 여러 회사의 FM을 단일 API로, 인프라 관리 없이 빌려 쓰는 완전관리형 서비스다. 모델은 정확도·비용·지연·모달리티를 따져 고른다. 사내 데이터로 답하게 하려면 **Knowledge Bases(RAG)**, 안전하게 막으려면 **Guardrails**, 다단계로 실제 작업을 시키려면 **Agents**를 쓴다.

다음 글에서는 Bedrock과 짝을 이루는 **Amazon SageMaker** — "직접 ML 모델을 학습하고 배포하는" 서비스를 보고, "언제 Bedrock을 쓰고 언제 SageMaker를 쓰는가"를 명확히 구분한다.

**문제 1.** 한 스타트업이 여러 회사의 파운데이션 모델(Claude, Llama, Titan 등)을 직접 GPU를 구매하거나 호스팅하지 않고 단일 API로 호출하려 한다. 가장 적합한 서비스는?

A) Amazon EC2에 각 모델을 직접 설치  
B) Amazon Bedrock  
C) Amazon S3  
D) AWS Glue  

**정답: B**  
해설: Bedrock은 여러 제공사의 FM을 단일 API로, 서버리스 방식으로 제공하는 완전관리형 서비스다. A는 직접 인프라를 관리해야 해서 요구사항에 어긋난다. C는 객체 스토리지, D는 데이터 통합(ETL) 서비스로 FM 제공이 본업이 아니다.

**문제 2.** 회사 내부 문서를 기반으로 챗봇이 최신 정보로 답하게 하고 싶지만, 모델 자체를 매번 재학습하는 비용은 피하고 싶다. 가장 적합한 접근은?

A) Bedrock Guardrails 설정  
B) Bedrock Knowledge Bases를 이용한 RAG  
C) 모델을 처음부터 새로 학습  
D) 모델 파라미터를 수동으로 편집  

**정답: B**  
해설: Knowledge Bases는 회사 문서를 임베딩해 벡터 DB에 저장하고, 질문 시 관련 내용을 검색해 모델에 첨부하는 RAG를 자동화한다. 모델 재학습 없이 최신 지식을 반영할 수 있다. A는 안전 필터링 기능이지 지식 주입이 아니다. C는 피하려던 고비용 방식이고, D는 현실적으로 불가능하다.

**문제 3.** 생성형 AI 챗봇이 욕설, 경쟁사 언급, 개인정보 노출을 하지 못하도록 입출력을 일관되게 필터링하려 한다. Bedrock의 어떤 기능을 써야 하는가?

A) Knowledge Bases  
B) Agents  
C) Guardrails  
D) JumpStart  

**정답: C**  
해설: Guardrails는 유해 콘텐츠, 거부 주제, 민감정보(PII), 금지어 등을 걸러주는 안전장치로, 모델과 독립적으로 정의해 여러 모델에 일관 적용할 수 있다. A는 검색 기반 지식 주입, B는 다단계 작업 수행, D는 SageMaker의 사전학습 모델 카탈로그로 이 문제와 무관하다.

**문제 4.** "내 주문 상태를 조회하고, 가능하면 배송지를 변경해줘" 같은 요청을 받아 모델이 스스로 여러 단계로 외부 API를 호출해 실제 작업을 완수하게 하려 한다. 적합한 기능은?

A) Bedrock Agents  
B) Bedrock Guardrails  
C) 단순 텍스트 생성 호출  
D) Amazon Polly  

**정답: A**  
해설: Agents는 모델이 다단계로 추론하면서 Lambda 같은 외부 API나 Knowledge Base를 호출해 실제 업무를 수행하게 한다. B는 안전 필터, C는 단순 생성으로 외부 행동을 못 한다. D는 음성 합성(TTS) 서비스로 무관하다.

**문제 5.** Bedrock에서 모델을 선택할 때 고려해야 할 기준으로 가장 거리가 먼 것은?

A) 작업에 필요한 정확도와 추론 능력  
B) 토큰당 비용과 응답 지연 시간  
C) 텍스트·이미지·임베딩 등 필요한 모달리티  
D) 모델을 직접 학습시킨 GPU의 물리적 위치  

**정답: D**  
해설: Bedrock은 서버리스로 인프라를 추상화하므로 사용자가 GPU의 물리적 위치를 신경 쓸 일이 없다. A·B·C는 모두 실제 모델 선택의 핵심 트레이드오프(정확도, 비용·지연, 모달리티)다. "가장 비싼 모델이 항상 정답은 아니다"가 선택의 원칙이다.
