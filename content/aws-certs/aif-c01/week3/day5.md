# Day 5 - Week 3 종합 복습: 생성형 AI 기초 한눈에 묶기

## 📌 핵심 정리

- 생성형 AI 는 새 콘텐츠를 만드는 FM/LLM 이고, **토큰 → 임베딩 → 컨텍스트 윈도우 → 추론**의 순서로 동작한다.
- 모델을 다루는 방법은 **프롬프트 → RAG → 파인튜닝** 순으로 비싸진다. 형식·톤은 프롬프트, 모르는 정보는 RAG, 깊은 내재화는 파인튜닝이다.
- Few-shot 과 RAG 는 둘 다 **가중치를 바꾸지 않는다.** 프롬프트에 예시나 문서를 끼워 넣을 뿐이다. 가중치가 바뀌는 것은 파인튜닝뿐이다.
- 위험은 환각·편향·비결정성이고, 증상마다 처방이 다르다. 환각은 근거(RAG)와 검토로, 편향은 측정(Clarify)으로, 비결정성은 추론 파라미터와 검증 단계로 다룬다.
- 고위험 결정에는 사람의 최종 검토(Human-in-the-loop)를 둔다. 생성형 AI 의 출력은 초안이지 검증된 사실이 아니다.

## 한 장으로 보는 Week 3

이번 주는 AIF-C01 의 도메인 2 "생성형 AI 기초"(채점 문항의 24%)를 통과했다. 가장 비중이 큰 도메인 3 "파운데이션 모델 응용"(28%)도 이 기초 위에 서 있으므로, 두 도메인을 합친 절반 이상이 이번 주 개념에 걸려 있다.

- 월요일: "생성형 AI 가 전통 ML 과 뭐가 다른가"로 시작해 파운데이션 모델과 LLM 을 잡았다.
- 화요일: 그 안을 열어 토큰·임베딩·컨텍스트 윈도우·추론을 봤다.
- 수요일: 모델에게 잘 말 거는 법(프롬프트 엔지니어링).
- 목요일: 그 한계와 위험(환각·편향·비결정성).

시험은 개념을 따로따로 묻기보다 "이 시나리오에 맞는 선택은?"으로 엮어 묻기 때문에, 개념 간의 연결을 잡는 것이 핵심이다.

```
[Day1] 생성형 AI = 새 콘텐츠 생성 (≠ 전통 ML의 판단/예측)
          └ 토대: 파운데이션 모델(FM) → 언어용 FM = LLM
                                          └ AWS: Amazon Bedrock으로 호출
                    │
[Day2] LLM 내부:  텍스트 → [토큰화] → [임베딩(의미 벡터)]
                          → [컨텍스트 윈도우 안 처리] → [추론(다음 토큰 예측)]
                    └ 비용=토큰, 기억한계=윈도우, 다양성=temperature
                    │
[Day3] 잘 쓰기:   프롬프트 엔지니어링 (지시·맥락·입력·형식)
                    └ Zero-shot / Few-shot(In-Context Learning) / CoT
                    └ 시도 순서: 프롬프트 → RAG → 파인튜닝
                    │
[Day4] 위험:      환각 · 편향 · 비결정성 (+프라이버시·저작권·유해성·주입)
                    └ 책임 있는 AI: Clarify(편향) / Guardrails(안전) / AI Service Cards(투명성)
                    └ 고위험 영역엔 Human-in-the-loop
```

이 흐름 하나면 Week 3 의 80%가 복습된다. 각 화살표가 "왜 그런가"를 설명할 수 있으면 시험 준비가 된 것이다.

## 핵심 용어 빠른 정리

| 용어 | 한 줄 정의 |
|------|-----------|
| 생성형 AI | 새로운 콘텐츠(텍스트·이미지·코드)를 만들어내는 AI |
| 파운데이션 모델(FM) | 한 번 사전학습해 여러 작업에 재사용하는 거대 토대 모델 |
| LLM | 언어를 다루는 FM, 본질은 다음 토큰 예측 |
| Transformer | 셀프 어텐션 기반의 LLM 핵심 아키텍처 |
| 토큰 | 모델이 텍스트를 자르는 단위(과금·한도의 기준) |
| 임베딩 | 토큰/텍스트를 의미를 담은 숫자 벡터로 변환한 것 |
| 컨텍스트 윈도우 | 한 번에 처리 가능한 입력+출력 토큰의 최대치 |
| 추론(Inference) | 학습된 모델로 답을 생성하는 과정(매 요청) |
| temperature | 출력의 다양성·창의성을 조절(낮을수록 일관) |
| Zero/Few-shot | 예시 0개 / 몇 개를 주는 프롬프트 기법 |
| RAG | 외부·사내 문서를 검색해 답에 반영하는 기법 |
| 파인튜닝 | 추가 학습으로 모델 가중치를 도메인에 맞게 조정 |
| 환각 | 사실 아닌 내용을 그럴듯하게 지어내는 현상 |
| 편향 | 데이터의 편견을 학습해 불공정한 출력을 내는 것 |
| 비결정성 | 같은 입력에도 출력이 달라질 수 있는 성질 |

> 💡 **관련 이론**: 이 용어들은 따로 외우기보다 "텍스트가 모델을 통과하는 여정"과 "모델을 다루는 방법의 사다리(프롬프트→RAG→파인튜닝)"라는 두 축에 걸어두면 오래 간다. 시험 문제 대부분은 이 두 축 위의 한 점을 가리킨다.

## 자주 나오는 비교 정리

- **전통 ML vs 생성형 AI**: 판단/예측이면 전통 ML, 새 콘텐츠 생성이면 생성형 AI.
- **프롬프트 vs RAG vs 파인튜닝**:
  - 형식·톤만 바꾸기 → 프롬프트(가장 싸고 빠름).
  - 모르는 정보(최신·사내) 공급 → RAG(가중치 변경 없음).
  - 도메인 패턴 깊이 내재화 → 파인튜닝(비싸고 가중치 변경).
- **Zero-shot vs Few-shot**: 예시 0개 vs 몇 개. 둘 다 In-Context Learning 이라 가중치를 바꾸지 않음(파인튜닝과 구분).
- **temperature 낮음 vs 높음**: 낮으면 일관·사실 기반, 높으면 다양·창의.

> ⚠️ **함정**: 시험에서 가장 헷갈리는 세 가지. ① "Few-shot = 학습"이 아니다. 예시를 프롬프트에 보여줄 뿐 가중치는 안 바뀐다. ② "RAG = 파인튜닝"이 아니다. RAG 는 학습이 아니라 "참고 자료를 끼워 넣는" 것이다. ③ "더 긴 프롬프트 = 더 좋은 답"이 아니다. 명확함이 길이보다 중요하다.

## 새 관점 1: 질문 하나가 답이 되기까지

요일별로 배운 것을 **요청 한 건의 일생**으로 다시 세운다. 사내 규정 챗봇에 "출장비 한도가 얼마야?"라고 묻는 상황이다.

| 순서 | 벌어지는 일 | 배운 날 | 돈·한도가 걸리는 곳 |
|------|------|------|------|
| ① | 질문을 임베딩으로 바꿔 벡터 저장소에서 가까운 규정 조각을 찾는다 | Day 2 | 임베딩 호출, 벡터 저장소 운영 |
| ② | 지시문 + 찾은 조각 + 질문을 하나의 프롬프트로 조립한다 | Day 3 | 조립된 길이만큼 **입력 토큰** |
| ③ | 프롬프트 전체가 컨텍스트 윈도우 안에 들어가야 한다 | Day 2 | 넘치면 잘리거나 요청이 거부된다 |
| ④ | 모델이 다음 토큰을 하나씩 뽑아 답을 만든다 | Day 1·2 | 답 길이만큼 **출력 토큰**, temperature 가 다양성을 정한다 |
| ⑤ | 답이 근거 문서와 맞는지, 유해·민감 내용은 없는지 거른다 | Day 4 | 가드레일 검사 |
| ⑥ | 환불·징계처럼 영향이 큰 건은 사람이 확인한다 | Day 4 | 사람의 시간 |

- ①이 빠지면 모델은 규정을 모른 채 ④에서 **그럴듯한 숫자를 지어낸다.** 환각의 대표 경로다.
- ②에서 문서를 너무 많이 붙이면 ③의 한도에 걸리고 비용도 는다. 그래서 RAG 는 "전부"가 아니라 "관련된 조각만" 넣는다.
- 챗봇은 턴마다 이전 대화를 ②에 다시 넣는다. 대화가 길수록 매 턴의 입력 토큰이 커진다.
- 시험 가이드는 이렇게 "윈도우 안에 무엇을 넣을지 설계하는 일"을 **컨텍스트 엔지니어링**이라고 부른다. 프롬프트 문장 다듬기보다 넓은 개념으로, 지시·검색 결과·대화 기록·도구 결과의 배분을 다룬다.

## 새 관점 2: 닮은 개념 가려내기

**임베딩 · 벡터 저장소 · RAG** 는 한 문장에 같이 나와서 같은 것처럼 보이지만 역할이 다르다.

| 개념 | 정체 | 비유 |
|------|------|------|
| 임베딩 | 텍스트를 의미가 담긴 숫자 벡터로 바꾼 **결과물**(그리고 바꾸는 모델) | 책마다 붙인 좌표 |
| 벡터 저장소(벡터 DB) | 그 벡터를 저장하고 가까운 것을 찾아 주는 **저장소** | 좌표로 책을 찾는 서가 |
| RAG | 찾은 내용을 프롬프트에 붙여 답하게 하는 **방식 전체** | 사서가 책을 펴 놓고 답하는 절차 |

**temperature · Top-P · Top-K** 는 모두 "다음 토큰을 얼마나 과감하게 고를까"를 정하지만 손대는 곳이 다르다. AWS 문서의 예를 빌린다. "말발굽 소리가 들린다. 저것은 ___"의 후보가 말 0.7, 얼룩말 0.2, 유니콘 0.1 이라고 하자.

| 파라미터 | 하는 일 | 위 예에서 |
|------|------|------|
| temperature | 확률 분포의 **모양**을 바꾼다. 낮으면 뾰족하게, 높으면 평평하게 | 높이면 유니콘이 뽑힐 확률이 커진다 |
| Top-K | 확률 상위 **K개**만 후보로 남긴다 | K=2 면 말·얼룩말만 후보 |
| Top-P | 누적 확률이 **P 에 찰 때까지**만 후보로 남긴다 | P=0.7 이면 말만, 0.9 면 말·얼룩말 |
| 최대 토큰(응답 길이) | 답의 길이를 제한한다 | 다양성과 무관, 비용·지연과 직결 |

- 셋 다 낮추면 일관되고, 높이면 다양해진다. 방향은 같으므로 시험에서는 "일관성이 필요 → 낮춘다, 창의성이 필요 → 높인다"로 답한다.
- 어느 파라미터도 **모델이 모르는 사실을 알게 해 주지는 않는다.** temperature 를 0 으로 해도 없는 지식은 생기지 않는다.

## 새 관점 3: 증상에서 처방으로

| 증상 | 원인 | 먼저 할 일 | 효과 없는 처방 |
|------|------|------|------|
| 사내 최신 규정을 틀리게 답한다 | 모델이 그 정보를 본 적이 없다 | RAG 로 문서 공급 | temperature 낮추기, "정확히 답하라" 지시 |
| 없는 논문·판례를 인용한다 | 환각 | 근거 문서 제공, 출처 요구, 사람 검토 | 모델을 더 큰 것으로만 교체 |
| 답의 형식이 매번 다르다 | 출력 형식 미지정 | 형식 지정, 예시(Few-shot) | 파인튜닝부터 시도 |
| 같은 질문에 답이 달라 테스트가 어렵다 | 샘플링의 비결정성 | temperature·Top-P 낮추기, 검증 단계 추가 | 프롬프트를 길게 쓰기 |
| 긴 대화 뒤에 앞 내용을 잊는다 | 컨텍스트 윈도우 초과 | 대화 요약, 관련 부분만 다시 넣기 | temperature 조정 |
| 요금이 예상보다 크다 | 입력·출력 토큰 과다 | 프롬프트·응답 길이 줄이기, 작은 모델 검토 | 예시를 더 많이 넣기 |
| 특정 집단에 불리한 답이 나온다 | 학습 데이터의 편향 | 집단별 결과 측정, 사람 감독 | 가드레일의 금지어만 추가 |
| 욕설·개인정보가 답에 섞인다 | 출력 통제 부재 | Guardrails 로 필터·마스킹 | Few-shot 예시 추가 |

## AWS 서비스 매핑 (AIF 에서 자주 묻는 연결)

| 필요 | AWS 서비스/기능 |
|------|-----------------|
| 여러 FM 을 단일 API 로 관리형 호출 | Amazon Bedrock |
| 임베딩 생성 | Amazon Titan Embeddings 등 Bedrock 의 임베딩 모델 |
| 임베딩 저장·유사도 검색(RAG) | Amazon OpenSearch Service, Amazon Aurora·RDS for PostgreSQL(pgvector), Amazon Neptune |
| RAG 를 관리형으로 한 번에 | Amazon Bedrock Knowledge Bases |
| 유해 콘텐츠 필터·PII 마스킹·주제 제한 | Amazon Bedrock Guardrails |
| 데이터·모델 편향 측정, 설명가능성 | Amazon SageMaker Clarify |
| AI 서비스의 용도·한계·공정성 공개 문서 | AWS AI Service Cards |
| 코드 생성·자동완성 보조 | Amazon Q Developer, Kiro |

- 벡터 저장소 줄의 네 서비스는 시험 가이드가 "임베딩을 벡터 데이터베이스에 저장하는 서비스"의 예로 직접 든 것이다. Amazon Kendra 는 벡터 DB 가 아니라 관리형 검색 서비스로 RAG 의 검색 단계를 맡을 수 있으며, 현재는 신규 고객에게 열려 있지 않다.
- 코딩 보조는 이름이 바뀌는 중이다. Amazon Q Developer 의 IDE 플러그인은 지원 종료가 공지됐고 AWS 는 후속으로 **Kiro** 를 안내한다. 최신 시험 가이드도 Kiro 를 범위 내 서비스로 든다.

> 🔍 **더 깊이**: 시험 시나리오는 보통 "요구사항 → 적합한 서비스"로 묻는다. "사내 문서 기반 챗봇"이면 Bedrock + 임베딩 + 벡터 DB(RAG), "출력에서 욕설·개인정보를 막아야 한다"면 Guardrails, "모델이 공정한지 점검"이면 Clarify, "투명성·책임성 문서가 필요"면 AI Service Cards. 키워드와 서비스의 짝을 외워두면 변형 문제도 풀린다.

## 📖 용어

- **파운데이션 모델(FM)** : 방대한 데이터로 한 번 사전학습해 여러 작업에 재사용하는 큰 모델.
- **토큰** : 모델이 글을 자르는 단위. 요금과 한도를 세는 기준이다.
- **임베딩** : 글의 의미를 숫자 벡터로 바꾼 것. 뜻이 비슷하면 벡터도 가깝다.
- **벡터 저장소** : 임베딩을 저장하고 가까운 벡터를 찾아 주는 저장소.
- **컨텍스트 윈도우** : 모델이 한 번에 볼 수 있는 토큰의 최대치. 입력과 출력을 합쳐 센다.
- **컨텍스트 엔지니어링** : 한정된 윈도우 안에 지시·문서·대화 기록 중 무엇을 넣을지 설계하는 일.
- **Top-P / Top-K** : 다음 토큰의 후보를 누적 확률 또는 개수로 잘라 내는 추론 파라미터.
- **RAG** : 관련 문서를 검색해 프롬프트에 붙여 답하게 하는 방식. 모델은 그대로 둔다.
- **환각** : 사실이 아닌 내용을 그럴듯하게 만들어 내는 현상.
- **Human-in-the-loop** : 중요한 출력은 사람이 최종 확인하도록 절차에 사람을 넣는 것.

A) 파인튜닝 → RAG → 프롬프트 엔지니어링  
B) 프롬프트 엔지니어링 → RAG → 파인튜닝  
C) RAG → 프롬프트 엔지니어링 → 파인튜닝  
D) 세 방법은 비용 차이가 없다  

**정답: B**  
해설: 가장 싸고 빠른 프롬프트 엔지니어링을 먼저, 외부/사내 지식이 필요하면 RAG, 도메인 패턴을 깊이 내재화해야 하면 마지막에 파인튜닝을 고려하는 것이 정석이다. A·C는 순서가 틀렸고, D는 파인튜닝이 가장 비싸므로 틀렸다.

**문제 2.** 다음 짝 중 AWS 서비스와 그 용도의 연결이 올바른 것은?

A) Amazon SageMaker Clarify - 데이터·모델의 편향 측정과 설명가능성  
B) Amazon Bedrock Guardrails - 모델 학습 속도 향상  
C) AWS AI Service Cards - 임베딩 벡터 저장  
D) Amazon Bedrock - 오직 이미지 압축  

**정답: A**  
해설: SageMaker Clarify는 편향 지표와 특성 중요도(설명가능성)를 제공한다. B의 Guardrails는 유해 콘텐츠 필터·PII 마스킹 등 안전 장치이지 학습 속도와 무관하다. C의 AI Service Cards는 용도·한계·공정성을 공개하는 투명성 문서이지 벡터 저장이 아니다. D의 Bedrock은 여러 FM을 호출하는 서비스로 이미지 압축이 본업이 아니다.

**문제 3.** "Few-shot 프롬프팅"과 "파인튜닝"의 가장 중요한 차이는?

A) Few-shot은 모델 가중치를 바꾸지 않고, 파인튜닝은 가중치를 변경한다  
B) Few-shot이 파인튜닝보다 항상 비싸다  
C) 둘 다 모델을 처음부터 재학습한다  
D) 파인튜닝은 예시를 프롬프트에 넣는 것이다  

**정답: A**  
해설: Few-shot은 프롬프트 안에 예시를 보여주는 In-Context Learning으로 가중치를 바꾸지 않는다. 반면 파인튜닝은 추가 학습으로 가중치를 변경한다. B는 일반적으로 파인튜닝이 더 비싸므로 틀렸고, C는 둘 다 처음부터 재학습하는 것이 아니며, D는 프롬프트에 예시를 넣는 것은 Few-shot의 설명이라 틀렸다.

**문제 4.** 사내 최신 정책 문서를 근거로 정확히 답하는 챗봇을 만들고, 환각을 줄이려 한다. 가장 적절한 조합은?

A) temperature를 최대로 높이고 예시를 늘린다  
B) 사내 문서를 임베딩해 벡터 DB에 저장하고 RAG로 관련 문서를 함께 제공한다  
C) 모델 크기만 키우면 자동으로 해결된다  
D) 프롬프트를 최대한 길게만 작성한다  

**정답: B**  
해설: 모델이 모르는 사내 정보는 RAG로 관련 문서를 검색해 프롬프트에 함께 넣어야 정확해지고 환각도 줄어든다. A는 temperature를 높여 오히려 환각을 키우고, C는 모델 크기가 사내 지식을 보장하지 않으며, D는 길이가 정확성을 보장하지 않으므로 모두 틀렸다.

**문제 5.** 생성형 AI의 위험과 그 설명이 잘못 짝지어진 것은?

A) 환각 - 사실이 아닌 내용을 그럴듯하게 생성  
B) 편향 - 데이터의 편견을 학습해 불공정한 출력  
C) 비결정성 - 같은 입력에도 출력이 달라질 수 있음  
D) 환각 - 모델이 응답을 영구적으로 거부하는 현상  

**정답: D**  
해설: 환각은 거짓 내용을 사실처럼 생성하는 것이지 응답 거부가 아니다. 따라서 D가 잘못된 짝이다. A는 환각, B는 편향, C는 비결정성의 정확한 설명이다. 같은 "환각" 용어라도 A는 옳고 D는 틀린 설명이라는 점에 주의해야 한다.
