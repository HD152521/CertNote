# Day 5 - Week 8 종합: 모니터링·집계·분석 시나리오 통합 복습

이번 주는 "로깅 그 자체"가 아니라 *쌓인 로그를 어떻게 신호로, 신호를 어떻게 대응으로 바꾸는가*를 다뤘다. 오늘은 네 날의 도구들 — CloudWatch(임계 탐지), Security Hub(집계·정규화·점수), Athena/OpenSearch/Logs Insights(분석), EventBridge/Security Lake(자동화·통합) — 을 하나의 흐름으로 꿰고, 시험에서 *도구를 헷갈리게 만드는 경계들*을 정리한다. 핵심은 개별 기능 암기가 아니라 "이 요구에는 왜 *이* 도구가 정답이고 *저* 도구는 왜 아닌가"를 즉답하는 것이다.

## 한 장으로 보는 탐지-집계-분석-대응 파이프라인

```
 [수집]            [탐지]              [집계·정규화]        [분석]              [자동화·대응]
CloudTrail ─┐   CloudWatch ─┐
VPC Flow ───┼─▶ Metric Filter│        Security Hub ─┐    Athena(S3,사후)
ELB/R53 ────┤   + Alarm      ├──핀딩──▶ (ASFF 정규화) ├──▶ Logs Insights ──┐
앱 로그 ─────┘   GuardDuty ───┤        보안점수/표준   │    OpenSearch       │
                Inspector ───┤        (CIS/FSBP)     │    (준실시간)        │
                Macie ───────┘                       │                     ▼
                                                      └──▶ EventBridge ──▶ SNS(알림)
                                                           (라우팅)     ──▶ Lambda/SSM(교정)
                                                                        ──▶ Step Functions(오케스트레이션)

 [통합 저장] Security Lake: 위 원시 로그들을 OCSF/Parquet로 정규화해 S3 데이터 레이크로 — Athena/OpenSearch/SIEM이 단일 스키마로 질의
```

> 💡 **관련 이론**: 이 흐름은 NIST CSF의 *Detect(탐지)* 와 *Respond(대응)* 기능을 AWS 서비스로 사상(map)한 것이다. CloudWatch/GuardDuty는 탐지, Security Hub는 탐지 결과의 집계·평가, EventBridge는 대응의 오케스트레이션을 담당한다. 시험 문제는 보통 "이 요구가 탐지인가, 집계인가, 분석인가, 대응인가"를 먼저 식별하면 후보 서비스가 좁혀진다.

## 질문 하나로 도구를 좁히는 결정 트리

시험장에서 실제로 돌려야 하는 것은 위 그림이 아니라 **질문의 순서**다. 지문을 읽고 아래 순서대로 물으면 대부분의 문항에서 후보가 하나로 줄어든다.

```
① 요구가 무엇을 하려는 것인가?
   ├─ "발견하고 싶다"        → 탐지 (②로)
   ├─ "모아서 보고 싶다"      → 집계  → Security Hub (컨트롤이면 + Config)
   ├─ "캐묻고 싶다"          → 분석  (③으로)
   └─ "자동으로 조치하고 싶다" → 대응  → EventBridge (+ Lambda/SSM/Step Functions)

② 무엇을 탐지하나?
   ├─ 특정 로그 패턴의 횟수    → CloudWatch 지표 필터 + 알람
   ├─ 위협 행위·악성 통신      → GuardDuty
   ├─ 소프트웨어 취약점        → Inspector
   ├─ 민감 데이터             → Macie
   ├─ 외부 노출 권한          → IAM Access Analyzer
   ├─ 구성이 기준을 벗어남     → Config / Security Hub 표준
   └─ 평소와 다른 메트릭       → CloudWatch Anomaly Detection

③ 데이터가 어디 있고 질문의 시제는?
   ├─ CloudWatch Logs + "지금"     → Logs Insights
   ├─ S3 + "그때"(일회성·저비용)    → Athena (+ 파티션·Parquet)
   ├─ 인덱스 + "계속"(상시 대시보드) → OpenSearch
   └─ 조직 전역 원시 로그 + 단일 스키마 → Security Lake(OCSF)
```

이 트리에서 실수가 가장 많이 나는 분기는 ①의 첫 갈래다. **"탐지"와 "집계"를 구분하지 못하면** Security Hub와 GuardDuty 사이에서 흔들린다. 판별법은 간단하다 — 지문이 *"무엇이 일어났는지 알아내라"*면 탐지, *"이미 여러 도구가 알아낸 것을 한곳에서 보라"*면 집계다.

두 번째로 실수가 많은 곳은 ③이다. "로그 분석"이라는 같은 표현이 세 도구 모두에 걸리므로, 지문에서 **데이터 위치**와 **비용/즉시성 언급**을 찾아야 한다. "비용을 최소화"는 Athena, "즉시·별도 적재 없이"는 Logs Insights, "상시 대시보드·전문검색"은 OpenSearch로 거의 예외 없이 이어진다.

## 경계 정리 1: "탐지" 도구들의 분담

가장 자주 헷갈리는 영역. 무엇을 *탐지*하느냐로 구분한다.

| 요구 | 정답 | 이유 |
|------|------|------|
| 특정 로그 패턴(루트 사용, 로그인 실패 N회)을 임계로 경보 | CloudWatch Metric Filter + Alarm | 단일 로그 그룹 내 패턴 → 숫자 → 임계 |
| 악성 IP 통신, 크립토마이닝, 자격증명 이상 사용 | GuardDuty | 위협 인텔·ML 기반 행위 탐지 |
| EC2/컨테이너/Lambda의 CVE 취약점 | Inspector | 소프트웨어 취약점 스캔 |
| S3의 PII/민감데이터 발견 | Macie | 데이터 분류·발견 |
| 시간대마다 변동하는 메트릭의 "평소와 다름" | CloudWatch Anomaly Detection | 임의 메트릭 ML 밴드 |
| 외부에 의도치 않게 공유된 리소스(버킷/역할) | IAM Access Analyzer | 외부 접근 가능성 분석 |

> ⚠️ **함정**: "보안 이상을 탐지"라는 모호한 표현에 GuardDuty를 반사적으로 고르면 안 된다. *무엇이* 이상인지가 결정한다 — 특정 API 호출 임계면 CloudWatch, 위협 행위면 GuardDuty, 취약점이면 Inspector, 민감데이터면 Macie.

## 경계 정리 2: "분석" 도구들의 분담

데이터 위치와 시간성이 결정한다.

| 요구 | 정답 | 핵심 기준 |
|------|------|-----------|
| S3에 쌓인 대용량 로그를 일회성 SQL로, 저비용 | Athena | 데이터=S3, 사후·일회성 |
| CloudWatch Logs에 있는 로그를 즉시 질의 | Logs Insights | 데이터=CloudWatch Logs, 즉시 |
| 준실시간 대시보드·전문검색·반복 상관 | OpenSearch | 인덱싱, 상시 운영 |
| 조직 전역 로그를 단일 정규화 스키마로 | Security Lake(+Athena/OpenSearch) | OCSF 정규화 저장소 |

> 🎯 **시나리오**: "90일 전 사고를 조사하는데 로그는 S3에만 있고 비용을 최소화"한다 → Athena + 파티셔닝. "로그가 CloudWatch Logs에 있고 사고 대응 중 즉시" → Logs Insights. "SOC가 상시 대시보드로 모니터링" → OpenSearch. 같은 "로그 분석"이라도 위치·시간성으로 답이 갈린다.

## 경계 정리 3: Security Hub vs Security Lake vs Config

세 서비스가 "조직 보안 상태"라는 비슷한 단어 주변에 모여 헷갈린다.

- **AWS Config**: 리소스 *구성*의 기록·변경 추적·규칙 평가. "이 리소스가 규정 설정인가?"의 *원천 평가 엔진*. Security Hub 표준 컨트롤이 내부적으로 사용.
- **Security Hub**: 여러 탐지기의 *핀딩*을 ASFF로 집계, 표준(CIS/FSBP) 컨트롤 점검, 보안 점수. "지금 우리 보안 상태와 핀딩 한눈에."
- **Security Lake**: *원시 보안 로그*를 OCSF로 정규화한 S3 데이터 레이크. "모든 로그를 단일 스키마로 모아 분석/SIEM에 제공."

```
Config      → 구성 평가(설정이 규정에 맞나)      → Security Hub 표준의 엔진
Security Hub → 핀딩 집계·점수(탐지 결과 대시보드)  → ASFF 포맷
Security Lake→ 원시 로그 정규화 저장소(분석용)     → OCSF 포맷
```

> ⚠️ **함정**: "여러 소스를 정규화"라는 말이 둘 다에 쓰여 헷갈린다. *핀딩*(탐지 결과)의 정규화·집계·점수는 Security Hub(ASFF). *원시 로그*의 정규화 저장·분석은 Security Lake(OCSF). 포맷 이름(ASFF vs OCSF)이 결정적 단서다.

## 통합 시나리오 워크스루

**시나리오 A — 루트 사용 즉시 탐지 및 알림**
1. CloudTrail(전 리전) → CloudWatch Logs.
2. Metric Filter: `$.userIdentity.type = "Root" ...`, `metricValue=1, defaultValue=0`.
3. Alarm: `Sum`, period 300, threshold ≥1, `notBreaching`, N=1/M=1.
4. SNS → 보안팀. (CIS 벤치마크 통제와 일치)
- **틀리는 지점**: `Average` 통계, `defaultValue` 누락, 단일 리전 trail, SNS KMS 키 정책 누락.

**시나리오 B — 다계정 보안 상태 일원화**
1. Organizations에서 Security Hub 위임 관리자 지정.
2. Central Configuration으로 FSBP/CIS 표준 멤버에 일괄 배포(각 멤버 Config 활성화 전제).
3. Cross-Region Aggregation으로 단일 리전 집계.
4. 보안 점수·핀딩을 위임 관리자 계정에서 통합 조회.
- **틀리는 지점**: 계정별 스크립트 배포(강제력 없음), SCP로 차단(예외 표현 불가), Config 미활성화 계정 방치.

**시나리오 C — CRITICAL 핀딩 자동 교정**
1. 모든 핀딩은 EventBridge로 자동 발행.
2. 규칙: `source=aws.securityhub`, `Severity.Label=CRITICAL`, `Workflow.Status=NEW`.
3. 대상: Step Functions → 격리 SG 적용 + EBS 스냅샷 + Security Hub 상태 갱신 + SNS.
4. 핸들러는 멱등, 실패 시 DLQ로 보존, 최소 권한 역할.
- **틀리는 지점**: 첫 조치로 인스턴스 종료(증거 파괴), 대응 역할에 광범위 권한, DLQ 없음.

**시나리오 D — 사후 포렌식**
1. CloudTrail/VPC Flow는 S3에 장기 보관(또는 Security Lake).
2. Athena로 파티션 한정 쿼리(특정 IP·기간·이벤트).
3. 상시 모니터링이 필요해지면 Firehose → OpenSearch로 핫 데이터 인덱싱 계층 추가.
- **틀리는 지점**: 파티션 키가 아닌 컬럼으로 기간 필터, 데이터 이벤트 미활성화로 "무엇을 가져갔나"에 답 못 함.

**시나리오 E — 로그가 조용해졌다**
1. 증상: 며칠째 보안 알람이 하나도 울리지 않고 대시보드가 평온하다.
2. 확인 순서: trail이 살아 있나(`StopLogging` 이벤트 검색) → CloudWatch Logs로 이벤트가 들어오고 있나 → 지표 필터가 매칭되고 있나(메트릭 그래프) → 알람 상태 이력 → SNS 구독·KMS 키 정책.
3. 구조적 해법: **하트비트 알람**(`treat-missing-data=breaching`)으로 로그 유입 중단 자체를 경보로 만든다.
- **핵심**: "조용함"은 안전의 증거가 아니라 **점검이 필요하다는 신호**다.

**시나리오 F — 알림이 너무 많아 아무도 안 본다**
1. 잘못된 대응: 표준 끄기, 알람 삭제, 임계 상향, 통합 비활성화 — 전부 *탐지를 줄이는* 선택이다.
2. 올바른 순서: (a) 등급별 SNS 토픽·채널 분리 → (b) N of M·복합 알람으로 지속성 요구 → (c) Security Hub 자동화 규칙으로 승인된 예외만 억제(사유 기록) → (d) 중간 이하 등급은 SQS 집계 후 일일 요약 → (e) 티켓을 핀딩당이 아니라 **리소스당** 생성.
3. 등급마다 **다른 시간 축**을 준다. CRITICAL은 윈도 없이 즉시.
- **핵심**: 노이즈는 *생성*이 아니라 *도달* 단계에서 자른다.

**시나리오 G — 같은 컨트롤이 수백 건 실패한다**
1. 잘못된 대응: 리소스를 하나씩 교정하는 티켓 200개.
2. 올바른 진단: 대량 실패는 개별 실수가 아니라 **잘못된 기본값**의 증상이다.
3. 해법: 계정 수준 기본 설정(예: 기본 암호화, 퍼블릭 액세스 차단), IaC 템플릿 수정, SCP로 예방적 차단. 그다음 남은 잔여만 개별 교정.
- **핵심**: 생성 속도가 교정 속도보다 빠르면 태세는 절대 개선되지 않는다.

> 🔍 **더 깊이**: 성숙한 조직은 이들을 *계층*으로 운영한다. 핫(최근, 빈번 질의)=OpenSearch, 웜/콜드(장기, 가끔 조사)=S3+Athena, 정규화 허브=Security Lake, 핀딩 평면=Security Hub, 자동화 신경계=EventBridge. 한 도구가 모든 걸 하지 않는다는 것, 그리고 각 도구의 *비용 모델*(상시 클러스터 vs 종량 스캔)이 계층화 결정을 좌우한다는 것이 실무·시험 공통의 통찰이다.

## 파이프라인의 조용한 실패 지점

week8 전체에서 반복해 나온 주제가 하나 있다 — **이 배관은 오류 없이 멈춘다.** 어느 지점이 끊겨도 화면에는 아무 표시가 없고, 오히려 평온해 보인다. 시험 문항의 상당수가 정확히 이 지점을 짚는다.

| 끊긴 곳 | 증상 | 확인 방법 | 구조적 해법 |
|---------|------|-----------|------------|
| trail이 CloudWatch Logs로 안 감 | 지표 필터가 항상 0 | 메트릭 그래프가 평평 | 하트비트 알람 |
| 로그 그룹 KMS 키 정책 누락 | 로그 수집 실패 | 키 정책의 서비스 주체 | 배포 시 정책 검증 |
| `defaultValue`·`Sum` 미설정 | 알람이 발동 안 함 | 알람 이력이 비어 있음 | 표준 템플릿(IaC) |
| SNS 토픽 KMS 정책 누락 | 알람은 ALARM인데 알림 없음 | 알람 상태 vs 수신 이력 대조 | **합성 이벤트 도달 시험** |
| Config 레코더 중지/범위 축소 | 컨트롤이 `NO_DATA`, **점수는 상승** | 평가된 컨트롤 수 추적 | 점수와 컨트롤 수를 함께 본다 |
| Security Hub 집계 리전 미지정 | 다른 리전 CRITICAL을 못 봄 | 리전별 핀딩 수 확인 | 집계 리전 구성 |
| 크로스계정 버스 권한 한쪽만 | 이벤트가 중앙에 안 옴 | DLQ 적체 여부 | DLQ 적체 자체를 알람으로 |
| 대응 핸들러 실패 | 핀딩은 있는데 조치가 없음 | Step Functions 실행 이력 | 재시도 + DLQ + 아카이브 재생 |
| 주기 작업 중단 | 상태형 위험이 방치됨 | 마지막 성공 실행 시각 | 실행 하트비트 |
| 데이터 이벤트 미활성화 | "무엇을 가져갔나"에 답 불가 | trail 이벤트 셀렉터 | 사전 활성화(소급 불가) |

마지막 행이 특히 중요하다. **로깅은 소급 적용되지 않는다.** 다른 실패는 발견 후 고치면 그 시점부터 정상화되지만, 데이터 이벤트를 켜지 않았던 기간은 영원히 공백으로 남는다. 이것이 week7에서 배운 원칙이 week8에서도 그대로 유효한 이유다.

> 📚 **사례**: 클라우드 침해 사후 보고서에서 되풀이되는 두 문장이 있다 — **"신호는 이미 로그에 있었다"**와 **"경보는 울렸지만 아무도 대응하지 않았다."** 2013년 Target 침해에서는 보안 도구의 경보가 발생했으나 대응으로 이어지지 않은 점이 미 상원 보고서 등을 통해 공개적으로 지적됐고, 대형 클라우드 침해 사례들에서도 침해 자체보다 *발견까지 걸린 시간*이 반복해 문제로 꼽혔다. 두 문장은 서로 다른 실패처럼 보이지만 원인은 하나다 — **신호가 사람과 자동화에 닿는 경로가 설계되지 않았다.** week8이 다룬 것은 결국 그 경로다. 로그를 숫자로 바꾸는 변환(day1), 여러 판단을 한 스키마로 모으는 정규화(day2), 쌓인 것을 캐묻는 질의(day3), 그리고 신호를 조치로 잇는 라우팅(day4). 어느 한 구간이 없으면 나머지가 전부 있어도 결과는 "탐지하지 않은 것"과 같아진다.

## 알림 피로: week8을 관통한 두 번째 주제

네 날 모두에서 같은 문제가 다른 얼굴로 나왔다. day1에서는 알람이 너무 많아지는 문제, day2에서는 컨트롤 핀딩이 리소스 수만큼 늘어나는 문제, day4에서는 자동화가 오히려 알림을 늘리는 문제. 시험에서는 **"노이즈를 줄이되 사각지대는 만들지 마라"**라는 정형화된 문장으로 나온다.

정답과 오답의 구분선은 하나다 — **탐지를 줄이는가, 도달을 줄이는가.**

| 접근 | 정답/오답 | 이유 |
|------|----------|------|
| 등급별 채널 분리 | **정답** | 탐지는 전부 유지, 도달만 조정 |
| N of M·복합 알람으로 지속성 요구 | **정답** | 단발 오탐만 걸러짐 |
| 승인된 예외를 사유와 함께 억제 | **정답** | 핀딩·기록은 남음 |
| 중간 이하 등급을 집계해 요약 | **정답** | 추세는 반드시 확인 |
| 티켓을 리소스당으로 묶기 | **정답** | 처리 가능한 단위로 변환 |
| 지표 필터·알람 삭제 | 오답 | 영구 사각지대 |
| 임계값을 크게 올리기 | 오답 | low-and-slow 공격에 투명해짐 |
| 표준·통합 비활성화 | 오답 | 원천 가시성 상실 |
| 탐지기의 신뢰 목록에 넣기 | 오답 | **핀딩을 만들지 않는다** |
| 전부 온콜로 보내기 | 오답 | 결과적으로 아무도 안 봄 = 탐지 중단 |

마지막 두 행이 짝을 이룬다는 점이 흥미롭다. **너무 적게 보내는 것과 너무 많이 보내는 것은 같은 결과에 도달한다** — 신호가 사람에게 닿지 않는다. 알림 설계는 "얼마나 보낼까"가 아니라 **"받는 사람이 매번 행동할 수 있는 양인가"**로 판단해야 한다.

## 비용·운영 함정 빠른 점검

- Athena: 파티션 프루닝 안 되면 전체 스캔(비용 폭탄). 컬럼형(Parquet)으로 절감. 작업 그룹에 스캔 상한.
- Athena 결과 버킷: 원본 로그만큼 민감하다 — 암호화·접근 제어를 동일 수준으로.
- OpenSearch: 상시 클러스터 비용. 장기 보관은 S3로 계층화. 도메인은 VPC 내 + FGAC.
- CloudWatch Logs: 모든 로그를 여기 넣지 않는다. 알람 걸 로그만, 원본은 S3 직행.
- CloudWatch: Metric Filter `defaultValue=0` + Alarm `Sum`이 카운트 탐지의 짝. 단, 하트비트 알람만 예외(`breaching`).
- 지표 필터 디멘션: 공격자가 제어하는 값(사용자명·IP)을 넣으면 카디널리티 폭발 → 비용 공격 가능.
- EventBridge: at-least-once → 멱등 핸들러 + DLQ + 아카이브(재생 가능성).
- 자동 대응 역할: 최소 권한 + 리소스 조건. 비가역 조치는 승인 게이트 뒤로.
- KMS: 로그 그룹·SNS 토픽 모두 **키 정책**에 서비스 주체 권한 필수(IAM만으로는 부족).
- Security Hub: 표준 여럿 켜면 통합 컨트롤 핀딩(`SECURITY_CONTROL`)도 함께.

## 이 주의 지식을 순서로: 무엇부터 세우는가

시험이 "가장 먼저 해야 할 것"을 묻는 형태로 나올 때를 대비해, 구축 순서를 한 줄로 정리해 둔다.

```
0. 로그 원본 확보        CloudTrail(전 리전·조직) → S3(별도 Log Archive 계정)
                         + 알람 걸 로그만 CloudWatch Logs로 이중 전달
                         ※ 소급 불가 — 가장 먼저, 데이터 이벤트 필요 여부도 지금 결정
   ▼
1. 구성 평가 기반        각 계정·리전 AWS Config 레코더 활성화
                         ※ 이것 없이는 Security Hub 표준이 전부 무의미
   ▼
2. 임계 탐지             CIS 모니터링 세트: 지표 필터 + 알람 + 하트비트
   ▼
3. 집계·표준             Security Hub 활성화 → CIS → FSBP → 통합 컨트롤 핀딩
                         → 위임 관리자 + 중앙 구성 + 집계 리전
   ▼
4. 질의 능력             Athena 테이블(파티션 프로젝션) + 작업 그룹 가드레일
                         (상시 감시가 필요하면 Firehose → OpenSearch 추가)
   ▼
5. 대응 자동화           EventBridge 규칙 → 가역 조치 자동 / 비가역은 승인 게이트
                         + DLQ + 아카이브 + 등급별 라우팅
   ▼
6. 조직 전역 표준화      Security Lake(OCSF) — 서드파티 SIEM·다계정 분석이 필요할 때
```

이 순서에는 논리가 있다. **아래 단계는 위 단계 없이 성립하지 않는다.** Config 없이 표준이 없고, 로그 없이 질의가 없으며, 집계 없이 단일 자동화가 없다. 시험에서 "먼저 해야 할 일"을 묻는 문항의 답은 거의 항상 **더 아래에 있는 전제**다 — "표준 컨트롤이 평가되지 않는다"의 답이 Config 활성화인 것처럼.

## 마무리

Week 8의 한 문장: **"로그는 쌓는 것이 아니라 *신호로 변환하고, 정규화해 모으고, 질의하고, 자동으로 대응*하는 것이다."** CloudWatch는 단일 신호 임계, Security Hub는 핀딩 집계·점수, Athena/OpenSearch/Logs Insights는 위치·시간성에 따른 분석, EventBridge는 대응 라우팅, Security Lake는 OCSF 정규화 허브.

시험 대비의 관점에서 이번 주가 남기는 것은 세 가지 반사다.

1. **분류 반사** — 지문을 읽고 "탐지/집계/분석/대응 중 무엇인가"를 먼저 판정한다. 그다음 "데이터가 어디 있고 시제가 무엇인가"를 묻는다. 이 두 질문으로 대부분의 후보가 하나로 좁혀진다.
2. **전제 반사** — 무언가 "동작하지 않는다"는 지문에서는 기능이 아니라 **전제**를 의심한다. Config가 꺼졌나, 로그 경로가 없나, 키 정책이 막았나, 파티션 키로 안 걸렀나.
3. **가역성 반사** — 자동 대응 설계 문항에서는 조치의 되돌릴 수 있음 여부로 보기를 가른다. 종료·삭제가 무인 자동화에 있으면 오답이다.

그리고 실무의 관점에서 남는 것은 하나다. **이 파이프라인은 만든 날이 가장 잘 동작하고, 이후로는 조용히 낡아 간다.** Config 범위가 좁아지고, 새 계정이 자동 등록에서 빠지고, 알림 채널의 구독자가 퇴사하고, 대응 핸들러의 권한이 회수된다. 어느 것도 오류를 내지 않는다. 그래서 탐지 파이프라인의 마지막 구성 요소는 언제나 **파이프라인 자신을 감시하는 장치** — 하트비트 알람, DLQ 적체 감시, 주기 작업의 실행 기록, 그리고 정기적인 합성 이벤트 도달 시험 — 이다. week9에서는 이 배관 위에 실제 탐지 서비스들(GuardDuty·Detective·Inspector)을 올리고, 그것들이 만든 핀딩을 어떻게 읽는지를 다룬다.

**문제 1.** "S3에 PII가 저장되어 있는지 발견", "EC2의 CVE 취약점 스캔", "악성 IP와의 통신 탐지"에 각각 대응하는 서비스 조합으로 옳은 것은?

A) Macie / Inspector / GuardDuty  
B) GuardDuty / Macie / Inspector  
C) Inspector / GuardDuty / Macie

**정답: A**  
해설: 민감데이터(PII) 발견은 Macie, 소프트웨어 취약점(CVE) 스캔은 Inspector, 위협 인텔·행위 기반 악성 통신 탐지는 GuardDuty다. 각 도구는 *무엇을* 탐지하느냐로 분담이 명확하며, Config/CloudWatch/Athena는 이 세 가지 탐지 역할과 다른 계층이다.

**문제 2.** 로그가 CloudWatch Logs에 있고, 사고 대응 중 별도 적재 없이 즉시 질의해 AccessDenied 추세를 보려 한다. 가장 적합한 도구는?

A) Athena  
B) Amazon OpenSearch에 새 도메인을 만들어 적재  
C) CloudWatch Logs Insights  
D) Security Lake  

**정답: C**  
해설: 데이터가 이미 CloudWatch Logs에 있고 즉시성이 요구되면 Logs Insights가 정답이다. Athena/Security Lake는 S3 데이터 대상이고, 사고 대응 중 OpenSearch 도메인을 새로 만들어 적재하는 것은 즉시성이 없다.

**문제 3.** 여러 탐지 서비스(GuardDuty, Inspector, Macie)의 핀딩을 단일 포맷으로 집계하고 CIS/FSBP 표준 합격률을 보안 점수로 보려 한다. 그리고 별개로, 조직 전역 *원시 로그*를 OCSF 표준으로 정규화해 SIEM이 질의하게 하려 한다. 각각의 서비스는?

A) 둘 다 Security Hub  
B) 핀딩 집계·점수는 Security Hub(ASFF), 원시 로그 OCSF 정규화는 Security Lake  
C) 핀딩 집계는 Security Lake, 원시 로그는 Security Hub  
D) 둘 다 AWS Config  

**정답: B**  
해설: 탐지기 핀딩의 집계·정규화(ASFF)·표준 점검·보안 점수는 Security Hub, 원시 보안 로그의 OCSF 정규화 데이터 레이크는 Security Lake다. 포맷 이름(ASFF vs OCSF)과 대상(핀딩 vs 원시 로그)이 구분 단서이며, Config는 구성 평가 엔진으로 둘 다 아니다.

**문제 4.** CloudTrail 로그로 5분 동안 콘솔 로그인 실패 5회 이상을 탐지하는 알람이 동작하지 않는다. 구성에서 함께 점검해야 할 두 가지는?

A) Metric Filter에 defaultValue=0 설정 여부와, Alarm Statistic이 Sum인지  
B) SNS 암호화와 KMS 키 정책  
C) 로그 그룹 보존 기간과 리전  
D) OpenSearch 인덱스 상태와 파티션  

**정답: A**  
해설: 카운트 기반 탐지는 Alarm Statistic이 Sum이어야 기간 내 발생 합을 임계와 비교할 수 있고, Metric Filter에 defaultValue=0이 없으면 결측 구간이 생겨 평가가 흔들린다. 이 둘은 짝으로 점검한다. SNS 암호화·보존 기간·OpenSearch는 이 카운트 탐지 동작과 무관하다.

**문제 5.** GuardDuty가 EC2 크립토마이닝을 탐지하면 자동으로 인스턴스를 격리하고 포렌식용 EBS 스냅샷을 만든 뒤 보안팀에 알리는 파이프라인을 구성한다. 운영 위생상 반드시 고려할 것을 모두 고른 묶음은?

A) 자동 대응 역할에 Administrator 부여, 핸들러는 단발 실행 가정  
B) 핸들러를 멱등하게 설계, 대상 실패 시 DLQ로 보존, 최소 권한 역할 + 리소스 조건  
C) EventBridge 대신 매분 폴링하는 cron  
D) 모든 핀딩을 무시 처리(SUPPRESSED)  

**정답: B**  
해설: EventBridge는 at-least-once 전달이라 핸들러는 멱등해야 하고, 대상 호출 실패 대비 DLQ로 이벤트를 보존하며, 자동 대응 역할은 최소 권한과 리소스 조건으로 공격 표면을 줄여야 한다. Administrator 부여·단발 가정은 위험하고, 폴링 cron은 비효율·지연이며, 핀딩 일괄 억제는 탐지를 무력화한다.
