# Day 1 - VPC 보안 설계: 네트워크가 첫 번째 방어선이다

클라우드 보안을 처음 배우는 사람은 흔히 IAM이 전부라고 생각한다. 권한만 잘 묶으면 안전하다는 믿음이다. 하지만 실제 침해 사고 보고서를 읽어보면 패턴이 다르다. 공격자는 거의 항상 "네트워크 도달 가능성(reachability)"을 먼저 확보한다. 노출된 RDP 포트, 인터넷에 열린 데이터베이스, 잘못 라우팅된 서브넷. IAM이 아무리 견고해도 공격 가능한 표면(attack surface)이 인터넷에 닿아 있으면 자격증명 탈취·취약점 익스플로잇의 첫 발판이 된다.

그래서 SCS-C03 시험은 도메인 3(Infrastructure Security, 약 20~22%)에서 네트워크를 "정책의 끝단"이 아니라 **가장 바깥의 방어선**으로 다룬다. 오늘은 VPC의 보안 설계를 본다. 서브넷을 어떻게 격리하는지, 라우팅 테이블이 왜 보이지 않는 보안 통제인지, 그리고 "이 리소스에 인터넷이 닿는가"라는 질문에 정확히 답하는 사고법을 정리한다.

## VPC라는 격리 경계: CIDR과 테넌시

VPC(Virtual Private Cloud)는 AWS 계정 안에서 논리적으로 격리된 가상 네트워크다. 핵심은 **격리**다. 다른 고객의 VPC와도, 같은 계정의 다른 VPC와도 기본적으로 트래픽이 흐르지 않는다. 명시적으로 Peering, Transit Gateway, VPC Endpoint를 연결하기 전까지는 완전한 사일로다.

| 구성 요소 | 보안 관점에서의 의미 |
|-----------|----------------------|
| **CIDR 블록** | VPC가 차지하는 사설 IP 주소 범위. 겹치면 Peering 불가 — 설계 시 비중첩 IPAM 필수 |
| **서브넷** | AZ에 묶인 IP 구획. Public/Private 구분은 라우팅으로 결정됨(서브넷 속성 아님) |
| **라우팅 테이블** | 어디로 트래픽을 보낼지 결정. 보이지 않는 보안 통제 |
| **테넌시(Tenancy)** | default / dedicated. 규제 요건상 물리 격리가 필요하면 dedicated |

> 💡 **관련 이론**: VPC는 네트워크 가상화의 한 형태다. 물리적으로는 다른 고객과 같은 하이퍼바이저·스위치를 공유하지만, AWS의 **Mapping Service**와 **Hyperplane**이 패킷 단위로 소유권을 검증한다. 한 인스턴스가 위조한 출발지 IP로 다른 VPC에 패킷을 보내려 해도 호스트 레벨에서 차단된다. 즉 "사설 IP가 겹쳐도 격리된다"는 보장이 소프트웨어 레이어에서 강제된다. 이 때문에 같은 10.0.0.0/16을 쓰는 두 VPC가 안전하게 공존할 수 있다(단 Peering은 못 함).

> 🔍 **더 깊이**: 보안 시험에서 "Public Subnet"이라는 용어는 함정이 될 수 있다. 서브넷 자체에 public/private 속성 플래그는 없다. 서브넷이 연결된 라우팅 테이블에 **Internet Gateway(IGW)로 향하는 0.0.0.0/0 경로**가 있으면 Public, 없으면 Private이다. 따라서 "이 서브넷이 인터넷에 노출됐는가"를 판단하려면 (1) 라우팅 테이블의 IGW 경로, (2) 인스턴스의 Public IP 할당 여부, (3) 보안 그룹/NACL을 모두 봐야 한다. 셋 중 하나라도 끊겨 있으면 인터넷 도달 불가.

## 3-Tier 서브넷 격리: 표준 패턴

가장 널리 쓰이는 격리 패턴은 계층(tier)별 서브넷 분리다.

```
VPC (10.0.0.0/16)
 ├── Public Subnet (10.0.0.0/24)   ← ALB, NAT Gateway, Bastion
 │     라우팅: 0.0.0.0/0 → IGW
 ├── App Subnet (10.0.10.0/24)     ← EC2, ECS, Lambda(VPC 연결)
 │     라우팅: 0.0.0.0/0 → NAT Gateway
 └── Data Subnet (10.0.20.0/24)    ← RDS, ElastiCache, Aurora
       라우팅: 로컬만 (인터넷 경로 없음)
```

- **Public Tier**: 인터넷에서 직접 받아야 하는 것만(로드밸런서, NAT, Bastion). 워크로드 자체는 두지 않는다.
- **App Tier**: 아웃바운드는 NAT를 통해 가능(패치 다운로드 등), 인바운드는 ALB에서만.
- **Data Tier**: 인터넷 경로 자체가 없음. App Tier에서만 접근. 가장 강한 격리.

> 💡 **관련 이론**: 이 계층 분리는 **Defense in Depth**(심층 방어, NSA가 정착시킨 군사 개념)의 네트워크 구현이다. 한 겹이 뚫려도 다음 겹이 막는다. 공격자가 ALB의 취약점으로 App Tier에 들어와도, Data Tier는 라우팅 자체가 없으므로 외부로 데이터를 직접 빼낼 수 없다. NIST SP 800-41(방화벽 가이드)은 이를 "tiered/segmented architecture"로 권고한다.

> ⚠️ **함정**: "Data Subnet에 인터넷 경로가 없으면 OS 패치를 어떻게 받나?"라는 질문이 시험에 나온다. 답은 RDS 같은 관리형 서비스는 AWS가 패치하므로 인터넷 경로가 필요 없다는 것. 만약 데이터 계층에 직접 운영하는 EC2 DB가 있다면 패치는 Systems Manager(SSM) + VPC Endpoint로 받는다. NAT를 열어 데이터 계층을 인터넷에 연결하는 보기는 거의 항상 오답.

## 라우팅 테이블: 보이지 않는 보안 통제

보안 엔지니어가 자주 놓치는 것이 라우팅 테이블이다. 보안 그룹·NACL은 "차단"을 명시하지만, 라우팅 테이블은 "경로가 없으면 갈 수 없다"는 **암묵적 차단**을 만든다.

| 대상(Destination) | 타깃(Target) | 의미 |
|-------------------|--------------|------|
| 10.0.0.0/16 | local | VPC 내부 통신(삭제 불가, 항상 존재) |
| 0.0.0.0/0 | igw-xxxx | 인터넷 양방향 |
| 0.0.0.0/0 | nat-xxxx | 아웃바운드만(인바운드 차단) |
| pl-xxxx (S3) | vpce-xxxx | Gateway Endpoint로 S3 사설 접근 |

> 🔍 **더 깊이**: 라우팅 테이블은 **서브넷 단위(혹은 게이트웨이 단위)**로 연결된다. 한 서브넷에 두 개의 라우팅 테이블을 동시에 연결할 수는 없다. 명시적으로 연결하지 않은 서브넷은 VPC의 **Main Route Table**을 사용한다. 보안 사고가 자주 나는 지점이 여기다 — 새 서브넷을 만들고 라우팅을 명시 연결하지 않았는데, Main Route Table에 IGW 경로가 있으면 의도치 않게 Public이 된다. 따라서 Main Route Table에는 절대 0.0.0.0/0 → IGW를 두지 않는 게 표준이다.

> 🎯 **시나리오**: "보안 감사 결과, Data Tier의 RDS가 인터넷에서 접근 가능한 것으로 의심된다. 무엇을 확인하나?" — 순서대로: (1) RDS의 `PubliclyAccessible` 플래그, (2) 서브넷 라우팅 테이블에 IGW 경로 존재 여부, (3) 보안 그룹 인바운드에 0.0.0.0/0, (4) NACL. 이 중 RDS가 진짜 인터넷에 닿으려면 라우팅(IGW)과 Public IP가 **모두** 있어야 한다. 라우팅이 없으면 SG가 열려 있어도 도달 불가. 이 "도달 가능성 분석"이 보안 엔지니어의 핵심 역량이다.

## NAT Gateway vs Internet Gateway: 방향성의 차이

| 항목 | Internet Gateway (IGW) | NAT Gateway |
|------|------------------------|-------------|
| 트래픽 방향 | 양방향(인/아웃) | 아웃바운드만 |
| 사용 위치 | Public Subnet | Public Subnet에 두고 Private이 사용 |
| 보안 의미 | 외부에서 시작 가능 | 외부에서 먼저 연결 불가 |
| 비용 | 무료 | 시간당 + 데이터 처리 요금 |

> 💡 **관련 이론**: NAT의 보안적 가치는 **비대칭성**에 있다. 내부에서 시작한 연결의 응답만 돌아올 수 있고, 외부가 먼저 연결을 시도할 수 없다. 이는 상태 추적(stateful translation) 덕분이다. 가정용 공유기의 NAT와 같은 원리다. 따라서 App Tier가 인터넷에서 패치를 받되 인터넷이 App Tier에 먼저 접근하지 못하게 하는 표준 수단이다. IPv6에서는 NAT 대신 **Egress-only Internet Gateway**가 같은 역할을 한다.

> ⚠️ **함정**: NAT Gateway는 **반드시 Public Subnet에** 있어야 한다(자신이 IGW로 나가야 하므로). NAT를 Private Subnet에 두면 동작하지 않는다. 또 NAT는 단방향이라 인바운드 차단을 보장하지만, 아웃바운드는 모두 허용하므로 **데이터 유출(exfiltration) 경로**가 될 수 있다. 민감 워크로드에서는 NAT 대신 VPC Endpoint로 필요한 서비스만 사설 연결하는 게 더 안전하다(Day 4 주제).

## 보안 관점의 VPC 추가 통제

```bash
# VPC Flow Logs 활성화 (Day 3에서 심화)
aws ec2 create-flow-logs \
  --resource-type VPC --resource-ids vpc-xxxx \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /vpc/flowlogs

# 기본 SG의 모든 규칙 제거 (최소 권한 시작점)
aws ec2 revoke-security-group-ingress \
  --group-id sg-default --protocol -1 --source-group sg-default

# DNS 쿼리 로깅 (Route 53 Resolver) — DNS 기반 exfil 탐지
aws route53resolver create-resolver-query-log-config \
  --name vpc-dns-log --destination-arn arn:aws:logs:...:log-group:/vpc/dns
```

> 🔍 **더 깊이**: VPC의 기본 보안 그룹과 기본 NACL은 동작이 다르다. **기본 SG**는 같은 SG에 속한 리소스끼리는 모두 허용, 그 외 인바운드는 차단(아웃바운드 전체 허용). **기본 NACL**은 모든 인바운드·아웃바운드를 허용한다. 그래서 "새 서브넷이 기본 NACL을 쓰면 NACL 레벨에서는 무방비"라는 점을 기억해야 한다. 격리는 라우팅과 SG로 만든다.

> 📚 **사례**: 2019년 Capital One 사고의 네트워크 측면을 보면, SSRF 취약점으로 EC2 메타데이터에 접근한 뒤 그 자격증명으로 S3 데이터를 빼냈다. 만약 S3 접근이 **VPC Endpoint + Endpoint Policy로만** 허용되고 인터넷 경로가 막혀 있었다면, 탈취한 자격증명으로도 외부에서 데이터를 가져가기 훨씬 어려웠을 것이다. 네트워크 격리는 IAM 침해 이후의 "두 번째 방어선"으로 작동한다.

## 정리하며

오늘 잡아야 할 그림은 세 가지다. 첫째, VPC는 강한 격리 경계이고 같은 IP가 겹쳐도 소프트웨어 레이어가 소유권을 강제한다. 둘째, 서브넷의 Public/Private은 속성이 아니라 **라우팅이 결정**하며, 라우팅 테이블은 "경로가 없으면 못 간다"는 보이지 않는 차단이다. 셋째, 3-Tier(Public/App/Data) 격리는 심층 방어의 네트워크 구현으로, Data Tier는 인터넷 경로 자체를 두지 않는 게 표준이다.

"이 리소스에 인터넷이 닿는가"라는 질문에 라우팅·Public IP·SG·NACL을 모두 따져 답하는 능력이 보안 엔지니어의 출발점이다. 다음 글에서는 그중 가장 자주 헷갈리는 **보안 그룹과 NACL의 차이**를 상태 저장/비저장 관점에서 정밀하게 본다.

**문제 1.** 한 보안 감사에서 RDS 인스턴스가 인터넷에서 접근 가능한지 의심된다. RDS가 실제로 인터넷에서 도달 가능하려면 반드시 충족돼야 하는 조건의 조합은?

A) 보안 그룹 인바운드에 0.0.0.0/0만 열려 있으면 충분하다  
B) 서브넷 라우팅 테이블에 IGW 경로 + RDS에 Public IP + SG/NACL 허용이 모두 필요하다  
C) NACL이 모든 트래픽을 허용하면 라우팅과 무관하게 도달 가능하다  
D) RDS의 PubliclyAccessible 플래그만 켜져 있으면 SG와 무관하게 도달 가능하다  

**정답: B**  
해설: 인터넷 도달 가능성은 여러 레이어가 동시에 충족돼야 성립한다. 인터넷으로 향하는 IGW 라우팅 경로, 리소스의 퍼블릭 주소, 그리고 보안 그룹과 NACL의 허용이 모두 있어야 한다. 보안 그룹만 열려 있어도 라우팅 경로가 없으면 패킷이 인터넷으로 나갈 수 없다. 라우팅이 빠지면 다른 통제가 열려 있어도 도달 불가다.

**문제 2.** 새로 만든 서브넷을 라우팅 테이블에 명시적으로 연결하지 않았다. 이 서브넷의 라우팅 동작은?

A) 인터넷 접근이 완전히 차단된 격리 서브넷이 된다  
B) VPC의 Main Route Table을 자동으로 사용한다  
C) 라우팅 테이블이 없으므로 VPC 내부 통신도 불가능하다  
D) 가장 가까운 AZ의 라우팅 테이블을 상속한다  

**정답: B**  
해설: 명시적으로 라우팅 테이블에 연결되지 않은 서브넷은 VPC의 메인 라우팅 테이블을 사용한다. 따라서 메인 라우팅 테이블에 인터넷 게이트웨이 경로가 들어 있으면 새 서브넷이 의도치 않게 인터넷에 노출된다. 이 때문에 메인 라우팅 테이블에는 인터넷 경로를 두지 않는 것이 안전한 기본값이다.

**문제 3.** Data Tier 서브넷(RDS 전용)의 라우팅 설계로 가장 적절한 것은?

A) 0.0.0.0/0 → NAT Gateway 경로를 두어 OS 패치를 받게 한다  
B) 0.0.0.0/0 → IGW 경로를 두어 외부 모니터링을 허용한다  
C) 로컬 경로만 두고 인터넷 경로를 두지 않는다  
D) 0.0.0.0/0 → Egress-only IGW 경로를 두어 IPv6 아웃바운드를 허용한다  

**정답: C**  
해설: 데이터 계층은 인터넷 경로 자체를 두지 않는 것이 가장 강한 격리다. 관리형 RDS의 패치는 AWS가 처리하므로 인터넷 경로가 필요 없다. 인터넷으로 향하는 경로를 추가하면 데이터 유출 경로가 생기므로, 외부 연결이 필요하면 NAT가 아니라 VPC 엔드포인트로 특정 서비스만 사설 연결하는 것이 표준이다.

**문제 4.** 민감 데이터를 다루는 App Tier에서 인터넷으로 데이터가 유출되는 것을 막으면서도 AWS 서비스(S3, DynamoDB) 접근은 허용하고 싶다. NAT Gateway 대비 더 안전한 접근은?

A) NAT Gateway의 아웃바운드를 모두 허용하되 SG로 목적지 IP를 제한한다  
B) VPC Endpoint(Gateway/Interface)로 해당 서비스만 사설 연결하고 인터넷 경로를 제거한다  
C) Internet Gateway를 두되 NACL로 아웃바운드 포트를 443만 허용한다  
D) Bastion Host를 통해서만 외부 통신을 중계하도록 강제한다  

**정답: B**  
해설: NAT는 아웃바운드를 폭넓게 허용하므로 데이터 유출 경로가 될 수 있다. 필요한 AWS 서비스만 VPC 엔드포인트로 사설 연결하고 인터넷 경로를 제거하면, 트래픽이 AWS 백본 내부에 머물고 외부로 데이터를 빼낼 경로 자체가 사라진다. 보안 그룹으로 목적지 IP를 제한하는 방식은 AWS 서비스 IP 범위가 광범위하게 변동해 실효성이 떨어진다.

**문제 5.** 기본(default) NACL과 기본 보안 그룹의 동작 차이로 옳은 것은?

A) 기본 NACL은 모든 인/아웃바운드를 허용하고, 기본 SG는 같은 SG 멤버 간만 허용한다  
B) 기본 NACL과 기본 SG 모두 모든 트래픽을 차단한다  
C) 기본 NACL은 모든 트래픽을 차단하고, 기본 SG는 모두 허용한다  
D) 둘 다 같은 SG/서브넷 멤버 간 통신만 허용한다  

**정답: A**  
해설: 기본 네트워크 ACL은 인바운드와 아웃바운드를 모두 허용해 사실상 무통제 상태다. 반면 기본 보안 그룹은 동일 보안 그룹에 속한 리소스 간 통신만 허용하고 그 외 인바운드는 차단하며 아웃바운드는 전체 허용한다. 따라서 실질적 격리는 라우팅과 보안 그룹으로 만들고, 네트워크 ACL은 보조적인 서브넷 단위 통제로 쓰는 것이 일반적이다.
