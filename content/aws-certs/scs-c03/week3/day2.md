# Day 2 - 보안 그룹 vs 네트워크 ACL: 상태 저장과 비저장의 본질

VPC 안에 두 개의 방화벽 계층이 있다. 보안 그룹(Security Group)과 네트워크 ACL(NACL)이다. 두 개념을 정확히 구분하지 못하면 시험에서도, 실무 트러블슈팅에서도 반복해서 막힌다. "왜 SG는 다 열었는데 응답이 안 오지?", "NACL에서 인바운드만 열었는데 왜 통신이 안 되지?" 같은 질문은 거의 모두 **상태 저장(stateful) vs 비저장(stateless)**의 차이를 놓쳐서 생긴다.

오늘은 이 둘을 본질부터 정리한다. 평가 순서, 상태 추적의 차이, 그리고 실무에서 가장 흔한 트러블슈팅 시나리오까지 본다. SCS-C03 도메인 3에서 거의 매 회차 출제되는 핵심 주제다.

## 두 방화벽의 위치: 어디에 붙는가

```
인터넷
  │
[ NACL ]  ← 서브넷 경계에 붙음 (서브넷 단위)
  │
[ 보안 그룹 ]  ← ENI(인스턴스)에 붙음 (리소스 단위)
  │
[ EC2 인스턴스 ]
```

- **NACL**: 서브넷 경계에서 동작. 서브넷을 드나드는 모든 트래픽을 검사한다.
- **보안 그룹**: ENI(Elastic Network Interface), 즉 인스턴스 단위로 동작. 리소스에 가장 가까운 방화벽.

| 항목 | 보안 그룹 (SG) | 네트워크 ACL (NACL) |
|------|----------------|---------------------|
| 적용 대상 | ENI / 인스턴스 | 서브넷 |
| 상태 | **Stateful** (상태 저장) | **Stateless** (비저장) |
| 규칙 | Allow만 가능 | Allow + **Deny 가능** |
| 평가 방식 | 모든 규칙 종합 평가 | 규칙 번호 순서대로, 첫 매치에서 종료 |
| 기본 동작 | 인바운드 차단 / 아웃바운드 허용 | (기본) 전체 허용 / (커스텀) 전체 차단 |

> 💡 **관련 이론**: 이 이중 구조는 네트워크 보안의 **계층화(layering)** 원칙이다. NACL은 서브넷 전체에 적용되는 광역 통제(coarse-grained), SG는 리소스별 정밀 통제(fine-grained)다. 전통적인 데이터센터에서 라우터 ACL(서브넷 경계)과 호스트 방화벽(서버별)을 나눈 것과 정확히 같은 사상이다. NACL로 서브넷 전체에 "이 포트는 절대 금지" 같은 강제 규칙을 걸고, SG로 각 리소스의 정밀한 허용을 관리한다.

## Stateful vs Stateless: 가장 중요한 차이

이 한 가지가 시험의 절반이다.

**보안 그룹(Stateful)**: 인바운드를 허용하면, 그에 대한 **응답(아웃바운드)은 규칙 없이 자동 허용**된다. 연결 상태를 추적하기 때문이다. 반대도 마찬가지 — 아웃바운드로 나간 요청의 응답 인바운드는 자동 허용된다.

**NACL(Stateless)**: 상태를 추적하지 않는다. 인바운드 요청을 허용했어도, **응답이 나가는 아웃바운드를 별도로 명시 허용**해야 한다. 응답은 보통 **임시 포트(ephemeral port, 1024~65535)**로 나가므로, NACL 아웃바운드에 이 범위를 열어야 한다.

```
# 시나리오: 웹 서버(443)에 인터넷 접속

[보안 그룹]
  인바운드: TCP 443 from 0.0.0.0/0   ← 이것만 있으면 됨
  (응답 아웃바운드는 자동 허용 - stateful)

[NACL]  ← 둘 다 명시해야 함 (stateless)
  인바운드: 규칙100  TCP 443  from 0.0.0.0/0  ALLOW
  아웃바운드: 규칙100  TCP 1024-65535  to 0.0.0.0/0  ALLOW  ← 임시 포트 필수!
```

> ⚠️ **함정**: 시험에서 가장 자주 나오는 함정이 바로 이 **임시 포트(ephemeral ports)**다. "NACL 인바운드에 443을 열었는데 웹 응답이 안 온다"는 시나리오의 답은 거의 항상 "아웃바운드 임시 포트(1024-65535)가 막혀 있다"이다. SG였다면 stateful이라 이 문제가 없다. 운영체제마다 임시 포트 범위가 다르다는 점도 알아두자(Linux 32768-60999, Windows Server 2008+ 49152-65535, NAT Gateway 1024-65535). 그래서 보통 안전하게 1024-65535를 다 연다.

> 🔍 **더 깊이**: Stateful 추적의 한 가지 미묘한 예외가 있다. 보안 그룹에서 인바운드 규칙을 허용했다가 **연결이 살아있는 도중에 규칙을 삭제**하면 어떻게 될까? TCP의 경우 이미 수립된(established) 연결은 보안 그룹이 계속 추적하므로 유지될 수 있다. 반면 NACL은 stateless라 규칙을 바꾸면 즉시 다음 패킷부터 적용된다. 그래서 "긴급 차단(emergency block)"이 필요하면 SG보다 NACL의 Deny 규칙이 더 즉각적이다. 단, 추적 연결 정리(connection tracking)는 idle 타임아웃이나 특정 조건에서 풀린다.

## NACL의 평가 순서: 규칙 번호가 운명을 가른다

NACL은 SG와 결정적으로 다르다. **규칙 번호가 낮은 것부터 순서대로 평가**하고, **첫 번째 매치에서 평가를 종료**한다(first-match wins).

```
인바운드 NACL 규칙:
  규칙 90:   DENY  TCP 22 from 203.0.113.50/32   ← 특정 IP 차단
  규칙 100:  ALLOW TCP 22 from 0.0.0.0/0         ← SSH 허용
  규칙 *:    DENY  ALL                            ← 암묵적 마지막(변경 불가)
```

이 경우 203.0.113.50은 규칙 90에서 먼저 DENY를 만나 차단된다. 규칙 100의 ALLOW까지 가지 않는다. **순서가 거꾸로면(100이 먼저면) 차단이 동작하지 않는다.**

> 💡 **관련 이론**: 이 "첫 매치 종료" 방식은 전통적인 라우터/방화벽 ACL과 동일하다(Cisco IOS ACL이 대표적). 그래서 규칙 번호를 보통 100 단위로 띄워 작성한다(100, 200, 300...). 나중에 사이에 규칙을 끼워 넣을 공간을 확보하기 위함이다. SG는 이런 순서가 없고 모든 규칙을 OR로 종합 평가하므로(어느 하나라도 허용하면 허용) 설계 사고가 완전히 다르다.

> 🎯 **시나리오**: "특정 악성 IP 한 개를 서브넷 전체에서 차단하고 싶다. SG로 가능한가?" — 불가능하다. SG는 Deny 규칙이 없다(Allow만 존재). 특정 IP를 차단하려면 **NACL의 Deny 규칙**을 낮은 번호로 추가해야 한다. 이것이 "SG로는 차단 불가, NACL로만 명시적 Deny 가능"이라는 핵심 차이다. 대규모 IP 차단이 필요하면 NACL 규칙 수 제한(기본 20, 최대 40)에 걸리므로 AWS Network Firewall이나 WAF를 쓴다.

## 평가 흐름: 패킷이 거치는 순서

인바운드 패킷이 EC2에 도달하기까지:

```
1. NACL 인바운드 (서브넷 진입)     → DENY면 여기서 끝
2. 보안 그룹 인바운드 (ENI 도착)    → 허용 안 되면 끝
3. EC2 처리 → 응답 생성
4. 보안 그룹 아웃바운드 (stateful → 자동 허용)
5. NACL 아웃바운드 (stateless → 명시 필요, 보통 임시 포트)
```

> 🔍 **더 깊이**: 한 가지 자주 묻는 질문 — "두 인스턴스가 **같은 서브넷 안에서** 통신하면 NACL이 적용되나?" 답은 **아니오**다. NACL은 서브넷 **경계**를 넘는 트래픽만 검사한다. 같은 서브넷 내부 통신은 NACL을 거치지 않고 SG만 적용된다. 반대로 SG는 같은 서브넷이든 다른 서브넷이든 ENI에 도달하는 모든 트래픽에 적용된다. 그래서 "같은 서브넷 내 격리"가 필요하면 SG로만 가능하다.

> ⚠️ **함정**: SG는 소스로 **다른 SG를 참조**할 수 있다(예: "ALB의 SG에서 오는 트래픽만 허용"). 이는 IP가 아니라 논리적 그룹 참조라 인스턴스가 늘어나도 규칙이 유지되는 큰 장점이다. NACL은 IP/CIDR만 참조 가능하고 SG 참조 불가. 시험에서 "오토스케일링으로 IP가 계속 바뀌는 백엔드에 ALB만 접근 허용"이라면 답은 NACL이 아니라 **SG 간 참조**다.

## 실무 트러블슈팅 매트릭스

| 증상 | 의심 1순위 | 확인 방법 |
|------|-----------|-----------|
| 연결 자체가 안 됨(timeout) | 라우팅 / SG 인바운드 / NACL | Reachability Analyzer |
| 요청은 가는데 응답이 없음 | NACL 아웃바운드 임시 포트 | NACL 아웃바운드 1024-65535 |
| 특정 IP만 막고 싶은데 안 됨 | SG로 시도(불가) | NACL Deny 규칙 사용 |
| 간헐적 차단 | NACL 규칙 순서(first-match) | 규칙 번호 정렬 확인 |
| 같은 서브넷 내 격리 안 됨 | NACL로 시도(미적용) | SG로 격리 |

```bash
# Reachability Analyzer로 경로 분석 (트러블슈팅의 정석)
aws ec2 create-network-insights-path \
  --source i-source --destination i-dest \
  --protocol tcp --destination-port 443

aws ec2 start-network-insights-analysis \
  --network-insights-path-id nip-xxxx
# 결과에 어느 컴포넌트(SG/NACL/Route)에서 막혔는지 정확히 표시됨
```

> 📚 **사례**: 실무에서 새벽에 가장 흔하게 호출되는 장애가 "NACL 잘못 건드림"이다. 누군가 보안 강화를 한다며 NACL 아웃바운드를 좁히면, stateful이 아닌 NACL 특성상 모든 응답 트래픽이 막혀 서브넷 전체가 먹통이 된다. 그래서 많은 조직이 **NACL은 거의 건드리지 않고 SG로만 정밀 통제**하는 전략을 쓴다. NACL은 "절대 안 되는 것"(예: 특정 악성 IP, DB 포트의 인터넷 노출)만 막는 보조 장치로 남긴다.

## 정리하며

핵심은 세 가지다. 첫째, **SG는 stateful**이라 응답이 자동 허용되고 **NACL은 stateless**라 응답(임시 포트)을 명시 허용해야 한다 — 이게 시험의 절반이다. 둘째, **NACL만 Deny가 가능**하고 규칙 번호 순서로 first-match 평가하며, SG는 Allow만 종합 평가한다. 셋째, **SG는 다른 SG를 참조**할 수 있고 같은 서브넷 내부도 통제하지만, NACL은 서브넷 경계만 보고 IP/CIDR만 참조한다.

실무 전략은 명확하다 — 정밀 통제는 SG로, 절대 금지 규칙(특정 IP 차단, 광역 deny)만 NACL로. 다음 글에서는 이 트래픽이 실제로 어떻게 흘렀는지 **VPC Flow Logs**로 들여다보며, 로그로 침해와 오구성을 탐지하는 법을 본다.

## 📝 연습 문제

**문제 1.** 한 엔지니어가 웹 서버 서브넷의 NACL 인바운드에 TCP 443을 0.0.0.0/0으로 허용했다. 그런데 외부에서 HTTPS 응답을 받지 못한다. 가장 가능성 높은 원인은?

A) 보안 그룹의 아웃바운드 443이 차단되어 있다  
B) NACL 아웃바운드에 임시 포트(1024-65535) 허용이 없다  
C) 라우팅 테이블에 로컬 경로가 누락되어 있다  
D) 보안 그룹이 stateless라 응답을 별도 허용해야 한다  

**정답: B**  
해설: 네트워크 ACL은 비저장 방식이라 요청을 허용해도 응답 트래픽을 자동으로 허용하지 않는다. HTTPS 응답은 클라이언트의 임시 포트 범위로 나가므로, 네트워크 ACL 아웃바운드에 임시 포트 범위를 명시적으로 허용해야 한다. 보안 그룹은 상태를 추적하므로 응답을 자동 허용하며, 이 증상의 원인이 아니다.

**문제 2.** 단일 악성 IP 주소 하나를 서브넷 전체에서 명시적으로 차단해야 한다. 올바른 접근은?

A) 보안 그룹 인바운드에 해당 IP를 Deny 규칙으로 추가한다  
B) 보안 그룹에서 0.0.0.0/0을 허용하되 해당 IP만 예외 처리한다  
C) 네트워크 ACL에 낮은 번호의 Deny 규칙으로 해당 IP를 추가한다  
D) 라우팅 테이블에서 해당 IP로 향하는 경로를 블랙홀로 설정한다  

**정답: C**  
해설: 보안 그룹은 허용 규칙만 지원하고 거부 규칙이 없으므로 특정 IP를 명시적으로 차단할 수 없다. 명시적 거부는 네트워크 ACL에서만 가능하며, 규칙 번호 순서대로 첫 매치에서 평가가 종료되므로 거부 규칙을 허용 규칙보다 낮은 번호로 두어야 효과가 있다.

**문제 3.** 오토스케일링으로 IP가 수시로 바뀌는 백엔드 인스턴스 그룹에 대해, 특정 ALB에서 오는 트래픽만 허용하고 싶다. 가장 적절한 방법은?

A) 백엔드 보안 그룹 인바운드의 소스로 ALB의 보안 그룹을 참조한다  
B) 백엔드 NACL에 ALB 인스턴스들의 IP를 모두 나열한다  
C) 백엔드 보안 그룹에 ALB 서브넷 CIDR을 허용한다  
D) 라우팅 테이블에서 ALB로만 향하는 경로를 추가한다  

**정답: A**  
해설: 보안 그룹은 소스로 다른 보안 그룹을 참조할 수 있어, IP가 변해도 그룹 멤버십으로 허용이 유지된다. 네트워크 ACL은 IP/CIDR만 참조하므로 IP가 자주 바뀌는 환경에 부적합하다. 서브넷 CIDR 허용은 같은 서브넷의 다른 리소스까지 열리므로 최소 권한에 어긋난다.

**문제 4.** 같은 서브넷 안에 있는 두 인스턴스 A, B 사이의 통신을 격리(차단)하려고 한다. 어떤 통제가 효과적인가?

A) 해당 서브넷의 네트워크 ACL 인바운드에 Deny 규칙을 추가한다  
B) 두 인스턴스의 보안 그룹 규칙으로 상호 트래픽을 허용하지 않는다  
C) 서브넷 라우팅 테이블에서 인스턴스 간 경로를 제거한다  
D) 네트워크 ACL과 보안 그룹 둘 중 어느 것으로도 가능하다  

**정답: B**  
해설: 네트워크 ACL은 서브넷 경계를 넘는 트래픽만 검사하므로 같은 서브넷 내부 통신에는 적용되지 않는다. 따라서 동일 서브넷 내 리소스 간 격리는 보안 그룹으로만 강제할 수 있다. 라우팅 테이블의 로컬 경로는 삭제할 수 없으므로 경로 제거 방식도 불가능하다.

**문제 5.** 보안 그룹과 네트워크 ACL의 평가 방식에 대한 설명으로 옳은 것은?

A) 보안 그룹은 규칙 번호 순서대로 첫 매치에서 평가를 종료한다  
B) 네트워크 ACL은 모든 규칙을 종합 평가하여 하나라도 허용하면 통과시킨다  
C) 보안 그룹은 모든 규칙을 종합 평가하고, 네트워크 ACL은 번호 순서대로 첫 매치에서 종료한다  
D) 둘 다 명시적 Deny 규칙을 우선 평가한 뒤 Allow를 본다  

**정답: C**  
해설: 보안 그룹은 순서 개념 없이 모든 허용 규칙을 종합 평가해, 어느 하나라도 매치하면 트래픽을 허용한다. 네트워크 ACL은 규칙 번호가 낮은 것부터 순서대로 평가하고 첫 매치에서 종료하므로, 거부 규칙을 허용 규칙보다 낮은 번호에 두어야 의도대로 동작한다.

**문제 6.** 보안 사고 대응 중 진행 중인 악성 연결을 즉시 끊어야 한다. 가장 즉각적으로 차단되는 통제는?

A) 보안 그룹에서 인바운드 허용 규칙을 삭제한다  
B) 네트워크 ACL에 해당 소스에 대한 Deny 규칙을 추가한다  
C) IAM 정책으로 해당 인스턴스의 권한을 회수한다  
D) 라우팅 테이블에서 VPC 로컬 경로를 삭제한다  

**정답: B**  
해설: 보안 그룹은 상태를 추적하므로 이미 수립된 연결은 규칙을 삭제해도 추적 정보로 한동안 유지될 수 있다. 반면 네트워크 ACL은 비저장 방식이라 규칙 변경이 다음 패킷부터 즉시 반영되므로 긴급 차단에 더 즉각적이다. 로컬 경로는 삭제할 수 없다.
