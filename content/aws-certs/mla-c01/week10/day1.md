# Day 1 - 도메인 1·2 통합 복습: 데이터 준비 + 모델 개발

마지막 주의 첫날이다. 오늘부터는 새 개념을 배우는 게 아니라 흩어진 지식을 시험장에서 꺼낼 수 있는 형태로 다시 묶는다. MLA-C01은 4개 도메인으로 나뉜다. **도메인 1(데이터 준비, 28%)** 과 **도메인 2(모델 개발, 26%)** 가 합쳐 절반이 넘는다. 즉 이 두 영역만 탄탄하면 합격선 대부분을 깔고 들어간다. 오늘은 데이터 수집·특성공학·Feature Store·Clarify와 모델 학습·튜닝·평가를 한 흐름으로 복습한다.

핵심 메시지 하나. **데이터 준비와 모델 개발은 "재현성과 일관성"이라는 한 축으로 연결된다.** 학습에 쓴 특성을 추론에도 똑같이 써야 하고(skew 방지), 학습에 쓴 데이터·하이퍼파라미터를 추적해야 하며, 편향과 누수는 데이터 단계에서 잡아야 한다.

## 도메인 1: 데이터 수집·저장 한눈에

데이터가 어디서 와서 어디에 쌓이는지를 먼저 정리하자.

| 요구사항 | AWS 서비스 |
|----------|------------|
| 실시간 스트림 수집 | Kinesis Data Streams / Firehose |
| 대량 일괄 적재(데이터레이크) | S3 |
| 서버리스 ETL·카탈로그 | AWS Glue (+ Glue Data Catalog) |
| 비주얼 데이터 준비(코드 없이) | SageMaker Data Wrangler |
| 대화형 분석 쿼리(S3 직접) | Amazon Athena |
| 분산 빅데이터 처리 | EMR (Spark) |

> 💡 **관련 이론**: 시험은 "실시간인가 일괄인가", "코드를 짤 것인가 비주얼로 할 것인가", "어디에 저장할 것인가"로 서비스를 가른다. 실시간 이벤트면 Kinesis, 적재 후 변환이면 Glue, 비주얼 전처리·빠른 EDA면 Data Wrangler, S3를 SQL로 즉석 조회면 Athena다. 데이터레이크의 중심은 거의 항상 S3이고, 나머지는 그 주변에서 수집·변환·조회 역할을 나눠 맡는다.

## 도메인 1: 특성공학과 Feature Store

특성공학의 단골 키워드를 정리한다. 수치형은 **정규화/표준화**, 범주형은 **원-핫/레이블 인코딩**, 결측은 **대치(imputation)**, 불균형은 **SMOTE·언더/오버샘플링**, 텍스트는 **토큰화·임베딩**이다.

**SageMaker Feature Store**는 특성을 한 번 정의해 학습과 추론이 함께 쓰게 만드는 중앙 저장소다. **온라인 스토어**는 저지연 단건 조회(실시간 추론), **오프라인 스토어**는 S3 기반 대량 조회(학습·배치)다.

> 💡 **관련 이론**: Feature Store의 존재 이유는 **training-serving skew 제거**다. 학습 때 계산한 특성과 추론 때 계산한 특성이 미세하게 달라지면 성능이 조용히 떨어진다. 특성을 한 곳에 정의·버전관리하고 온라인/오프라인 양쪽이 같은 정의를 공유하면 이 불일치가 사라진다. "여러 팀·여러 모델이 같은 특성을 재사용", "학습과 실시간 추론의 특성을 일치"라는 키워드가 나오면 Feature Store다.

## 도메인 1: SageMaker Clarify — 편향과 설명가능성

Clarify는 두 가지를 한다. ① **편향 탐지(bias detection)** — 학습 전 데이터 편향, 학습 후 모델 편향을 측정한다. ② **설명가능성(explainability)** — SHAP 값으로 어떤 특성이 예측에 얼마나 기여했는지 보여준다.

> 🔍 **더 깊이**: 편향은 두 시점에서 본다. **사전(pre-training)** 편향은 데이터 자체의 불균형(예: 특정 집단 표본 부족)을, **사후(post-training)** 편향은 모델 예측이 집단별로 다르게 나오는지를 측정한다. "공정성·편향·차별을 점검하라"는 Clarify, "예측 근거를 설명하라/특성 기여도"는 Clarify의 SHAP이다. 모니터링 단계에서는 Model Monitor가 Clarify와 연동해 운영 중 편향·특성 기여도 드리프트를 감시한다.

## 도메인 2: 학습 — 빌트인 알고리즘과 모드

모델 개발은 "어떤 알고리즘을, 어떻게 학습시키는가"다. 빌트인 알고리즘의 대표 매핑을 외우자.

| 문제 유형 | 대표 알고리즘 |
|-----------|---------------|
| 표 형식 분류/회귀 | XGBoost, Linear Learner |
| 이미지 분류·객체탐지 | Image Classification, Object Detection |
| 텍스트 분류·임베딩 | BlazingText |
| 시계열 예측 | DeepAR |
| 클러스터링 | K-Means |
| 차원 축소 | PCA |
| 이상 탐지 | Random Cut Forest (RCF) |
| 추천 | Factorization Machines |

> ⚠️ **함정**: 알고리즘 매핑은 가장 자주 출제된다. "시계열 다변량 예측"에 회귀를 고르면 틀린다 — DeepAR이다. "실시간 스트림 이상치"는 RCF, "수천 차원 희소 추천"은 Factorization Machines다. 또 학습 데이터 입력 모드도 묻는다. 데이터가 인스턴스 디스크보다 크거나 시작 지연을 줄이고 싶으면 **Pipe 모드**(또는 최신 **Fast File 모드**)로 S3에서 스트리밍하고, 작은 데이터면 **File 모드**로 통째로 복사한다.

## 도메인 2: 하이퍼파라미터 튜닝(AMT)

SageMaker Automatic Model Tuning(AMT)은 하이퍼파라미터 탐색을 자동화한다. 전략은 **Bayesian**(과거 결과로 다음 후보를 똑똑하게 고름, 기본 권장), **Random**(병렬·광범위 탐색), **Grid**(소규모 이산 공간), **Hyperband**(성능 낮은 학습을 조기 종료해 자원 절약)다.

> 💡 **관련 이론**: 튜닝 전략 선택은 "예산 효율 vs 병렬성"이다. Bayesian은 적은 시도로 좋은 값을 찾지만 순차적 성격이 강하고, Random/Grid는 병렬화가 쉽지만 비효율적이며, Hyperband는 가망 없는 학습을 일찍 끊어 대규모 탐색의 비용을 줄인다. "적은 학습 횟수로 효율적 탐색"은 Bayesian, "조기 종료로 자원 절약"은 Hyperband가 키워드다. 정의 시 `objective_metric`(최적화 대상)과 탐색 범위를 지정한다.

## 도메인 2: 평가 — 올바른 지표 고르기

학습이 끝나면 올바른 지표로 평가해야 한다. 지표 선택은 거의 항상 "데이터가 불균형한가, 무엇을 더 중요하게 보는가"로 결정된다.

| 상황 | 지표 |
|------|------|
| 균형 잡힌 분류 | Accuracy |
| 불균형 분류, 전반 성능 | F1, AUC-ROC |
| 거짓양성 비용이 큼(스팸 오분류) | Precision 중시 |
| 거짓음성 비용이 큼(질병 놓침) | Recall 중시 |
| 회귀 | RMSE, MAE, R² |

> ⚠️ **함정**: 불균형 데이터에서 Accuracy를 고르면 틀린다. 99%가 정상인 사기탐지에서 "전부 정상"이라 찍어도 정확도 99%지만 사기는 하나도 못 잡는다. 이런 시나리오는 F1·AUC·Recall로 평가해야 한다. "사기/질병을 놓치면 안 된다"는 **Recall**, "오탐(거짓경보) 비용이 크다"는 **Precision**이 핵심어다. 과적합 징후(학습 정확도↑·검증 정확도↓)는 정규화·드롭아웃·조기종료·데이터 증강으로 대응한다.

## 정리하며

도메인 1·2를 한 흐름으로 묶으면 이렇다. 데이터는 **Kinesis/S3/Glue/Data Wrangler**로 수집·변환하고, 특성은 **Feature Store**로 학습-추론 일관성을 보장하며, **Clarify**로 편향·설명가능성을 점검한다. 모델은 문제 유형에 맞는 **빌트인 알고리즘**을 골라 적절한 **입력 모드**로 학습하고, **AMT**로 튜닝하며, **불균형을 고려한 지표**로 평가한다. 이 두 도메인이 시험의 절반이니, 키워드→서비스/지표 매핑을 반사적으로 떠올릴 수 있어야 한다.

## 📝 연습 문제

**문제 1.** 한 팀은 동일한 고객 특성(최근 구매액, 가입 기간 등)을 실시간 추천 모델과 야간 배치 이탈 예측 모델 양쪽에서 사용한다. 학습과 추론 사이 특성 불일치(skew)를 막고 특성을 재사용하려 한다. 가장 적절한 것은?

A) 각 모델이 자체 전처리 코드를 별도로 유지  
B) SageMaker Feature Store(온라인 + 오프라인 스토어)  
C) S3에 CSV로 매번 새로 저장  
D) Athena 쿼리로 매 호출마다 특성 재계산  

**정답: B**  
해설: Feature Store는 특성을 한 번 정의해 온라인 스토어(저지연 실시간 추론)와 오프라인 스토어(대량 학습·배치)가 동일한 정의를 공유하게 하여 training-serving skew를 제거하고 특성 재사용을 가능케 한다. A는 코드 중복으로 불일치를 키우고, C는 버전·일관성 관리가 없으며, D는 매 호출 재계산으로 실시간 저지연 요구를 충족하지 못한다.

**문제 2.** 신용 심사 모델을 배포하기 전에 특정 성별·연령 집단에 대해 예측이 불공정하게 치우치지 않는지 점검하고, 각 특성이 개별 예측에 얼마나 기여했는지도 설명하려 한다. 가장 적절한 도구는?

A) SageMaker Model Monitor  
B) SageMaker Clarify  
C) SageMaker Debugger  
D) CloudWatch Logs  

**정답: B**  
해설: Clarify는 사전·사후 편향 지표로 집단 간 공정성을 측정하고 SHAP 기반 특성 기여도로 예측을 설명하므로 두 요구를 모두 충족한다. A는 운영 중 데이터·품질 드리프트 모니터링이 주목적이고, C는 학습 과정의 텐서·자원 디버깅용이며, D는 단순 로그 수집으로 편향·설명가능성 분석을 제공하지 않는다.

**문제 3.** 99.5%가 정상 거래이고 0.5%만 사기인 데이터로 분류 모델을 만들었다. 모델 성능을 가장 적절히 평가하는 지표 조합은?

A) Accuracy 단독  
B) F1 점수와 AUC-ROC, 사기 탐지를 위한 Recall  
C) RMSE  
D) R² 결정계수  

**정답: B**  
해설: 극심한 불균형 데이터에서 Accuracy는 "전부 정상" 예측만으로도 99.5%가 나와 사기 탐지력을 전혀 반영하지 못하므로, 불균형에 강한 F1·AUC와 놓친 사기를 잡아내는 Recall로 평가해야 한다. A는 불균형에서 오해를 부르고, C·D는 회귀 지표라 분류 성능 평가에 부적합하다.

**문제 4.** 학습 데이터셋이 단일 인스턴스의 로컬 디스크 용량보다 훨씬 크고, 학습 시작 시 전체를 복사하느라 지연이 큰 문제가 있다. 가장 적절한 개선은?

A) File 모드로 전체 데이터를 인스턴스에 복사  
B) Pipe 모드(또는 Fast File 모드)로 S3에서 스트리밍 입력  
C) 데이터를 무작위로 1%만 학습에 사용  
D) 더 작은 인스턴스로 교체  

**정답: B**  
해설: Pipe 모드(및 Fast File 모드)는 S3에서 데이터를 스트리밍해 전체를 복사하지 않으므로, 디스크 용량을 초과하는 대용량 데이터와 시작 지연 문제를 동시에 해결한다. A는 바로 그 복사 지연을 유발하고, C는 데이터를 버려 성능을 떨어뜨리며, D는 용량 문제를 악화시킨다.

**문제 5.** 제한된 학습 예산 안에서 가능한 한 적은 학습 시도로 좋은 하이퍼파라미터 조합을 찾으려 한다. SageMaker AMT에서 가장 적절한 전략은?

A) Grid Search  
B) Bayesian 최적화  
C) 수동으로 하나씩 시도  
D) 모든 조합을 무작위로 무한 탐색  

**정답: B**  
해설: Bayesian 최적화는 이전 시도 결과를 활용해 유망한 후보를 우선 탐색하므로 적은 학습 횟수로 좋은 조합을 찾는 데 가장 효율적이다. A는 이산 공간 전수 탐색이라 시도 수가 많고, C는 비효율·비재현적이며, D는 예산 제약과 정반대로 비효율적이다.
