# Day 4 - 자주 틀리는 함정·키워드: "요구사항 → SageMaker 기능" 번역표

## 📌 핵심 정리

- 시험이 어려운 이유는 개념을 몰라서가 아니라 **시나리오를 기능으로 번역하지 못해서**인 경우가 많다.
- 순서를 고정하라: 문항을 읽으며 키워드로 **정답을 먼저 떠올린 뒤** 보기에서 그 이름을 찾는다. 보기부터 읽으면 흔들린다.
- 혼동 짝은 **미세 조건어**로 갈린다 — "배포 전 vs 운영 중", "일회 vs 지속", "같은 프레임워크 vs 다른 프레임워크".
- 3대 함정: 불균형인데 Accuracy, 알고리즘 오매핑, 실시간을 0으로 스케일. 알고만 있으면 즉시 걸러진다.
- 비용 절감 보기가 **다른 요구(성능·가용성·보안)를 깨면 오답**이다. 싸다고 정답이 아니다.

## 핵심 번역표 — 요구사항 → 기능

이 표가 머릿속에 박히면 종합 문제 풀이 속도가 크게 빨라진다.

> 💡 **관련 이론**: 이 표의 가치는 "보기를 보기 전에 정답을 먼저 떠올리는 것"이다. 시험 보기는 그럴듯한 함정으로 채워져 있어서, 정답을 먼저 정하지 않고 보기를 읽으면 흔들린다. 문제를 읽으며 키워드를 잡아 기능 이름을 머릿속에 적은 뒤, 그 이름이 보기에 있는지 확인하는 순서가 가장 안전하다.

## 단골 혼동 짝 — 무엇이 다른가

가장 자주 헷갈리는 쌍을 명확히 구분하자.

| 혼동 쌍 | 구분 기준 |
|----------|-----------|
| Model Monitor vs Clarify | 운영 중 드리프트 감시=Monitor / 배포 전 일회 편향·설명 분석=Clarify |
| Data Quality vs Model Quality | 입력 분포·스키마 변화 / 정답 대비 성능 저하(라벨 필요) |
| MME vs MCE | 같은 컨테이너·다수 모델 / 다른 프레임워크·소수 모델 |
| 비동기 vs 배치 변환 | 개별 요청을 큐로 받아 S3에 결과 / 전체 데이터셋을 작업 단위로 |
| 서버리스 vs 비동기 | 작은 페이로드·짧은 처리·간헐 / 큰 페이로드·긴 처리·큐 |
| Data Wrangler vs Processing Job | 비주얼·코드 없이 / 내 스크립트를 관리형 실행 |
| Feature Store 온라인 vs 오프라인 | 저지연 단건 조회(실시간) / S3 대량 조회(학습·배치) |
| Gateway vs Interface 엔드포인트 | 라우팅 테이블·S3/DynamoDB / ENI·대부분의 서비스 |
| CloudTrail vs CloudWatch | 누가 무슨 행위(API 감사) / 시스템 지표·로그·알람 |
| Pipelines vs Step Functions | SageMaker 특화 ML CI/CD / 범용 서비스 오케스트레이션 |
| Bayesian vs Hyperband | 적은 시도로 효율 탐색 / 가망 없는 학습 조기 종료 |
| File vs Pipe vs Fast File | 전체 복사 / 스트리밍 / 즉시 접근 + 필요분 스트리밍 |
| 데이터 병렬 vs 모델 병렬 | 데이터를 쪼갬(데이터가 많음) / 모델을 쪼갬(GPU에 안 들어감) |
| Precision vs Recall | 오탐 비용이 큼 / 놓침 비용이 큼 |
| 추론 파이프라인 vs 프로덕션 변형 | 순차 체인(전처리→모델) / 트래픽 분배(A/B) |
| Glue vs EMR | 서버리스 ETL·카탈로그 / 클러스터 직접 운영·대규모 Spark |

> ⚠️ **함정**: 시험은 이 혼동 쌍을 일부러 같은 문항의 보기로 나란히 놓는다. "편향을 감시하라"에서 Model Monitor의 Bias Drift와 Clarify를 둘 다 보기로 주고, "일회성 사전 점검"이면 Clarify, "운영 중 지속 감시"면 Model Monitor(+Clarify 연동)로 갈린다. 미세한 조건어("배포 전" vs "운영 중", "일회" vs "지속")가 정답을 가른다.

## 함정 유형 1 — 불균형인데 Accuracy를 고르게 유도

불균형 데이터(사기·질병·이탈)에서 Accuracy를 보기에 매력적으로 배치한다. 99% 정상 데이터에서 "전부 정상" 모델도 정확도 99%다. 정답은 거의 항상 **F1·AUC·Recall**이다. "놓치면 안 됨"=Recall, "오탐 비용 큼"=Precision.

> 🔍 **더 깊이**: 지표 문제는 "비용 비대칭"을 읽어야 한다. 거짓음성(놓침)의 비용이 크면 Recall, 거짓양성(오경보)의 비용이 크면 Precision, 둘의 균형이 중요하면 F1이다. 임계값(threshold)을 조정하면 Precision-Recall이 트레이드오프된다는 점도 함께 묻는다. 의료 진단처럼 놓침이 치명적이면 임계값을 낮춰 Recall을 올리는 식이다.

## 함정 유형 2 — 알고리즘 매핑을 뒤섞기

"시계열 예측"에 Linear Learner, "이상 탐지"에 K-Means처럼 비슷해 보이는 오답을 준다. 매핑을 확실히: 시계열=**DeepAR**, 이상치=**RCF**, 클러스터링=**K-Means**, 차원축소=**PCA**, 표 형식 분류/회귀=**XGBoost**, 추천(희소)=**Factorization Machines**, 텍스트=**BlazingText**.

| 오답 유인 | 왜 끌리나 | 정답 |
|-----------|-----------|------|
| 시계열 → Linear Learner | "예측=회귀"라는 연상 | DeepAR |
| 이상 탐지 → K-Means | "이상치는 군집 밖"이라는 연상 | Random Cut Forest |
| 세그먼트 나누기 → XGBoost | "분류=XGBoost"라는 연상 | 라벨이 없으면 K-Means |
| 추천 → K-Means | "비슷한 사용자 묶기"라는 연상 | 희소 상호작용이면 Factorization Machines |
| 특성이 너무 많음 → 특성 삭제 | 단순 직관 | PCA로 차원 축소 |

## 함정 유형 3 — 실시간을 0으로 스케일하려는 시도

"트래픽이 0까지 떨어지니 실시간 엔드포인트를 0대로 스케일하라"는 보기는 틀린다. 실시간은 **최소 1대 유지**가 강제다. 0 스케일이 필요하면 **서버리스/비동기/배치**로 가야 한다. 또 XGBoost에 GPU(p4d)를 붙이는 보기도 함정 — 트리 모델은 CPU가 정답이다.

> ⚠️ **함정**: "비용을 줄여라"는 키워드가 나오면 보기마다 비용 절감 기법이 그럴듯하게 섞인다. 동종 다수 모델→MME, 딥러닝 추론→Inferentia, 간헐 트래픽→서버리스/비동기, 학습 비용·중단 허용→Spot은 맞지만, "XGBoost를 GPU로", "실시간을 0으로", "정확도가 중요한데 데이터를 버려서"는 비용은 줄어도 요구를 깨는 함정이다. 비용 절감이 다른 요구(성능·가용성)를 희생하면 오답이다.

## 함정 유형 4 — 도구를 원래 용도 밖으로 밀어 넣기

보기가 "존재하는 서비스"를 쓰되 **역할을 살짝 비튼다.** 서비스 이름이 익숙해서 그냥 넘어가기 쉽다.

| 함정 보기 | 왜 틀렸나 |
|-----------|-----------|
| Model Monitor가 재학습을 수행한다 | Monitor는 감지·알림까지. 재학습은 EventBridge → Pipeline |
| KMS로 인터넷 접근을 차단한다 | KMS는 저장 암호화. 네트워크는 VPC 엔드포인트·격리 |
| CloudTrail로 지연 시간을 모니터링한다 | CloudTrail은 API 감사. 지표는 CloudWatch |
| Clarify로 운영 중 드리프트를 지속 감시한다 | 지속 감시는 Model Monitor(Clarify 연동) |
| Debugger로 편향을 측정한다 | Debugger는 학습 과정 진단. 편향은 Clarify |
| Feature Store에 학습 스크립트를 저장한다 | Feature Store는 특성 저장소이지 코드 저장소가 아니다 |
| 서버리스 추론으로 학습 비용을 줄인다 | 추론 옵션이라 학습 비용과 무관 |

## 함정 유형 5 — 조건을 하나 빠뜨린 "거의 정답"

가장 아픈 함정이다. 조건이 세 개인데 두 개만 만족하는 보기를 정답 옆에 둔다.

```text
[조건 체크 방식]
  문항에서 조건을 뽑는다        조건①  조건②  조건③
        ▼
  보기 A : VPC 엔드포인트만       ✓      ✗      ✗   → 탈락
  보기 B : VPC + 격리             ✓      ✓      ✗   → "거의 정답" 함정
  보기 C : VPC + 격리 + KMS       ✓      ✓      ✓   → 정답
  보기 D : IAM 정책 강화만        ✗      ✗      ✗   → 탈락
```

- 조건 개수를 먼저 세고, 보기마다 몇 개를 만족하는지 표시한다.
- 조건 하나가 "인터넷 비경유", 또 하나가 "외부 유출 차단"처럼 **비슷해 보이지만 다른 요구**일 때 특히 위험하다.
- 반대로 조건이 하나뿐인데 구성 요소가 잔뜩 붙은 보기는 "LEAST operational overhead" 기준에서 밀린다.

## 함정 유형 6 — 최상급 한정어를 흘려 읽기

| 한정어 | 무엇을 비교하나 | 흔한 오답 |
|--------|-----------------|-----------|
| MOST cost-effective | 비용 | 성능은 좋지만 비싼 구성 |
| LEAST operational overhead | 운영 부담 | EC2에 직접 구축·자체 스크립트 |
| MOST secure | 보안 | 작동은 하지만 노출 경로가 남는 구성 |
| LEAST latency | 지연 | 배치·비동기처럼 즉시성이 없는 옵션 |
| FASTEST to implement | 구현 속도 | 커스텀 컨테이너·직접 구현 |

## 오답 패턴: 증상 → 원인 → 조치

| 증상 | 원인 | 조치 |
|------|------|------|
| 보기를 읽다 마음이 바뀌어 틀린다 | 정답을 먼저 정하지 않고 보기부터 읽음 | 키워드→기능 번역을 머릿속에 적은 뒤 보기 확인 |
| 혼동 짝에서 매번 반대를 고른다 | 미세 조건어를 안 읽음 | "배포 전/운영 중", "일회/지속"에 밑줄 |
| 조건 세 개 중 두 개짜리 보기를 고른다 | 조건 개수를 세지 않음 | 조건에 번호를 매기고 보기마다 체크 |
| 비용 문항에서 성능을 깨는 보기를 고른다 | 한정어만 보고 다른 요구를 무시 | 요구를 깨는 보기는 한정어와 무관하게 탈락 |
| 아는 서비스 이름이 보이면 반사적으로 고른다 | 서비스의 "역할"이 아니라 "이름"으로 판단 | 그 서비스가 정확히 무엇을 하는지 되뇌기 |
| 시간이 모자라 뒤쪽을 못 푼다 | 한 문항에 과도하게 체류 | 2분 초과 시 임시 답 + 표시 후 이동 |

- **혼동 짝** : 시험이 일부러 같은 문항의 보기로 나란히 놓는 비슷한 두 기능. 미세 조건어로 갈린다.
- **미세 조건어** : "배포 전 vs 운영 중", "일회 vs 지속", "개별 요청 vs 전체 데이터셋"처럼 정답을 가르는 짧은 수식어.
- **최상급 한정어** : MOST cost-effective, LEAST operational overhead 등 비교 기준을 지정하는 표현. 여러 보기가 다 작동할 때 정답을 하나로 좁힌다.
- **거의 정답 함정** : 요구 조건 중 하나를 빠뜨린 보기. 정답 바로 옆에 배치되어 가장 많이 걸린다.
- **역할 비틀기 함정** : 실제 존재하는 서비스를 원래 용도가 아닌 일에 쓰게 하는 보기(예: Model Monitor가 재학습을 수행).
- **비용 비대칭** : 거짓양성과 거짓음성의 손실 크기가 다른 상황. 이 비대칭이 Precision·Recall 중 무엇을 볼지 결정한다.
- **임계값(threshold)** : 분류 확률을 양성/음성으로 가르는 기준값. 낮추면 Recall이 오르고 Precision이 내려간다.
- **소거법** : 요구를 하나라도 위반하는 보기를 지워 후보를 줄이는 풀이 방식.

## 📝 연습 문제

**문제 1.** 배포 전에 모델 예측이 특정 집단에 불공정한지 한 번 점검하고, 동시에 각 특성의 예측 기여도를 SHAP로 보고하려 한다. 가장 적절한 기능은?

A) Model Monitor (Bias Drift)  
B) SageMaker Clarify  
C) CloudWatch 대시보드  
D) Model Registry  

**정답: B**  
해설: "배포 전 일회 점검 + 편향 측정 + SHAP 기여도"는 Clarify의 정확한 역할이다. A의 Bias Drift는 운영 중 지속 감시용이라 "배포 전 일회" 조건과 어긋나고, C는 운영 지표 시각화, D는 모델 버전 관리로 편향·설명과 무관하다.

**문제 2.** 학습 작업이 중단되어도 재시작할 수 있고 비용을 최대한 절감하려 한다. 단, 마감이 빠듯하지는 않다. 가장 적절한 선택은?

A) 온디맨드 인스턴스 고정  
B) Managed Spot Training(Spot 인스턴스)  
C) 더 큰 GPU 인스턴스로 빨리 끝내기  
D) 서버리스 추론으로 전환  

**정답: B**  
해설: Managed Spot Training은 중단 가능한 Spot 인스턴스를 써서 학습 비용을 크게 절감하며 체크포인트로 재시작을 지원하므로 "중단 허용 + 비용 절감 + 여유 있는 마감"에 적합하다. A는 절감이 없고, C는 비용을 늘리며, D는 추론 옵션이라 학습 비용 절감과 무관하다.

**문제 3.** 다음 중 요구사항과 기능 매핑이 잘못된 것은?

A) 입력 데이터 분포 변화 감지 → Model Monitor(Data Quality)  
B) 누가 엔드포인트를 삭제했는지 감사 → CloudTrail  
C) 인터넷 없이 S3 접근 → KMS 암호화  
D) 동종 모델 수백 개 비용 절감 → 멀티모델 엔드포인트(MME)  

**정답: C**  
해설: 인터넷 없이 S3·ECR에 접근하는 것은 VPC 엔드포인트(PrivateLink)의 역할이며, KMS는 저장 데이터 암호화로 네트워크 경로와 무관하므로 C가 잘못된 매핑이다. A·B·D는 각각 Data Quality 드리프트 감지, CloudTrail API 감사, MME 다수 모델 비용 절감으로 모두 올바른 매핑이다.

**문제 4.** 트래픽이 업무 시간에만 있고 야간·주말엔 거의 0으로 떨어지는 사내 도구의 추론 비용을 줄이려 한다. 첫 호출의 약간의 지연(콜드 스타트)은 허용된다. 가장 적절한 옵션은?

A) 실시간 엔드포인트를 0대로 오토스케일  
B) 서버리스 추론  
C) 배치 변환  
D) 더 큰 인스턴스의 실시간 엔드포인트  

**정답: B**  
해설: 간헐적 트래픽 + 0까지 스케일 + 콜드 스타트 허용은 서버리스 추론의 정확한 조건으로 유휴 시 비용이 0에 가깝다. A는 실시간이 최소 1대를 강제해 0 스케일이 불가능하고, C는 즉시 응답이 아닌 일괄 처리이며, D는 always-on 비용을 오히려 늘린다.

**문제 5.** Model Monitor의 Data Quality와 Model Quality 모니터 차이로 가장 정확한 것은?

A) Data Quality는 정답 라벨이 필요하고 Model Quality는 필요 없다  
B) Data Quality는 입력 데이터 분포·스키마 변화를 보고, Model Quality는 실제 정답 대비 예측 성능 저하를 보며 ground truth 수집이 필요하다  
C) 둘 다 편향만 측정한다  
D) Model Quality는 학습 전에만 동작한다  

**정답: B**  
해설: Data Quality는 입력 분포·스키마 드리프트를 베이스라인과 비교하고, Model Quality는 실제 정답과 예측을 대조해 성능 저하를 측정하므로 ground truth 라벨 수집이 필요하다. A는 라벨 필요 주체가 뒤바뀌었고, C는 편향만 본다는 잘못된 한정이며, D는 Model Quality가 운영 중 감시 기능이라 사실과 다르다.
