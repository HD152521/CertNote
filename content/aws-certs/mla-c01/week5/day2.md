# Day 2 - 분산 학습: 데이터 병렬과 모델 병렬

모델 한 대 장비에 다 안 들어가거나, 데이터가 너무 많아 한 GPU로는 며칠이 걸린다면 여러 장비·GPU에 학습을 쪼개야 한다. 이것이 분산 학습이다. 핵심은 "무엇을 쪼개느냐" — 데이터를 쪼개느냐, 모델을 쪼개느냐 — 두 갈래다.

MLA-C01 시험에서 분산 학습은 "모델이 GPU 메모리에 안 들어간다", "학습이 너무 느리다", "수십억 파라미터 모델을 학습한다" 같은 증상으로 등장한다. 오늘은 데이터 병렬, 모델 병렬, 그리고 SageMaker가 제공하는 분산 학습 라이브러리를 본다.

## 데이터 병렬 vs 모델 병렬

분산 학습의 두 패러다임을 먼저 명확히 구분한다.

| 구분 | 데이터 병렬 (Data Parallel) | 모델 병렬 (Model Parallel) |
|------|---------------------------|---------------------------|
| 쪼개는 대상 | 데이터(배치)를 GPU마다 분배 | 모델 자체를 여러 GPU에 분할 |
| 각 GPU가 가진 것 | 모델 전체 복제본 | 모델의 일부 레이어/파라미터 |
| 해결하는 문제 | 학습 속도(처리량) | 모델이 한 GPU 메모리에 안 들어감 |
| 동기화 | 그래디언트를 all-reduce로 평균 | 활성값·그래디언트를 단계 간 전달 |
| 대표 상황 | 데이터 많고 모델은 GPU에 들어감 | 초대형 모델(수십억 파라미터) |

핵심 직관: **데이터 병렬은 "모델은 들어가는데 느릴 때", 모델 병렬은 "모델 자체가 안 들어갈 때"** 쓴다. 시험 키워드 "out of memory / 모델이 너무 커서"는 모델 병렬, "학습이 너무 오래 걸림 / 데이터가 큼"은 데이터 병렬이다.

> 💡 **관련 이론**: 데이터 병렬의 수학적 근거는 미니배치 그래디언트의 선형성이다. 전체 배치의 그래디언트는 각 GPU가 계산한 부분 배치 그래디언트의 평균과 같다. 그래서 GPU마다 모델 복제본으로 부분 배치를 처리한 뒤 all-reduce로 그래디언트를 합쳐 평균하면, 한 대로 큰 배치를 처리한 것과 수학적으로 동등한 업데이트가 된다. 모델 병렬은 다르다. 연산 그래프 자체를 잘라 한 GPU의 출력(활성값)이 다음 GPU의 입력이 되므로, GPU 간 의존성과 통신 비용이 본질적으로 더 크다.

## 데이터 병렬: 처리량을 늘린다

데이터 병렬은 가장 흔한 분산 방식이다. 각 GPU(혹은 장비)가 모델 전체 복제본을 갖고, 서로 다른 데이터 조각으로 forward/backward를 수행한 뒤 그래디언트를 모아 평균한다.

```
[GPU 0]  배치 조각 0  →  그래디언트 g0  ┐
[GPU 1]  배치 조각 1  →  그래디언트 g1  ├─ all-reduce → 평균 ḡ → 모든 GPU 동일 갱신
[GPU 2]  배치 조각 2  →  그래디언트 g2  ┘
```

```python
from sagemaker.pytorch import PyTorch

estimator = PyTorch(
    entry_point='train.py',
    instance_type='ml.p4d.24xlarge',
    instance_count=2,                       # 여러 장비
    framework_version='2.0', py_version='py310',
    distribution={                          # SageMaker 데이터 병렬 활성화
        'smdistributed': {'dataparallel': {'enabled': True}}
    }
)
```

**SageMaker Distributed Data Parallel (SMDDP)**은 AWS 네트워크(EFA 등)에 최적화된 all-reduce를 제공해, 표준 PyTorch DDP보다 통신 효율이 좋다. 데이터 병렬을 늘리면 처리량이 거의 선형으로 증가하지만, 통신 오버헤드 때문에 무한히 선형은 아니다.

> ⚠️ **함정**: 데이터 병렬로 GPU 수를 N배 늘리면 유효 배치 크기도 N배가 된다. 이때 학습률을 그대로 두면 수렴이 나빠질 수 있어 보통 학습률을 함께 조정(예: linear scaling)한다. "GPU만 늘리면 자동으로 더 잘 학습된다"는 오해를 시험이 노린다.

## 모델 병렬: 모델을 쪼갠다

모델 병렬은 모델 자체가 한 GPU 메모리에 안 들어갈 때 쓴다. 수십억~수천억 파라미터의 거대 언어 모델이 대표적이다. 모델 병렬에는 두 결이 있다.

- **텐서/파이프라인 분할**: 레이어들을 여러 GPU에 나눠 배치. 한 GPU의 출력이 다음 GPU의 입력이 됨(파이프라인 병렬), 혹은 한 레이어의 텐서 연산 자체를 쪼갬(텐서 병렬).
- **샤딩(sharding)**: 옵티마이저 상태·그래디언트·파라미터를 GPU 간에 분산 저장해 메모리를 절약(ZeRO/FSDP 계열).

```python
estimator = PyTorch(
    entry_point='train.py',
    instance_type='ml.p4d.24xlarge', instance_count=2,
    framework_version='2.0', py_version='py310',
    distribution={
        'smdistributed': {
            'modelparallel': {                 # SageMaker 모델 병렬
                'enabled': True,
                'parameters': {'partitions': 4, 'tensor_parallel_degree': 2}
            }
        }
    }
)
```

**SageMaker Distributed Model Parallel (SMP)**은 모델 분할·파이프라인 실행·샤딩을 자동화한다. 사용자가 수작업으로 레이어를 GPU에 배치하지 않아도 라이브러리가 메모리에 맞게 분할 전략을 잡아준다.

> 💡 **관련 이론**: 거대 모델을 쪼갤 때 핵심 트레이드오프는 "메모리 절약 vs 통신 비용"이다. 모델을 잘게 쪼갤수록 GPU당 메모리는 줄지만 GPU 간 활성값·파라미터 전송이 늘어 느려진다. 그래서 실무에서는 데이터 병렬·텐서 병렬·파이프라인 병렬·샤딩을 조합한 "하이브리드 병렬"을 쓴다. 예를 들어 노드 안에서는 텐서 병렬(빠른 NVLink), 노드 간에는 데이터 병렬(상대적으로 느린 네트워크)로 통신 패턴을 토폴로지에 맞춘다.

## 대규모 학습 인프라

분산 학습 성능은 알고리즘뿐 아니라 인프라가 좌우한다.

- **EFA (Elastic Fabric Adapter)**: 노드 간 저지연 고대역 네트워크. 분산 학습의 all-reduce 통신 병목을 줄인다. p4d/p5 같은 GPU 인스턴스에서 활성화.
- **FSx for Lustre**: 고처리량 병렬 파일시스템. 대용량 학습 데이터를 S3보다 빠르게 GPU에 공급해 데이터 로딩 병목을 줄인다.
- **인스턴스 선택**: 다중 GPU 단일 노드(예: p4d.24xlarge = 8 GPU)면 노드 내 NVLink로 빠르다. 노드를 여러 개 쓰면 EFA로 노드 간 통신.

```
S3 (원천 데이터)
   └─ FSx for Lustre (고속 캐시) → 여러 학습 노드에 빠르게 공급
학습 노드들 ── EFA(저지연 네트워크) ── all-reduce / 모델 병렬 통신
```

> 📚 **사례**: 한 연구팀이 70억 파라미터 모델을 단일 ml.g5 인스턴스에서 학습하려다 GPU OOM에 부딪혔다. 데이터 병렬로 노드를 늘려도 복제본이 여전히 한 GPU에 안 들어가 소용없었다. SMP의 모델 병렬+샤딩으로 파라미터·옵티마이저 상태를 GPU 간에 분산하자 메모리에 들어갔고, 노드 간엔 EFA를, 데이터 공급엔 FSx for Lustre를 붙여 학습 시간을 크게 줄였다. 교훈: OOM은 GPU 추가(데이터 병렬)가 아니라 모델 병렬로 푼다.

## 어떻게 고르는가

판단 흐름: ① 모델이 한 GPU에 들어가는가? 들어가는데 느리다 → **데이터 병렬**(GPU/노드 추가, SMDDP). ② 안 들어간다(OOM) → **모델 병렬/샤딩**(SMP). ③ 둘 다 → 하이브리드. 추가로 데이터 로딩이 병목이면 FSx for Lustre, 노드 간 통신이 병목이면 EFA. "더 빨리"는 데이터 병렬, "안 들어가서"는 모델 병렬이라는 매핑이 핵심이다.

## 정리하며

분산 학습은 "무엇을 쪼개느냐"로 갈린다. **데이터 병렬**은 데이터를 GPU마다 나눠 각자 모델 복제본으로 학습 후 그래디언트를 all-reduce로 평균하며, 학습 속도(처리량) 문제를 푼다(SMDDP). **모델 병렬**은 모델 자체를 여러 GPU에 분할·샤딩해 한 GPU 메모리에 안 들어가는 초대형 모델을 학습한다(SMP). 인프라로는 노드 간 통신에 EFA, 데이터 공급에 FSx for Lustre가 붙는다. 시험에서 "OOM/모델이 큼"은 모델 병렬, "느림/데이터 큼"은 데이터 병렬이다.

다음 글에서는 학습이 잘 돌아가는지, 어디서 느려지고 어디서 망가지는지 들여다보는 디버깅·프로파일링을 본다.

## 📝 연습 문제

**문제 1.** 학습할 모델은 단일 GPU 메모리에 충분히 들어가지만, 데이터셋이 매우 커서 한 GPU로는 학습이 며칠 걸린다. 가장 적합한 분산 전략은?

A) 모델 병렬로 모델을 여러 GPU에 분할  
B) 데이터 병렬로 여러 GPU/노드에 배치를 분배하고 그래디언트를 all-reduce  
C) 배치 크기를 1로 줄인다  
D) 학습을 CPU로 옮긴다  

**정답: B**  
해설: 모델이 GPU에 들어가는데 느린 경우는 처리량 문제이므로 데이터 병렬로 여러 장비에 데이터를 분배해 거의 선형으로 속도를 높인다. A는 모델이 안 들어갈 때 쓰는 전략이라 불필요하고, C는 오히려 느려지며, D는 GPU 가속을 버리는 잘못된 선택이다.

---

**문제 2.** 70억 파라미터 모델을 학습하려는데 단일 GPU에서 메모리 부족(OOM)이 발생한다. 데이터 병렬로 노드를 추가해도 해결되지 않는다. 근본 해결책은?

A) 데이터 병렬 GPU 수를 두 배로 늘린다  
B) SageMaker 모델 병렬(SMP)로 모델 파라미터·옵티마이저 상태를 여러 GPU에 분할·샤딩한다  
C) 학습률을 낮춘다  
D) 에폭 수를 줄인다  

**정답: B**  
해설: OOM은 모델 복제본 자체가 한 GPU에 안 들어가는 문제로, 데이터 병렬은 각 GPU에 전체 복제본을 두므로 해결되지 않는다. 모델 병렬/샤딩으로 모델을 GPU 간에 나눠야 한다. A는 같은 OOM이 반복되고, C·D는 메모리 사용량과 무관하다.

**문제 3.** 데이터 병렬에서 GPU 수를 늘려 유효 배치 크기가 커졌다. 이때 흔히 함께 조정해야 하는 것은?

A) 모델 아키텍처  
B) 학습률(예: 배치 증가에 맞춰 스케일링)  
C) S3 버킷 리전  
D) IAM 역할  

**정답: B**  
해설: 데이터 병렬로 유효 배치가 커지면 학습률을 그대로 두면 수렴이 나빠질 수 있어 보통 학습률을 함께 조정(linear scaling 등)한다. A는 분산 전략과 무관하게 바꿀 이유가 없고, C·D는 학습 수렴과 관계없는 설정이다.

**문제 4.** 다수 GPU 노드 간 all-reduce 통신이 병목이 되어 분산 학습 확장 효율이 떨어진다. AWS에서 노드 간 저지연 고대역 통신을 제공하는 것은?

A) Elastic Fabric Adapter (EFA)  
B) Amazon SQS  
C) CloudFront  
D) Route 53  

**정답: A**  
해설: EFA는 HPC·분산 학습용 저지연 고대역 네트워크 인터페이스로, p4d/p5 등에서 노드 간 all-reduce 통신 병목을 줄인다. B는 메시지 큐, C는 CDN, D는 DNS로 모두 분산 학습의 GPU 간 통신과 무관하다.

**문제 5.** 대용량 학습 데이터를 여러 GPU 노드에 고처리량으로 공급해 데이터 로딩 병목을 줄이려 한다. 적합한 서비스는?

A) S3에서 매 스텝마다 단건 GET  
B) FSx for Lustre 고성능 병렬 파일시스템으로 S3 데이터를 캐시·공급  
C) DynamoDB 테이블 스캔  
D) EBS 단일 볼륨을 한 노드에만 부착  

**정답: B**  
해설: FSx for Lustre는 S3와 연동되는 고처리량 병렬 파일시스템으로 대규모 학습 데이터를 여러 노드에 빠르게 공급해 로딩 병목을 줄인다. A는 단건 호출로 처리량이 낮고, C는 분석용 NoSQL로 부적합하며, D는 단일 노드 전용이라 분산 공급이 안 된다.
