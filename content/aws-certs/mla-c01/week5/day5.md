# Day 5 - Week 5 종합: 모델 개발 2 복습

## 📌 핵심 정리

- Week 5의 관통 원리 — **필요한 만큼만 내려가고, 증상에 맞는 도구·지표를 고른다.**
- **커스텀 학습**: 스크립트 모드 → requirements 확장 → BYOC. "최소 노력"이면 위쪽, "시스템 의존성"이면 BYOC.
- **분산 학습**: 느리다 → 데이터 병렬(SMDDP) / OOM → 모델 병렬·샤딩(SMP). **OOM을 GPU 추가로 풀면 오답.**
- **관측**: 모델 이상 → Debugger(+`StopTraining` 액션) / 자원 비효율 → Profiler / 전반 알람 → CloudWatch.
- **평가**: 불균형이면 정확도 금지(F1·재현율·AUC-PR), 큰 오차 중요하면 RMSE, 학습-검증 격차는 과적합.

## 한 장으로 보는 Week 5

이번 주는 "내 코드로 학습하고, 크게 학습하고, 학습을 들여다보고, 결과를 제대로 평가한다"는 모델 개발의 두 번째 절반이었다.

```
[커스텀 학습]      내 코드를 어디까지 가져오나
   스크립트 모드 → requirements 확장 → BYOC

[분산 학습]        무엇을 쪼개나
   데이터 병렬(느림) ↔ 모델 병렬(안 들어감)

[디버깅·프로파일링] 학습 안을 들여다본다
   Debugger(모델 텐서) ↔ Profiler(자원)

[모델 평가]        결과가 정말 좋은가
   지표 선택 + 과적합 진단 + 교차검증
```

- 커스텀 학습은 "최소 노력" 쪽(스크립트 모드)을 기본으로 두고 **필요한 만큼만 아래로** 내려간다.
- 분산은 **증상**(느림 vs OOM)으로, 관측은 **관심사**(모델 vs 자원)로, 평가는 **문제 성격**(불균형·이상치)으로 갈린다.

```text
                            그리고 끝난 뒤 ──► 평가: 지표 선택 · 과적합 · 교차검증
```

## 커스텀 학습 복습

"내 코드를 어디까지 가져오느냐"의 스펙트럼이다.

| 방식 | 가져오는 것 | 적합 상황 |
|------|-----------|----------|
| 스크립트 모드 | train.py | 표준 PyTorch/TF 코드, 최소 노력 |
| requirements 확장 | train.py + 파이썬 패키지 | 추가 pip 패키지만 필요 |
| BYOC | Docker 이미지 전체 | 시스템 패키지·특수 런타임 |

기억할 규약: 데이터는 `SM_CHANNEL_<채널명>`, 모델 저장은 `SM_MODEL_DIR`(`/opt/ml/model`). BYOC는 `/opt/ml/input/data/<채널명>/` 입력, `train` 실행 규약.

| 규약 | 값 | 어기면 생기는 일 |
|------|----|----------------|
| 입력 데이터 | `/opt/ml/input/data/<채널명>/` | 학습 스크립트에서 파일을 못 찾는다 |
| 모델 저장 | `/opt/ml/model` (`SM_MODEL_DIR`) | 학습은 성공하는데 S3에 산출물이 없다 |
| 하이퍼파라미터 | `/opt/ml/input/config/hyperparameters.json` | 값이 기본값으로만 돌아간다 |
| 실행 규약(BYOC) | 컨테이너를 `train` 인자로 실행 | 작업이 즉시 실패한다 |

입력 모드도 함께 기억한다 — **File**(전부 복사 후 시작) / **Pipe**(스트리밍) / **FastFile**(필요할 때 지연 로딩). 시작 지연이 문제면 FastFile·Pipe를 검토한다.

> 💡 **관련 이론**: 이 계층은 관심사 분리다. 학습 로직과 실행 환경을 분리해, 환경이 표준이면 코드만 갈아끼우고(스크립트 모드) 환경이 특수할 때만 환경을 직접 만든다(BYOC). 시험이 "최소 노력"을 강조하면 위쪽을, "시스템 의존성/미지원 프레임워크"를 말하면 아래쪽을 고른다.

## 분산 학습 복습

"무엇을 쪼개느냐"로 갈린다.

- **데이터 병렬**: 데이터를 GPU마다 나누고 모델 복제본으로 학습 후 그래디언트 all-reduce 평균. 해결하는 문제 = **속도(처리량)**. SMDDP. 주의: 유효 배치 증가 → 학습률 조정.
- **모델 병렬**: 모델 자체를 GPU에 분할·샤딩. 해결하는 문제 = **OOM(모델이 안 들어감)**. SMP.
- **인프라**: 노드 간 통신 = EFA, 데이터 공급 = FSx for Lustre.

| 병렬 축 | 쪼개는 대상 | 얻는 것 | 어디서 쓰나 |
|---------|-----------|--------|------------|
| 데이터 병렬 | 배치 | 처리량 | 노드 간(all-reduce만 오가면 됨) |
| 텐서 병렬 | 한 레이어의 연산 | 메모리 | 노드 안(통신이 매우 잦음) |
| 파이프라인 병렬 | 레이어 묶음 | 메모리 | 노드 안/간, 단 유휴(버블) 발생 |
| 샤딩(ZeRO/FSDP) | 파라미터·그래디언트·옵티마이저 상태 | 메모리 | 메모리가 크게 모자랄 때 |

OOM이 "조금 모자란" 수준이면 병렬화 전에 **혼합 정밀도 · 배치 축소 + 그래디언트 누적 · 활성값 체크포인팅**부터 시도한다.

> ⚠️ **함정**: OOM을 데이터 병렬(GPU 추가)로 풀려는 보기는 오답이다. 데이터 병렬은 각 GPU에 전체 복제본을 두므로 모델이 안 들어가면 GPU를 늘려도 똑같이 OOM이다. OOM은 모델 병렬/샤딩으로 푼다. 반대로 "느리다"는 데이터 병렬이다.

## 디버깅·프로파일링 복습

학습 내부를 두 관점으로 본다.

| 도구 | 보는 것 | 대표 증상 |
|------|--------|----------|
| Debugger | 모델 텐서(그래디언트·손실·가중치) | 그래디언트 소실/폭발, 손실 정체, 과적합 |
| Profiler | 시스템 자원(GPU/CPU·I/O) | GPU 저활용, 데이터 로딩·CPU 병목 |
| CloudWatch | 전반 메트릭·로그·알람 | 운영 모니터링 |

기억할 점: Debugger 규칙은 기본적으로 감지·보고만 하고, 자동 중단하려면 **action(StopTraining)**을 붙여야 한다. GPU 저활용은 데이터 파이프라인(worker 증가, FSx 캐시, 프리페치)으로 푼다.

증상에서 도구·조치까지 한 줄로 잇는 연습이 시험에 그대로 나온다.

| 증상 | 도구 | 조치 |
|------|------|------|
| 손실이 몇 천 스텝째 그대로 | Debugger `loss_not_decreasing` | 학습률·데이터 점검, `StopTraining`으로 비용 차단 |
| 손실이 `NaN`이 됨 | Debugger `exploding_tensor` | 학습률↓, 그래디언트 클리핑, 입력 정규화 |
| 검증 손실만 다시 상승 | Debugger `overfit` | 정규화·증강·조기 종료 |
| GPU 활용률 25% | Profiler | 로더 워커↑, FSx 캐시, 프리페치 |
| CPU만 100%로 붙어 있음 | Profiler | 전처리 사전 배치화·경량화 |
| 여러 학습 작업의 손실을 비교하고 싶다 | CloudWatch + `metric_definitions` | 로그에서 정규식으로 지표 추출 |
| 실패 시 즉시 알림을 받고 싶다 | CloudWatch 알람 / EventBridge | SNS·Lambda로 후속 자동화 |

> 💡 **관련 이론**: Debugger는 모델이라는 수학적 프로세스의 내부 상태를, Profiler는 그 프로세스가 도는 물리 자원의 사용 패턴을 본다. 두 층위를 함께 봐야 "왜 학습이 안 되나"와 "왜 비싼가"를 동시에 푼다.

## 모델 평가 복습

"문제에 맞는 지표"로 "일반화"를 잰다.

- **분류**: 혼동행렬 → 정밀도(거짓경보 억제)·재현율(놓침 방지)·F1·AUC. **불균형이면 정확도 금지**, F1·재현율·AUC-PR.
- **회귀**: RMSE(큰 오차 민감)·MAE(이상치 둔감)·R².
- **과적합**: 학습-검증 격차로 진단 → 정규화·드롭아웃·증강·조기 종료.
- **교차검증**: k-fold로 평가 분산↓. 불균형 = stratified, 시계열 = time-series split.
- **누수 점검**: 전처리는 반드시 **분할 이후 학습 세트 기준**으로. 점수가 비현실적으로 높으면 과적합보다 누수를 먼저 의심한다.

| 시나리오 문장의 신호 | 골라야 할 지표 |
|---------------------|---------------|
| "사기가 1%", "희귀 질병", "놓치면 안 됨" | 재현율 · AUC-PR (정확도 금지) |
| "정상 사용자를 잘못 차단하면 안 됨" | 정밀도 |
| "정밀도와 재현율 모두 중요" | F1 |
| "가끔 발생하는 큰 오차가 치명적" | RMSE |
| "이상치가 많아 영향을 줄이고 싶다" | MAE |
| "데이터가 적어 평가가 들쭉날쭉" | k-fold 교차검증 |

> 📚 **사례**: 한 팀이 "정확도 98%" 사기 탐지 모델을 자랑했지만 실제로는 사기를 거의 못 잡았다(불균형). 재현율을 보니 12%였다. 평가 지표를 F1·재현율로 바꾸고 stratified k-fold로 검증한 뒤, 임계값과 클래스 가중치를 조정해 재현율을 끌어올렸다. 교훈: 숫자 하나(정확도)에 속지 말고 문제 성격에 맞는 지표로 본다.

## 종합 의사결정 흐름

이번 주 전체를 하나의 판단 트리로 묶으면:

```
학습할 때
 ├─ 내 코드 종류?  표준 프레임워크 → 스크립트 모드
 │                 +파이썬 패키지 → requirements
 │                 +시스템 패키지 → BYOC
 ├─ 규모?          느림 → 데이터 병렬 / OOM → 모델 병렬
 └─ 문제 생기면    모델 이상 → Debugger / 자원 비효율 → Profiler

평가할 때
 ├─ 분류?  불균형 → F1·재현율·AUC / 균형 → 정확도 가능
 ├─ 회귀?  큰 오차 중요 → RMSE / 이상치 둔감 → MAE
 ├─ 일반화?  학습-검증 격차 크면 과적합 → 정규화·증강·조기종료
 └─ 데이터 적음?  k-fold 교차검증 (불균형=stratified, 시계열=time-split)
```

## 한 코드 안에서 다시 보기

이번 주에 나온 설정들이 실제로는 하나의 Estimator에 함께 붙는다. 각 인자가 어느 주제에서 왔는지 확인하며 읽는다.

```python
from sagemaker.pytorch import PyTorch
from sagemaker.debugger import Rule, rule_configs

estimator = PyTorch(
    entry_point='train.py', source_dir='src', role=role,   # ← 커스텀 학습(스크립트 모드)
    framework_version='2.0', py_version='py310',
    instance_type='ml.p4d.24xlarge', instance_count=2,
    distribution={'torch_distributed': {'enabled': True}},  # ← 분산 학습
    rules=[Rule.sagemaker(                                  # ← 관측(Debugger)
        rule_configs.loss_not_decreasing(),
        actions=rule_configs.ActionList(rule_configs.StopTraining())
    )],
    metric_definitions=[                                    # ← 관측(CloudWatch 지표)
        {'Name': 'validation:f1', 'Regex': r'val_f1: ([0-9\.]+)'}
    ],
    enable_sagemaker_metrics=True,
    use_spot_instances=True, max_run=86400, max_wait=172800,
    checkpoint_s3_uri='s3://my-bucket/ckpt/',               # ← 비용·생존성
)
estimator.fit({'training': 's3://my-bucket/train/'})
```

- `val_f1`을 지표로 올려 두면, 평가에서 고른 지표가 그대로 모니터링·튜닝 목표가 된다.
- 스팟과 체크포인트는 한 세트, 규칙과 액션도 한 세트다. 한쪽만 켜면 효과가 없다.

## 자주 걸리는 오답 패턴

| 그럴듯한 오답 | 왜 틀렸나 |
|--------------|----------|
| OOM인데 데이터 병렬 GPU를 늘린다 | 각 GPU에 전체 복제본이 그대로 올라가 OOM이 반복된다 |
| `requirements.txt`에 apt 패키지 이름을 적는다 | pip는 파이썬 패키지만 설치한다 → BYOC 필요 |
| Debugger 규칙만 등록하면 알아서 멈춘다 | 규칙은 감지·보고까지. 중단은 action의 몫이다 |
| 학습이 느리니 더 비싼 GPU로 바꾼다 | GPU가 이미 놀고 있으면 노는 시간만 비싸진다 |
| 시스템 의존성이 없는데 BYOC로 간다 | 불필요한 Docker 빌드·유지보수 부담 |
| 불균형 데이터에서 정확도 99%를 근거로 든다 | "전부 음성"만 찍어도 나오는 숫자다 |
| 스팟만 켜고 체크포인트는 안 건다 | 중단될 때마다 처음부터 → 절감이 재학습 비용에 잡아먹힌다 |
| 무작위 k-fold를 시계열 데이터에 쓴다 | 미래 정보가 학습에 흘러 평가가 부풀려진다 |

다음 주에는 학습한 모델을 실제로 서비스에 올리는 모델 배포와 추론을 다룬다.

## 📖 용어

- **스크립트 모드** : 학습 스크립트만 넘기고 실행 환경은 AWS 컨테이너에 맡기는 방식. 이번 주의 기본값.
- **BYOC** : Docker 이미지를 직접 만들어 ECR에 올려 쓰는 방식. 시스템 패키지·특수 런타임이 필요할 때만.
- **`SM_MODEL_DIR`** : 컨테이너 안 `/opt/ml/model`. 여기 저장한 것만 S3로 올라간다.
- **데이터 병렬 / 모델 병렬** : 데이터를 쪼개 빨라지는 방식 / 모델을 쪼개 메모리에 넣는 방식.
- **샤딩** : 파라미터·그래디언트·옵티마이저 상태를 GPU들에 나눠 보관해 메모리를 줄이는 기법.
- **EFA / FSx for Lustre** : 노드 간 저지연 네트워크 / 대용량 데이터를 빠르게 공급하는 병렬 파일시스템.
- **Debugger 액션 / Profiler** : Debugger 액션은 규칙 위반 시 실행할 조치로, `StopTraining`으로 비용이 새는 학습을 끊는다. Profiler는 GPU·CPU·I/O가 각각 얼마나 바쁜지 측정해 병목을 찾아 주는 도구다.
- **`metric_definitions`** : 학습 로그에서 정규식으로 숫자를 뽑아 CloudWatch 지표로 올리는 설정.
- **AUC-PR** : 정밀도-재현율 곡선의 면적. 양성이 매우 드문 데이터에서 ROC-AUC보다 정직한 지표.
- **데이터 누수** : 평가 시점에 알 수 없어야 할 정보가 학습에 섞여 점수가 부풀려지는 현상.

## 📝 연습 문제

**문제 1.** PyTorch 학습 코드를 SageMaker에서 최소 노력으로 돌리려는데 추가로 transformers 파이썬 패키지만 필요하다. 시스템 패키지는 없다. 가장 적합한 방식은?

A) BYOC로 Docker 이미지를 직접 빌드  
B) 스크립트 모드 + source_dir의 requirements.txt에 transformers 추가  
C) 내장 알고리즘으로 전환  
D) 모델 병렬을 활성화  

**정답: B**  
해설: 표준 프레임워크에 파이썬 패키지만 추가하면 되므로 스크립트 모드에 requirements.txt로 충분하며 Docker가 필요 없다. A는 시스템 의존성이 없는데 과한 작업이고, C는 자체 코드를 못 쓰며, D는 분산 전략으로 패키지 추가와 무관하다.

**문제 2.** 수십억 파라미터 모델이 단일 GPU 메모리에 들어가지 않아 OOM이 난다. 데이터 병렬로 노드를 늘려도 같은 OOM이 반복된다. 올바른 해결책은?

A) 데이터 병렬 GPU 수를 더 늘린다  
B) SageMaker 모델 병렬(SMP)로 모델을 GPU 간에 분할·샤딩한다  
C) 배치 크기를 키운다  
D) Profiler를 활성화하면 OOM이 사라진다  

**정답: B**  
해설: OOM은 모델 복제본이 한 GPU에 안 들어가는 문제이므로 모델 병렬/샤딩으로 모델을 GPU 간에 나눠야 하며, 데이터 병렬은 전체 복제본을 각 GPU에 두므로 해결되지 않는다. A는 같은 OOM 반복, C는 메모리를 더 쓰고, D는 진단 도구일 뿐 메모리를 늘려주지 않는다.

**문제 3.** Debugger의 loss_not_decreasing 규칙이 손실 정체를 감지했지만 학습이 끝까지 돌며 비용만 발생했다. 자동 중단으로 비용을 막으려면?

A) 규칙만 더 추가한다  
B) 규칙에 StopTraining action을 연결한다  
C) Profiler로 전환한다  
D) instance_type을 더 큰 것으로 바꾼다  

**정답: B**  
해설: Debugger 규칙은 기본적으로 감지·보고만 하므로 자동 중단하려면 StopTraining 등의 action을 명시적으로 연결해야 한다. A는 규칙을 늘려도 여전히 보고만 하고, C는 자원 분석 도구라 학습 중단과 무관하며, D는 비용을 오히려 늘린다.

**문제 4.** 거래의 0.5%만 사기인 불균형 데이터에서 모델이 "정확도 99.5%"로 보고됐다. 평가에 대한 올바른 판단은?

A) 정확도 99.5%이므로 우수한 모델이다  
B) 불균형 때문에 정확도가 왜곡될 수 있으므로 F1·재현율·AUC-PR로 다시 평가한다  
C) 회귀 지표 RMSE로 평가한다  
D) 교차검증은 불필요하다  

**정답: B**  
해설: 0.5% 양성 불균형에서는 "전부 정상" 예측만으로도 99.5% 정확도가 나오므로 정확도는 신뢰할 수 없고 F1·재현율·AUC-PR로 희귀 양성 탐지력을 봐야 한다. A는 정확도 함정에 빠진 것이고, C는 분류에 회귀 지표를 쓴 오류이며, D는 안정적 평가를 포기하는 잘못된 판단이다.

**문제 5.** ml.p4d 인스턴스로 학습하는데 학습이 예상보다 느리고 GPU 활용률이 낮다. 원인 진단과 1차 개선 방향으로 가장 적절한 것은?

A) Debugger의 vanishing_gradient 규칙으로 그래디언트를 본다  
B) Profiler로 병목을 진단하고, 데이터 로딩 병목이면 DataLoader worker 증가·FSx 캐시·프리페치로 개선한다  
C) 모델 병렬을 무조건 활성화한다  
D) 학습률을 10배 올린다  

**정답: B**  
해설: GPU 저활용·느린 학습은 자원 효율 문제이므로 Profiler로 병목을 찾고, 데이터 로딩 병목이면 데이터 공급 파이프라인을 개선해 GPU 활용률을 높인다. A는 모델 텐서를 보는 도구로 활용률과 무관하고, C는 OOM이 아닌데 과한 조치이며, D는 수렴 동작만 바꿔 활용률 개선과 무관하다.
