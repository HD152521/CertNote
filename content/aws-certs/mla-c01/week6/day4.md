# Day 4 - 배치·서버리스 추론 심화: 대량 처리 튜닝과 비용 트레이드오프

## 📌 핵심 정리

- 배치와 서버리스는 **always-on 비용 0**을 공유하지만 용도가 정반대다 — 대량 일괄 vs 간헐 개별 요청.
- 배치 처리량 레버는 **InstanceCount(병렬) · SplitType(분할) · BatchStrategy/MaxPayload/MaxConcurrentTransforms(미니배치)**.
- 입력이 **분할 가능해야** 인스턴스를 늘린 효과가 난다. 단일 대용량 파일은 아무리 늘려도 안 빨라진다.
- 예측을 원본 ID와 매칭하려면 `input_filter`/`output_filter`/`join_source`를 쓴다.
- 서버리스는 `MemorySize` + `MaxConcurrency`만 지정. 콜드 스타트는 **Provisioned Concurrency**로 완화(상시 비용 발생).

## 배치 변환 — 대량 처리 튜닝

동기 엔드포인트의 반대편에 있는 두 가지, **배치 변환**과 **서버리스 추론**을 깊이 판다. 먼저 배치 변환은 S3의 대량 입력을 읽어 일괄 추론하고 결과를 S3에 쓴다. 처리량을 높이는 레버는 세 가지다.

- **InstanceCount**: 인스턴스를 늘리면 데이터가 분산되어 병렬 처리. 가장 직접적인 수평 확장.
- **데이터 분할(SplitType)**: `Line`(레코드 줄 단위), `RecordIO`, `TFRecord` 등으로 큰 파일을 레코드 단위로 쪼개 여러 인스턴스/배치에 분배.
- **미니배치(BatchStrategy, MaxPayloadInMB, MaxConcurrentTransforms)**: 한 번에 모델에 보내는 레코드 묶음 크기와 동시 요청 수를 조절.

```text
배치 변환의 병렬 분산 구조

 S3 입력 (여러 파일 또는 분할 가능한 포맷)
   part-000.csv  part-001.csv  part-002.csv  part-003.csv
        │             │             │             │
        ▼             ▼             ▼             ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ 인스턴스1│  │ 인스턴스2│  │ 인스턴스3│  │ 인스턴스4│   ← instance_count=4
   └─────────┘  └─────────┘  └─────────┘  └─────────┘
        │             │             │             │
        └─────────────┴──────┬──────┴─────────────┘
                             ▼
                       S3 출력 (.out)
                             │
                             ▼
                    작업 종료 → 클러스터 전부 삭제(비용 0)

 ⚠ 입력이 분할 불가능한 단일 거대 파일이면 인스턴스1만 일하고 나머지는 논다.
```

```python
from sagemaker.transformer import Transformer

transformer = Transformer(
    model_name="churn-model",
    instance_count=8,                 # 8대로 병렬 처리
    instance_type="ml.m5.xlarge",
    strategy="MultiRecord",           # 여러 레코드를 한 미니배치로
    max_payload=6,                    # 미니배치 최대 6MB
    max_concurrent_transforms=4,      # 인스턴스당 동시 요청 4
    output_path="s3://bkt/out/",
)
transformer.transform(
    data="s3://bkt/in/",
    content_type="text/csv",
    split_type="Line",                # 줄 단위 분할
)
```

파라미터별로 무엇을 조절하는지 정리하면 다음과 같다.

| 파라미터 | 조절 대상 | 올리면 | 주의 |
|----------|-----------|--------|------|
| `instance_count` | 병렬도(수평 확장) | 처리 시간 단축 | 비용도 비례 증가. 분할 가능해야 효과 |
| `split_type` | 입력을 어떻게 쪼갤지 | `Line` 등으로 분산 가능해짐 | `None`이면 파일 단위로만 분배된다 |
| `strategy` | 한 요청에 담는 레코드 수 | `MultiRecord`로 오버헤드 감소 | 모델이 단건만 받으면 `SingleRecord` |
| `max_payload` | 미니배치 최대 크기(MB) | 요청당 처리량 증가 | 너무 크면 모델 메모리 초과 |
| `max_concurrent_transforms` | 인스턴스당 동시 요청 수 | 인스턴스 활용률 상승 | 과하면 컨테이너가 밀린다 |

- `strategy="MultiRecord"`는 여러 레코드를 한 요청으로 묶어 처리량을 높이고, `SingleRecord`는 한 번에 한 레코드만 보낸다(모델이 단건 입력만 받을 때).
- `split_type`은 `None`(파일 통째) · `Line`(줄 단위) · `RecordIO` · `TFRecord` 중에서 입력 포맷에 맞춰 고른다.

> 💡 **관련 이론**: 배치 변환의 처리량은 결국 "병렬도 × 인스턴스당 효율"이다. 인스턴스 수를 늘리면 선형에 가깝게 빨라지지만 비용도 비례해 늘고, 데이터가 여러 파일로 나뉘어 있거나 `SplitType`으로 쪼갤 수 있어야 분산이 효과를 본다. 입력이 거대한 단일 파일이고 분할 불가하면 한 인스턴스가 다 떠안아 확장이 안 된다. 그래서 배치 입력은 **여러 파일로 샤딩**하거나 줄 단위 분할이 가능한 포맷으로 두는 것이 튜닝의 시작이다.

> ⚠️ **함정**: 배치 변환은 입력 레코드와 출력 예측을 다시 연결(join)하는 것이 까다로울 수 있다. 입력 ID와 예측을 함께 출력하려면 `input_filter`/`output_filter`/`join_source` 파라미터(JSONPath)로 입력 일부를 출력에 합쳐야 한다. "예측 결과를 원본 레코드와 어떻게 매칭하느냐"는 실무·시험 단골 함정이다.

## 입력 ID와 예측 결과 결합하기

모델에는 ID 열을 넣으면 안 되지만, 출력에는 ID가 있어야 쓸모가 있다. 이 모순을 필터 파라미터로 푼다.

```python
transformer.transform(
    data="s3://bkt/in/",
    content_type="text/csv",
    split_type="Line",
    input_filter="$[1:]",        # 0번 열(고객 ID)을 빼고 모델에 전달
    join_source="Input",         # 입력 레코드를 출력에 다시 붙인다
    output_filter="$[0,-1]",     # 최종 출력은 [고객 ID, 예측값]만 남긴다
)
```

```text
입력  : [C1001, 34, 서울, 12.5]
         └ ID    └───── 피처 ─────┘

input_filter="$[1:]"   ─▶ 모델 입력: [34, 서울, 12.5]
모델 출력                ─▶ 예측: 0.87
join_source="Input"    ─▶ 결합: [C1001, 34, 서울, 12.5, 0.87]
output_filter="$[0,-1]"─▶ 최종: [C1001, 0.87]
```

## 배치 vs 실시간 — 언제 배치가 이득인가

같은 모델로 100만 건을 처리한다고 하자. 실시간 엔드포인트로 100만 번 호출하면 always-on 인스턴스 비용 + 호출 오버헤드가 들고, 트래픽 스파이크 관리도 해야 한다. 배치 변환은 클러스터를 잠깐 띄워 100만 건을 분산 처리하고 끝나면 종료해 비용이 처리 시간에만 발생한다.

> 🔍 **더 깊이**: 실시간 엔드포인트는 "요청당 즉시 응답"에 최적화되어 개별 요청 지연이 낮지만, 대량 일괄에서는 인스턴스를 계속 켜둔 채 순차/동시 호출을 받아야 해 비효율적이다. 배치는 "데이터 지역성 + 일괄 분산"으로 대량 처리량을 극대화한다. 정리하면 **즉시성이 필요 없는 대량 처리 = 배치가 거의 항상 저렴하고 빠르다**. 단 결과를 실시간으로 못 받으므로 즉시성이 조금이라도 필요하면 배치는 탈락이다.

## 서버리스 추론 — 동시성과 콜드 스타트

서버리스 추론은 지정할 것이 딱 두 개다.

- **MemorySizeInMB**(1024~6144): 메모리를 키우면 할당되는 컴퓨팅도 함께 커진다.
- **MaxConcurrency**: 동시에 처리할 최대 요청 수. 이를 넘는 요청은 스로틀링된다.
- 인스턴스 타입을 고르지 않는다 → **GPU를 쓸 수 없다**는 뜻이기도 하다.
- 트래픽이 오면 자동으로 컴퓨팅을 띄우고, 없으면 0으로 줄인다.

```python
from sagemaker.serverless import ServerlessInferenceConfig

serverless_config = ServerlessInferenceConfig(
    memory_size_in_mb=2048,   # 1024 ~ 6144
    max_concurrency=20,       # 동시 처리 최대 요청 수
)
predictor = model.deploy(serverless_inference_config=serverless_config)
```

문제는 **콜드 스타트**다. 한동안 호출이 없다가 첫 요청이 오면 컨테이너를 띄우고 모델을 로드하는 동안 지연이 발생한다.

```text
콜드 스타트 vs 워밍된 상태

[콜드]  요청 ─▶ │컨테이너 기동│모델 다운로드·로드│추론│ ─▶ 응답
                └─────────── 수 초 ────────────┘ ↑ 여기만 실제 추론

[워밍]  요청 ─▶ │추론│ ─▶ 응답            (밀리초~수백 ms)

Provisioned Concurrency = 지정한 수만큼을 "워밍" 상태로 붙잡아 두는 것
                          → 콜드 스타트 제거, 대신 그만큼 상시 비용 발생
```

일관된 저지연이 필요하면 **Provisioned Concurrency(프로비저닝된 동시성)**를 설정해 일정 수의 인스턴스를 미리 데워둘 수 있다. 단 이 경우 그만큼 상시 비용이 발생해 "완전 0 비용" 이점은 일부 사라진다.

> 💡 **관련 이론**: 서버리스의 비용 모델은 "처리한 요청의 컴퓨팅 시간 + (선택) Provisioned Concurrency 상시분"이다. 트래픽이 **드물수록** 0 스케일 덕에 실시간 대비 절감 폭이 크고, 트래픽이 **꾸준히 많을수록** 절감 이점이 사라지거나 역전된다. Provisioned Concurrency는 콜드 스타트를 없애지만 상시 비용을 부르므로, "간헐적 트래픽이지만 첫 응답 지연은 못 견딘다"는 절충 상황에서만 의미가 있다.

## 서버리스 vs 실시간 — 손익분기

직관적으로 잡으면, 엔드포인트가 대부분 유휴라면 서버리스가 싸고, 거의 항상 바쁘면 실시간이 싸다. 둘 사이 어딘가에 손익분기가 있다.

| 판단 축 | 서버리스가 유리 | 실시간이 유리 |
|---------|----------------|---------------|
| 트래픽 패턴 | 간헐적, 유휴 구간이 김 | 꾸준하거나 항상 높음 |
| 지연 SLA | 첫 응답 지연을 감수 가능 | 일관된 저지연이 필수 |
| 하드웨어 | CPU로 충분 | **GPU 필요**(서버리스는 불가) |
| 페이로드 | 4MB 이하 | 6MB 이하 |
| 운영 부담 | 인스턴스 관리 없음 | 스케일링·용량 계획 필요 |
| 비용 구조 | 처리 시간만 과금 | 가동 시간 전체 과금 |

> ⚠️ **함정**: "비용 절감 = 서버리스"라는 단순 매핑은 오답을 부른다. 서버리스가 유리한 조건은 ① 트래픽이 간헐적이고 ② 콜드 스타트를 감수할 수 있을 때다. 고정적으로 높은 트래픽에 서버리스를 쓰면 컴퓨팅 시간 과금이 누적되어 실시간보다 비싸질 수 있고, 콜드 스타트로 SLA를 못 맞춘다. 시험에서 트래픽 패턴(간헐 vs 꾸준)과 지연 SLA(콜드 스타트 허용 여부)를 먼저 확인하라.

## 비동기 추론과의 경계 다시 보기

배치·서버리스를 정리하다 보면 비동기와 헷갈리기 쉽다. 세 가지를 분리하자.

| 구분 | 배치 변환 | 서버리스 | 비동기 |
|------|-----------|----------|--------|
| 엔드포인트 | 없음(작업 단위) | 있음 | 있음 |
| 응답 방식 | S3에 결과 기록 | 동기 응답 | 큐 처리 후 S3 + SNS |
| 요청 단위 | 전체 데이터셋 | 개별 요청 | 개별 요청 |
| 페이로드 | 데이터셋 전체 | <4MB | <1GB |
| 처리시간 | 작업 단위(장시간 가능) | <60초 | <60분 |
| 유휴 비용 | 0(끝나면 종료) | 0(0 스케일) | 0(0 스케일) |
| 대표 신호 | "야간 일괄 점수화" | "가끔 호출, 유휴 많음" | "큰 파일, 몇 분 걸림" |

페이로드/처리시간이 서버리스 한계를 넘는 개별 요청은 비동기로, 즉시성이 없는 대량은 배치로 간다.

## 증상 → 원인 → 조치

| 증상 | 원인 | 조치 |
|------|------|------|
| 인스턴스를 8대로 늘렸는데 배치가 그대로 느리다 | 입력이 분할 불가능한 단일 대용량 파일 | 입력을 여러 파일로 샤딩 + `split_type="Line"` |
| 배치 중 모델 컨테이너가 메모리 부족으로 죽는다 | `max_payload`가 커서 미니배치가 과대 | `max_payload` 축소 또는 `SingleRecord`로 전환 |
| 출력 파일에 예측값만 있고 누구 것인지 모른다 | 입력 ID를 결합하지 않음 | `join_source="Input"` + `output_filter` 지정 |
| 서버리스 첫 요청만 수 초 걸린다 | 콜드 스타트 | Provisioned Concurrency 설정 |
| 서버리스에서 요청이 스로틀링된다 | 동시 요청이 `MaxConcurrency` 초과 | `MaxConcurrency` 상향, 호출 측 재시도·백오프 |
| 서버리스로 바꿨더니 비용이 더 늘었다 | 트래픽이 꾸준히 높아 처리 시간 과금 누적 | 실시간 + 오토스케일링으로 복귀 |
| GPU 모델을 서버리스로 못 올린다 | 서버리스는 GPU 미지원 | 실시간(GPU) 또는 비동기로 배포 |

## 📖 용어

- **배치 변환(Batch Transform)** : 엔드포인트 없이 S3의 대량 데이터를 한 번에 추론하고 끝나면 사라지는 작업.
- **샤딩(Sharding)** : 큰 데이터를 여러 조각으로 나눠 두는 것. 나눠 둬야 여러 인스턴스가 나눠 처리할 수 있다.
- **SplitType** : 입력을 어떤 단위로 쪼갤지 지정하는 옵션. 줄 단위(`Line`)가 가장 흔하다.
- **미니배치(BatchStrategy)** : 모델에 한 번에 보내는 레코드 묶음. 여러 건을 묶으면(`MultiRecord`) 오버헤드가 준다.
- **MaxConcurrentTransforms** : 인스턴스 한 대가 동시에 처리할 요청 수. 인스턴스 활용률을 좌우한다.
- **join_source** : 배치 출력에 원본 입력 레코드를 다시 붙여 주는 옵션. ID 매칭에 쓴다.
- **JSONPath 필터** : `$[1:]`처럼 레코드에서 특정 열만 골라내는 표기법. 입력·출력 필터에 쓴다.
- **MaxConcurrency** : 서버리스 엔드포인트가 동시에 처리할 최대 요청 수. 넘으면 스로틀링된다.
- **Provisioned Concurrency** : 서버리스에서 일정 수를 미리 워밍해 두는 설정. 콜드 스타트를 없애는 대신 상시 비용이 든다.
- **스로틀링(Throttling)** : 허용 한도를 넘은 요청을 서비스가 거절하거나 미루는 것.

## 📝 연습 문제

**문제 1.** 배치 변환 작업이 너무 느리다. 입력은 줄 단위 CSV로 여러 파일에 나뉘어 있다. 처리량을 높이는 가장 직접적인 방법은?

A) instance_count를 늘리고 split_type을 Line으로 설정해 데이터를 병렬 분산한다  
B) 실시간 엔드포인트로 전환한다  
C) max_concurrent_transforms를 0으로 설정한다  
D) 출력 포맷을 JSON으로 바꾼다  

**정답: A**  
해설: 배치 변환의 처리량은 인스턴스 수를 늘려 데이터를 여러 인스턴스에 병렬 분산할 때 가장 직접적으로 향상되며, `split_type=Line`으로 레코드 단위 분할이 가능해야 분산이 효과를 본다. B는 대량 일괄에 비효율적이고, C는 동시 요청을 막아 오히려 느려지며, D는 출력 포맷 변경으로 처리량과 무관하다.

**문제 2.** 서버리스 추론 엔드포인트가 한동안 호출이 없다가 첫 요청에서 응답이 느리다. 일관된 저지연이 필요하지만 트래픽은 여전히 간헐적이다. 적절한 조치는?

A) MaxConcurrency를 1로 줄인다  
B) Provisioned Concurrency를 설정해 일정 수 인스턴스를 미리 데워둔다  
C) 메모리를 1024MB로 낮춘다  
D) 배치 변환으로 전환한다  

**정답: B**  
해설: 콜드 스타트로 인한 첫 요청 지연은 Provisioned Concurrency로 일정 수의 인스턴스를 미리 워밍해두면 해소된다(상시 비용은 일부 발생). A는 동시성만 줄여 콜드 스타트와 무관하고, C는 메모리를 줄여 오히려 성능이 떨어질 수 있으며, D는 개별 요청 즉시 응답이 필요한 상황과 맞지 않는다.

**문제 3.** 100만 건의 누적 데이터를 모델로 점수화하는데 즉시성은 필요 없고 비용을 최소화하려 한다. 또 예측 결과를 원본 레코드의 고객 ID와 매칭해 출력해야 한다. 적절한 접근은?

A) 실시간 엔드포인트로 100만 번 호출  
B) 배치 변환을 쓰고 input_filter/output_filter/join_source로 입력 ID를 출력에 결합  
C) 서버리스 추론으로 100만 번 동기 호출  
D) 멀티모델 엔드포인트 사용  

**정답: B**  
해설: 즉시성 불필요 + 대량 + 비용 최소화는 배치 변환이 정답이고, 입력 ID와 예측을 매칭하려면 `input_filter`/`output_filter`/`join_source`로 입력 일부를 출력에 결합한다. A·C는 개별 호출 방식이라 대량 처리에 비효율적이고 비싸며, D는 다수 모델 서빙 기능으로 단일 모델 대량 점수화와 무관하다.

**문제 4.** 다음 중 서버리스 추론이 실시간 엔드포인트보다 비용상 유리한 조건으로 가장 적절한 것은?

A) 트래픽이 24시간 꾸준히 높을 때  
B) 트래픽이 간헐적이고 유휴 시간이 많으며 콜드 스타트를 감수할 수 있을 때  
C) 페이로드가 500MB로 매우 클 때  
D) 일관된 한 자릿수 밀리초 지연이 SLA로 요구될 때  

**정답: B**  
해설: 서버리스는 트래픽이 없으면 0으로 스케일되므로 유휴 시간이 많은 간헐적 트래픽에서 비용이 유리하며, 이때 콜드 스타트 허용이 전제다. A는 꾸준히 높은 트래픽이라 실시간이 더 유리하거나 서버리스가 역전되고, C는 서버리스 페이로드 한계(약 4MB)를 초과하며, D는 콜드 스타트 때문에 서버리스가 보장하기 어렵다.

**문제 5.** 배치 변환, 서버리스, 비동기 추론을 구분한 설명으로 가장 정확한 것은?

A) 셋 다 동기 응답을 즉시 반환한다  
B) 배치는 엔드포인트 없이 전체 데이터셋 일괄, 서버리스는 작은 페이로드 개별 동기 요청, 비동기는 큰 페이로드(1GB)·긴 처리(60분) 큐 기반이다  
C) 서버리스가 가장 큰 페이로드(1GB)를 지원한다  
D) 비동기는 엔드포인트 없이 작업 단위로만 동작한다  

**정답: B**  
해설: 배치 변환은 엔드포인트 없이 대량 일괄, 서버리스는 작은 페이로드(약 4MB)의 개별 동기 요청에 간헐 트래픽용, 비동기는 큰 페이로드(1GB)·긴 처리(60분)를 큐로 처리하는 방식으로 셋의 경계가 명확하다. A는 배치·비동기가 즉시 동기 응답이 아니므로 틀렸고, C는 1GB를 지원하는 것은 비동기이며, D는 비동기가 엔드포인트를 갖는다는 점에서 틀렸다(엔드포인트 없는 것은 배치).
