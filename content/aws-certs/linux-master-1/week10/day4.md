# Day 4 - 원격 GUI: VNC와 X 윈도 시스템의 클라이언트·서버 역전

지금까지 다룬 SSH는 텍스트 셸을 원격으로 다루는 방법이었다. 그러나 그래픽 환경(GUI)을 통째로 원격에서 쓰려면 다른 기술이 필요하다. 오늘은 화면을 그대로 전송하는 **VNC**와, 리눅스 GUI의 토대인 **X 윈도 시스템**을 다룬다. X 윈도의 핵심은 직관과 정반대인 **클라이언트-서버 역전** 개념이다. 이걸 똑바로 이해하지 못하면 실기에서 반드시 틀린다.

오늘의 핵심 통찰: **X 윈도 시스템에서 "서버"는 화면·키보드·마우스를 가진 사용자 앞의 기기이고, "클라이언트"는 그림을 그려달라고 요청하는 응용프로그램이다.** 우리의 상식("내 PC가 클라이언트, 멀리 있는 게 서버")과 정반대다. 이 역전을 받아들이는 것이 X 윈도 학습의 전부라 해도 과언이 아니다.

## 원격 데스크톱 — 화면을 통째로 전송하는 VNC

**VNC(Virtual Network Computing)**는 원격 컴퓨터의 화면을 그대로 내 화면에 띄우고, 내 키보드·마우스 입력을 원격으로 보내는 화면 공유 기술이다.

| 구성요소 | 역할 |
|----------|------|
| VNC 서버 | 원격(접속 대상) 컴퓨터에서 실행, 자기 화면을 전송 |
| VNC 뷰어(클라이언트) | 사용자 앞 컴퓨터에서 실행, 원격 화면을 표시·조작 |
| RFB 프로토콜 | VNC가 화면·입력을 주고받는 프로토콜 |

VNC는 화면 번호(display)마다 포트가 정해진다:

```text
VNC 기본 포트 = 5900 + 디스플레이 번호
  :0  → 5900
  :1  → 5901
  :2  → 5902
```

```bash
# 서버 측: TigerVNC 서버 설치·실행
dnf install tigervnc-server
vncserver :1                 # 디스플레이 1번(포트 5901)으로 서버 시작
vncpasswd                    # VNC 접속 비밀번호 설정
vncserver -kill :1           # 서버 종료

# 클라이언트 측: 뷰어로 접속
vncviewer 192.168.1.10:1     # 또는 192.168.1.10:5901
```

> ⚠️ **함정**: VNC 포트는 **5900 + 디스플레이 번호**다. `:1`은 5901, `:2`는 5902다. "디스플레이 1번이 5900"이라고 적은 보기는 틀렸다(그건 :0). 이 +번호 계산이 단골 출제 포인트다.

> 💡 **개념**: VNC는 RDP(윈도)와 같은 "화면 통째 전송" 방식이다. 화면의 픽셀을 압축해 보내므로, X 포워딩처럼 개별 창만 보내는 것과 달리 데스크톱 전체를 그대로 가져온다. 다만 VNC 자체는 암호화가 약하므로, 실무에서는 보통 **SSH 터널 위에 VNC를 실어** 안전하게 쓴다.

> 📚 **유래/사례**: VNC가 SSH 터널과 짝지어 쓰이는 이유는 RFB 프로토콜의 암호화가 빈약하기 때문이다. `ssh -L 5901:localhost:5901 user@host`로 터널을 뚫고 `vncviewer localhost:5901`로 접속하면, 픽셀 데이터가 SSH 암호화 터널을 지나 안전해진다. "VNC + SSH 터널"이 실무 표준 조합이다.

## X 윈도 시스템 — 리눅스 GUI의 토대

리눅스의 그래픽 환경은 **X 윈도 시스템(X11)**이라는 토대 위에 GNOME·KDE 같은 데스크톱 환경이 얹힌 구조다. X는 "그림 그리기"를 네트워크 프로토콜로 추상화한 점이 독특하다.

| 구성요소 | 역할 |
|----------|------|
| X 서버 | 화면·키보드·마우스 등 **하드웨어를 관리**, 그리기 요청을 받아 실제로 그림 |
| X 클라이언트 | 응용프로그램(터미널·브라우저 등), "이렇게 그려줘"라고 X 서버에 요청 |
| 윈도 매니저 | 창의 테두리·이동·최소화 등 창 관리(클라이언트의 일종) |
| 디스플레이 매니저 | 그래픽 로그인 화면(gdm, lightdm) 제공 |

### 클라이언트-서버 역전 — 가장 중요한 개념

```text
[사용자 앞 모니터·키보드 = X 서버] ←─ 그리기 요청 ─ [응용프로그램 = X 클라이언트]
        (화면을 가진 쪽이 서버)                      (그림을 부탁하는 쪽이 클라이언트)
```

상식과 정반대다. 화면·입력장치(하드웨어)를 가진 사용자 앞 기기가 **X 서버**이고, 멀리서든 가까이서든 "이 창을 그려줘"라고 요청하는 응용프로그램이 **X 클라이언트**다.

> 🔍 **핵심 구분**: 왜 역전됐나? X 서버는 "그리기 서비스를 제공하는 쪽"이고, 응용프로그램은 그 서비스를 "이용하는 쪽(클라이언트)"이기 때문이다. 서비스를 제공하는 게 서버라는 일반 원칙에는 충실하다 — 다만 "제공하는 서비스 = 화면 그리기"라는 점만 이해하면 된다. "화면 가진 쪽 = X 서버"가 정답 신호다.

> ⚠️ **함정**: "원격 서버에서 실행한 프로그램이 X 서버"라는 보기는 틀렸다. 원격에서 돌더라도 응용프로그램은 항상 **X 클라이언트**이고, 그 그림이 표시되는 내 앞 화면이 **X 서버**다. 이 역전을 뒤집은 보기가 시험의 단골 함정이다.

## DISPLAY 환경변수 — 어디에 그릴지 지정

X 클라이언트는 어느 X 서버(어느 화면)에 그릴지 **DISPLAY 환경변수**로 안다.

```text
DISPLAY 형식 = 호스트:디스플레이번호.화면번호
  :0           → 로컬 0번 디스플레이
  :0.0         → 로컬 0번 디스플레이의 0번 모니터
  192.168.1.5:0 → 원격 호스트 192.168.1.5의 0번 디스플레이
```

```bash
# 현재 DISPLAY 확인
echo $DISPLAY
# :0

# 원격 X 서버로 출력하도록 지정(원격 디스플레이에 그림)
export DISPLAY=192.168.1.5:0
xclock                       # 이제 192.168.1.5의 화면에 시계가 뜸
```

> 💡 **개념**: DISPLAY는 X 클라이언트에게 "그 그림을 어느 화면으로 보낼까"를 알려주는 주소다. 로컬이면 `:0`, 원격 화면에 띄우려면 `호스트:0`을 지정한다. SSH X11 포워딩(`ssh -X`)을 쓰면 이 DISPLAY가 자동으로 `localhost:10.0` 같은 값으로 설정돼 터널을 통해 안전하게 전달된다.

> 🔍 **핵심 구분**: DISPLAY가 `:0`이면 로컬, `호스트명:0`이면 원격이다. SSH X11 포워딩에서는 보통 `localhost:10.0`처럼 10번대 디스플레이가 잡히는데, 이는 SSH가 터널 끝에 가상 X 디스플레이를 만들어 연결하기 때문이다. "DISPLAY = 그림 보낼 화면 주소"로 기억하라.

## xhost와 xauth — X 서버 접근 제어

아무나 내 화면에 창을 띄우면 곤란하므로, X 서버는 접근 제어 메커니즘을 둔다. 두 방식을 구분해야 한다.

| 도구 | 방식 | 설명 |
|------|------|------|
| xhost | 호스트 기반 | 특정 호스트(IP) 단위로 X 서버 접근 허용/차단 |
| xauth | 쿠키 기반 | 매직 쿠키(MIT-MAGIC-COOKIE)로 사용자 단위 인증 |

```bash
# xhost — 호스트 단위 제어
xhost +192.168.1.5      # 이 호스트의 X 접근 허용
xhost -192.168.1.5      # 이 호스트 차단
xhost +                 # 모든 호스트 허용(위험! 보안 취약)
xhost -                 # 기본 인증으로 복귀
xhost                   # 현재 접근 목록 확인

# xauth — 매직 쿠키 기반 제어
xauth list              # 현재 등록된 인증 쿠키 목록
xauth add ...           # 쿠키 추가
```

> ⚠️ **함정**: `xhost +`(인자 없이 +)는 모든 호스트의 X 접근을 허용하는 매우 위험한 명령이다. 누구나 내 화면을 캡처하거나 키 입력을 가로챌 수 있다. 시험에서 "보안상 위험한 명령"으로 자주 나온다. 반대로 `xhost -`는 호스트 기반 허용을 끄고 기본 인증으로 돌린다.

> 🔍 **핵심 구분**: xhost는 **호스트(IP) 단위**의 거친 제어, xauth는 **매직 쿠키로 사용자 단위**의 정밀한 제어다. xhost는 같은 호스트의 모든 사용자를 허용해버려 보안이 약하고, xauth는 쿠키를 가진 특정 사용자만 허용해 더 안전하다. 그래서 SSH X11 포워딩은 xauth 쿠키 방식을 쓴다.

> 📚 **유래/사례**: 실무에서 `export DISPLAY=원격:0` + `xhost +` 조합으로 GUI를 띄우다 보안 사고로 이어지는 경우가 많았다. 그래서 오늘날은 평문 X 포워딩 대신 `ssh -X`(신뢰 시 `-Y`)로 암호화 터널 + xauth 쿠키를 자동 처리하는 방식이 표준이다. "원격 GUI 안전하게 = ssh -X"를 기억하라.

### 직접 쳐보기 — X 포워딩으로 원격 GUI 띄우기

```bash
# SSH X11 포워딩으로 원격 프로그램을 내 화면에 띄우기
ssh -X alice@192.168.1.10
echo $DISPLAY          # localhost:10.0 (포워딩으로 자동 설정됨)
xclock                 # 원격에서 실행되나 내 화면에 표시됨
xeyes                  # 또 다른 X 클라이언트 테스트
```

## 마무리 — VNC와 X 윈도 한눈에 정리

VNC는 화면 전체를 픽셀로 전송하는 원격 데스크톱(포트 5900+디스플레이번호)이고, 보안을 위해 SSH 터널과 짝지어 쓴다. X 윈도 시스템은 리눅스 GUI의 토대로, **화면을 가진 쪽이 X 서버, 그림을 요청하는 응용프로그램이 X 클라이언트**라는 역전이 핵심이다. DISPLAY로 그릴 화면을 지정하고, xhost(호스트)·xauth(쿠키)로 접근을 통제하며, 안전한 원격 GUI는 `ssh -X`로 구현한다.

시험 직전 체크리스트:
- VNC 포트 = 5900 + 디스플레이 번호 (:1 → 5901)
- X 서버 = 화면·입력장치 가진 사용자 앞 기기, X 클라이언트 = 응용프로그램(역전!)
- DISPLAY = 그림 보낼 화면 주소(`:0` 로컬, `호스트:0` 원격)
- xhost = 호스트 단위, xauth = 매직 쿠키 단위
- `xhost +`(인자 없음)는 전체 허용으로 매우 위험
- 안전한 원격 GUI = `ssh -X`(X11 포워딩, xauth 자동)

## 📝 연습 문제

**문제 1.** X 윈도 시스템에서 X 서버와 X 클라이언트의 역할로 옳은 것은?

A) X 서버는 응용프로그램이고, X 클라이언트는 화면을 가진 사용자 앞 기기다

B) X 서버는 화면·키보드·마우스를 관리하는 사용자 앞 기기이고, X 클라이언트는 그리기를 요청하는 응용프로그램이다

C) X 서버는 원격 호스트에서만 실행되고, X 클라이언트는 로컬에서만 실행된다

D) X 서버와 X 클라이언트는 항상 같은 컴퓨터에서만 동작한다

**정답: B**

해설: X 윈도는 역전 구조로, 화면·입력장치(하드웨어)를 가진 사용자 앞 기기가 X 서버이고, "그려달라"고 요청하는 응용프로그램이 X 클라이언트다. A는 둘을 정반대로 설명했고, C는 위치를 잘못 고정했으며, D는 X가 네트워크로 분리 동작할 수 있다는 핵심을 부정한다. "화면 가진 쪽 = X 서버".

**문제 2.** VNC 서버를 디스플레이 `:2`로 실행했을 때 기본적으로 사용하는 TCP 포트는?

A) 5900

B) 5901

C) 5902

D) 5920

**정답: C**

해설: VNC 포트는 5900 + 디스플레이 번호이므로 `:2`는 5902다. A(5900)는 `:0`, B(5901)는 `:1`에 해당하고, D(5920)는 계산 규칙에 맞지 않는다. "5900 + 디스플레이 번호"라는 공식을 정확히 적용하는 것이 핵심이다.

**문제 3.** X 클라이언트가 그림을 출력할 대상 X 서버(화면)를 지정하는 환경변수는?

A) `TERM`

B) `DISPLAY`

C) `PATH`

D) `XAUTHORITY`

**정답: B**

해설: `DISPLAY` 환경변수는 X 클라이언트에게 어느 X 서버(화면)에 출력할지 `호스트:디스플레이번호` 형식으로 알려준다. A(TERM)는 터미널 종류, C(PATH)는 실행 파일 검색 경로, D(XAUTHORITY)는 인증 쿠키 파일 경로라 출력 화면 지정과 다르다. "DISPLAY = 그림 보낼 화면 주소"가 핵심이다.

**문제 4.** 다음 중 보안상 매우 위험하여 권장되지 않는 X 접근 제어 명령은?

A) `xhost +192.168.1.5` — 특정 호스트만 허용

B) `xhost +` — 모든 호스트의 X 접근을 허용

C) `xhost -192.168.1.5` — 특정 호스트 차단

D) `xauth list` — 인증 쿠키 목록 조회

**정답: B**

해설: 인자 없는 `xhost +`는 모든 호스트의 X 서버 접근을 허용해 누구나 화면 캡처·키 입력 가로채기가 가능한 매우 위험한 명령이다. A는 특정 호스트만 허용하므로 상대적으로 안전하고, C는 차단, D는 단순 조회라 위험하지 않다. "xhost +(인자 없음) = 전체 허용·위험"을 기억하라.

**문제 5.** 원격 컴퓨터의 데스크톱 화면 전체를 픽셀 단위로 전송하여 그대로 조작하게 해주는 원격 접속 방식은?

A) SSH 텍스트 셸 접속

B) VNC 원격 데스크톱

C) FTP 파일 전송

D) Telnet

**정답: B**

해설: VNC는 RFB 프로토콜로 원격 화면을 픽셀 단위로 전송하고 입력을 되돌려 보내는 원격 데스크톱 방식이다. A(SSH 셸)·D(Telnet)는 텍스트 기반 원격 접속, C(FTP)는 파일 전송이라 GUI 화면 공유가 아니다. "화면 전체 전송 = VNC"가 핵심이다.

**문제 6.** xhost와 xauth의 X 접근 제어 방식 차이로 옳은 것은?

A) xhost는 매직 쿠키 기반, xauth는 호스트 기반이다

B) xhost는 호스트(IP) 단위 제어, xauth는 매직 쿠키로 사용자 단위 인증을 한다

C) 둘 다 호스트 단위로만 제어하며 차이가 없다

D) xhost는 파일 전송, xauth는 화면 전송을 제어한다

**정답: B**

해설: xhost는 호스트(IP) 단위의 거친 제어이고, xauth는 MIT-MAGIC-COOKIE로 사용자 단위의 정밀한 인증을 한다. A는 두 방식을 정반대로 설명했고, C는 둘의 차이를 부정했으며, D는 둘 다 X 접근 제어 도구임을 무시했다. "xhost=호스트, xauth=쿠키"가 핵심이다.

**문제 7.** SSH X11 포워딩(`ssh -X`)을 사용해 원격 프로그램을 실행했을 때의 동작으로 옳은 것은?

A) 원격에서 실행한 프로그램의 GUI 창이 암호화 터널을 통해 사용자 앞 화면에 표시된다

B) 프로그램이 원격 화면에만 표시되고 로컬에서는 볼 수 없다

C) DISPLAY가 항상 `:0`으로 고정되어 로컬 프로그램만 실행된다

D) X11 포워딩은 텍스트만 전송하며 GUI는 지원하지 않는다

**정답: A**

해설: `ssh -X`는 원격에서 실행한 X 클라이언트(프로그램)의 GUI를 SSH 암호화 터널과 xauth 쿠키를 통해 사용자 앞 X 서버(화면)에 안전하게 표시한다. B는 포워딩의 목적과 반대이고, C의 DISPLAY는 보통 `localhost:10.0`으로 잡히며, D는 X11 포워딩이 GUI를 위한 기능임을 부정한다. "ssh -X = 원격 GUI를 내 화면에 안전하게".
