# Day 2 - 파티션과 마운트: fdisk · gdisk · parted · mkfs · mount/umount · /etc/fstab 6필드

빈 디스크 한 장을 시스템에 꽂았다고 바로 파일을 저장할 수는 없다. 디스크가 실제로 쓰이기까지는 **세 단계의 의식(ritual)** 을 거친다. 첫째 **파티션(partition)** 으로 공간을 구획하고, 둘째 그 파티션을 **파일시스템으로 포맷(`mkfs`)** 하고, 셋째 디렉터리 트리 어딘가에 **마운트(`mount`)** 해서 비로소 접근 가능하게 만든다. 그리고 이 마운트를 부팅 때마다 자동으로 재현하는 설정이 **`/etc/fstab`** 이다.

리눅스마스터 1급 실기는 이 흐름의 각 단계를 집요하게 묻는다. "MBR과 GPT의 차이는?", "fdisk와 parted의 차이는?", "fstab의 4번째 필드는?", "마운트 중인 파티션을 umount하면?" 같은 단답이 이 영역에서 쏟아진다. 오늘은 디스크 한 장이 사용 가능해지기까지의 전 과정을, 각 도구와 fstab 6필드를 정밀하게 짚으며 따라간다.

핵심 직관: **파티션 → 포맷 → 마운트는 순서가 바뀌면 안 되는 파이프라인**이다. 그리고 fstab은 이 파이프라인의 마지막 단계를 "영구화"하는 장치다.

## 디스크 장치 이름과 파티션 명명 규칙

리눅스는 디스크를 `/dev/` 아래의 블록 장치 파일로 표현한다.

| 장치 패턴 | 의미 |
|-----------|------|
| `/dev/sda`, `/dev/sdb` | SATA/SCSI/USB 디스크 (a=첫째, b=둘째…) |
| `/dev/sda1`, `/dev/sda2` | sda의 첫째·둘째 **파티션** |
| `/dev/nvme0n1` | 첫째 NVMe SSD |
| `/dev/nvme0n1p1` | nvme0n1의 첫째 파티션 (`p` 접두 주의) |
| `/dev/vda` | 가상화 환경의 virtio 디스크 |

> 💡 **개념**: 숫자가 디스크 뒤에 바로 붙는지(`sda1`), `p`를 사이에 두는지(`nvme0n1p1`)가 헷갈리는 단골 포인트다. 이름이 숫자로 끝나는 장치(nvme, mmcblk 등)는 파티션 번호와 구분하려고 `p`를 넣는다. `sda`는 문자로 끝나니 바로 `1`을 붙여도 모호하지 않다.

```bash
# 직접 쳐보기 — 디스크와 파티션 전체 조망
lsblk                  # 트리 형태로 디스크-파티션-마운트 한눈에
lsblk -f               # + 파일시스템 타입, UUID, 마운트포인트
fdisk -l               # 모든 디스크의 파티션 테이블 (root 필요)
cat /proc/partitions   # 커널이 인식한 파티션 목록
```

## MBR vs GPT — 두 가지 파티션 테이블 방식

파티션 정보를 디스크 어디에 어떤 형식으로 적느냐가 **파티션 테이블 방식**이고, 크게 둘이다.

| 항목 | MBR (DOS) | GPT |
|------|-----------|-----|
| 등장 | 1983 (BIOS 시대) | 2000s (UEFI) |
| 최대 디스크 크기 | **2TB** | 사실상 무제한(~9.4ZB) |
| 주 파티션 수 | **최대 4개** (확장+논리로 우회) | **128개** (기본) |
| 백업 | 단일 (디스크 첫 섹터) | **주+백업** (앞뒤 이중) |
| 식별 | 섹터 번호 기반 | **GUID/UUID** 기반 |
| 펌웨어 | BIOS | UEFI(+호환 BIOS) |

> 💡 **개념**: MBR의 "주 파티션 4개 제한"은 파티션 테이블 공간이 64바이트(16바이트×4)뿐이기 때문이다. 더 쪼개려면 주 파티션 하나를 **확장 파티션(extended)** 으로 만들고 그 안에 **논리 파티션(logical)** 을 여러 개 둔다. 그래서 MBR에서 논리 파티션 번호는 항상 **5번부터** 시작한다(`sda5`, `sda6`…). "MBR에서 5번째 파티션의 정체는?" → 첫 논리 파티션이 정답.

> ⚠️ **함정**: 2TB가 넘는 디스크는 MBR로는 전체를 쓸 수 없다 — 2TB 이후 공간이 주소 표현 범위를 벗어난다. 대용량 디스크는 반드시 GPT여야 한다. 그리고 GPT는 UEFI 펌웨어와 짝을 이루는 게 정석이다.

> 📚 **유래/사례**: MBR(Master Boot Record)은 디스크 첫 512바이트에 부트로더 코드 + 파티션 테이블 + 시그니처를 욱여넣은 1983년의 설계다. 40년 전 PC의 제약이 오늘날 "주 파티션 4개" 같은 화석 규칙으로 남았다. GPT는 이 한계를 걷어내며 각 파티션에 고유 GUID를 부여해, 디스크 순서가 바뀌어도 파티션을 안정적으로 식별한다.

## 파티션 도구 3종: fdisk · gdisk · parted

파티션을 만들고 지우는 대화형 도구 셋의 역할 분담이 명확하다.

| 도구 | 주 대상 | 특징 |
|------|---------|------|
| **fdisk** | MBR (최신 버전은 GPT도) | 가장 전통적, 대화형 메뉴 |
| **gdisk** | **GPT 전용** | fdisk와 유사한 인터페이스의 GPT판 |
| **parted** | MBR + GPT 모두 | 스크립트화 가능, 2TB↑ 능숙, 비대화형 명령 지원 |

fdisk 대화형 핵심 키:

```bash
fdisk /dev/sdb
# 명령 모드에서:
#   p  : 현재 파티션 테이블 출력(print)
#   n  : 새 파티션 생성(new)
#   d  : 파티션 삭제(delete)
#   t  : 파티션 타입(시스템 ID) 변경 — 예: 82=swap, 83=Linux, 8e=LVM
#   l  : 알려진 타입 코드 목록
#   w  : 변경 저장 후 종료(write) — 이걸 눌러야 디스크에 반영
#   q  : 저장 없이 종료(quit)
```

> 💡 **개념**: fdisk에서 `w`를 누르기 전까지는 **디스크에 아무것도 쓰이지 않는다.** 모든 편집은 메모리상에서만 일어나고, `w`가 커밋, `q`가 롤백이다. 실수했다면 `q`로 빠져나오면 원상복구된다. 시험에서 "fdisk 변경사항을 디스크에 반영하는 명령은?" → `w`.

> 🔍 **더 깊이**: parted는 비대화형으로 한 줄에 끝낼 수 있어 자동화에 유리하다. 예: `parted /dev/sdb --script mklabel gpt mkpart primary ext4 0% 100%`. 또 parted는 파티션 타입 라벨(`mklabel msdos` / `mklabel gpt`)로 MBR/GPT를 선택한다. fdisk가 단위를 섹터·실린더로 다루는 반면 parted는 `%`나 `GB` 같은 사람 친화적 단위를 쓴다.

> ⚠️ **함정**: 파티션 타입 코드를 헷갈리지 말 것. `83`=Linux 일반, `82`=Linux swap, `8e`=Linux LVM, `fd`=Linux RAID autodetect. swap 파티션을 만들 때 타입을 `82`로 바꾸지 않아도 동작은 하지만, 시스템이 swap임을 자동 인식하는 데 도움을 준다. "LVM용 파티션 타입 코드는?" → `8e`.

```bash
# 직접 쳐보기 — 파티션 생성 흐름 (실습 디스크에서만!)
fdisk /dev/sdb          # n→p→번호→크기 지정→w
partprobe /dev/sdb      # 커널에 파티션 테이블 재읽기 요청
lsblk /dev/sdb          # 새 파티션 확인
```

## mkfs — 파티션을 파일시스템으로 포맷

파티션을 만들었다고 끝이 아니다. 그 안을 **특정 파일시스템 구조로 초기화**해야 파일을 담을 수 있다. 이게 `mkfs`(make filesystem)다.

```bash
mkfs.ext4 /dev/sdb1        # ext4로 포맷
mkfs -t ext4 /dev/sdb1     # 위와 동일 (-t로 타입 지정)
mkfs.xfs /dev/sdb1         # xfs로 포맷
mkfs.vfat /dev/sdb1        # FAT (USB 등)
mke2fs -t ext4 /dev/sdb1   # ext 계열 저수준 도구
```

> 💡 **개념**: `mkfs.ext4 file` ≡ `mkfs -t ext4 file`이다. `mkfs`는 사실상 `mkfs.<타입>` 도우미를 호출하는 프론트엔드다. 포맷은 inode 테이블·슈퍼블록·블록 그룹을 디스크에 새로 쓰는 작업이므로 **기존 데이터를 모두 날린다.** 시험에서 "ext4로 포맷하는 명령" 단답으로 자주 나온다.

> ⚠️ **함정**: `mkfs`를 **마운트된 파티션**이나 **사용 중인 파티션**에 실행하면 큰 사고다. 또 디스크 전체(`/dev/sdb`)에 포맷하면 파티션 테이블째 날아간다 — 반드시 파티션(`/dev/sdb1`)을 지정한다. "이미 데이터가 있는 파티션에 mkfs 하면?" → 전부 삭제된다.

```bash
# 직접 쳐보기 — 포맷 후 확인
mkfs.ext4 /dev/sdb1
blkid /dev/sdb1          # 새로 생긴 UUID와 TYPE 확인
tune2fs -L data /dev/sdb1   # 볼륨 라벨 부여 (선택)
```

## mount와 umount — 파일시스템을 트리에 붙이고 떼기

리눅스에는 윈도우의 "C:", "D:" 같은 드라이브 문자가 없다. 모든 저장 공간은 **단 하나의 디렉터리 트리(`/`)** 의 어딘가에 붙는다. 파일시스템을 특정 디렉터리(마운트 포인트)에 연결하는 게 `mount`다.

```bash
mount /dev/sdb1 /mnt/data       # sdb1을 /mnt/data에 마운트
mount -t ext4 /dev/sdb1 /mnt/data   # 타입 명시
mount -o ro /dev/sdb1 /mnt/data     # 읽기 전용으로
mount                            # 현재 마운트된 모든 것 출력
umount /mnt/data                 # 마운트 해제 (경로 또는 장치로)
umount /dev/sdb1
```

> 💡 **개념**: 마운트 포인트로 쓰는 디렉터리에 **원래 파일이 있었다면**, 마운트하는 동안 그 파일들은 **가려져서 보이지 않는다**(사라진 게 아니라 덮인 것). umount하면 다시 나타난다. 그래서 마운트 포인트는 빈 디렉터리를 쓰는 게 관례다.

> ⚠️ **함정**: 어떤 프로세스가 그 파일시스템 안의 파일을 쓰고 있으면 `umount`가 **"target is busy"** 로 거부된다. 누가 쓰는지는 `lsof /mnt/data` 또는 `fuser -m /mnt/data`로 찾는다. 정 안 되면 `umount -l`(lazy, 새 접근 차단 후 마지막 사용 끝나면 해제)을 쓴다. "마운트 중인 파티션 umount 거부 원인은?" → 사용 중인 프로세스 존재.

```bash
# 직접 쳐보기 — 마운트 진단
mount | grep sdb1            # sdb1이 어디 붙었나
findmnt /mnt/data           # 마운트 정보 트리 형태로
fuser -m /mnt/data          # 사용 중인 프로세스 PID
umount /mnt/data
```

## /etc/fstab — 부팅 시 자동 마운트의 6필드

`mount` 명령은 **일시적**이다. 재부팅하면 사라진다. 부팅 때마다 자동으로, 또는 `mount -a`로 일괄 재현하려면 **`/etc/fstab`** 에 등록해야 한다. 각 줄은 공백으로 구분된 **6개 필드**다 — 여기가 오늘의 최대 시험 격전지.

```
UUID=abc-123  /mnt/data  ext4  defaults  0  2
#    1           2        3      4        5  6
```

| # | 필드 | 의미 | 주의/값 |
|---|------|------|---------|
| 1 | **장치(파일시스템)** | UUID= / LABEL= / /dev/sdb1 | **UUID 권장**(장치명은 부팅 순서 바뀌면 어긋남) |
| 2 | **마운트 포인트** | 붙일 디렉터리 | swap은 `none` 또는 `swap` |
| 3 | **파일시스템 타입** | ext4, xfs, swap, vfat, nfs… | `auto`=자동 감지 |
| 4 | **마운트 옵션** | defaults, ro, noexec, noauto… | 콤마로 나열 |
| 5 | **dump** | 백업(dump) 대상 여부 | **0**=안 함(거의 항상 0), 1=함 |
| 6 | **fsck 순서(pass)** | 부팅 시 검사 순서 | **0**=검사 안 함, **1**=루트(`/`), **2**=나머지 |

> 💡 **개념**: 6번째 필드(pass/순서)가 단골 함정이다. **루트 파일시스템(`/`)은 1**, 그 외 검사할 파일시스템은 **2**, 검사 안 할 것(swap, 네트워크 FS 등)은 **0**이다. 1번을 먼저 검사하고 2번들을 병렬로 검사한다. "fstab 6번째 필드에서 루트 파일시스템 값은?" → 1.

> 🔍 **더 깊이**: 1번 필드에 `/dev/sdb1` 같은 장치명을 쓰면 위험하다. 디스크를 추가/제거하면 커널이 부여하는 이름(`sdb` → `sdc`)이 바뀌어 엉뚱한 디스크가 마운트될 수 있다. **UUID**는 파일시스템에 고정된 고유 식별자라 순서가 바뀌어도 안전하다. `blkid`로 UUID를 확인해 `UUID=...` 형태로 적는 게 정석이다.

> ⚠️ **함정**: 5번(dump)과 6번(pass)을 헷갈리지 말 것. 5번은 백업 도구 `dump`용 플래그(거의 0), 6번은 부팅 시 `fsck` 검사 순서. 또 4번 옵션의 **`noauto`** 는 "부팅 시 자동 마운트 안 함, 수동 `mount`만 허용"이고, **`defaults`** 는 `rw,suid,dev,exec,auto,nouser,async`의 묶음이다.

주요 마운트 옵션:

| 옵션 | 의미 |
|------|------|
| `defaults` | rw, suid, dev, exec, auto, nouser, async 묶음 |
| `ro` / `rw` | 읽기 전용 / 읽기쓰기 |
| `noexec` | 이 FS의 실행 파일 실행 금지(보안) |
| `nosuid` | SUID/SGID 비트 무시(보안) |
| `noauto` | 부팅 시 자동 마운트 안 함 |
| `usrquota`,`grpquota` | 디스크 쿼터 활성화 (Day4 연계) |

> 📚 **유래/사례**: fstab을 잘못 편집하면(존재하지 않는 장치, 오타) 부팅이 emergency mode로 떨어질 수 있다. 그래서 fstab을 고친 뒤에는 **재부팅 전에 반드시 `mount -a`로 검증**하는 게 철칙이다. 오류 없이 모두 마운트되면 안전, 에러가 나면 그 줄을 고쳐야 한다.

```bash
# 직접 쳐보기 — fstab 작성과 검증
blkid /dev/sdb1                     # UUID 확보
# /etc/fstab에 줄 추가 후:
mount -a                            # fstab 전체를 적용 (오류 검증!)
findmnt --verify                    # fstab 문법/논리 검증
systemctl daemon-reload            # systemd가 fstab 변경 인식
```

## 마무리

오늘의 파이프라인을 한 줄로: **파티션(fdisk/gdisk/parted) → 포맷(mkfs) → 마운트(mount) → 영구화(fstab)**. MBR은 2TB·주4개 한계, GPT는 무제한·128개·UUID 식별. fdisk=MBR중심, gdisk=GPT전용, parted=둘다·스크립트. fstab 6필드는 **장치(UUID)·마운트포인트·타입·옵션·dump(0)·pass(루트1/나머지2/안함0)** — 이 순서가 곧 시험 문제다. fstab 수정 후 `mount -a` 검증은 반드시. 다음 Day 3에서는 파티션을 유연하게 늘리는 LVM과 가상메모리 스왑을 다룬다.

## 📝 연습 문제

**문제 1.** MBR 파티션 방식에서 만들 수 있는 주 파티션(primary partition)의 최대 개수는?

A) 2개
B) 4개
C) 8개
D) 128개

**정답: B**

해설: MBR의 파티션 테이블은 64바이트(16바이트×4)뿐이라 주 파티션이 최대 4개다. 더 나누려면 주 파티션 하나를 확장 파티션으로 만들고 그 안에 논리 파티션을 둔다. GPT가 128개다.

---

**문제 2.** `/etc/fstab`의 6번째 필드(fsck pass)에서 루트 파일시스템(`/`)에 지정해야 할 값으로 옳은 것은?

A) 0
B) 1
C) 2
D) 3

**정답: B**

해설: 6번째 필드는 부팅 시 fsck 검사 순서다. 루트(`/`)는 1, 나머지 검사 대상은 2, 검사 안 할 것(swap 등)은 0이다. 1을 먼저 검사한 뒤 2번들을 검사한다.

---

**문제 3.** 파티션 `/dev/sdb1`을 ext4 파일시스템으로 포맷하는 명령으로 옳은 것은?

A) `mount.ext4 /dev/sdb1`
B) `fdisk.ext4 /dev/sdb1`
C) `mkfs.ext4 /dev/sdb1`
D) `fsck.ext4 /dev/sdb1`

**정답: C**

해설: `mkfs.ext4`(또는 `mkfs -t ext4`)가 파티션을 ext4로 포맷한다. `mount`는 마운트, `fdisk`는 파티션 편집, `fsck`는 파일시스템 검사다.

**문제 4.** `umount /mnt/data` 실행 시 "target is busy" 오류가 발생하는 가장 일반적인 원인은?

A) 파일시스템이 손상되었다
B) 해당 파일시스템 내 파일을 사용 중인 프로세스가 있다
C) fstab에 등록되지 않았다
D) 읽기 전용으로 마운트되었다

**정답: B**

해설: 어떤 프로세스가 그 파일시스템 안의 파일을 열고 있거나 그 디렉터리를 작업 디렉터리로 쓰면 umount가 거부된다. `lsof`나 `fuser -m`으로 범인을 찾거나, `umount -l`(lazy)로 처리한다.

**문제 5.** `/etc/fstab`의 1번째 필드에 `/dev/sdb1` 같은 장치명 대신 `UUID=...`를 쓰는 주된 이유는?

A) UUID가 장치명보다 마운트 속도가 빠르다
B) 디스크 추가/제거로 장치명이 바뀌어도 올바른 파일시스템을 안정적으로 식별하기 위해
C) UUID만 읽기 전용 마운트를 지원하기 때문
D) 장치명은 fstab에서 문법 오류로 처리되기 때문

**정답: B**

해설: 커널이 부여하는 `sda`/`sdb` 이름은 디스크 추가·제거나 부팅 순서에 따라 바뀔 수 있다. UUID는 파일시스템 고유 식별자라 순서가 바뀌어도 정확히 같은 파티션을 가리킨다. `blkid`로 확인한다.

**문제 6.** GPT 파티션 테이블을 전용으로 다루는 대화형 도구로 옳은 것은?

A) fdisk
B) gdisk
C) mkfs
D) tune2fs

**정답: B**

해설: gdisk는 GPT 전용 파티션 편집 도구로 fdisk와 유사한 인터페이스를 제공한다. parted는 MBR/GPT 모두 다루며, 구버전 fdisk는 MBR 중심이었다.

**문제 7.** 리눅스에서 LVM(논리 볼륨)용으로 쓸 파티션에 fdisk로 지정하는 파티션 타입(시스템 ID) 코드로 옳은 것은?

A) 82
B) 83
C) 8e
D) fd

**정답: C**

해설: `8e`가 Linux LVM 타입이다. `82`는 Linux swap, `83`은 Linux 일반 파일시스템, `fd`는 Linux RAID autodetect다.
