# Day 1 - 파일시스템 종류와 구조: ext2/3/4 · xfs · btrfs · 저널링 · inode와 블록

## 📌 핵심 정리

- **파일의 이름은 파일의 일부가 아니다.** 실체는 inode에, 이름은 디렉터리의 "이름 → inode 번호" 목록에 있다.
- 공간 할당 단위는 **블록**, 파일시스템 전체 지도는 **슈퍼블록**(백업 사본이 여러 곳에 있다).
- 저널링의 기본 모드(ordered)가 지키는 것은 **메타데이터 일관성**이지 사용자 데이터가 아니다.
- ext2(무저널) → ext3(저널) → ext4(익스텐트·최대 1EB). xfs는 **줄일 수 없고**, btrfs는 CoW·스냅샷이 무기다.
- 용량은 남았는데 파일이 안 만들어지면 **inode 고갈**이다. `df -h`가 아니라 **`df -i`**로 확인한다.

## inode — 파일의 실체를 담는 메타데이터 구조

같은 물리 디스크라도 어떤 파일시스템으로 포맷하느냐에 따라 최대 파일 크기·복구 능력·성능이 완전히 달라진다. 그 출발점은 파일이 실제로 어떻게 표현되는지다.

- inode(index node)는 **하나의 파일 또는 디렉터리에 대한 모든 메타데이터를 담는 고정 크기 구조체**다.
- 파일시스템을 만들 때(`mkfs`) inode 테이블의 개수가 정해지고, 파일 하나당 inode 하나가 소비된다.

| 항목 | 설명 |
|------|------|
| **파일 타입** | 일반 파일 / 디렉터리 / 심볼릭 링크 / 디바이스 등 |
| **권한 모드** | rwxrwxrwx (12비트, SUID/SGID/Sticky 포함) |
| **소유자 UID / GID** | 누구의 파일인가 |
| **링크 카운트** | 이 inode를 가리키는 하드링크 수 |
| **크기** | 바이트 단위 파일 크기 |
| **타임스탬프** | atime(접근), mtime(수정), ctime(inode 변경) |
| **데이터 블록 포인터** | 실제 내용이 저장된 블록 위치들 |

- 여기서 결정적으로 빠진 것이 하나 있다. **파일 이름은 inode에 없다.** 이름은 부모 디렉터리가 들고 있다.

> 💡 **개념**: 디렉터리는 "파일을 담는 폴더"가 아니라, **"파일이름 → inode번호" 쌍의 목록을 내용으로 가진 특수한 파일**이다. `ls`가 하는 일은 현재 디렉터리 파일을 열어 그 목록을 읽는 것뿐이다. 그래서 디렉터리에서 파일을 지우려면(`unlink`) 디렉터리에 대한 쓰기 권한이 필요하지, 파일 자체에 대한 권한은 필요 없다. Sticky bit(`/tmp`의 `t`)가 이 허점을 막는 장치다.

> 🔍 **더 깊이**: inode의 데이터 블록 포인터는 전통적으로 **직접 블록 12개 + 단일 간접 + 이중 간접 + 삼중 간접** 구조를 썼다(ext2/3). 작은 파일은 직접 포인터 12개로 충분하지만, 큰 파일은 "포인터를 담은 블록을 가리키는 포인터"를 단계적으로 쌓아 표현한다. ext4는 이 방식 대신 **익스텐트(extent)** — "시작 블록 + 연속 길이"로 범위를 한 번에 표현 — 를 도입해, 연속된 큰 파일을 훨씬 적은 메타데이터로 다룬다. 단편화가 적은 대용량 파일에서 성능이 크게 오른다.

> ⚠️ **함정**: "디스크 용량은 남았는데 파일을 못 만든다"는 상황은 **inode 고갈**이다. `df -h`는 블록(용량) 사용률을, `df -i`는 inode 사용률을 따로 보여준다. 수많은 작은 파일(메일 큐, 세션 파일 등)이 쌓이면 용량은 멀쩡한데 inode가 100%가 되어 `No space left on device`가 뜬다. 시험에서 "용량 여유 있는데 파일 생성 실패 → 원인은?" 답이 inode 고갈이다.

```bash
# 직접 쳐보기 — inode 관찰
ls -i file.txt              # 파일의 inode 번호 출력
stat file.txt               # inode, 링크 수, 타임스탬프 전부
df -i                       # 파일시스템별 inode 사용량
ls -id /tmp                 # 디렉터리의 inode 번호
```

> 📚 **유래/사례**: "inode"의 어원은 명확하지 않지만 Dennis Ritchie는 "index node"의 줄임이라고 회고했다. 1970년대 초기 유닉스부터 파일 메타데이터를 이름과 분리해 번호로 관리한 이 설계가, 지금까지도 리눅스 파일시스템의 근간으로 살아남았다.

## 하드링크와 심볼릭 링크 — inode 관점에서 본 차이

inode를 이해하면 두 링크의 차이가 자명해진다.

- **하드링크(hard link)**: 같은 inode 번호에 **새로운 이름**을 하나 더 붙이는 것.
  - inode의 링크 카운트가 1 증가한다. 둘은 완전히 동등한 "원본"이며, 하나를 지워도 inode는 카운트가 0이 될 때까지 살아남는다.
  - **같은 파일시스템 안에서만** 가능하고, 디렉터리에는 보통 못 건다.
- **심볼릭 링크(symbolic/soft link)**: 대상의 **경로 문자열을 내용으로 가진 별도의 작은 파일**(별도 inode).
  - 원본을 지우면 링크는 깨진다(dangling). 파일시스템 경계를 넘을 수 있고 디렉터리도 가리킬 수 있다.

| 구분 | 하드링크 | 심볼릭 링크 |
|------|----------|-------------|
| inode | 원본과 **동일** | **별도** inode |
| 링크 카운트 | 증가시킴 | 영향 없음 |
| 파일시스템 경계 | 못 넘음 | 넘을 수 있음 |
| 디렉터리 대상 | 불가(보통) | 가능 |
| 원본 삭제 시 | 데이터 유지 | 깨진 링크 |

> 💡 **개념**: `rm`이 하는 일은 데이터를 지우는 게 아니라 **디렉터리에서 이름을 떼고 inode의 링크 카운트를 1 줄이는 것**이다. 카운트가 0이 되고 그 파일을 연 프로세스도 없을 때 비로소 블록이 회수된다. 그래서 실행 중인 프로세스가 연 로그 파일을 `rm`해도 디스크가 즉시 비지 않는다 — 프로세스가 닫을 때까지 inode가 살아 있기 때문이다.

```bash
# 직접 쳐보기 — 링크와 링크 카운트
echo hello > a.txt
ln a.txt b.txt        # 하드링크
ls -li a.txt b.txt    # inode 번호 동일, 링크 카운트 2
ln -s a.txt c.txt     # 심볼릭 링크
ls -li c.txt          # 별도 inode, '->' 표시
```

## 저널링 — 정전에도 파일시스템이 깨지지 않는 원리

- ext2까지의 파일시스템은 갑작스러운 정전이나 크래시가 나면 **파일시스템이 일관성을 잃을** 수 있었다.
- 예: "새 파일의 블록을 할당했지만 그 블록을 inode에 연결하기 직전에 전원이 나가면", 블록은 점유됐는데 아무도 가리키지 않는 유령 블록이 생긴다.
- 부팅 시 이걸 잡으려고 `fsck`가 **전체 디스크를 스캔**했는데, 대용량 디스크에서는 수십 분~수 시간이 걸렸다.
- **저널링(journaling)**은 실제 위치에 쓰기 전에 **앞으로 무엇을 쓸지(트랜잭션)를 저널이라는 전용 영역에 먼저 기록**한다.
- 작업이 정상 완료되면 저널 엔트리를 지우고, 도중에 크래시가 나면 부팅 시 저널만 재생(replay)해 일관성을 복원한다. 전체 스캔이 필요 없어 복구가 초 단위로 끝난다.

ext3/ext4의 저널링 모드 세 가지:

| 모드 | 저널에 기록하는 것 | 안전성 | 성능 |
|------|--------------------|--------|------|
| **journal** | 메타데이터 **+ 데이터** 모두 | 가장 높음 | 가장 느림(두 번 씀) |
| **ordered** (기본) | 메타데이터만, 단 데이터를 먼저 디스크에 쓴 뒤 메타데이터 커밋 | 높음 | 균형 |
| **writeback** | 메타데이터만, 데이터 순서 보장 안 함 | 낮음 | 가장 빠름 |

> 💡 **개념**: 가장 흔한 오해가 "저널링이 데이터를 보호한다"는 것이다. 기본 모드(ordered)는 **메타데이터의 일관성**을 보장할 뿐, 마지막 순간에 쓰던 사용자 데이터 자체의 무손실을 보장하지는 않는다. 데이터까지 저널에 이중 기록하는 `journal` 모드만 데이터를 보호한다. 시험에서 "ext3 기본 저널링이 보장하는 것은?" → **메타데이터 일관성**이 정답이다.

> 🔍 **더 깊이**: ext4의 저널은 별도의 작은 영역에 존재하며 `tune2fs -l`로 "Journal inode" 항목을 확인할 수 있다. `data=ordered`는 마운트 옵션(`/etc/fstab` 또는 `mount -o data=ordered`)으로 조절한다. btrfs와 xfs는 ext와 다른 방식을 쓴다 — xfs는 메타데이터 저널링을, btrfs는 **copy-on-write(CoW)** 를 써서 저널 대신 항상 새 위치에 쓰고 원자적으로 포인터를 교체한다. 그래서 btrfs는 스냅샷이 자연스럽게 공짜로 나온다.

> 📚 **유래/사례**: ext3는 ext2에 저널링만 얹어 **디스크 포맷 호환**을 유지한 채 나왔다(2001). 그래서 ext3 파티션을 ext2로 마운트하거나 그 반대가 가능했다. 이 "기존 자산을 깨지 않는 진화" 전략이 ext 계열이 리눅스 기본 파일시스템으로 오래 군림한 비결이다.

## 파일시스템 계보: ext2 → ext3 → ext4 · xfs · btrfs

ext 계열의 진화를 한눈에:

| 항목 | ext2 | ext3 | ext4 |
|------|------|------|------|
| 저널링 | 없음 | 있음 | 있음 |
| 최대 파일 크기 | 2TB | 2TB | **16TB** |
| 최대 파일시스템 | 32TB | 32TB | **1EB(엑사바이트)** |
| 블록 할당 | 간접 블록 | 간접 블록 | **익스텐트** |
| 특징 | 단순·빠름 | ext2+저널 | 익스텐트, 지연할당, 하위호환 |

다른 주요 파일시스템:

| 파일시스템 | 핵심 특성 | 강점 |
|------------|-----------|------|
| **xfs** | 메타데이터 저널링, 익스텐트, 동적 inode | 대용량 파일·병렬 I/O에 강함. RHEL 7+ 기본 |
| **btrfs** | Copy-on-Write, 스냅샷, 내장 RAID, 풀링 | 스냅샷·체크섬·볼륨관리 통합 |
| **swap** | 파일시스템 아님, 가상메모리 교체영역 | (Day3에서 다룸) |

> 💡 **개념**: xfs는 **줄일 수 없다(shrink 불가)**. 늘리기(`xfs_growfs`)만 가능하다. ext4는 `resize2fs`로 늘리고 줄이는 게(언마운트 후) 모두 된다. 이 비대칭성은 LVM과 함께 자주 출제된다 — "xfs로 만든 LV를 줄이려면?" → 백업 후 재생성밖에 없다.

> 🔍 **더 깊이**: btrfs의 Copy-on-Write는 데이터를 덮어쓰지 않고 항상 새 블록에 쓴 뒤 메타데이터 포인터를 원자적으로 교체한다. 덕분에 **스냅샷이 거의 공짜**(변경된 블록만 추가 점유)이고, 모든 블록에 체크섬이 있어 silent corruption(조용한 데이터 손상)을 탐지·복구할 수 있다. 다만 데이터베이스처럼 같은 위치를 끊임없이 덮어쓰는 워크로드에서는 CoW 단편화로 느려질 수 있어 해당 파일에 `nodatacow` 속성을 주기도 한다.

```bash
# 직접 쳐보기 — 파일시스템 종류 확인
df -T                       # 마운트된 파일시스템과 그 타입
lsblk -f                    # 블록 장치별 FSTYPE, UUID
blkid                       # 장치별 UUID와 TYPE
cat /proc/filesystems       # 커널이 지원하는 파일시스템 목록
tune2fs -l /dev/sda1 | head # ext 계열 슈퍼블록 정보(저널 포함)
```

## 블록과 슈퍼블록 — 파일시스템의 기본 단위와 지도

- **블록(block)**은 파일시스템이 디스크 공간을 할당하는 최소 단위다. 보통 1KB, 2KB, 4KB 중 하나로 `mkfs` 시 정해진다.
- 1바이트짜리 파일도 최소 한 블록(예: 4KB)을 통째로 차지한다 — 실제 용량(`du`)이 명목 크기(`ls -l`)보다 큰 이유, 즉 **내부 단편화(internal fragmentation)**다.
- **슈퍼블록(superblock)**은 파일시스템 전체의 메타데이터 — 블록 크기, 총 블록 수, inode 수, 마운트 횟수, 파일시스템 상태 등 — 를 담은 "지도"다.
- 이게 손상되면 파일시스템 전체를 읽을 수 없으므로, 파일시스템은 슈퍼블록의 **백업 사본을 여러 위치에 복제**해 둔다.

> ⚠️ **함정**: 슈퍼블록이 깨졌을 때 `fsck -b <백업블록번호> /dev/sdaX`로 백업 슈퍼블록을 써서 복구한다. 백업 위치는 `dumpe2fs /dev/sdaX | grep -i superblock` 또는 `mke2fs -n`(실제 포맷 없이 위치만 출력)으로 알아낸다. "주 슈퍼블록 손상 시 대처" 단답으로 나온다.

> 📚 **유래/사례**: 블록 크기를 4KB로 잡는 관행은 대부분의 CPU 메모리 페이지 크기(4KB)와 맞추기 위함이다. 파일시스템 블록과 메모리 페이지가 정렬되면 페이지 캐시 ↔ 디스크 사이 I/O가 1:1로 깔끔하게 매핑돼 효율이 높다.

다음 Day 2에서는 이 파일시스템을 실제 디스크에 올리는 과정 — 파티션, mkfs, mount, fstab — 을 다룬다.

## 📖 용어

- **inode** : 파일의 타입·권한·소유자·크기·타임스탬프·데이터 블록 위치를 담는 구조체. **파일명은 여기 없다**.
- **디렉터리** : "파일이름 → inode번호" 목록을 내용으로 갖는 특수한 파일. 폴더가 아니라 색인표다.
- **링크 카운트** : 한 inode를 가리키는 이름의 개수. 0이 되고 아무도 안 열고 있어야 블록이 회수된다.
- **익스텐트(extent)** : "시작 블록 + 연속 길이"로 범위를 한 번에 표현하는 ext4의 할당 방식.
- **inode 고갈** : 용량은 남았는데 inode를 다 써서 파일을 못 만드는 상태. `df -i`로 확인한다.
- **하드링크 vs 심볼릭 링크** : 같은 inode에 이름을 하나 더 다는 것과, 경로 문자열을 담은 별도 파일.
- **저널링** : 실제로 쓰기 전에 "무엇을 쓸지"를 전용 영역에 먼저 적어 크래시 복구를 빠르게 하는 기법.
- **ordered / journal / writeback** : ext의 저널링 모드. 기본 ordered는 **메타데이터만** 보장한다.
- **`fsck`** : 파일시스템 일관성을 검사·복구하는 명령. 저널링 도입 전엔 전체 스캔이 필요했다.
- **CoW(Copy-on-Write)** : 덮어쓰지 않고 새 블록에 쓴 뒤 포인터를 바꾸는 방식. btrfs의 스냅샷이 여기서 나온다.
- **블록(block)** : 파일시스템이 공간을 할당하는 최소 단위(보통 4KB). 작은 파일도 한 블록을 통째로 쓴다.
- **내부 단편화** : 블록 단위 할당 때문에 실제 점유 용량이 파일 크기보다 커지는 현상.
- **슈퍼블록** : 파일시스템 전체의 설정과 상태를 담은 지도. 손상에 대비해 백업 사본이 여러 곳에 있다.
- **`resize2fs` / `xfs_growfs`** : ext는 늘리고 줄이기가 되지만, xfs는 **늘리기만** 된다.

## 📝 연습 문제

**문제 1.** 리눅스에서 파일의 이름(filename)이 실제로 저장되는 위치로 옳은 것은?

A) 파일의 inode 안
B) 파일이 속한 부모 디렉터리의 데이터 안
C) 슈퍼블록의 파일 이름 테이블 안
D) 파일의 첫 번째 데이터 블록 헤더 안

**정답: B**

해설: 파일 이름은 inode에 없다. 부모 디렉터리가 "이름 → inode번호" 매핑을 내용으로 가지며, 이름은 거기에 저장된다. inode는 권한·소유자·크기·블록 포인터 등 메타데이터만 담는다.

---

**문제 2.** `df -h`로 보면 디스크 용량이 충분한데도 새 파일 생성 시 "No space left on device" 오류가 발생했다. 가장 가능성 높은 원인은?

A) 슈퍼블록 손상
B) 저널 영역 가득 참
C) inode 고갈
D) 블록 크기 불일치

**정답: C**

해설: 수많은 작은 파일이 쌓이면 용량(블록)은 남아도 inode가 100%가 되어 새 파일을 만들 수 없다. `df -i`로 inode 사용률을 확인하면 진단된다.

---

**문제 3.** ext3의 기본 저널링 모드인 `ordered`가 보장하는 것으로 가장 정확한 것은?

A) 마지막에 쓰던 사용자 데이터까지 무손실 보존
B) 파일시스템 메타데이터의 일관성
C) 디스크 전체의 물리적 무결성
D) 삭제된 파일의 복구 가능성

**정답: B**

해설: ordered 모드는 메타데이터만 저널링하므로 파일시스템 구조의 일관성을 보장한다. 사용자 데이터 자체까지 보호하려면 데이터를 이중 기록하는 `journal` 모드를 써야 한다.

**문제 4.** ext4 파일시스템이 ext3 대비 도입한 핵심 변경으로 옳지 않은 것은?

A) 간접 블록 대신 익스텐트(extent) 방식 도입
B) 최대 파일시스템 크기를 1EB로 확장
C) 저널링 기능을 처음으로 추가
D) 최대 단일 파일 크기를 16TB로 확장

**정답: C**

해설: 저널링은 ext3에서 이미 추가됐다. ext4의 핵심은 익스텐트, 대용량 한계 확장(파일 16TB, FS 1EB), 지연 할당 등이다.

**문제 5.** 하드링크와 심볼릭 링크의 차이에 대한 설명으로 옳은 것은?

A) 하드링크는 별도 inode를 갖고, 심볼릭 링크는 원본과 같은 inode를 공유한다
B) 하드링크는 파일시스템 경계를 넘을 수 있고, 심볼릭 링크는 넘을 수 없다
C) 하드링크는 원본과 같은 inode를 공유하고 링크 카운트를 증가시킨다
D) 심볼릭 링크는 원본을 삭제해도 데이터가 유지된다

**정답: C**

해설: 하드링크는 같은 inode에 이름을 추가하므로 링크 카운트가 증가하고 원본 삭제 후에도 데이터가 유지된다. 단 같은 파일시스템 안에서만 가능하다. 심볼릭 링크는 별도 inode에 경로 문자열을 담으며 경계를 넘고 디렉터리도 가리킬 수 있으나 원본 삭제 시 깨진다.

**문제 6.** xfs 파일시스템에 대한 설명으로 옳은 것은?

A) `resize2fs`로 크기를 줄일 수 있다
B) 크기를 늘릴 수만 있고 줄일 수는 없다
C) 저널링을 지원하지 않는다
D) ext2와 디스크 포맷이 호환된다

**정답: B**

해설: xfs는 `xfs_growfs`로 확장만 가능하며 축소(shrink)는 불가능하다. 줄이려면 백업 후 재생성해야 한다. `resize2fs`는 ext 계열 전용 도구다.

**문제 7.** 주 슈퍼블록이 손상되어 파일시스템을 마운트할 수 없을 때 사용할 수 있는 복구 방법으로 옳은 것은?

A) inode 테이블을 재생성한다
B) 저널을 재생(replay)하면 자동 복구된다
C) 백업 슈퍼블록 위치를 찾아 `fsck -b`로 복구한다
D) 블록 크기를 변경하면 복구된다

**정답: C**

해설: 파일시스템은 슈퍼블록의 백업 사본을 여러 위치에 둔다. `dumpe2fs`나 `mke2fs -n`으로 백업 위치를 알아낸 뒤 `fsck -b <백업번호>`로 복구한다.
