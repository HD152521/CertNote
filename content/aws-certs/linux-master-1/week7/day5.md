# Day 5 - Week 7 종합 복습: 백업과 시스템 관리의 큰 그림

이번 주는 리눅스 **시스템 관리의 하부 구조**를 다뤘다. Day 1에서 소프트웨어를 설치·관리하는 패키지 체계(rpm/yum, dpkg/apt)를, Day 2에서 그것을 직접 만드는 소스 컴파일과 라이브러리를, Day 3에서 시스템의 심장인 커널과 모듈을, Day 4에서 하드웨어를 표현하는 장치 파일과 프린터를 배웠다. 오늘은 마지막 주제인 **백업**(tar/dump/restore/rsync/dd/cpio)을 더한 뒤, 한 주를 하나의 그림으로 잇고 종합 문제로 점검한다.

이번 주를 관통하는 통찰: **거의 모든 리눅스 관리 도구는 "저수준 단일 도구"와 "고수준 자동화 도구"의 2단 구조를 가진다.** 패키지는 rpm↔yum, dpkg↔apt. 모듈은 insmod↔modprobe. 저수준은 하나를 직접 다루고, 고수준은 의존성·저장소·자동화를 처리한다. 이 패턴을 잡으면 명령 암기가 구조 이해로 바뀐다.

## 백업 — tar·dump·restore·rsync·dd·cpio

백업은 데이터 손실에 대비해 사본을 만드는 일이다. 도구마다 작동 층위와 용도가 다르다.

```bash
tar -czvf backup.tar.gz /home/user      # 디렉터리를 압축 아카이브로(가장 보편적)
tar -xzvf backup.tar.gz                  # 복원(풀기)
rsync -av /src/ /backup/                 # 증분 동기화(바뀐 부분만)
rsync -avz /src/ user@host:/backup/      # 원격으로 압축 전송(z)
dd if=/dev/sda of=/backup/disk.img       # 디스크를 블록 단위 통째로 복제
dump -0u -f /backup/full.dump /dev/sda1  # 파일시스템 레벨 0(전체) 백업
restore -rf /backup/full.dump            # dump 백업 복원
find /home | cpio -ov > backup.cpio      # find와 결합한 아카이브
```

| 도구 | 층위 | 특징 | 용도 |
|------|------|------|------|
| `tar` | 파일/디렉터리 | 묶기+압축, 가장 보편 | 일반 백업·배포 |
| `rsync` | 파일/디렉터리 | **증분**(바뀐 것만), 원격 | 주기적 동기화 |
| `dd` | **블록(장치)** | 디스크 통째 복제, 비트 단위 | 디스크 이미지·복제 |
| `dump`/`restore` | **파일시스템** | 레벨 0~9 증분, ext 계열 | 파일시스템 전체 백업 |
| `cpio` | 파일(stdin) | `find`와 결합 | 선택적 아카이브 |

> 💡 **개념**: 백업 도구는 **작동 층위**로 이해해야 한다. `tar`/`rsync`/`cpio`는 **파일 단위**로 동작해 파일·디렉터리를 골라 백업한다. `dump`/`restore`는 **파일 시스템 단위**로 동작하며 레벨(0=전체, 1~9=증분)을 지원한다. `dd`는 가장 낮은 **블록(장치) 단위**로, 빈 공간까지 포함해 디스크를 비트 그대로 복제한다 — 그래서 디스크 통째 이미지나 부팅 디스크 복제에 쓴다. 층위가 다르면 용도가 다르다.

> 🔍 **더 깊이**: `rsync`의 강점은 **증분 전송**이다. 처음엔 전체를 복사하지만, 다음부터는 바뀐 파일·바뀐 블록만 전송해 시간과 대역폭을 크게 아낀다. `-a`(archive, 권한·시각·링크 보존), `-v`(상세), `-z`(전송 시 압축), `--delete`(원본에 없는 파일을 백업에서도 삭제)가 핵심 옵션이다. 원격 백업의 사실상 표준이다. 경로 끝의 슬래시(`/src/`)는 "디렉터리 안의 내용"을 의미해 결과가 달라지니 주의한다.

> ⚠️ **함정**: `dd`는 강력한 만큼 위험하다. `if`(input file)와 `of`(output file)를 바꿔 쓰면 백업하려던 디스크를 빈 이미지로 덮어써 데이터를 통째로 날린다 — 그래서 "data destroyer"라는 별명이 있다. 또 `dump`는 ext2/3/4에 특화돼 xfs 등에는 쓸 수 없다(xfs는 `xfsdump`). 도구마다 지원 파일 시스템이 다르다는 점을 기억하자.

```bash
# 직접 쳐보기 — 백업 연습 (안전한 디렉터리에서)
mkdir -p /tmp/src /tmp/dst
echo "hello" > /tmp/src/a.txt
tar -czvf /tmp/backup.tar.gz /tmp/src      # tar 백업
tar -tzvf /tmp/backup.tar.gz               # 내용 확인(풀지 않고)
rsync -av /tmp/src/ /tmp/dst/              # rsync 동기화
echo "world" >> /tmp/src/a.txt
rsync -av /tmp/src/ /tmp/dst/              # 두 번째: 바뀐 것만 전송
```

## 한 주 통합 — 2단 구조로 꿰기

이번 주 핵심을 하나의 표로 정리하면 "저수준↔고수준" 패턴이 선명하게 드러난다.

| 영역 | 저수준(단일·수동) | 고수준(자동·의존성) |
|------|---------------------|----------------------|
| RPM 패키지 | `rpm -ivh` | `yum/dnf install` |
| DEB 패키지 | `dpkg -i` | `apt install` |
| 커널 모듈 | `insmod` / `rmmod` | `modprobe` / `modprobe -r` |

> 💡 **개념**: 세 줄 모두 "저수준은 파일/대상 하나를 직접 다루고 의존성을 자동 해결하지 못하며, 고수준은 저장소/의존성 지도를 참고해 자동 처리한다"는 같은 원리다. `rpm -ivh`가 의존성 오류로 멈추는 것, `dpkg -i`가 "설정 안 됨" 상태로 남는 것, `insmod`가 "Unknown symbol"로 실패하는 것 — 모두 같은 이유(의존성 수동)다. 그래서 실무·시험의 정답은 대개 고수준 도구다.

## 소스 설치와 커널 컴파일 — 같은 make, 다른 결과

| 흐름 | 일반 소스 설치 | 커널 컴파일 |
|------|----------------|-------------|
| 설정 | `./configure --prefix=` | `make menuconfig` (.config) |
| 빌드 | `make` | `make` |
| 설치 | `make install` | `make modules_install` + `make install` |

> 🔍 **더 깊이**: 둘 다 `make`로 빌드하지만 설정 방식이 다르다. 일반 소스는 `./configure`가 시스템을 정찰해 Makefile을 만들고, 커널은 `make menuconfig`로 기능을 직접 선택(`*`/`M`/제외)해 `.config`를 만든다. 커널은 설치도 두 갈래 — 모듈은 `make modules_install`(→/lib/modules), 커널 이미지는 `make install`(→/boot + GRUB). 라이브러리는 동적(`.so`, ldd/ldconfig로 관리)과 정적(`.a`)으로 나뉜다.

## 장치와 백업의 만남 — dd가 블록을 다루는 이유

> 💡 **개념**: Day 4의 "블록 장치(`b`) vs 문자 장치(`c`)"가 백업과 직결된다. `dd`가 디스크를 통째 복제할 수 있는 것은 디스크가 **블록 장치**라 블록 단위로 임의 접근이 되기 때문이다. 문자 장치(터미널·키보드)는 흐름이라 이미지로 복제할 수 없다. 그래서 `dd if=/dev/sda`(블록 장치)는 되지만 `dd if=/dev/tty0`(문자 장치)는 디스크 이미지 백업의 의미가 없다. 장치 종류 → 백업 가능 방식이 한 줄로 이어진다.

> 📚 **유래/사례**: 백업 도구들의 나이대가 곧 설계 철학을 보여준다. `dump`/`restore`와 `dd`는 1970년대 유닉스부터 있던 고전으로, 파일 시스템·장치를 직접 다룬다. `tar`(tape archive)는 본래 자기 테이프에 백업하려고 만든 도구라 이름에 "tape"가 남았다. `cpio`도 같은 시대 테이프 도구다. `rsync`는 1996년 등장한 비교적 신참으로, 네트워크 시대에 맞춰 "바뀐 부분만 전송"을 핵심으로 삼았다. 오래된 도구일수록 낮은 층위(블록·파일시스템·테이프)를, 새 도구일수록 효율적 네트워크 동기화를 지향한다.

## 마무리

Week 7은 시스템 관리의 토대를 쌓았다. 패키지(저수준 rpm/dpkg ↔ 고수준 yum/apt), 소스 컴파일(configure→make→make install)과 라이브러리(정적 .a / 동적 .so + ldd/ldconfig), 커널과 모듈(insmod ↔ modprobe, menuconfig→make→modules_install→install), 장치 파일(블록 b / 문자 c, 주·부 번호, udev)과 프린터(CUPS의 lp/lpr 두 계열), 그리고 백업(층위별 tar·rsync·dump·dd·cpio). 관통하는 패턴은 **저수준↔고수준 2단 구조**와 **작동 층위(파일·파일시스템·블록)**다. 이 두 렌즈로 보면 흩어진 명령들이 하나의 체계로 정렬된다.

**문제 9.** 백업 도구 `dd`의 작동 층위와 용도로 가장 정확한 것은?

A) 파일 단위로 동작하며 바뀐 파일만 증분 전송한다

B) 블록(장치) 단위로 동작하며 디스크를 비트 그대로 통째 복제한다

C) 파일시스템 단위로 동작하며 레벨 0~9 증분을 지원한다

D) 패키지 단위로 동작하며 의존성을 백업한다

**정답: B**

해설: `dd`는 가장 낮은 블록(장치) 단위로 동작해 빈 공간까지 포함한 디스크 이미지를 비트 그대로 복제하므로 디스크 복제·부팅 이미지에 쓴다. A는 rsync, C는 dump/restore의 특징이다. D는 백업 도구의 동작과 무관하다. `dd`는 if/of를 바꾸면 데이터를 날리므로 주의한다.

**문제 10.** 원격 서버로 바뀐 파일만 증분 전송하며 압축까지 적용해 동기화하려 한다. 가장 적절한 명령은?

A) `dd if=/src of=user@host:/backup`

B) `rsync -avz /src/ user@host:/backup/`

C) `tar -czvf /src user@host:/backup`

D) `cpio -o /src user@host`

**정답: B**

해설: `rsync`는 증분 전송이 핵심이며 `-a`(보존)·`-v`(상세)·`-z`(압축)로 원격 동기화에 가장 적합하다. A의 dd는 원격 경로 구문을 그렇게 쓰지 않고 블록 복제용이며, C의 tar는 원격 대상을 그 형식으로 받지 않고, D의 cpio도 원격 동기화 구문이 아니다.

**문제 11.** 다음 중 "저수준 단일 도구 ↔ 고수준 자동화 도구" 짝으로 잘못된 것은?

A) `rpm -ivh` ↔ `yum install`

B) `dpkg -i` ↔ `apt install`

C) `insmod` ↔ `modprobe`

D) `tar` ↔ `ldconfig`

**정답: D**

해설: tar(백업 아카이브)와 ldconfig(동적 링커 캐시 갱신)는 서로 다른 영역의 도구로 저수준↔고수준 짝이 아니다. A(RPM 패키지), B(DEB 패키지), C(커널 모듈)는 모두 "단일 대상 직접 처리 ↔ 의존성 자동 해결"의 올바른 2단 구조 짝이다.

**문제 12.** `dump`/`restore`와 `tar`의 차이로 가장 적절한 것은?

A) `dump`는 파일시스템 단위로 동작하며 레벨 0~9 증분 백업을 지원하고, `tar`는 파일·디렉터리 단위로 동작한다

B) `tar`는 블록 단위로 디스크를 복제하고, `dump`는 패키지를 백업한다

C) 둘 다 네트워크 전송 전용 도구다

D) `dump`는 압축만, `tar`는 증분만 지원한다

**정답: A**

해설: `dump`/`restore`는 파일 시스템 레벨에서 동작하며 레벨 0(전체)~9(증분)을 지원하고 ext 계열에 특화돼 있다. `tar`는 파일·디렉터리 단위의 아카이브·압축 도구다. B는 둘의 기능을 잘못 바꿨고, C는 네트워크 전용이 아니며, D는 두 도구의 특성을 뒤섞은 오답이다.
