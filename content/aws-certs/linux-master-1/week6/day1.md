# Day 1 - 프로세스 관리: PID부터 시그널·우선순위까지

리눅스에서 "실행 중인 프로그램"은 모두 **프로세스(process)**다. 우리가 `ls`를 치는 순간, 셸은 새 프로세스를 만들어 `ls` 프로그램을 그 안에서 돌린다. 디스크에 잠자고 있는 실행 파일(프로그램)과, 메모리에 올라와 CPU를 받아 동작하는 프로세스는 구분해야 한다. 프로그램은 명사, 프로세스는 동사다.

오늘은 프로세스를 식별하는 번호(PID/PPID)부터, 그 상태를 들여다보는 도구(ps·top·htop·pgrep·pstree), 프로세스에게 말을 거는 유일한 수단인 **시그널**(kill·killall), 그리고 누가 CPU를 더 먼저 받을지 정하는 **우선순위**(nice·renice)까지 한 번에 꿴다. 이 네 축이 리눅스마스터 1급 프로세스 영역의 거의 전부다.

## 프로세스의 신원 — PID와 PPID

모든 프로세스는 태어날 때 고유한 번호 **PID(Process ID)**를 부여받는다. 그리고 자신을 만든 부모 프로세스의 번호 **PPID(Parent PID)**를 함께 가진다. 즉 리눅스의 모든 프로세스는 가계도(tree)를 이룬다.

이 나무의 뿌리는 PID 1번이다. 전통적 init 시스템에서는 `init`, 현대 시스템에서는 `systemd`가 1번을 차지한다. 부팅 직후 커널이 직접 띄우는 첫 사용자 공간 프로세스이며, 모든 프로세스의 조상이다.

```bash
echo $$        # 현재 셸 자신의 PID
echo $PPID     # 현재 셸의 부모 PID
ps -p 1        # PID 1번이 무엇인지 확인 (systemd 또는 init)
```

> 💡 **개념**: PID 1번(init/systemd)은 절대 죽지 않는다. 부모가 먼저 종료된 자식(고아 프로세스)은 자동으로 1번에게 입양되어 정리된다. 이 입양 메커니즘이 시스템이 좀비로 가득 차지 않게 막는 핵심이다.

새 프로세스는 부모를 **fork()**해서 복제된 뒤 **exec()**로 다른 프로그램으로 갈아탄다. 이 fork-exec 모델은 Day 2에서 자세히 다룬다. 오늘은 "자식은 부모로부터 PPID로 연결되며, 부모 환경(변수·작업 디렉터리 등)을 물려받는다"는 점만 기억하자.

> 🔍 **직접 쳐보기**: `bash`를 한 번 더 실행해 서브셸로 들어간 뒤 `echo $$`로 PID를 확인하고, `echo $PPID`가 바깥 셸의 PID와 같은지 비교해 보자. `exit`로 나오면 다시 원래 PID로 돌아온다. 프로세스 계층이 눈에 보인다.

## 프로세스 목록 보기 — ps의 두 얼굴

`ps`(process status)는 현재 프로세스의 스냅샷을 보여준다. 문제는 `ps`가 역사적으로 두 가지 옵션 문법(BSD 스타일·UNIX 스타일)을 모두 지원해 헷갈린다는 점이다. 실무와 시험에서 압도적으로 많이 쓰는 두 조합만 확실히 익히면 된다.

| 명령 | 스타일 | 의미 | 특징 |
|------|--------|------|------|
| `ps aux` | BSD (하이픈 없음) | 모든 사용자의 모든 프로세스 | %CPU·%MEM·START 등 표시 |
| `ps -ef` | UNIX (하이픈 있음) | 모든 프로세스 전체 목록 | PPID 컬럼 표시 |
| `ps -u user` | UNIX | 특정 사용자 프로세스 | 사용자별 필터 |
| `ps -p PID` | UNIX | 특정 PID 정보 | 단일 프로세스 |

```bash
ps aux                 # 전체 프로세스 + CPU/메모리 사용률
ps -ef                 # 전체 프로세스 + PPID(부모 추적에 유리)
ps -ef | grep nginx    # 특정 프로그램 프로세스만 추리기
ps aux --sort=-%cpu    # CPU 사용률 내림차순 정렬
```

`ps aux`의 STAT(상태) 컬럼이 자주 출제된다. 각 글자의 의미를 알아두자.

| STAT | 의미 |
|------|------|
| R | 실행 중 또는 실행 대기(Running) |
| S | 인터럽트 가능한 대기(Sleeping) |
| D | 인터럽트 불가 대기(주로 I/O) |
| T | 정지(Stopped, Ctrl+Z 등) |
| Z | 좀비(Zombie, 종료됐으나 회수 안 됨) |
| <  | 높은 우선순위(낮은 nice) |
| N | 낮은 우선순위(높은 nice) |

> ⚠️ **함정**: `ps aux`에는 하이픈을 붙이지 않고, `ps -ef`에는 붙인다. `ps -aux`처럼 섞어 쓰면 일부 시스템에서 경고가 뜨거나 다르게 해석된다. "aux는 맨몸, ef는 하이픈"으로 외우자. 그리고 `Z`(좀비)는 종료된 자식을 부모가 회수(wait)하지 않아 PID만 남은 상태다 — Day 2 핵심.

> 📚 **유래/사례**: `ps aux`의 BSD 문법은 버클리 유닉스에서, `ps -ef`의 UNIX 문법은 AT&T 시스템 V에서 왔다. 리눅스의 procps는 둘을 모두 받아들이기 때문에 같은 정보를 두 방식으로 볼 수 있다. 시험에서는 "aux는 사용률, ef는 부모 추적"이라는 용도 차이로 출제되는 경우가 많다.

## 실시간 모니터링 — top과 htop

`ps`가 정지 사진이라면 `top`은 동영상이다. 기본 3초마다 갱신되며 CPU·메모리를 많이 먹는 프로세스를 위에서부터 보여준다.

```bash
top              # 실시간 프로세스 모니터 진입
```

`top` 화면 안에서 쓰는 단축키가 실기에 나온다.

| 키 | 동작 |
|----|------|
| `P` | CPU 사용률 순 정렬(기본) |
| `M` | 메모리 사용률 순 정렬 |
| `k` | 프로세스에 시그널 전송(kill) — PID 입력 |
| `r` | 우선순위 변경(renice) — PID 입력 |
| `1` | CPU 코어별 사용률 펼치기 |
| `q` | 종료 |

상단 요약줄의 **load average**(1·5·15분 평균 부하)도 자주 묻는다. CPU 코어 수보다 큰 값이 지속되면 과부하 신호다.

`htop`은 top의 개선판으로, 색상·마우스·코어별 막대그래프를 제공하고 화살표로 프로세스를 직접 선택해 F9로 kill할 수 있다. 다만 배포판 기본 설치가 아닌 경우가 많아 별도 설치(`yum install htop` 또는 `apt install htop`)가 필요하다.

> 💡 **개념**: `top`은 모든 배포판에 기본 탑재되지만 `htop`은 별도 설치가 필요한 외부 도구라는 점이 시험 포인트다. 둘 다 "k"로 시그널을 보내고 "r"(top)/F9(htop)로 우선순위를 바꾼다.

> 🔍 **직접 쳐보기**: `top`을 실행한 뒤 대문자 `M`을 눌러 메모리 정렬로 바꿔 보고, `1`을 눌러 코어별 사용률이 펼쳐지는지 확인하자. `q`로 빠져나온다. 단축키가 대소문자를 구분한다는 점에 주의(`P`는 정렬, 소문자 `p`는 다른 동작).

## 프로세스 찾기와 가계도 — pgrep·pstree

`ps -ef | grep` 조합은 흔하지만, 검색용 grep 프로세스 자신까지 결과에 끼어드는 단점이 있다. `pgrep`은 이름으로 PID만 깔끔하게 뽑아준다.

```bash
pgrep sshd          # sshd 프로세스들의 PID만 출력
pgrep -l sshd       # PID + 프로세스 이름 함께
pgrep -u root cron  # root 소유의 cron 프로세스 PID
pgrep -c bash       # 조건에 맞는 프로세스 개수
```

`pstree`는 프로세스를 부모-자식 트리 형태로 그려준다. 누가 누구를 띄웠는지 한눈에 보인다.

```bash
pstree              # 전체 프로세스 트리
pstree -p           # 각 프로세스의 PID 함께 표시
pstree -p 1         # systemd(1번) 아래 트리만
```

> 🔍 **직접 쳐보기**: `pstree -p | head -20`으로 시스템 최상단 트리를 보자. 맨 위에 `systemd(1)` 또는 `init(1)`이 있고, 그 아래로 모든 서비스가 가지처럼 뻗어 있다. PID 1번이 모든 것의 조상임을 눈으로 확인할 수 있다.

## 프로세스에 말 걸기 — 시그널과 kill

프로세스를 직접 멈추거나 재시작시키는 유일한 통신 수단이 **시그널(signal)**이다. `kill`이라는 이름 때문에 "죽이는" 명령으로 오해하기 쉽지만, 실제로는 "지정한 번호의 시그널을 보내는" 명령이다. 시그널 종류에 따라 종료·재설정·일시정지 등 다양한 동작을 한다.

핵심 시그널 세 개의 번호와 의미는 반드시 외운다.

| 번호 | 이름 | 의미 | 무시 가능? |
|------|------|------|-----------|
| 1 | SIGHUP | 터미널 끊김 / 설정 재읽기(reload) | 가능 |
| 9 | SIGKILL | 강제 종료(즉시, 무조건) | **불가** |
| 15 | SIGTERM | 정상 종료 요청(기본값) | 가능 |
| 2 | SIGINT | 인터럽트(Ctrl+C) | 가능 |
| 18/19 | SIGCONT/SIGSTOP | 재개 / 정지 | STOP은 불가 |

```bash
kill 1234            # PID 1234에 기본 시그널 15(SIGTERM) 전송
kill -9 1234         # 9번(SIGKILL) 강제 종료
kill -15 1234        # 15번(SIGTERM) 정상 종료 명시
kill -1 1234         # 1번(SIGHUP) — 보통 데몬 설정 재읽기
kill -HUP 1234       # 이름으로도 지정 가능
kill -l              # 시그널 번호↔이름 전체 목록
```

`kill`에 옵션 없이 PID만 주면 기본값은 **15번(SIGTERM)**이다. 이것은 "정리할 시간을 줄 테니 알아서 곱게 종료하라"는 정중한 요청이다. 프로세스는 이 시그널을 받아 열린 파일을 닫고 임시 파일을 지운 뒤 종료할 수 있다.

반면 **9번(SIGKILL)**은 프로세스에게 통보 없이 커널이 즉시 메모리에서 제거한다. 프로세스는 SIGKILL을 가로채거나 무시할 수 없으므로 확실히 죽는다. 대신 정리 작업을 못 하므로 임시 파일·잠금 파일이 남거나 데이터가 손상될 수 있다.

> ⚠️ **함정**: 항상 9번부터 쓰면 안 된다. **15번(정상 종료)을 먼저 시도하고, 그래도 안 죽으면 9번(강제)**을 쓰는 것이 올바른 순서다. SIGKILL(9)과 SIGSTOP(19)만이 무시·차단이 불가능한 두 시그널이라는 점도 자주 출제된다.

이름으로 한꺼번에 죽이려면 `killall`(이름 기준)이나 `pkill`(패턴 기준)을 쓴다.

```bash
killall httpd        # httpd라는 이름의 모든 프로세스에 시그널 15
killall -9 httpd     # 강제 종료
pkill -u alice       # alice 사용자의 모든 프로세스
pkill -HUP sshd      # sshd에 HUP 전송(설정 재읽기)
```

> 💡 **개념**: `kill`은 **PID**로, `killall`/`pkill`은 **이름/패턴**으로 시그널을 보낸다. SIGHUP(1)은 데몬에게 "죽지 말고 설정 파일만 다시 읽어라"는 의미로 자주 쓰인다(예: `kill -HUP $(pgrep -x sshd)`). 그래서 1번은 "재시작 없는 리로드"의 대명사다.

> 📚 **유래/사례**: SIGHUP의 H-U-P은 "Hang Up"(전화 끊기)의 약자다. 옛날 모뎀 터미널 연결이 끊기면 커널이 그 터미널에 붙은 프로세스에 SIGHUP을 보냈다. 오늘날 데몬들이 이 신호를 "설정 재읽기"로 재해석하면서, 서비스 무중단 리로드의 표준 신호가 되었다. `nohup`(no hang up) 명령이 바로 이 SIGHUP을 무시하게 만들어 로그아웃 후에도 프로세스를 살려두는 도구다.

## 우선순위 조정 — nice와 renice

CPU가 한정된 상황에서 어떤 프로세스를 먼저 돌릴지 정하는 값이 **nice 값**이다. 이름이 "친절함(nice)"인 이유는, 값이 높을수록 다른 프로세스에게 CPU를 양보하는 "착한" 프로세스가 되기 때문이다.

nice 값의 범위는 **-20부터 19까지**이며, 기본값은 0이다.

| nice 값 | 의미 | 우선순위 |
|---------|------|----------|
| -20 | 가장 이기적(양보 안 함) | 가장 높음 |
| 0 | 기본값 | 보통 |
| 19 | 가장 친절(가장 많이 양보) | 가장 낮음 |

```bash
nice -n 10 ./backup.sh     # nice 10으로 낮춰서 실행(양보)
nice -n -5 ./urgent.sh     # nice -5로 높여 실행(우선)
nice ./job.sh              # -n 생략 시 기본 +10 적용
```

이미 실행 중인 프로세스의 우선순위는 `renice`로 바꾼다.

```bash
renice 15 -p 1234          # PID 1234의 nice를 15로 변경
renice -n 5 -p 1234        # -n 옵션으로도 지정
renice 10 -u alice         # alice의 모든 프로세스 nice를 10으로
```

> ⚠️ **함정**: **음수 nice(우선순위 상승)는 root만 설정**할 수 있다. 일반 사용자는 자기 프로세스의 nice를 올릴(숫자를 키울) 수만 있고, 한 번 양보한 우선순위를 다시 끌어올리지 못한다. 또한 `nice`는 "새로 실행할 때", `renice`는 "이미 도는 프로세스"라는 점을 헷갈리지 말자. nice의 기본 적용값(-n 생략 시)은 +10이다.

> 💡 **개념**: nice 값과 실제 스케줄링 우선순위(PRI)는 반대 방향처럼 보이지만 연동된다. nice가 낮을수록(-20에 가까울수록) 우선순위가 높아 CPU를 더 자주 받는다. `top`에서 NI 컬럼이 nice 값, PR 컬럼이 커널 우선순위다.

> 🔍 **직접 쳐보기**: `nice -n 19 sleep 100 &`로 가장 양보하는 프로세스를 띄운 뒤 `ps -o pid,ni,cmd -p $!`로 NI 컬럼이 19인지 확인하자. 이어 `renice 5 -p $!`로 바꾸고 다시 확인하면 NI가 5로 줄어든다(일반 사용자는 올리기만 가능).

## 성능 분석 — 어느 자원이 병목인가

`top`은 "지금 누가 CPU를 먹고 있나"는 알려주지만 "어젯밤 3시에 무슨 일이 있었나"는 답하지 못한다. 실시간 관찰과 **과거 이력 수집**은 도구가 다르다.

### sysstat과 sar — 성능 이력을 남기는 표준 도구

**sysstat** 패키지는 시스템 활동을 주기적으로 수집해 파일로 남기고, **`sar`**(System Activity Reporter)로 그 이력을 다시 읽게 해 준다. 수집은 cron이 담당한다 — `/etc/cron.d/sysstat`에 등록된 **`sa1`**이 기본 10분마다 스냅숏을 뜨고 **`sa2`**가 하루치 요약 리포트를 만들며, 원본은 날짜별 파일 `sa01`, `sa02`…로 쌓인다.

| 항목 | RHEL 계열 | 데비안 계열 |
|------|-----------|-------------|
| 설치 | `dnf install sysstat` | `apt install sysstat` |
| 수집 시작 | 설치 후 서비스 시작 | `/etc/default/sysstat`에서 `ENABLED="true"`로 바꿔야 시작 |
| 데이터 위치 | `/var/log/sa/saDD` | `/var/log/sysstat/saDD` |

`sar`는 옵션 한 글자로 볼 자원을 고른다.

| 옵션 | 보여주는 것 | 눈여겨볼 값 |
|------|-------------|-------------|
| `-u` | CPU 사용률(기본) | `%user` `%system` `%iowait` `%idle` |
| `-r` | 메모리 사용량 | `kbmemfree` `%memused` `kbcached` |
| `-W` / `-S` | 스왑 발생량 / 스왑 공간 | `pswpin/s` `pswpout/s`, `%swpused` |
| `-b` | 디스크 I/O 전체 전송률 | `tps` `rtps` `wtps` |
| `-d` | 디스크 **장치별** 활동 | `await` `%util` |
| `-n DEV` | 네트워크 인터페이스별 트래픽 | `rxkB/s` `txkB/s` |
| `-q` | 실행 큐와 load average | `runq-sz` `ldavg-1/5/15` |

```bash
sar -u 1 5                        # CPU를 1초 간격 5회 실시간 관찰
sar -r                            # 오늘 수집된 메모리 이력 전체
sar -n DEV 2 3                    # 네트워크 인터페이스별 2초 간격 3회
sar -f /var/log/sa/sa15           # 15일자 파일에서 과거 이력 조회
sar -u -s 03:00:00 -e 04:00:00    # 특정 시간대만 잘라 보기
```

> 💡 **개념**: `sar`의 진짜 가치는 **`-f`로 과거를 되짚는 것**이다. 장애가 지나간 뒤 접속해 `top`을 봐야 이미 정상이지만, sar 데이터가 쌓여 있으면 그 시각의 CPU·메모리·디스크·네트워크를 나란히 놓고 무엇이 먼저 튀었는지 볼 수 있다.

> ⚠️ **함정**: 데비안·우분투는 sysstat을 설치만 해서는 **수집이 시작되지 않는다**. `/etc/default/sysstat`의 `ENABLED`를 `"true"`로 바꾸고 서비스를 다시 시작해야 데이터가 쌓인다.

### vmstat·iostat·mpstat·pidstat — 무엇을 답해 주는가

| 도구 | 답해 주는 질문 | 핵심 컬럼 |
|------|----------------|-----------|
| `vmstat 1` | 시스템 전체가 지금 무엇에 막혀 있나 | `r`(실행 대기), `b`(I/O 대기), `si`·`so`(스왑 in/out), `wa` |
| `iostat -x 1` | **어느 디스크**가 얼마나 바쁜가 | `tps`, `await`(평균 응답 ms), `%util`(장치 포화도) |
| `mpstat -P ALL 1` | **어느 CPU 코어**에 부하가 몰렸나 | 코어별 `%usr` `%sys` `%iowait` |
| `pidstat 1` | **어느 프로세스**가 자원을 먹나 | `-u` CPU, `-r` 메모리, `-d` 디스크 I/O |
| `free -h` | 메모리가 정말 부족한가 | `available`(실제 여유), `buff/cache` |
| `uptime` | 최근 부하 추세 | load average 1·5·15분 |

`sar`·`iostat`·`mpstat`·`pidstat`는 모두 **sysstat 패키지**에 함께 들어 있고, `vmstat`·`free`·`uptime`은 `procps`(procps-ng)의 기본 도구다.

### load average 읽는 법

`top`·`uptime` 상단의 세 숫자는 **1분·5분·15분 평균 부하**로, 리눅스에서는 "실행 중이거나 실행을 기다리는(R) 프로세스 + 인터럽트 불가 대기(D, 대개 디스크 I/O) 프로세스"의 평균 개수다.

- 판단 기준은 **CPU 코어 수**다. 코어가 4개면 4.0이 "빈틈없이 꽉 찬" 상태이고 8.0이면 절반이 순서를 기다리는 과부하다. 코어 수는 `nproc`으로 확인한다.
- 세 숫자의 **기울기**를 본다. `10.0 4.0 2.0`이면 부하가 급격히 오르는 중이고, `2.0 4.0 10.0`이면 이미 지나간 사건이다.
- 리눅스의 load average에는 **디스크 I/O 대기(D 상태)가 포함**되므로 CPU가 한가해도 스토리지가 느리면 값이 치솟는다.

### 병목 판단 흐름 — CPU인가, I/O인가, 메모리인가

load average가 높다는 사실만으로는 무엇을 늘려야 할지 알 수 없다. 세 갈래를 지표로 갈라낸다.

| 병목 | 결정적 지표 | 보조 신호 | 처방 방향 |
|------|-------------|-----------|-----------|
| **CPU bound** | `%user`+`%system` 높고 `%iowait` 낮음 | `vmstat`의 `r`이 코어 수보다 큼, `mpstat`에서 특정 코어 포화 | 코어 증설, 알고리즘 개선, `nice`로 배치 작업 양보 |
| **I/O bound** | `%iowait` 높음 | `vmstat`의 `b`가 큼, `iostat`의 `%util` 100% 근접·`await` 급증, `ps`의 `D` 상태 | 디스크 교체(SSD), I/O 분산, 쿼리·캐시 개선 |
| **메모리 부족** | `si`·`so`(스왑 in/out)가 지속 발생 | `free`의 `available` 바닥, `sar -W`의 `pswpout/s` 증가, OOM 로그 | 메모리 증설, 프로세스 사용량 축소 |

```bash
nproc                # 코어 수 — load average 해석의 기준
vmstat 1 5           # r / b / si / so / wa 를 한 화면에서 비교
iostat -x 1 3        # await·%util 로 디스크 포화 확인
pidstat -d 1 3       # I/O를 실제로 일으키는 프로세스 지목
```

> ⚠️ **함정**: `free`의 `free`(여유) 값이 작다고 메모리 부족이 아니다. 리눅스는 남는 메모리를 **버퍼·캐시**로 최대한 써 두었다가 필요하면 즉시 돌려준다. 실제 여유는 `available` 열로 판단하고, 진짜 부족의 증거는 **스왑 in/out(`si`·`so`)이 계속 발생하는 것**이다. 스왑 사용량이 높아도 유입·유출이 없으면 이미 잠든 페이지일 뿐 병목이 아니다.

> 🔍 **직접 쳐보기**: `vmstat 1 10`을 돌려 두고 다른 터미널에서 `dd if=/dev/zero of=/tmp/t bs=1M count=1000 oflag=direct`로 디스크 부하를 준 뒤 `b`와 `wa`가 함께 오르는지 보라. `iostat -x 1`에서 그 장치의 `%util`이 100%에 붙으면 "I/O bound"의 지표 조합이다. 끝나면 `rm /tmp/t`.

## 오늘의 정리

프로세스는 PID로 식별되고 PPID로 부모와 연결되어 트리를 이룬다. 상태는 `ps aux`(사용률)·`ps -ef`(부모 추적)·`top`(실시간)·`pstree`(계층)으로 본다. 제어는 시그널로 하며, 15(정상 종료) → 9(강제 종료) 순서가 원칙이고, 1(HUP)은 설정 재읽기다. 우선순위는 nice(-20~19)로 정하되 음수는 root 전용, `nice`는 실행 시·`renice`는 실행 중에 쓴다. 성능은 sysstat의 `sar`로 이력을 남겨 `-u/-r/-b/-n DEV`로 되짚고, `vmstat`(전체)·`iostat`(디스크)·`mpstat`(코어)·`pidstat`(프로세스)로 범위를 좁힌 뒤 `%iowait`·`r`/`b`·`si`/`so`로 CPU·I/O·메모리 중 어디가 병목인지 가른다. 이 좌표계를 잡으면 어떤 프로세스 문제도 풀린다.

## 📝 연습 문제

**문제 1.** 모든 프로세스를 부모 프로세스(PPID) 정보와 함께 출력하려 할 때 가장 적절한 명령은?

A) `ps aux`

B) `ps -ef`

C) `ps -u`

D) `ps -p`

**정답: B**

해설: `ps -ef`는 UNIX 스타일로 PPID 컬럼을 포함해 부모-자식 관계 추적에 적합하다. A(`ps aux`)는 %CPU·%MEM 등 사용률 중심이라 PPID가 기본 표시되지 않는다. C는 특정 사용자 필터, D는 특정 PID 조회 옵션으로 인자가 더 필요하다. "ef는 하이픈, aux는 맨몸"과 "ef는 부모 추적"으로 구분한다.

**문제 2.** 프로세스에 시그널을 보내는 `kill` 명령에서 옵션 없이 PID만 지정했을 때 기본으로 전송되는 시그널은?

A) 1번 (SIGHUP)

B) 2번 (SIGINT)

C) 9번 (SIGKILL)

D) 15번 (SIGTERM)

**정답: D**

해설: `kill PID`의 기본 시그널은 15번 SIGTERM으로, 프로세스에 정리할 시간을 주는 정상 종료 요청이다. A(SIGHUP)는 설정 재읽기, B(SIGINT)는 Ctrl+C 인터럽트, C(SIGKILL)는 강제 종료다. 올바른 순서는 15번을 먼저 시도하고 안 되면 9번을 쓰는 것이다.

**문제 3.** 다음 중 프로세스가 가로채거나 무시할 수 없어 반드시 동작하는 시그널은?

A) 1번 (SIGHUP)

B) 9번 (SIGKILL)

C) 15번 (SIGTERM)

D) 2번 (SIGINT)

**정답: B**

해설: 9번 SIGKILL은 프로세스가 핸들러로 가로채거나 무시할 수 없어 커널이 즉시 메모리에서 제거한다(SIGSTOP 19번도 동일하게 차단 불가). A·C·D는 모두 프로세스가 시그널 핸들러로 가로채거나 무시할 수 있다. 그래서 SIGKILL은 곱게 안 죽는 프로세스의 최후 수단이다.

**문제 4.** nice 값에 대한 설명으로 옳은 것은?

A) 범위는 0부터 39까지이며 값이 클수록 우선순위가 높다

B) 범위는 -20부터 19까지이며 값이 낮을수록 우선순위가 높다

C) 범위는 -19부터 20까지이며 일반 사용자도 음수로 낮출 수 있다

D) 범위는 1부터 99까지이며 root만 설정 가능하다

**정답: B**

해설: nice 값은 -20(가장 높은 우선순위)부터 19(가장 낮은 우선순위)까지이며 기본값은 0이다. 값이 낮을수록 CPU를 더 자주 받는다. A·C·D는 범위가 모두 틀렸다. 음수 nice(우선순위 상승)는 root만 설정할 수 있고, 일반 사용자는 양보(숫자 증가)만 가능하다.

**문제 5.** `httpd`라는 이름의 모든 프로세스를 한 번에 종료하려 한다. 가장 적절한 명령은?

A) `kill httpd`

B) `killall httpd`

C) `pstree httpd`

D) `nice httpd`

**정답: B**

해설: `killall`은 프로세스 이름을 기준으로 해당하는 모든 프로세스에 시그널(기본 15)을 보낸다. A(`kill`)는 PID만 받으므로 이름을 직접 쓸 수 없다. C(`pstree`)는 트리를 그려 보여줄 뿐 종료 기능이 없고, D(`nice`)는 우선순위 지정 명령이다. 이름이 아닌 PID로 보낼 때는 `kill`을 쓴다.

**문제 6.** 실행 중인 PID 2000번 프로세스의 nice 값을 10으로 변경하려 한다. 올바른 명령은?

A) `nice -n 10 2000`

B) `renice 10 -p 2000`

C) `kill -10 2000`

D) `pgrep -n 10 2000`

**정답: B**

해설: 이미 실행 중인 프로세스의 우선순위는 `renice`로 바꾸며 `renice 10 -p 2000` 형태로 쓴다. A(`nice`)는 새로 실행할 명령에만 적용되고 PID를 받지 않는다. C는 PID 2000에 10번 시그널(SIGUSR1)을 보내는 것이라 의미가 전혀 다르다. D(`pgrep`)는 이름으로 PID를 찾는 명령이다.

**문제 7.** SIGHUP(1번) 시그널을 실행 중인 데몬에 보내는 가장 일반적인 목적은?

A) 프로세스를 강제로 즉시 종료한다

B) 프로세스를 일시 정지시킨다

C) 데몬이 죽지 않고 설정 파일을 다시 읽도록 한다

D) 프로세스의 nice 값을 0으로 초기화한다

**정답: C**

해설: 많은 데몬은 SIGHUP(1)을 "재시작 없이 설정 파일을 다시 읽으라"는 신호로 해석해 무중단 리로드에 활용한다(예: `kill -HUP $(pgrep sshd)`). A는 SIGKILL(9), B는 SIGSTOP(19), D는 시그널과 무관한 nice 동작이다. HUP은 "Hang Up"에서 유래해 현재는 reload의 대명사가 되었다.
