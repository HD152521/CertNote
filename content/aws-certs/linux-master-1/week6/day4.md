# Day 4 - 작업 예약: cron의 5필드부터 at·batch까지

시스템 관리에서 가장 강력한 자동화 도구는 "정해진 시각에 알아서 도는 작업"이다. 매일 새벽 3시 백업, 매시 정각 로그 정리, 매주 월요일 보고서 생성 — 이 모든 반복 작업을 사람이 일일이 실행하지 않아도 되게 해 주는 것이 **작업 예약(job scheduling)**이다.

리눅스에는 두 종류의 예약 도구가 있다. **반복 실행**을 담당하는 **cron**과, **한 번만** 정해진 시각에 실행하는 **at/batch**다. cron은 데몬(crond)이 분 단위로 깨어나 예약 목록을 검사하고, at은 지정 시각이 되면 큐에 든 작업을 한 번 실행하고 끝낸다. 오늘의 핵심은 cron의 **5필드 시간 표기**를 정확히 읽고 쓰는 것이다.

## cron의 구조 — crond 데몬과 crontab

**cron**은 반복 작업을 예약하는 시스템이다. 백그라운드 데몬 `crond`가 1분마다 깨어나 모든 사용자의 예약 목록(crontab)을 확인하고, 실행 시각이 된 작업을 실행한다. 예약 목록을 담는 파일·테이블을 **crontab(cron table)**이라 부른다.

사용자별 crontab을 관리하는 명령이 `crontab`이다.

| 명령 | 동작 |
|------|------|
| `crontab -e` | 내 crontab 편집(없으면 새로 생성) |
| `crontab -l` | 내 crontab 목록 출력 |
| `crontab -r` | 내 crontab 전체 삭제 |
| `crontab -u user -e` | 특정 사용자의 crontab 편집(root) |

```bash
crontab -e              # 편집기로 내 예약 작업 추가/수정
crontab -l              # 현재 등록된 예약 작업 보기
crontab -r              # 모든 예약 작업 삭제(주의!)
crontab -u alice -l     # alice의 예약 작업 보기(root 권한)
```

> ⚠️ **함정**: `crontab -r`은 **확인 없이 전체를 삭제**한다. 편집하려던 `-e`를 키보드에서 한 칸 옆 `-r`로 잘못 누르면 모든 예약이 날아간다. 실무에서는 `crontab -l > backup.txt`로 백업 후 작업하는 습관이 권장된다. `-l`(목록)·`-e`(편집)·`-r`(삭제)을 명확히 구분하자.

## crontab의 5필드 — 시간 표기의 핵심

crontab 한 줄은 **5개의 시간 필드 + 실행할 명령**으로 구성된다. 이 5필드의 순서와 범위가 시험의 절대 핵심이다.

```
┌───────────── 분 (minute,   0-59)
│ ┌─────────── 시 (hour,     0-23)
│ │ ┌───────── 일 (day,      1-31)
│ │ │ ┌─────── 월 (month,    1-12)
│ │ │ │ ┌───── 요일 (weekday, 0-7, 0과 7 모두 일요일)
│ │ │ │ │
* * * * *  실행할_명령
```

| 위치 | 필드 | 범위 | 비고 |
|------|------|------|------|
| 1 | 분(minute) | 0-59 | |
| 2 | 시(hour) | 0-23 | 24시간제 |
| 3 | 일(day of month) | 1-31 | |
| 4 | 월(month) | 1-12 | jan-dec도 가능 |
| 5 | 요일(day of week) | 0-7 | **0과 7 = 일요일**, 1=월 … 6=토 |

특수 문자로 패턴을 표현한다.

| 기호 | 의미 | 예 |
|------|------|-----|
| `*` | 모든 값 | `* * * * *` = 매분 |
| `,` | 나열 | `0,30` = 0분과 30분 |
| `-` | 범위 | `1-5` = 1~5 |
| `/` | 간격(step) | `*/10` = 10마다 |

실전 예시로 패턴을 익히자.

```bash
# 분 시 일 월 요일  명령
  0  3  *  *  *    /backup.sh        # 매일 새벽 3시 0분
  30 2  *  *  1    /weekly.sh        # 매주 월요일 새벽 2시 30분
  0  */6 * *  *    /check.sh         # 6시간마다(0,6,12,18시)
  */10 * * *  *    /poll.sh          # 10분마다
  0  0  1  *  *    /monthly.sh       # 매월 1일 자정
  0  9  *  *  1-5  /workday.sh       # 평일(월~금) 오전 9시
  15 14 1  *  *    /report.sh        # 매월 1일 14시 15분
```

> 💡 **개념**: 5필드 순서는 "**분-시-일-월-요일**"이며 시간 단위가 작은 것부터 큰 것 순이다(요일만 예외로 맨 뒤). 요일은 0=일요일에서 시작해 6=토요일이고, **7도 일요일**로 인정된다. 24시간제이므로 오후 2시는 14다. 이 순서를 "분시일월요"로 외운다.

> ⚠️ **함정**: 일(3번째)과 요일(5번째)을 **둘 다 지정**하면 OR로 동작한다 — 둘 중 하나라도 맞으면 실행된다. 예를 들어 `0 0 13 * 5`는 "매월 13일 **또는** 매주 금요일"마다 실행되지(둘 다 만족하는 13일의 금요일만이 아님), AND가 아니다. 이 OR 동작은 함정 문제의 단골이다.

> 🔍 **직접 쳐보기**: `crontab -e`로 `*/2 * * * * date >> ~/crontest.log` 한 줄을 넣고 저장하자. 2분마다 현재 시각이 파일에 쌓인다. 몇 분 뒤 `cat ~/crontest.log`로 누적을 확인하고, 다 봤으면 `crontab -e`에서 그 줄을 지운다. 5필드가 실제로 어떻게 도는지 눈으로 본다.

## 시스템 crontab — /etc/crontab과 cron.d

사용자 crontab(`crontab -e`로 만드는 것)과 별개로, 시스템 전역 예약을 두는 곳이 있다. 바로 `/etc/crontab` 파일과 `/etc/cron.d/` 디렉터리다.

이들의 결정적 차이는 **사용자(user) 필드가 하나 더 있다**는 점이다. 사용자 crontab은 그 사용자 권한으로 실행되므로 누구인지 적을 필요가 없지만, 시스템 crontab은 어느 사용자 권한으로 실행할지 명시해야 한다.

```
# /etc/crontab 형식 (필드 6개 = 5시간필드 + 사용자 + 명령)
# 분 시 일 월 요일  사용자  명령
  0  4  *  *  *    root    /usr/local/bin/cleanup.sh
```

| 위치 | 사용자 crontab | 시스템 crontab(/etc/crontab) |
|------|----------------|------------------------------|
| 만드는 법 | `crontab -e` | 파일 직접 편집 |
| 필드 수 | 5필드 + 명령 | 5필드 + **사용자** + 명령 |
| 실행 권한 | 등록한 사용자 | 지정한 사용자 필드 |
| 저장 위치 | `/var/spool/cron/사용자명` | `/etc/crontab`, `/etc/cron.d/*` |

또한 정해진 주기별 디렉터리도 있다. 스크립트를 그냥 넣어두기만 하면 자동 실행된다.

| 디렉터리 | 실행 주기 |
|----------|-----------|
| `/etc/cron.hourly/` | 매시간 |
| `/etc/cron.daily/` | 매일 |
| `/etc/cron.weekly/` | 매주 |
| `/etc/cron.monthly/` | 매월 |

> 💡 **개념**: **사용자 crontab은 5필드, 시스템 crontab(/etc/crontab·cron.d)은 6필드(사용자 추가)**라는 차이가 핵심 출제 포인트다. `/etc/cron.d/`는 패키지가 자기 예약을 추가하기 좋은 곳으로, `/etc/crontab`과 같은 6필드 형식을 쓴다. `cron.daily` 같은 디렉터리는 시각을 적지 않고 스크립트만 넣는다(실행 시각은 anacron/시스템이 관리).

> 📚 **유래/사례**: cron은 그리스어 'chronos'(시간)에서 왔다. 1970년대 유닉스부터 있었고, 노트북처럼 항상 켜져 있지 않은 시스템을 위해 `anacron`이 추가되었다 — cron은 정확히 그 시각에 꺼져 있으면 작업을 건너뛰지만, anacron은 "마지막 실행 후 N일 지났으면 켜진 직후에라도 실행"한다. `cron.daily` 등이 anacron과 연동되는 이유다.

## 접근 제어 — cron.allow와 cron.deny

누가 cron을 쓸 수 있는지는 두 파일로 제어한다.

| 파일 | 의미 |
|------|------|
| `/etc/cron.allow` | 여기 적힌 사용자만 cron 사용 가능(화이트리스트) |
| `/etc/cron.deny` | 여기 적힌 사용자만 cron 사용 불가(블랙리스트) |

판정 규칙은 명확하다. **`cron.allow`가 존재하면 그 목록만 허용**되고 `cron.deny`는 무시된다. `cron.allow`가 없고 `cron.deny`만 있으면 deny 목록 외 전원이 허용된다. 둘 다 없으면 보통 root만(또는 배포판에 따라 전원) 허용된다.

> 💡 **개념**: 우선순위는 **allow > deny**다. allow 파일이 존재하는 순간 그것이 유일한 기준이 되어 deny는 효력을 잃는다. at도 동일하게 `/etc/at.allow`·`/etc/at.deny`로 제어된다.

## 한 번만 실행 — at과 batch

cron이 "반복"이라면 `at`은 "딱 한 번"이다. 지정한 시각에 명령을 한 번 실행하고 큐에서 사라진다.

```bash
at 17:00                  # 오후 5시에 실행할 명령 입력 모드
at> /usr/local/bin/report.sh
at> <Ctrl+D로 입력 종료>

at now + 2 hours          # 지금부터 2시간 뒤
at 10:30 tomorrow         # 내일 오전 10시 30분
at midnight               # 오늘 자정
echo "/backup.sh" | at 3am  # 파이프로 명령 전달
```

at 작업을 관리하는 명령이 따로 있다.

| 명령 | 동작 |
|------|------|
| `at 시각` | 그 시각에 실행할 작업 등록 |
| `atq` (또는 `at -l`) | 대기 중인 at 작업 목록 |
| `atrm 번호` (또는 `at -d`) | 대기 작업 삭제 |

`batch`는 at의 변형으로, **시각을 지정하지 않고** 시스템 부하(load average)가 낮아지면(보통 0.8 미만) 자동으로 실행한다. CPU가 한가할 때 무거운 작업을 돌리고 싶을 때 쓴다.

```bash
batch                     # 시스템이 한가해지면 실행
at> /heavy-compute.sh
at> <Ctrl+D>
```

| 구분 | cron | at | batch |
|------|------|-----|-------|
| 실행 횟수 | 반복 | 1회 | 1회 |
| 실행 시점 | 정해진 주기 | 지정 시각 | 부하 낮을 때 |
| 데몬 | crond | atd | atd |
| 등록 | crontab -e | at 시각 | batch |

> ⚠️ **함정**: **cron은 반복, at/batch는 1회성**이다. "매일 새벽 백업"은 cron, "내일 한 번만 점검"은 at이다. at은 입력을 `Ctrl+D`(EOF)로 끝내며, 등록 목록은 `atq`, 삭제는 `atrm`이다(`at -l`/`at -d`도 동일). batch는 시각이 아니라 부하를 기준으로 실행한다는 점이 at과의 차이다.

> 🔍 **직접 쳐보기**: `echo "echo hello > ~/at-test.txt" | at now + 1 minute`을 실행하고 `atq`로 대기 목록을 확인하자. 1분 뒤 `cat ~/at-test.txt`에 hello가 적혀 있으면 성공이고, `atq`에서는 작업이 사라진다(1회성 확인). 취소하려면 `atq`로 번호를 보고 `atrm 번호`.

## 오늘의 정리

cron은 crond 데몬이 분 단위로 검사하는 반복 예약 시스템이다. crontab은 `-e`(편집)·`-l`(목록)·`-r`(삭제, 주의)로 관리하며, 5필드는 "분(0-59) 시(0-23) 일(1-31) 월(1-12) 요일(0-7, 0·7=일)" 순서다. `*,-/` 기호로 패턴을 만들고, 일·요일을 동시 지정하면 OR다. 시스템 crontab(/etc/crontab·cron.d)은 사용자 필드가 더 붙어 6필드다. 접근은 allow>deny 우선순위로 제어한다. at/batch는 1회성으로, at은 지정 시각·batch는 낮은 부하 시 실행하며 `atq`·`atrm`으로 관리한다.

**문제 1.** crontab의 시간 필드 5개를 왼쪽부터 순서대로 바르게 나열한 것은?

A) 시 - 분 - 일 - 월 - 요일

B) 분 - 시 - 일 - 월 - 요일

C) 분 - 시 - 월 - 일 - 요일

D) 요일 - 분 - 시 - 일 - 월

**정답: B**

해설: crontab 5필드는 "분(0-59) - 시(0-23) - 일(1-31) - 월(1-12) - 요일(0-7)" 순서다. A는 분과 시가 뒤바뀌었고, C는 일과 월이 뒤바뀌었으며, D는 요일이 맨 앞에 오는 잘못된 순서다. "분시일월요"로 외운다.

**문제 2.** crontab 항목 `30 2 * * 1 /backup.sh`가 실행되는 시점으로 옳은 것은?

A) 매일 오전 1시 2분 30초

B) 매주 월요일 오전 2시 30분

C) 매월 1일 오전 2시 30분

D) 매주 일요일 오전 2시 30분

**정답: B**

해설: 필드 순서가 분(30)-시(2)-일(*)-월(*)-요일(1)이므로 "매주 월요일 오전 2시 30분"이다. 요일 필드의 1은 월요일이다(0·7=일요일). A는 초 단위가 cron에 없고 분/시 해석이 틀렸으며, C는 요일이 아니라 일 필드를 본 오답, D는 요일 0/7(일요일)과 혼동했다.

**문제 3.** crontab 요일 필드에서 일요일을 나타내는 값으로 모두 옳은 것은?

A) 0과 7

B) 1과 8

C) 6과 7

D) 7만 가능

**정답: A**

해설: cron 요일 필드는 0~7 범위에서 0과 7이 모두 일요일을 의미하며, 1=월요일 … 6=토요일이다. B(8)는 범위를 벗어났고, C(6)는 토요일이며, D는 0도 일요일임을 놓쳤다. 일요일이 양 끝(0과 7)에 모두 매핑된다는 점이 함정 포인트다.

**문제 4.** `*/15 * * * *`로 예약된 작업의 실행 주기로 옳은 것은?

A) 매일 15시에 실행

B) 매월 15일에 실행

C) 15분마다 실행

D) 15초마다 실행

**정답: C**

해설: 첫 번째(분) 필드의 `*/15`는 "15분 간격(step)"을 의미해 매시 0·15·30·45분에 실행된다. A는 시 필드, B는 일 필드와 혼동한 것이고, D는 cron이 초 단위를 지원하지 않으므로 틀렸다. `/`는 간격을 나타내는 step 기호다.

**문제 5.** 사용자 crontab(`crontab -e`)과 시스템 crontab(`/etc/crontab`)의 가장 큰 형식 차이는?

A) 시스템 crontab에는 시간 필드가 없다

B) 시스템 crontab에는 실행 사용자 필드가 추가되어 6필드가 된다

C) 사용자 crontab은 분 단위를 지원하지 않는다

D) 두 형식은 완전히 동일하다

**정답: B**

해설: 시스템 crontab(`/etc/crontab`, `/etc/cron.d/*`)은 5개 시간 필드 뒤에 "실행 사용자" 필드가 하나 더 붙어 6필드다(어느 사용자 권한으로 실행할지 지정). 사용자 crontab은 등록자 권한으로 돌므로 사용자 필드가 없다(5필드). A·C는 사실이 아니고, D는 사용자 필드 차이를 무시한 오답이다.

**문제 6.** cron 접근 제어 파일 `/etc/cron.allow`와 `/etc/cron.deny`의 우선순위에 대한 설명으로 옳은 것은?

A) cron.allow가 존재하면 그 목록만 허용되고 cron.deny는 무시된다

B) cron.deny가 항상 cron.allow보다 우선한다

C) 두 파일이 모두 있으면 cron 자체가 비활성화된다

D) cron.allow는 블랙리스트, cron.deny는 화이트리스트다

**정답: A**

해설: `cron.allow`가 존재하면 그것이 유일한 기준(화이트리스트)이 되어 그 목록의 사용자만 허용되고 `cron.deny`는 무시된다(allow > deny). B는 우선순위가 반대이고, C는 사실이 아니며, D는 allow(화이트리스트)와 deny(블랙리스트)의 역할을 뒤바꿨다.

**문제 7.** cron, at, batch의 차이에 대한 설명으로 옳은 것은?

A) cron은 1회성, at은 반복 실행이다

B) cron은 반복 실행, at은 지정 시각에 1회, batch는 시스템 부하가 낮을 때 1회 실행한다

C) batch는 정해진 시각에 반복 실행한다

D) at과 batch는 모두 crond 데몬이 처리한다

**정답: B**

해설: cron은 정해진 주기로 반복, at은 지정한 시각에 한 번, batch는 시각 대신 시스템 부하(load average)가 낮아질 때 한 번 실행한다. A는 cron과 at의 성격을 뒤바꿨고, C는 batch가 부하 기준 1회임을 무시했다. D는 at/batch가 crond가 아니라 atd 데몬이 처리하므로 틀렸다.
