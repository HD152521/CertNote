# Day 2 - 데몬과 프로세스 생애: fork·exec부터 좀비·고아까지

어제 우리는 프로세스를 식별하고 제어하는 법을 배웠다. 오늘은 한 걸음 더 들어가 **프로세스가 어떻게 태어나고, 어떻게 일하며, 어떻게 죽는지** 그 생애 전체를 들여다본다. 핵심은 네 가지다 — 백그라운드에서 묵묵히 도는 **데몬(daemon)**, 화면을 차지하는 **포그라운드**와 뒤로 보내는 **백그라운드**, 부모가 회수하지 않아 시체로 남은 **좀비**와 부모를 잃은 **고아**, 그리고 모든 프로세스 생성의 원리인 **fork와 exec**.

이 개념들은 어제의 PID/PPID 가계도 위에서 자연스럽게 이어진다. 프로세스가 자식을 낳고(fork), 다른 프로그램으로 변신하고(exec), 죽은 뒤 부모가 거두는(wait) 한살이를 이해하면 좀비와 고아가 왜 생기는지 단번에 풀린다.

## 데몬이란 무엇인가

**데몬(daemon)**은 사용자와 직접 대화하지 않고 백그라운드에서 특정 서비스를 제공하는 프로세스다. 웹 서버(httpd), SSH 접속(sshd), 예약 작업(crond), 메일(postfix) 등이 모두 데몬이다. 이름 끝에 **'d'**가 붙는 관례가 있어 sshd·httpd·crond처럼 d로 끝나면 십중팔구 데몬이다.

데몬의 특징은 다음과 같다.

| 특징 | 설명 |
|------|------|
| 제어 터미널 없음 | 특정 터미널에 묶이지 않아 로그아웃해도 계속 동작 |
| 백그라운드 상주 | 부팅 시 시작되어 시스템 종료까지 메모리에 상주 |
| 부모는 보통 1번 | systemd/init이 직접 관리하거나 입양 |
| 이름에 'd' | sshd, httpd, crond, rsyslogd 등 |

데몬이 서비스를 제공하는 방식은 크게 두 가지다.

| 방식 | 동작 | 예 |
|------|------|-----|
| Standalone(독립) | 데몬이 항상 떠 있다가 요청을 직접 처리 | httpd, sshd |
| Super-daemon(슈퍼) | xinetd/inetd가 대기하다 요청 시 자식 데몬 실행 | 옛 telnet, ftp |

> 💡 **개념**: standalone 방식은 응답이 빠르지만 항상 메모리를 차지한다. super-daemon(xinetd) 방식은 평소 메모리를 아끼지만 요청마다 새로 띄우느라 응답이 느리다. 자주 쓰는 서비스는 standalone, 가끔 쓰는 서비스는 super-daemon이 유리하다는 트레이드오프가 시험에 나온다.

> 📚 **유래/사례**: 'daemon'은 그리스 신화의 "보이지 않게 일을 돕는 정령"에서 따왔다. MIT의 Project MAC에서 백그라운드 보조 프로세스를 이렇게 부른 것이 시초다. 악마(demon)와 철자가 다르며, 사용자 눈에 안 보이게 묵묵히 일한다는 뜻을 담았다.

## 포그라운드와 백그라운드

셸에서 명령을 그냥 실행하면 **포그라운드(foreground)**로 돈다. 이때 셸은 그 명령이 끝날 때까지 기다리며, 우리는 다른 명령을 칠 수 없다. 명령 끝에 **`&`**를 붙이면 **백그라운드(background)**로 보내져, 셸은 바로 프롬프트를 돌려주고 우리는 계속 작업할 수 있다.

```bash
sleep 100          # 포그라운드: 100초 동안 프롬프트가 멈춤
sleep 100 &        # 백그라운드: 즉시 프롬프트 복귀, [1] 12345 출력
```

실행 중인 작업(job)을 포그라운드와 백그라운드 사이에서 옮기는 명령들이 핵심이다.

| 명령/키 | 동작 |
|---------|------|
| `&` (명령 뒤) | 처음부터 백그라운드 실행 |
| `Ctrl+Z` | 포그라운드 작업을 **일시 정지**(Stopped) |
| `jobs` | 현재 셸의 작업 목록과 작업 번호 확인 |
| `bg %1` | 정지된 1번 작업을 백그라운드에서 **재개** |
| `fg %1` | 1번 작업을 포그라운드로 가져옴 |
| `nohup ... &` | 로그아웃 후에도 살아남게 실행 |

```bash
sleep 200            # 실행 중...
# (Ctrl+Z 입력) → [1]+ Stopped  sleep 200
jobs                 # [1]+ Stopped sleep 200
bg %1                # 백그라운드로 재개 → [1]+ sleep 200 &
fg %1                # 다시 포그라운드로
nohup ./long.sh &    # 로그아웃해도 계속, 출력은 nohup.out에 저장
```

> ⚠️ **함정**: `Ctrl+Z`는 종료가 아니라 **일시 정지(SIGSTOP, 상태 T)**다. 종료는 `Ctrl+C`(SIGINT)다. 정지된 작업은 `bg`/`fg`로 되살려야 하며, 그냥 두고 셸을 닫으면 사라질 수 있다. 또한 `&`만으로는 셸 종료 시 SIGHUP을 받아 죽을 수 있으므로, 로그아웃 후에도 살리려면 `nohup`을 함께 써야 한다.

> 🔍 **직접 쳐보기**: `sleep 300`을 실행하고 `Ctrl+Z`로 멈춘 뒤 `jobs`로 상태가 `Stopped`인지 보자. `bg %1`로 재개하면 `Running`으로 바뀐다. `fg %1`로 다시 가져와 `Ctrl+C`로 종료하면 완전히 사라진다. 작업 제어의 한 사이클이다.

## fork와 exec — 프로세스 탄생의 원리

리눅스에서 새 프로그램을 실행하는 과정은 **fork → exec** 두 단계로 이루어진다. 이 모델은 유닉스 설계의 핵심이다.

1. **fork()**: 부모 프로세스가 자기 자신을 거의 똑같이 **복제**한다. 이때 새 PID를 가진 자식 프로세스가 생기고, 자식의 PPID는 부모의 PID가 된다. 복제 직후에는 부모와 자식이 같은 프로그램 코드를 실행한다.

2. **exec()**: 복제된 자식이 자신의 메모리 내용을 **다른 프로그램으로 통째로 교체**한다. PID는 그대로 유지되지만, 실행되는 프로그램은 완전히 바뀐다.

```
[셸 프로세스] --fork()--> [자식(셸 복제본)] --exec("/bin/ls")--> [ls 프로세스]
   PID 1000                  PID 1500              PID 1500(유지)
                             PPID 1000             PPID 1000
```

예를 들어 셸에서 `ls`를 치면, 셸은 자신을 fork해 자식을 만들고, 그 자식이 exec로 `ls` 프로그램이 된 뒤 실행을 마치면 종료된다. 부모 셸은 `wait()`로 자식이 끝나길 기다렸다가 프롬프트를 돌려준다.

| 시스템 호출 | 역할 | PID 변화 |
|------------|------|----------|
| fork() | 프로세스 복제(자식 생성) | 새 PID 생성 |
| exec() | 현재 프로세스를 다른 프로그램으로 교체 | PID 유지 |
| wait() | 부모가 자식 종료를 기다리고 회수 | — |
| exit() | 프로세스 종료(종료 코드 반환) | — |

> 💡 **개념**: exec는 **새 프로세스를 만들지 않는다**. 현재 프로세스의 껍데기(PID)는 그대로 두고 알맹이(실행 코드)만 갈아끼운다. 그래서 `exec ls`를 셸에서 직접 치면 셸 자신이 ls로 변신해 버려, ls가 끝나면 셸도 함께 종료된다. fork(복제)와 exec(교체)를 분리한 것이 유닉스의 우아함이다.

> 📚 **유래/사례**: fork-exec 분리 덕분에 셸은 자식을 fork한 직후, exec 전에 입출력 리다이렉션(`>`, `<`)이나 파이프(`|`)를 설정할 수 있다. 만약 "복제와 교체"가 한 번에 묶여 있었다면 이런 유연한 입출력 재배치가 불가능했을 것이다. 이 설계가 유닉스 파이프라인 철학의 토대다.

## 좀비 프로세스 — 회수되지 않은 시체

자식 프로세스가 `exit()`로 종료하면, 커널은 그 종료 코드를 부모가 가져갈 수 있도록 잠시 보관한다. 부모가 `wait()`를 호출해 이 종료 코드를 거두면 자식의 흔적이 완전히 사라진다. 그런데 부모가 `wait()`를 하지 않으면, 자식은 이미 죽었지만 종료 코드만 남은 채 프로세스 테이블에 흔적이 남는다. 이것이 **좀비(zombie, defunct) 프로세스**다.

| 항목 | 좀비 프로세스 |
|------|--------------|
| 상태(STAT) | Z (또는 `<defunct>` 표시) |
| 메모리 | 거의 사용 안 함(껍데기만) |
| 원인 | 부모가 wait()로 종료 코드를 회수하지 않음 |
| 위험 | PID 자리를 차지 — 다량 누적 시 PID 고갈 |
| 해결 | 부모 프로세스를 종료/재시작 → 좀비가 1번에 입양되어 정리 |

```bash
ps aux | grep -w Z         # 좀비 상태 프로세스 찾기
ps -ef | grep defunct      # defunct로 표시된 좀비 확인
```

좀비는 이미 죽은 상태라 `kill -9`로 죽일 수 없다(이미 죽어 있으니까). 좀비를 없애려면 그 **부모 프로세스**를 종료하거나 재시작해야 한다. 부모가 사라지면 좀비는 PID 1번(systemd/init)에 입양되고, 1번이 즉시 `wait()`로 회수해 정리한다.

> ⚠️ **함정**: 좀비 프로세스는 메모리를 거의 안 쓰지만 **PID 슬롯**을 점유한다. 잘못 만든 프로그램이 좀비를 계속 양산하면 PID가 고갈되어 새 프로세스를 못 만드는 사태가 온다. 좀비를 `kill -9 좀비PID`로 죽이려는 시도는 무의미하다 — 표적은 **부모**다.

## 고아 프로세스 — 부모를 잃은 자식

**고아(orphan) 프로세스**는 좀비와 정반대 상황이다. 자식이 아직 살아 일하고 있는데 **부모가 먼저 종료**해 버린 경우다.

좀비가 "자식은 죽었는데 부모가 안 거둠"이라면, 고아는 "부모가 죽었는데 자식은 살아 있음"이다. 이 둘을 뒤집어 외우면 헷갈리지 않는다.

부모를 잃은 고아는 즉시 **PID 1번(systemd/init)에 입양**된다. 입양된 고아의 PPID는 1번으로 바뀌고, 1번이 그 부모 역할을 대신해 나중에 고아가 종료하면 `wait()`로 깔끔히 회수한다. 따라서 고아는 좀비와 달리 **시스템에 해롭지 않다** — 정상적인 입양 메커니즘으로 처리된다.

| 구분 | 좀비(Zombie) | 고아(Orphan) |
|------|--------------|--------------|
| 자식 상태 | 죽음(종료됨) | 살아 있음(실행 중) |
| 부모 상태 | 살아 있으나 wait 안 함 | 먼저 종료됨 |
| PPID | 원래 부모 | 1번으로 변경(입양) |
| 위험성 | PID 점유, 누적 시 문제 | 무해(1번이 정상 회수) |
| 해결 | 부모 종료/재시작 | 자동 입양으로 해결 |

> 💡 **개념**: 핵심 대비표 한 줄 — **좀비는 죽은 자식 + 안 거두는 부모(위험), 고아는 산 자식 + 죽은 부모(무해, 1번이 입양)**. 시험은 거의 항상 이 둘을 뒤바꿔 함정을 낸다. "Z 상태 = 좀비, defunct 표시"도 함께 외운다.

> 🔍 **직접 쳐보기**: `ps -ef`를 실행해 PPID(세 번째 컬럼)가 `1`인 프로세스들을 살펴보자. 부팅 시 시작된 데몬들과 입양된 고아들이 모두 1번을 부모로 가진다. 1번이 어떻게 모든 미아의 보호자 역할을 하는지 실제 목록으로 확인할 수 있다.

> 📚 **유래/사례**: 고아 입양 메커니즘이 없다면, 백그라운드로 실행한 `nohup ./job &` 같은 프로세스는 셸(부모)이 종료되는 순간 회수자 없는 상태가 되어 결국 좀비가 될 것이다. 1번 프로세스의 입양 덕분에 우리는 로그아웃 후에도 백그라운드 작업을 안심하고 돌릴 수 있다.

## 오늘의 정리

데몬은 터미널 없이 백그라운드에서 서비스를 제공하며 이름이 보통 'd'로 끝나고, standalone과 super-daemon 두 방식이 있다. 작업 제어는 `&`(백그라운드)·`Ctrl+Z`(정지)·`bg`·`fg`·`jobs`·`nohup`으로 한다. 새 프로세스는 fork(복제)→exec(교체)로 탄생하며 exec는 PID를 유지한다. 좀비는 죽은 자식을 부모가 안 거둔 위험 상태(부모 처리로 해결), 고아는 부모를 잃은 산 자식이 1번에 입양되는 무해한 상태다. 이 한살이를 이해하면 프로세스 영역이 하나로 꿰인다.

A) 제어 터미널에 묶이지 않아 로그아웃해도 계속 동작한다

B) 이름이 보통 'd'로 끝난다(sshd, httpd, crond 등)

C) 반드시 포그라운드에서 사용자와 대화하며 동작한다

해설: 데몬은 사용자와 직접 대화하지 않고 백그라운드에서 서비스를 제공하는 프로세스이므로 C가 틀렸다. A·B·D는 모두 데몬의 올바른 특징이다. 'd' 접미사(sshd·crond), 터미널 비종속, 백그라운드 상주가 데몬의 3대 특징이다.

A) 작업이 SIGINT로 즉시 종료된다

**문제 3.** 새 프로그램을 실행하는 fork-exec 모델에 대한 설명으로 옳은 것은?

A) fork()는 현재 프로세스를 다른 프로그램으로 교체하고 PID를 바꾼다

B) exec()는 새 프로세스를 생성하며 새 PID를 부여한다

C) fork()는 프로세스를 복제해 새 PID의 자식을 만들고, exec()는 PID를 유지한 채 프로그램만 교체한다

D) fork()와 exec()는 항상 한 번의 시스템 호출로 동시에 처리된다

**정답: C**

해설: fork()는 프로세스를 복제해 새 PID의 자식을 만들고, exec()는 그 자식의 PID를 유지한 채 실행 코드만 다른 프로그램으로 교체한다. A·B는 fork와 exec의 역할을 뒤바꿨다. D는 둘이 분리되어 있어 그 사이에 리다이렉션·파이프를 설정할 수 있다는 유닉스 설계의 핵심을 놓친 설명이다.

**문제 4.** 좀비(zombie) 프로세스가 발생하는 원인으로 가장 정확한 것은?

A) 자식이 종료됐는데 부모가 wait()로 종료 코드를 회수하지 않아서

B) 부모가 먼저 종료되어 자식이 1번에 입양되어서

C) 프로세스가 nice 값을 너무 높게 설정해서

D) 프로세스가 SIGKILL을 무시해서

**정답: A**

해설: 좀비는 자식이 exit()로 종료한 뒤 부모가 wait()로 종료 코드를 거두지 않아 프로세스 테이블에 Z 상태로 남는 것이다. B는 고아(orphan)의 상황이다. C·D는 좀비와 무관하다. 좀비는 부모를 종료/재시작하면 1번에 입양되어 정리된다.

**문제 5.** 고아(orphan) 프로세스에 대한 설명으로 옳은 것은?

A) 자식이 종료됐는데 부모가 회수하지 않아 Z 상태로 남는다

B) 부모가 먼저 종료되어 살아 있는 자식의 PPID가 1번으로 바뀌며 무해하다

C) 메모리를 과다하게 점유해 시스템을 마비시킨다

D) kill -9로만 제거할 수 있다

**정답: B**

해설: 고아는 부모가 먼저 종료된 뒤에도 살아 있는 자식으로, 즉시 PID 1번(systemd/init)에 입양되어 PPID가 1로 바뀌고 종료 시 정상 회수된다(무해). A는 좀비의 설명이다. C·D는 고아의 특징이 아니다. "좀비=죽은 자식, 고아=산 자식"으로 구분한다.

**문제 6.** 좀비 프로세스를 제거하기 위한 가장 올바른 방법은?

A) 좀비 PID에 `kill -9`를 보낸다

B) 좀비 PID의 nice 값을 19로 낮춘다

C) 좀비를 만든 부모 프로세스를 종료하거나 재시작한다

D) 시스템 전체를 재부팅하는 것이 유일한 방법이다

**정답: C**

해설: 좀비는 이미 죽은 상태라 `kill -9`가 통하지 않으므로(A 오답), 그 부모 프로세스를 종료/재시작해야 한다. 부모가 사라지면 좀비는 1번에 입양되어 즉시 회수된다. B는 무관하고, D는 부모만 처리하면 되므로 과도한 조치다.

**문제 7.** 로그아웃한 뒤에도 백그라운드 작업이 SIGHUP에 죽지 않고 계속 실행되도록 하려는 명령은?

A) `./job.sh &`

B) `nohup ./job.sh &`

C) `Ctrl+Z` 후 `bg`

D) `kill -HUP ./job.sh`

**정답: B**

해설: `nohup`(no hang up)은 SIGHUP을 무시하게 만들어 셸 종료(로그아웃) 후에도 프로세스가 살아남게 하며, 출력은 nohup.out에 저장된다. A(`&`만)는 셸 종료 시 SIGHUP을 받아 죽을 수 있다. C는 같은 세션 내 작업 제어일 뿐이고, D는 오히려 HUP을 보내는 명령이라 의도와 반대다.
