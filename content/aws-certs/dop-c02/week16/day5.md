# Day 5 - D-Day 마무리: 시험장 전략과 마지막 시나리오 통합 점검

16주의 마지막 글이다. 오늘 할 일은 새로운 지식을 욱여넣는 것이 아니라 — 그건 오히려 해롭다 — **이미 가진 지식을 시험장에서 최대치로 끌어내는 조건을 만드는 것**이다. DOP-C02 같은 Professional 시험의 합/불은 종종 "아는 것"이 아니라 "아는 것을 3시간 동안 일관되게 발휘하는 것"에서 갈린다. 75문항의 긴 시나리오를 읽다 보면 집중력이 흔들리고, 매력적인 오답에 끌리고, 페이스가 무너진다. 오늘은 그 흔들림을 막는 체크리스트와 시험장 전략, 그리고 6개 도메인을 가로지르는 마지막 통합 시나리오 모의로 감을 마무리한다.

핵심 원칙 하나만 기억하자. **시험 직전 48시간은 "공부"가 아니라 "컨디션 관리"의 시간이다.** 새 자료를 펴는 순간 "내가 모르는 게 이렇게 많았나" 하는 불안이 자신감을 갉아먹는다. D-1일에 모의고사를 새로 풀어 점수가 낮게 나오면 그 불안이 시험장까지 따라온다. 이 시기엔 본 자료(week16 day1~4의 ⭐ 핵심 포인트와 박스)만 반복하며 "나는 이미 충분히 안다"는 상태를 유지하는 게 점수에 더 이롭다.

## 시험 환경 메커니즘 — Pearson VUE와 OnVUE의 차이

> 🔍 **더 깊이**: DOP-C02는 두 가지 방식으로 응시한다. **Pearson VUE 시험 센터**(오프라인)와 **OnVUE 온라인 감독(proctored)**(집/사무실). OnVUE는 편하지만 환경 요건이 까다롭다 — 방에 혼자, 책상 위 완전 청소(메모지·전자기기·음료 금지), 360도 방 스캔, 시험 내내 웹캠·마이크 켜짐, 자리 이탈 금지(화장실 불가), 안정적 네트워크. 체크인은 시작 30분 전부터 가능하고, 시스템 사전 점검(System Test)을 며칠 전 반드시 돌려야 한다(카메라·마이크·대역폭). 한 가지 자주 놓치는 점: **영어가 모국어가 아닌 응시자는 영문 시험에 한해 30분 추가 시간(ESL +30분)을 신청**할 수 있다(예약 시 별도 신청, 시험 당일엔 불가). 한국어 시험을 선택할 수도 있으나, 일부 번역이 어색해 의미가 모호할 때를 대비해 **영문 토글로 원문을 확인하는 습관**이 안전하다. 시험 도구에는 문항 마킹(flag for review)·노트 기능이 있고, 제출 즉시 잠정 합/불이 화면에 뜨며 공식 결과지(도메인별 competency 포함)는 보통 며칠 내 이메일로 온다.

"직전엔 자라"가 과학인 이유다.

## 시험장 의사결정 전략 — 두 보기로 좁힌 뒤 이기는 법

Professional 시험의 보기는 4개 중 2개가 "명백히 틀림"이라 빠르게 제거되고, 남은 2개에서 승부가 난다. 이 2개를 가르는 기술이 합/불을 결정한다.

> 🎯 **시나리오(의사결정 기술)**: 두 보기 A·B가 모두 "기술적으로 동작"한다면, 질문의 **한정어(qualifier)**로 결정한다. (1) "**MOST cost-effective**"면 → 매니지드/서버리스/사용량 과금 쪽, 상시 가동·과대 프로비저닝은 탈락(예: Logs 영구 보존 vs S3+Athena → 후자). (2) "**LEAST operational overhead**"면 → AWS 네이티브 통합·자동화 쪽, 직접 Lambda 스크립트·자체 구현은 탈락(예: Lambda 스캔 vs Auto-Enable → 후자). (3) "**MINIMUM changes / least disruptive**"면 → 기존 구조 재사용·코드 무변경 쪽(예: Parameter Store 마이그레이션 vs Secrets Manager 회전 → 코드 무변경이면 후자). (4) "**automatically / across all accounts**"면 → 신규 자동 포함·Org 통합 쪽(StackSets Service-Managed, Auto-Enable). 한정어를 못 읽으면 두 정답 사이에서 동전 던지기가 되고, 읽으면 90% 이긴다.

> ⚠️ **함정**: 시험장에서 빠지기 쉬운 함정 패턴. (1) **처음 보는 그럴듯한 서비스명** — 보통 오답 미끼다(실재하지 않거나 맥락에 안 맞음). (2) **"All of the above / None of the above"** — Professional엔 드물고, 보이면 의심하라. (3) **암호화(KMS)와 무결성(서명)의 혼동** — "위·변조 방지"에 KMS를 고르면 틀린다. (4) **탐지와 대응의 혼동** — "자동으로 차단/수정"인데 GuardDuty(탐지만)를 고르면 틀린다(대응은 Config Remediation/SSM/Lambda). (5) **푸시 vs 폴링** — AppConfig는 폴링이다. (6) **첫 직감을 근거 없이 바꾸기** — 새 단서가 없으면 첫 답을 유지하는 편이 통계적으로 유리하다.

**문제 1.** 한 글로벌 핀테크가 monorepo로 40개 서비스를 운영한다. `services/payments/**` 경로 변경 시에만 payments 파이프라인이 돌고, 빌드 아티팩트는 위·변조가 방지돼야 하며, Lambda 함수는 10% 카나리 5분 후 전체 전환과 알람 시 자동 롤백이 필요하다. 가장 적절한 조합은?

A) CodePipeline V1 + KMS 암호화 + AllAtOnce 배포

B) CodePipeline V2(filePaths 트리거) + AWS Signer/Notation 서명 + Inspector 스캔 + CodeDeploy `Canary10Percent5Minutes` + CloudWatch Alarm 자동 롤백

C) Jenkins + S3 ACL + Rolling 배포

D) CodePipeline V2 + KMS 서명 + Linear 배포

**정답: B**

해설: 경로 필터는 V2 filePaths 트리거, 위·변조 방지는 서명(Signer/Notation)+Inspector(KMS 암호화가 아님), 10% 카나리 5분은 `Canary10Percent5Minutes`, 알람 자동 롤백은 CodeDeploy+CloudWatch Alarm이다. V1(A)은 경로 필터 없음·AllAtOnce는 리스크 큼, S3 ACL/Rolling(C)은 무결성·요건 불충족, "KMS 서명"(D)은 용어 자체가 틀림(KMS는 암호화)이며 Linear는 "10% 카나리 두 단계"가 아니다.

**문제 2.** 60개 계정 환경에서 ① 모든 계정에 GuardDuty·Config 활성 + 신규 계정 자동 포함 ② S3 공개 시 자동 차단(단, 프로덕션 리소스 삭제 등 위험 조치는 사람 승인) ③ 탈취된 IAM 자격 자동 무효화를 모두 만족하려 한다. 가장 적절한 설계는?

A) 각 계정 수동 활성화 + Lambda가 모든 조치 즉시 실행

B) Audit 계정 Delegated Admin + Org Auto-Enable / Config Rule + SSM Automation(`aws:approve`로 위험 조치 게이트) / GuardDuty Finding → EventBridge → Lambda(자격 무효화)

C) StackSets로만 보안 활성 + 모든 자동화는 Step Functions Express

D) Security Hub만 켜고 나머지는 수동

**정답: B**

해설: 신규 자동 포함은 Delegated Admin + Auto-Enable, 자동 수정+사람 게이트는 Config Rule + SSM `aws:approve`, 자격 무효화 자동 대응은 GuardDuty→EventBridge→Lambda다(예방·탐지·대응 심층 방어). 수동+무조건 즉시 실행(A)은 누락·폭주 위험, StackSets만+Express(C)는 신규 자동·감사에 부적합, Security Hub만(D)은 집계일 뿐 탐지·대응이 빠졌다.

**문제 3.** 결제 DB는 RTO 1분·RPO 수 초가 필요하고, 세션 저장소(키-값)는 두 리전 동시 쓰기가 필요하며, 파트너가 목적지 IP를 방화벽에 화이트리스트해 IP를 바꿀 수 없는데 1초 페일오버를 원한다. 또 페일오버 절차가 주 리전 장애에 의존하면 안 된다. 가장 적절한 조합은?

A) RDS Multi-AZ + DynamoDB Multi-AZ + Route 53 Failover, 페일오버 Lambda는 주 리전

B) Aurora Global Database + DynamoDB Global Tables + Global Accelerator(고정 Anycast IP), 페일오버 자동화(Health Check+EventBridge+Step Functions)는 DR 리전에서 구동

C) RDS Read Replica + ElastiCache + CloudFront

D) Aurora Global + DynamoDB Global Tables + Route 53(TTL 0)

**정답: B**

해설: RTO1분/RPO수초 SQL=Aurora Global, 두 리전 동시 쓰기 키-값=DynamoDB Global Tables, 고정 IP+1초 페일오버=Global Accelerator(DNS TTL 우회), 페일오버 자동화는 DR 리전 구동(2021 us-east-1 교훈)이다. Multi-AZ(A)는 멀티 리전 아님·주 리전 Lambda는 그 리전 사망 시 무용, (C)는 SQL DR/동시 쓰기/고정 IP 모두 부적합, Route 53 TTL 0(D)도 DNS 캐싱으로 1초·고정 IP를 보장 못 한다.

**문제 4.** 50개 마이크로서비스의 분산 트레이스가 필요한데 트래픽이 커서 전수 트레이싱은 비용이 크고, 벤더 종속 없이 여러 백엔드로 보내야 하며, 멀티 계정 관찰성을 단일 대시보드로 통합해야 한다. 가장 적절한 조합은?

A) X-Ray 100% 트레이싱 + 계정별 개별 대시보드

B) ADOT(OpenTelemetry) + 커스텀 샘플링(중요 경로 高·헬스체크 0%) + CloudWatch OAM(Sink/Link)

C) CloudWatch Logs Insights로 트레이스 재구성 + Lambda 집계

D) Inspector + Grafana 자체 호스팅

**정답: B**

해설: 벤더 중립·다중 백엔드는 ADOT(OpenTelemetry), 비용 효율은 커스텀 샘플링, 멀티 계정 통합은 OAM이다. 100% 트레이싱(A)은 비용 폭발·개별 대시보드는 통합 실패, Logs로 트레이스 재구성(C)은 요청 경로를 못 꿰고, Inspector(D)는 취약점 스캔이라 무관하다.

**문제 5.** 규제 산업에서 SOC 2 감사 증거를 분기마다 자동 수집·보고해야 한다. CloudTrail·Config·Security Hub는 이미 활성화돼 있고, CloudTrail 로그는 침해 시 공격자가 지울 수 없어야 한다. 가장 적절한 설계는?

A) 각 계정 기본 Trail 유지 + Athena로 매번 수동 집계

B) Audit Manager(SOC 2 프레임워크)로 증거 자동 수집·Report 생성 + Log Archive 계정에 Org Trail 집중 + S3 Object Lock(WORM)으로 불변화

C) Macie로 증거 수집 + CloudWatch Logs 영구 보존

D) Config Aggregator로 보고서 생성 + 각 계정에서 로그 보관

**정답: B**

해설: 증거 자동 수집·보고는 Audit Manager(소스 서비스 활성 전제 충족), 로그 무결성은 Log Archive 계정 집중 + S3 Object Lock(WORM)으로 불변화다(운영/증거 권한 분리). Athena 수동(A)·Macie(C, PII용)·Config Aggregator 보고서(D)는 컴플라이언스 증거 자동화가 아니고, 각 계정 보관은 침해 시 삭제 위험이다.

**문제 6.** 개발자에게 IAM Role 셀프서비스 생성을 위임하되, 만든 Role이 회사 정책 상한(특정 리전만 등)을 넘지 못하게 안전하게 강제하려 한다. 가장 적절한 방법은?

A) 개발자에게 `iam:CreateRole`을 포함한 AdministratorAccess를 부여하고 회사 정책 위반은 CloudTrail 사후 감사로 적발

C) Role 생성을 전면 금지하고 필요한 Role은 플랫폼팀이 티켓을 받아 수동으로 대신 생성

## 🧠 마지막 20분 시험장 운용

> 🎯 **시나리오(종료 전 전략)**: 마지막 20~30분은 새 문제가 아니라 **flag된 문항**에 쓴다. 우선순위: (1) 2분 이상 고민했던 시나리오 문항부터 — 처음엔 안 보이던 한정어(MOST/LEAST)가 다시 보면 잡힌다. (2) 답을 바꿀 만한 **새로운 근거**가 없으면 첫 직감을 유지한다(근거 없는 변경은 통계적으로 손해). (3) 빈 칸은 0개여야 한다 — 전혀 모르겠으면 그럴듯한 매니지드/자동화 보기를 찍는다(Professional의 정답은 대개 "AWS 네이티브·자동·최소 운영" 쪽). (4) 매우 긴 시나리오는 마지막 문장(실제 질문)과 한정어를 먼저 읽고 보기를 본 뒤 본문에서 단서를 역추적하면 빠르다.

```
당일 페이스 운용
==================================================
  체크인(시작 30분 전)
        │
        ▼
  시험 시작 (180분, 75문항)
   ├─ 0~25문 : 페이스 기준선 (목표 ~55분, 침착)
   ├─ 25~55문: 본격 풀이 (목표 ~80분, 막히면 flag)
```

## 정리하며 — 16주의 끝에서

오늘 다룬 것은 지식이 아니라 그 지식을 발휘하는 조건이다. 첫째, **직전 48시간은 공부가 아니라 컨디션 관리** — 새 자료·새 모의를 피하고 본 자료 반복으로 자기효능감과 수면(기억 공고화)을 지킨다. 둘째, **시험 환경 메커니즘**(OnVUE 요건·ESL +30분·영문 토글·마킹·잠정 결과)을 미리 알아 변수에 흔들리지 않는다. 셋째, **두 보기로 좁힌 뒤 한정어(MOST cost-effective / LEAST operational overhead / MINIMUM changes / automatically)로 결정**하는 것이 합/불의 기술이고, 암호화↔서명·탐지↔대응·푸시↔폴링의 혼동이 대표 함정이다. 넷째, **빈출 30선**과 통합 시나리오 12문항으로 도메인을 가로지르는 단서 매핑을 마지막으로 점검했다. 다섯째, **마지막 20분은 flag 문항에 쓰고 첫 직감을 함부로 바꾸지 않으며 빈 답을 0으로** 만든다.

16주 동안 SDLC 자동화부터 멀티 계정 거버넌스, 복원력의 수학, 관찰성의 이론, 보안의 심층 방어까지 — DOP-C02의 여섯 도메인을 단순 암기가 아니라 "왜 그런가"의 원리로 꿰어 왔다. 이제 남은 건 그 이해를 시험장에서 차분히 꺼내는 일뿐이다. 충분히 준비했다. 합격을 기원한다. Fighting!

해설: 한정된 시간은 flag 문항에 집중하고, 근거 없는 답 변경은 통계적으로 손해이므로 첫 직감을 유지하며, 빈 답은 절대 남기지 않는다. 전체 재검토(C)는 시간 부족, 자신 있는 문항 재확인(D)은 비효율이다.

**문제 5.** "LEAST operational overhead"로 60개 계정에 신규 계정 포함 보안 베이스라인을 적용해야 한다. Self-Managed StackSets와 Service-Managed StackSets + Auto-Deployment 중 올바른 선택과 근거는?

A) Self-Managed — 각 계정 실행 Role을 직접 정의해 더 세밀한 권한 제어가 가능해서

B) Service-Managed + Auto-Deployment — Organizations 통합으로 실행 Role을 AWS가 자동 관리하고 신규 계정이 자동 포함돼 운영 부담이 최소

C) 둘 다 OU 타깃 배포를 지원하므로 운영 부담이 사실상 동일

D) EventBridge 스케줄로 매일 Lambda를 돌려 신규 계정을 스캔하고 베이스라인을 API 배포

**정답: B**

해설: LEAST operational overhead 한정어가 결정한다 — Service-Managed는 Role 자동 관리 + Auto-Deployment(신규 자동)로 부담이 최소다. Self-Managed(A)는 각 계정 Role 수동 셋업(비Org·레거시일 때만), Lambda 스캔(D)은 가장 큰 부담이다.

**문제 6.** "구성이 바뀌면 즉시 반영"을 가정하고 AppConfig를 설계했는데 지연이 발생한다. 올바른 이해는?

A) AppConfig는 본래 즉시 푸시 모델이므로 동작이 어긋난 버그 — AWS Support에 문의해야 한다

B) AppConfig는 폴링 모델이므로 클라이언트가 설정 간격마다 가져온다 — 반영 지연은 정상이며 폴링 간격으로 제어한다

C) 즉시 반영이 필요하면 Secrets Manager로 교체하고 회전 이벤트로 갱신을 트리거해야 한다

D) AppConfig 변경을 EventBridge 이벤트로 받아 애플리케이션에 푸시하도록 아키텍처를 바꿔야 한다

**정답: B**

해설: AppConfig는 Agent/Extension이 주기적으로 폴링하는 모델이다 — 즉시 푸시가 아니며 지연은 폴링 간격에 달렸다. 버그(A)가 아니고, Secrets(C)는 피처 플래그 요건(검증·점진)을 못 채운다.

**문제 7.** Professional 시험에서 전혀 모르는 문항을 만났을 때 빈 답을 남기지 않기 위한 합리적 추측 방향은?

A) 가장 길고 기술 용어가 많아 정교해 보이는 보기

B) AWS 네이티브·자동화·최소 운영 부담을 시사하는 보기(처음 보는 의심스러운 서비스명·수동 운영 보기는 회피)

C) 보기 중 가장 처음(A)에 배치된 것 — 출제 관성상 정답일 확률

D) 가장 비싸고 기능이 많은 풀스택 솔루션 — 안전하게 상위 옵션

**정답: B**

해설: DOP 정답은 대개 "AWS 네이티브·자동·최소 운영" 쪽으로 수렴하고, 처음 보는 서비스명이나 수동 스크립트 보기는 함정인 경우가 많다. 길이(A)·순서(C)·비용(D)은 근거가 아니다.
