# Day 2 - Kinesis Data Streams: 샤드, 파티션 키, 처리량

어제 배운 배치 수집은 "모았다가 한꺼번에"였다. 오늘부터는 정반대 세계, 스트리밍이다. 클릭스트림, IoT 센서, 결제 트랜잭션, 게임 텔레메트리처럼 데이터가 끊임없이 흘러들어오고, 그것을 초 단위로 처리해야 하는 상황. 그 한가운데 있는 서비스가 **Amazon Kinesis Data Streams(KDS)** 다.

KDS는 한마디로 "확장 가능한 실시간 데이터 파이프"다. 수많은 프로듀서가 데이터를 밀어넣고, 수많은 컨슈머가 거의 동시에 읽어간다. 오늘은 이 파이프의 내부 구조(샤드), 데이터를 어느 칸에 넣을지 정하는 파티션 키, 그리고 처리량 계산을 본다.

## 스트림은 샤드의 모음이다

KDS 스트림은 하나의 거대한 통이 아니라 **샤드(shard)** 라는 여러 레인으로 나뉜다. 샤드는 처리량의 기본 단위이자 병렬성의 단위다. 각 샤드는 고정된 용량을 가진다.

```
샤드 1개의 용량:
- 쓰기(입력): 1 MB/s  또는  1,000 records/s
- 읽기(출력): 2 MB/s  (공유 처리량 기준)
```

즉 스트림의 총 처리량 = 샤드 수 × 샤드당 용량이다. 초당 5MB를 써야 한다면 최소 5개의 샤드가 필요하다. 샤드를 늘리면(resharding) 처리량이 비례해서 늘어난다.

```python
import boto3
kinesis = boto3.client("kinesis")

kinesis.create_stream(StreamName="clickstream", ShardCount=5)

# 트래픽 증가 시 샤드 분할로 처리량 확장
kinesis.update_shard_count(
    StreamName="clickstream",
    TargetShardCount=10,
    ScalingType="UNIFORM_SCALING"
)
```

> 💡 **관련 이론**: KDS에는 두 가지 용량 모드가 있다. **Provisioned 모드**는 샤드 수를 직접 지정하고 그만큼 과금되며 처리량 계산을 스스로 해야 한다. **On-demand 모드**는 트래픽에 따라 샤드를 자동 조절(최대 200MB/s, 200,000 records/s까지 자동 확장)하고 사용량만큼 과금된다. 트래픽이 예측 가능하고 안정적이면 Provisioned가 저렴하고, 변동이 크거나 예측이 어려우면 On-demand가 운영 부담을 없앤다. 시험은 이 트레이드오프를 자주 묻는다.

## 파티션 키: 레코드를 어느 샤드에 넣을까

프로듀서가 레코드를 보낼 때 반드시 **파티션 키(partition key)** 를 함께 지정한다. KDS는 이 키를 MD5 해싱해서 어느 샤드로 보낼지 결정한다. 같은 파티션 키를 가진 레코드는 항상 같은 샤드로 가고, **샤드 내에서는 순서가 보장된다.**

```python
# 사용자 ID를 파티션 키로 → 같은 사용자의 이벤트는 같은 샤드, 순서 보장
kinesis.put_record(
    StreamName="clickstream",
    Data=b'{"event":"page_view","page":"/checkout"}',
    PartitionKey="user-8821"          # 이 키가 샤드를 결정
)
```

여기서 핵심 함정은 **핫 샤드(hot shard / hot partition)** 다. 파티션 키 분포가 고르지 않으면 특정 샤드에만 트래픽이 몰려, 그 샤드는 `ProvisionedThroughputExceededException`으로 throttle되는데 다른 샤드는 한가하다. 예를 들어 파티션 키를 "country"로 잡으면 트래픽 대부분이 한 나라에 쏠릴 때 한 샤드만 터진다.

> 💡 **관련 이론**: 핫 샤드를 피하려면 카디널리티가 높고 분포가 고른 파티션 키를 골라야 한다. user_id, device_id, session_id처럼 값이 많고 균등한 키가 좋고, country·region·status처럼 값이 적고 편향된 키는 나쁘다. 단, "같은 키 = 순서 보장"이라는 성질 때문에 순서가 중요한 단위(예: 사용자별 이벤트 순서)를 파티션 키로 삼아야 하는 트레이드오프가 있다. 분산과 순서 보장 사이의 균형이 설계 포인트다.

## 프로듀서와 컨슈머

**프로듀서**는 스트림에 데이터를 넣는 쪽이다. 선택지가 여러 가지다.

```
- PutRecord / PutRecords API (SDK 직접 호출)
- KPL (Kinesis Producer Library): 자동 배칭·집계·재시도로 고처리량
- Kinesis Agent: 로그 파일을 자동으로 스트림에 전송
```

**컨슈머**는 스트림에서 데이터를 읽는 쪽이다. 두 가지 읽기 방식이 있다.

| 방식 | 처리량 | 지연 | 특징 |
|------|--------|------|------|
| 공유 처리량(Shared / classic) | 샤드당 2MB/s를 모든 컨슈머가 나눠 씀 | 폴링(GetRecords) | 컨슈머가 늘면 경쟁 |
| 향상된 팬아웃(Enhanced Fan-Out) | 컨슈머마다 샤드당 2MB/s 전용 | push, ~70ms | 컨슈머별 독립 대역폭 |

컨슈머가 여러 개이고 각자 풀 대역폭이 필요하면 향상된 팬아웃을 쓴다. 컨슈머 측 처리는 보통 **KCL(Kinesis Client Library)** 로 샤드 분배·체크포인트(어디까지 읽었는지)·장애 복구를 자동 관리하거나, **Lambda 이벤트 소스 매핑**으로 서버리스하게 처리한다.

```python
# Lambda를 KDS 컨슈머로: 샤드마다 배치로 레코드가 들어옴
import base64, json

def handler(event, context):
    for record in event["Records"]:
        payload = base64.b64decode(record["kinesis"]["data"])
        data = json.loads(payload)
        # 처리 로직...
    return {"processed": len(event["Records"])}
```

## 데이터 보존과 재처리

KDS는 데이터를 즉시 버리지 않고 **보존 기간(retention)** 동안 보관한다. 기본 24시간, 최대 365일까지 늘릴 수 있다. 이 덕분에 컨슈머가 잠시 죽었다 살아나도 놓친 데이터를 다시 읽을 수 있고, 보존 기간 안에서는 같은 데이터를 여러 컨슈머가 독립적으로 재처리할 수 있다.

> 💡 **관련 이론**: 보존 기간은 KDS가 단순 메시지 큐(소비하면 사라지는 SQS)와 다른 결정적 차이다. KDS는 로그(append-only log)에 가까워서, 여러 컨슈머가 같은 스트림을 각자의 위치(체크포인트)에서 독립적으로 읽는 "팬아웃" 소비가 가능하다. 처리 로직 버그를 고친 뒤 보존 기간 내 데이터를 처음부터 다시 흘려 재처리(replay)하는 패턴도 여기서 나온다. SQS는 이런 재처리/멀티 컨슈머 팬아웃이 기본 동작이 아니다.

## 정리

- 스트림 = 샤드의 모음. 처리량 = 샤드 수 × (쓰기 1MB/s·1,000rec/s, 읽기 2MB/s)
- 파티션 키가 샤드를 결정하고 샤드 내 순서를 보장 → 분포 고른 키로 핫 샤드 방지
- 프로듀서: PutRecords/KPL/Agent, 컨슈머: KCL/Lambda, 고대역폭은 향상된 팬아웃
- 보존 기간(기본 24h, 최대 365일)으로 재처리·멀티 컨슈머 가능

## 📝 연습 문제

**문제 1.** 한 KDS 스트림에서 특정 샤드만 지속적으로 ProvisionedThroughputExceededException이 발생하고 나머지 샤드는 거의 비어 있다. 가장 가능성 높은 원인은?

A) 파티션 키 분포가 편향되어 핫 샤드가 발생  
B) 보존 기간이 너무 짧음  
C) 컨슈머가 너무 많음  
D) On-demand 모드를 사용 중  

**정답: A**  
해설: 특정 샤드만 throttle되고 나머지는 한가한 것은 전형적인 핫 샤드(hot partition) 증상으로, 파티션 키 분포가 고르지 않아 트래픽이 한 샤드로 쏠린 결과다. 카디널리티가 높고 균등한 키로 바꿔야 한다. 보존 기간은 throttle과 무관하고, 컨슈머 수는 읽기 쪽 문제이며, On-demand 모드라면 오히려 자동 확장으로 이 문제가 완화된다.

**문제 2.** 초당 약 8MB, 6,000개의 레코드를 KDS Provisioned 모드로 안정적으로 수집하려 한다. 최소 샤드 수는?

A) 6개  
B) 8개  
C) 2개  
D) 10개  

**정답: B**  
해설: 샤드당 쓰기 용량은 1MB/s 또는 1,000 records/s 중 먼저 도달하는 한계다. 8MB/s에는 8샤드, 6,000 records/s에는 6샤드가 필요하므로 둘 다 만족하려면 더 큰 값인 8개가 필요하다. 6개는 처리량(MB) 한계를, 2개는 둘 다 초과한다. 10개는 동작하지만 최소가 아니다.

**문제 3.** 같은 사용자가 발생시킨 클릭 이벤트들을 반드시 발생 순서대로 처리해야 한다. KDS에서 이를 보장하는 설계는?

A) 매 레코드마다 무작위 파티션 키 사용  
B) 샤드를 1개로 고정  
C) 사용자 ID를 파티션 키로 사용  
D) 향상된 팬아웃 활성화  

**정답: C**  
해설: KDS는 같은 파티션 키의 레코드를 같은 샤드로 보내고 샤드 내 순서를 보장하므로, 사용자 ID를 파티션 키로 쓰면 사용자별 순서가 유지된다. 무작위 키는 여러 샤드로 흩어져 순서가 깨진다. 샤드 1개는 전체 순서를 보장하지만 처리량이 1MB/s로 묶여 확장 불가다. 향상된 팬아웃은 읽기 대역폭 기능으로 순서와 무관하다.

**문제 4.** 5개의 서로 다른 컨슈머 애플리케이션이 각각 풀 대역폭으로 동일 스트림을 낮은 지연으로 독립 소비해야 한다. 적절한 기능은?

A) 공유 처리량(classic) GetRecords 폴링  
B) 샤드 수를 5개로 고정  
C) 보존 기간을 365일로 연장  
D) 향상된 팬아웃(Enhanced Fan-Out)  

**정답: D**  
해설: 향상된 팬아웃은 컨슈머마다 샤드당 2MB/s 전용 대역폭을 push 방식(약 70ms 지연)으로 제공해, 여러 컨슈머가 서로 경쟁하지 않고 독립적으로 소비할 수 있다. 공유 처리량은 샤드당 2MB/s를 모든 컨슈머가 나눠 써서 컨슈머가 늘수록 느려진다. 보존 기간·샤드 수는 컨슈머 간 대역폭 경쟁 문제를 해결하지 못한다.

**문제 5.** 컨슈머 처리 로직에 버그가 있었음을 발견하고, 지난 3일간 들어온 데이터를 처음부터 다시 처리하려 한다. 이를 가능하게 하는 KDS의 특성은?

A) 보존 기간을 충분히 길게 설정해 두면 해당 구간을 재처리(replay)할 수 있다  
B) SQS처럼 소비하면 메시지가 삭제되므로 불가능하다  
C) 파티션 키를 바꾸면 자동 재처리된다  
D) 샤드를 분할하면 과거 데이터가 복원된다  

**정답: A**  
해설: KDS는 append-only 로그처럼 동작해 보존 기간(기본 24h, 최대 365일) 안의 데이터를 보관하므로, 컨슈머를 과거 위치(시퀀스/타임스탬프)부터 다시 읽게 해 재처리할 수 있다. 3일 재처리를 하려면 보존을 3일 이상으로 설정해 두었어야 한다. SQS와 달리 소비해도 데이터가 사라지지 않으며, 파티션 키 변경이나 리샤딩은 재처리와 무관하다.
