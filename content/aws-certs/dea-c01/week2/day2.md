# Day 2 - Kinesis Data Streams: 샤드, 파티션 키, 처리량

## 📌 핵심 정리

- 스트림 = 샤드의 모음. 프로비저닝 모드의 처리량 = 샤드 수 × (쓰기 1MB/s 또는 1,000 records/s, 읽기 2MB/s).
- 파티션 키의 해시가 샤드를 정하고, 같은 키는 같은 샤드에서 순서가 보장된다. 분포가 고른 키로 **핫 샤드**를 피한다.
- 프로듀서는 PutRecords·KPL·Agent, 컨슈머는 KCL·Lambda. 컨슈머가 여럿이고 각자 풀 대역폭이 필요하면 **향상된 팬아웃**이다.
- 보존 기간(기본 24시간, 최대 365일) 안에서는 재처리와 멀티 컨슈머 독립 소비가 가능하다. 이것이 SQS 와의 결정적 차이다.
- 트래픽이 예측 가능하면 프로비저닝, 변동이 크면 온디맨드. 온디맨드도 한 파티션 키가 샤드 한도를 넘는 쏠림은 풀어주지 못한다.

## 스트림은 샤드의 모음이다

어제 배운 배치 수집은 "모았다가 한꺼번에"였다. 오늘부터는 정반대 세계, 스트리밍이다. 클릭스트림, IoT 센서, 결제 트랜잭션, 게임 텔레메트리처럼 데이터가 끊임없이 흘러들어오고, 그것을 초 단위로 처리해야 하는 상황. 그 한가운데 있는 서비스가 **Amazon Kinesis Data Streams(KDS)** 다.

KDS는 한마디로 "확장 가능한 실시간 데이터 파이프"다. 수많은 프로듀서가 데이터를 밀어넣고, 수많은 컨슈머가 거의 동시에 읽어간다. 오늘은 이 파이프의 내부 구조(샤드), 데이터를 어느 칸에 넣을지 정하는 파티션 키, 그리고 처리량 계산을 본다.

KDS 스트림은 하나의 거대한 통이 아니라 **샤드(shard)** 라는 여러 레인으로 나뉜다. 샤드는 처리량의 기본 단위이자 병렬성의 단위다. 각 샤드는 고정된 용량을 가진다.

```
샤드 1개의 용량:
- 쓰기(입력): 1 MB/s  또는  1,000 records/s
- 읽기(출력): 2 MB/s  (공유 처리량 기준)
```

즉 스트림의 총 처리량 = 샤드 수 × 샤드당 용량이다. 초당 5MB를 써야 한다면 최소 5개의 샤드가 필요하다. 샤드를 늘리면(resharding) 처리량이 비례해서 늘어난다.

```python
import boto3
kinesis = boto3.client("kinesis")

kinesis.create_stream(StreamName="clickstream", ShardCount=5)

# 트래픽 증가 시 샤드 분할로 처리량 확장
kinesis.update_shard_count(
    StreamName="clickstream",
    TargetShardCount=10,
    ScalingType="UNIFORM_SCALING"
)
```

> 💡 **관련 이론**: KDS에는 두 가지 용량 모드가 있다. **Provisioned 모드**는 샤드 수를 직접 지정하고 그만큼 과금되며 처리량 계산을 스스로 해야 한다. **On-demand 모드**는 트래픽에 따라 샤드를 자동 조절(다수 리전 기준 쓰기 200MB/s, 200,000 records/s까지 자동 확장하며 일부 리전은 상한이 더 높다)하고 사용량만큼 과금된다. 트래픽이 예측 가능하고 안정적이면 Provisioned가 저렴하고, 변동이 크거나 예측이 어려우면 On-demand가 운영 부담을 없앤다. 이 트레이드오프는 시나리오 문제의 판단 기준이 된다.

## 파티션 키: 레코드를 어느 샤드에 넣을까

프로듀서가 레코드를 보낼 때 반드시 **파티션 키(partition key)** 를 함께 지정한다. KDS는 이 키를 MD5 해싱해서 어느 샤드로 보낼지 결정한다. 같은 파티션 키를 가진 레코드는 항상 같은 샤드로 가고, **샤드 내에서는 순서가 보장된다.**

```python
# 사용자 ID를 파티션 키로 → 같은 사용자의 이벤트는 같은 샤드, 순서 보장
kinesis.put_record(
    StreamName="clickstream",
    Data=b'{"event":"page_view","page":"/checkout"}',
    PartitionKey="user-8821"          # 이 키가 샤드를 결정
)
```

여기서 핵심 함정은 **핫 샤드(hot shard / hot partition)** 다. 파티션 키 분포가 고르지 않으면 특정 샤드에만 트래픽이 몰려, 그 샤드는 `ProvisionedThroughputExceededException`으로 throttle되는데 다른 샤드는 한가하다. 예를 들어 파티션 키를 "country"로 잡으면 트래픽 대부분이 한 나라에 쏠릴 때 한 샤드만 터진다.

핫 샤드를 피하려면 카디널리티가 높고 분포가 고른 파티션 키를 골라야 한다. user_id, device_id, session_id처럼 값이 많고 균등한 키가 좋고, country·region·status처럼 값이 적고 편향된 키는 나쁘다. 단, "같은 키 = 순서 보장"이라는 성질 때문에 순서가 중요한 단위(예: 사용자별 이벤트 순서)를 파티션 키로 삼아야 하는 트레이드오프가 있다. 분산과 순서 보장 사이의 균형이 설계 포인트다.

## 프로듀서와 컨슈머

**프로듀서**는 스트림에 데이터를 넣는 쪽이다. 선택지가 여러 가지다.

```
- PutRecord / PutRecords API (SDK 직접 호출)
- KPL (Kinesis Producer Library): 자동 배칭·집계·재시도로 고처리량
- Kinesis Agent: 로그 파일을 자동으로 스트림에 전송
```

**컨슈머**는 스트림에서 데이터를 읽는 쪽이다. 두 가지 읽기 방식이 있다.

| 방식 | 처리량 | 지연 | 특징 |
|------|--------|------|------|
| 공유 처리량(Shared / classic) | 샤드당 2MB/s를 모든 컨슈머가 나눠 씀 | 폴링(GetRecords) | 컨슈머가 늘면 경쟁 |
| 향상된 팬아웃(Enhanced Fan-Out) | 컨슈머마다 샤드당 2MB/s 전용 | push, ~70ms | 컨슈머별 독립 대역폭 |

컨슈머가 여러 개이고 각자 풀 대역폭이 필요하면 향상된 팬아웃을 쓴다. 컨슈머 측 처리는 보통 **KCL(Kinesis Client Library)** 로 샤드 분배·체크포인트(어디까지 읽었는지)·장애 복구를 자동 관리하거나, **Lambda 이벤트 소스 매핑**으로 서버리스하게 처리한다.

```python
# Lambda를 KDS 컨슈머로: 샤드마다 배치로 레코드가 들어옴
import base64, json

def handler(event, context):
    for record in event["Records"]:
        payload = base64.b64decode(record["kinesis"]["data"])
        data = json.loads(payload)
        # 처리 로직...
    return {"processed": len(event["Records"])}
```

## 데이터 보존과 재처리

KDS는 데이터를 즉시 버리지 않고 **보존 기간(retention)** 동안 보관한다. 기본 24시간, 최대 365일까지 늘릴 수 있다. 이 덕분에 컨슈머가 잠시 죽었다 살아나도 놓친 데이터를 다시 읽을 수 있고, 보존 기간 안에서는 같은 데이터를 여러 컨슈머가 독립적으로 재처리할 수 있다.

보존 기간은 KDS가 단순 메시지 큐(소비하면 사라지는 SQS)와 다른 결정적 차이다. KDS는 로그(append-only log)에 가까워서, 여러 컨슈머가 같은 스트림을 각자의 위치(체크포인트)에서 독립적으로 읽는 "팬아웃" 소비가 가능하다. 처리 로직 버그를 고친 뒤 보존 기간 내 데이터를 처음부터 다시 흘려 재처리(replay)하는 패턴도 여기서 나온다. SQS는 이런 재처리/멀티 컨슈머 팬아웃이 기본 동작이 아니다.

## 샤드 수를 손으로 계산하기

프로비저닝 모드의 샤드 수는 **쓰기와 읽기 중 더 큰 요구**로 정해진다. AWS 가 제시하는 계산식은 다음과 같다.

```
쓰기 대역폭(KB/s) = 평균 레코드 크기(KB, 올림) × 초당 레코드 수
읽기 대역폭(KB/s) = 쓰기 대역폭 × 컨슈머 수        ← 공유 처리량 컨슈머 기준
샤드 수 = ceil( max( 쓰기 대역폭 / 1024 , 읽기 대역폭 / 2048 ) )
```

여기에 "샤드당 초당 1,000 레코드"라는 건수 한도를 따로 확인해야 한다. 레코드가 작으면 바이트보다 건수가 먼저 찬다.

| 상황 | 쓰기(바이트) | 쓰기(건수) | 읽기 | 필요한 샤드 |
|------|------|------|------|------|
| 2KB × 3,000건/s, 컨슈머 1개 | 6,000KB/s → 6 | 3,000건 → 3 | 6,000/2048 → 3 | **6** |
| 2KB × 3,000건/s, 공유 컨슈머 3개 | 6 | 3 | 18,000/2048 → 9 | **9** |
| 0.2KB × 9,000건/s, 컨슈머 1개 | 실제 1,800KB/s → 2 | 9,000건 → 9 | 1 | **9** |

- 공식에서 평균 레코드 크기를 1KB 단위로 **올림**하는 이유가 셋째 줄에 있다. 0.2KB 를 1KB 로 올려 계산하면 9,000KB/s 가 되어 건수 한도와 같은 답(9샤드)이 나온다.
- 둘째 줄이 자주 놓치는 지점이다. 쓰기는 6샤드로 충분한데 **읽는 쪽이 3배로 늘어** 9샤드가 필요해진다. 이때 샤드를 늘리는 대신 컨슈머를 향상된 팬아웃으로 바꾸면 읽기 항이 사라져 6샤드로 돌아간다.
- 셋째 줄은 작은 레코드의 함정이다. 이 경우 KPL 의 **집계(aggregation)** 로 작은 레코드 여러 개를 KDS 레코드 하나에 담으면 건수 한도에서 벗어난다.

## 읽기 쪽 한도와 향상된 팬아웃의 실체

공유 처리량 컨슈머는 `GetRecords` 로 **끌어온다(pull).** 이 API 자체에 한도가 있다.

| 항목 | 공유 처리량 | 향상된 팬아웃(EFO) |
|------|------|------|
| 전달 방식 | HTTP 로 `GetRecords` 폴링 | HTTP/2 로 `SubscribeToShard`, KDS 가 밀어 준다(push) |
| 읽기 처리량 | 샤드당 합계 2MB/s 를 모든 컨슈머가 나눠 씀 | 등록한 컨슈머마다 샤드당 최대 2MB/s 전용 |
| API 한도 | 샤드당 초당 5회 호출, 호출당 최대 10MB·10,000 레코드 | 폴링이 없으므로 해당 없음 |
| 전파 지연 | 컨슈머 1개일 때 평균 200ms 안팎, 5개면 1,000ms 안팎 | 컨슈머 수와 무관하게 평균 70ms 수준 |
| 스트림당 컨슈머 수 | 제한은 없지만 늘수록 서로 느려짐 | 스트림당 등록 컨슈머 20개까지 |
| 추가 비용 | 없음 | 컨슈머-샤드 시간 + 읽어 간 데이터량 |

- 공유 처리량에서 컨슈머가 늘면 느려지는 이유는 두 가지다. 2MB/s 를 나눠 쓰고, **샤드당 초당 5회**라는 호출 횟수도 나눠 쓴다. 컨슈머 5개면 각자 초당 1회꼴로만 폴링할 수 있어 지연이 1초 근처로 간다.
- `GetRecords` 한 번이 10MB 를 받아 가면 이후 5초간 같은 샤드의 호출이 스로틀된다. 샤드의 읽기 한도 2MB/s 를 5초치 미리 당겨 쓴 셈이기 때문이다.
- EFO 는 공짜가 아니다. "컨슈머가 한두 개이고 200ms 지연이 괜찮다"면 공유 처리량이 더 싸다. 지문에 "여러 애플리케이션이 각자", "지연을 최소화"가 함께 나와야 EFO 다.
- KCL 2.x 이상으로 컨슈머를 만들면 기본으로 EFO 를 쓰도록 구성된다. 의도치 않은 EFO 과금이 여기서 나온다.

## 온디맨드 모드는 실제로 어떻게 늘어나나

"자동 확장"이라고 해서 무한대로 즉시 늘지는 않는다.

- 새 온디맨드 스트림은 **쓰기 4MB/s, 읽기 8MB/s** 용량으로 시작한다.
- 스트림은 **최근 30일 동안 관측된 쓰기 피크의 2배**까지 받아낼 수 있도록 용량을 유지한다. 피크가 40MB/s 였다면 80MB/s 까지는 바로 받는다.
- 트래픽이 **15분 안에 이전 피크의 2배를 넘게** 뛰면 쓰기 스로틀이 날 수 있다. 예고된 대형 이벤트 직전의 급증이 여기에 걸린다. 프로듀서는 재시도해야 한다.
- 상한은 리전마다 다르다. 다수 리전은 쓰기 200MB/s·읽기 400MB/s 까지이고, 일부 대형 리전은 그보다 훨씬 높으며 상향 요청도 가능하다.
- 온디맨드는 트래픽이 늘면 샤드를 **균등하게** 쪼갠다. 특정 해시 키에 몰린 트래픽을 골라 격리하지는 않는다. 그래서 **파티션 키 하나가 샤드 한도(1MB/s, 1,000건/s)를 넘으면 온디맨드에서도 스로틀된다.** "온디맨드로 바꾸면 핫 샤드가 해결된다"는 보기는 키 쏠림이 원인일 때 오답이다.
- 프로비저닝 ↔ 온디맨드 전환은 스트림당 24시간에 2회까지 가능하고, 전환 중에도 읽기·쓰기는 계속된다.

| 판단 기준 | 프로비저닝 | 온디맨드 |
|------|------|------|
| 과금 | 샤드 수 × 시간(+ PUT 단위) | 쓰고 읽은 데이터량(GB) |
| 용량 관리 | 직접 계산, 직접 리샤딩 | 서비스가 관리 |
| 유리한 트래픽 | 일정하고 예측 가능 | 변동 크고 예측 불가, 신규 워크로드 |
| 샤드 세밀 제어 | 특정 샤드만 골라 분할 가능 | 불가 |

## 리샤딩: 분할과 병합에서 벌어지는 일

- 리샤딩은 항상 **둘씩** 일어난다. 분할(split)은 샤드 하나를 둘로, 병합(merge)은 인접한 둘을 하나로 만든다. `UpdateShardCount` 는 이 과정을 목표 샤드 수에 맞춰 대신 수행한다(프로비저닝 모드 전용).
- 대상이 된 원래 샤드를 **부모**, 새로 생긴 샤드를 **자식**이라 부른다. 부모 샤드는 닫혀서 더는 쓰기를 받지 않지만, 안에 있던 데이터는 보존 기간이 끝날 때까지 읽을 수 있다.
- 순서를 지키려면 **부모 샤드를 끝까지 읽은 뒤 자식 샤드를 읽어야** 한다. KCL 은 리스 테이블에 부모·자식 관계를 기록해 이 순서를 자동으로 지킨다. 직접 API 로 컨슈머를 짜면 이 처리를 스스로 해야 한다.
- 프로비저닝 모드는 샤드 단위 과금이므로 분할은 비용을 올리고 병합은 내린다. 피크가 지난 뒤 병합하지 않으면 빈 샤드에 돈을 계속 낸다.

```bash
# 특정 핫 샤드만 골라 반으로 분할 (프로비저닝 모드)
aws kinesis split-shard \
  --stream-name clickstream \
  --shard-to-split shardId-000000000003 \
  --new-starting-hash-key 170141183460469231731687303715884105728

# 인접한 한가한 샤드 두 개를 병합
aws kinesis merge-shards \
  --stream-name clickstream \
  --shard-to-merge shardId-000000000005 \
  --adjacent-shard-to-merge shardId-000000000006
```

> ⚠️ **함정**: 핫 샤드의 원인이 "키 하나에 트래픽이 몰림"이면 샤드를 아무리 쪼개도 그 키는 여전히 한 샤드로 간다. 분할이 통하는 경우는 "여러 키가 우연히 같은 해시 범위에 몰린" 때뿐이다. 키 하나가 문제면 키 설계를 바꿔야 한다(예: `user_id` 대신 `user_id#난수 접미사`. 단, 그 사용자의 순서 보장은 포기하게 된다).

## 프로듀서 쪽에서 놓치기 쉬운 것

| 항목 | 내용 |
|------|------|
| `PutRecord` | 한 건씩 전송. 응답으로 시퀀스 번호를 받는다 |
| `PutRecords` | 요청당 최대 500건. **일부만 실패할 수 있고**, 한 건이 실패해도 뒤 레코드는 계속 처리된다 |
| 부분 실패 처리 | HTTP 200 이 와도 응답의 `FailedRecordCount` 를 확인해 실패한 레코드만 다시 보내야 한다 |
| 순서 | `PutRecords` 는 요청 안 레코드의 순서를 보장하지 않는다. 엄격한 순서가 필요하면 같은 샤드로 `PutRecord` 를 쓴다 |
| KPL 집계 | 작은 사용자 레코드 여러 개를 KDS 레코드 하나에 담아 초당 1,000건 한도를 우회 |
| KPL 수집 | 여러 KDS 레코드를 `PutRecords` 한 번으로 묶어 HTTP 요청 수를 줄임 |
| 레코드 크기 | base64 인코딩 전 페이로드 기준 상한이 있다. 오랫동안 1MB 였고 현재는 간헐적인 대형 레코드를 위해 10MiB 까지 허용한다. 샤드의 지속 쓰기 한도는 여전히 1MB/s 다 |

- `PutRecords` 응답을 확인하지 않는 코드는 스로틀된 레코드를 **조용히 잃는다.** "간헐적으로 데이터가 빠진다 + 예외 로그는 없다"는 증상의 흔한 원인이다.
- KPL 로 집계한 레코드는 **읽는 쪽이 풀 줄 알아야** 한다. KCL 은 자동으로 풀지만, 집계를 모르는 소비자(예: Redshift 스트리밍 수집)는 묶인 바이너리 그대로 받는다. 소비자 종류에 따라 집계를 꺼야 할 수 있다.
- KPL 은 레코드를 모았다가 보내므로 버퍼링만큼 지연이 생긴다. 건당 지연이 더 중요하면 SDK 로 직접 보낸다.

## Lambda 를 컨슈머로 쓸 때의 실패 처리

Lambda 이벤트 소스 매핑은 샤드마다 배치를 순서대로 넘긴다. 기본 설정을 모르면 **독약 레코드 하나가 샤드 전체를 멈춘다.**

| 설정 | 기본값 | 의미 |
|------|------|------|
| `BatchSize` | 100 (최대 10,000) | 한 번 호출에 넘기는 레코드 수 |
| `MaximumBatchingWindowInSeconds` | 0 | 배치를 채우려고 기다리는 시간 |
| `MaximumRetryAttempts` | -1 (무한) | 실패 배치를 레코드가 만료될 때까지 재시도 |
| `MaximumRecordAgeInSeconds` | -1 (무한) | 이보다 오래된 레코드는 건너뜀 |
| `BisectBatchOnFunctionError` | false | 실패 시 배치를 반으로 쪼개 문제 레코드를 좁혀 감 |
| `ParallelizationFactor` | 1 (최대 10) | 샤드 하나를 동시에 처리하는 배치 수. 파티션 키 단위 순서는 유지 |
| `DestinationConfig` | 없음 | 포기한 배치의 정보를 SQS·SNS 로 보냄 |
| `StartingPosition` | 필수 | `TRIM_HORIZON`(가장 오래된 것부터) / `LATEST` / `AT_TIMESTAMP` |

- 함수가 오류를 반환하면 Lambda 는 그 샤드의 **다음 레코드로 넘어가지 않고** 같은 배치를 재시도한다. 기본값(무한 재시도)에서는 해석할 수 없는 레코드 하나가 보존 기간이 끝날 때까지 샤드를 막는다.
- 표준 조합은 `BisectBatchOnFunctionError=true` + 재시도 횟수 제한 + 실패 대상(SQS/SNS) 지정이다. 문제 레코드만 격리하고 나머지는 흘려보낸다.
- 재시도가 있으므로 같은 레코드를 두 번 받을 수 있다. 함수는 멱등하게 짠다.
- 처리가 밀리면 샤드를 늘리거나 `ParallelizationFactor` 를 올린다. 샤드가 늘면 동시에 도는 배치 수도 늘어난다.

## 지표로 증상 읽기

| CloudWatch 지표 | 올라가면 | 볼 곳 |
|------|------|------|
| `WriteProvisionedThroughputExceeded` | 쓰기 스로틀 | 샤드 부족인지, 특정 샤드 쏠림인지(샤드 단위 향상된 모니터링) |
| `ReadProvisionedThroughputExceeded` | 읽기 스로틀 | 공유 처리량 컨슈머가 너무 많음 → EFO 또는 샤드 증설 |
| `GetRecords.IteratorAgeMilliseconds` | 컨슈머가 뒤처짐 | 컨슈머 처리 속도, 오류로 인한 재시도 정체 |
| Lambda `IteratorAge` | 함수가 스트림을 못 따라감 | 배치 크기, 병렬화 계수, 함수 오류 |
| `IncomingBytes` / `IncomingRecords` | 유입량 추세 | 샤드 수 재계산의 근거 |

- 이터레이터 에이지가 계속 늘어 보존 기간에 닿으면 **읽지 못한 데이터가 만료돼 사라진다.** KDS 에서 데이터 유실이 실제로 일어나는 경로가 이것이다. 알람은 스로틀보다 이터레이터 에이지에 먼저 건다.

## 지문 단서 → 정답 판별표

| 지문 단서 | 정답 | 이유 |
|------|------|------|
| "특정 샤드만 스로틀, 나머지는 한가" | 파티션 키 분포 개선 | 샤드 증설·온디맨드는 키 쏠림을 못 푼다 |
| "쓰기는 여유 있는데 컨슈머를 추가하자 지연 증가" | 향상된 팬아웃 | 공유 2MB/s·초당 5회 호출 경쟁 |
| "트래픽을 예측할 수 없고 용량 관리를 하고 싶지 않다" | 온디맨드 모드 | 샤드 자동 관리 |
| "트래픽이 일정하고 비용을 최소화" | 프로비저닝 모드 | 샤드 수 고정이 저렴 |
| "버그 수정 후 지난 7일 데이터를 다시 처리" | 보존 기간을 7일 이상으로 설정 | 기본 24시간으로는 부족 |
| "레코드가 아주 작고 초당 건수가 많다" | KPL 집계 | 초당 1,000건 한도 우회 |
| "Lambda 가 같은 배치에서 계속 실패해 처리가 멈춤" | 배치 분할 + 재시도 제한 + 실패 대상 | 독약 레코드 격리 |
| "이터레이터 에이지가 계속 증가" | 컨슈머 처리량 확대(샤드·병렬화 계수) | 만료 전 따라잡기 |
| "저장 데이터 암호화" | KMS 키로 서버 측 암호화 활성화 | 스트림 단위 설정 |

내일은 샤드도 컨슈머 코드도 없이 스트림을 S3·Redshift 로 흘려보내는 Data Firehose 를 다룬다.

## 📖 용어

- **샤드(shard)** : 스트림을 이루는 처리량의 기본 단위. 샤드마다 쓰기·읽기 한도가 정해져 있다.
- **파티션 키** : 레코드를 어느 샤드에 넣을지 정하는 값. 같은 키는 항상 같은 샤드로 간다.
- **핫 샤드** : 키가 쏠려 특정 샤드에만 트래픽이 몰리는 현상. 그 샤드만 스로틀된다.
- **스로틀(throttle)** : 한도를 넘는 요청을 서비스가 거부하는 것. `ProvisionedThroughputExceededException` 으로 나타난다.
- **리샤딩** : 샤드를 분할하거나 병합해 스트림의 처리량을 바꾸는 작업.
- **향상된 팬아웃(EFO)** : 컨슈머마다 전용 읽기 대역폭을 주고 레코드를 밀어 주는 방식.
- **KPL / KCL** : 프로듀서용·컨슈머용 라이브러리. 배칭·집계와 샤드 분배·체크포인트를 대신 처리한다.
- **체크포인트** : 컨슈머가 어디까지 읽었는지 기록해 둔 위치. KCL 은 DynamoDB 리스 테이블에 저장한다.
- **이터레이터 에이지** : 컨슈머가 방금 읽은 레코드가 스트림에 들어온 지 얼마나 됐는지. 클수록 밀려 있다는 뜻이다.
- **보존 기간** : 스트림이 레코드를 보관하는 시간. 이 안에서는 다시 읽을 수 있다.

## 📝 연습 문제

**문제 1.** 한 KDS 스트림에서 특정 샤드만 지속적으로 ProvisionedThroughputExceededException이 발생하고 나머지 샤드는 거의 비어 있다. 가장 가능성 높은 원인은?

A) 파티션 키 분포가 편향되어 핫 샤드가 발생  
B) 보존 기간이 너무 짧음  
C) 컨슈머가 너무 많음  
D) On-demand 모드를 사용 중  

**정답: A**  
해설: 특정 샤드만 throttle되고 나머지는 한가한 것은 전형적인 핫 샤드(hot partition) 증상으로, 파티션 키 분포가 고르지 않아 트래픽이 한 샤드로 쏠린 결과다. 카디널리티가 높고 균등한 키로 바꿔야 한다. 보존 기간은 throttle과 무관하고, 컨슈머 수는 읽기 쪽 문제이며, On-demand 모드라면 오히려 자동 확장으로 이 문제가 완화된다.

**문제 2.** 초당 약 8MB, 6,000개의 레코드를 KDS Provisioned 모드로 안정적으로 수집하려 한다. 최소 샤드 수는?

A) 6개  
B) 8개  
C) 2개  
D) 10개  

**정답: B**  
해설: 샤드당 쓰기 용량은 1MB/s 또는 1,000 records/s 중 먼저 도달하는 한계다. 8MB/s에는 8샤드, 6,000 records/s에는 6샤드가 필요하므로 둘 다 만족하려면 더 큰 값인 8개가 필요하다. 6개는 처리량(MB) 한계를, 2개는 둘 다 초과한다. 10개는 동작하지만 최소가 아니다.

**문제 3.** 같은 사용자가 발생시킨 클릭 이벤트들을 반드시 발생 순서대로 처리해야 한다. KDS에서 이를 보장하는 설계는?

A) 매 레코드마다 무작위 파티션 키 사용  
B) 샤드를 1개로 고정  
C) 사용자 ID를 파티션 키로 사용  
D) 향상된 팬아웃 활성화  

**정답: C**  
해설: KDS는 같은 파티션 키의 레코드를 같은 샤드로 보내고 샤드 내 순서를 보장하므로, 사용자 ID를 파티션 키로 쓰면 사용자별 순서가 유지된다. 무작위 키는 여러 샤드로 흩어져 순서가 깨진다. 샤드 1개는 전체 순서를 보장하지만 처리량이 1MB/s로 묶여 확장 불가다. 향상된 팬아웃은 읽기 대역폭 기능으로 순서와 무관하다.

---

**문제 4.** 5개의 서로 다른 컨슈머 애플리케이션이 각각 풀 대역폭으로 동일 스트림을 낮은 지연으로 독립 소비해야 한다. 적절한 기능은?

A) 공유 처리량(classic) GetRecords 폴링  
B) 샤드 수를 5개로 고정  
C) 보존 기간을 365일로 연장  
D) 향상된 팬아웃(Enhanced Fan-Out)  

**정답: D**  
해설: 향상된 팬아웃은 컨슈머마다 샤드당 2MB/s 전용 대역폭을 push 방식(약 70ms 지연)으로 제공해, 여러 컨슈머가 서로 경쟁하지 않고 독립적으로 소비할 수 있다. 공유 처리량은 샤드당 2MB/s를 모든 컨슈머가 나눠 써서 컨슈머가 늘수록 느려진다. 보존 기간·샤드 수는 컨슈머 간 대역폭 경쟁 문제를 해결하지 못한다.

**문제 5.** 컨슈머 처리 로직에 버그가 있었음을 발견하고, 지난 3일간 들어온 데이터를 처음부터 다시 처리하려 한다. 이를 가능하게 하는 KDS의 특성은?

A) 보존 기간을 충분히 길게 설정해 두면 해당 구간을 재처리(replay)할 수 있다  
B) SQS처럼 소비하면 메시지가 삭제되므로 불가능하다  
C) 파티션 키를 바꾸면 자동 재처리된다  
D) 샤드를 분할하면 과거 데이터가 복원된다  

**정답: A**  
해설: KDS는 append-only 로그처럼 동작해 보존 기간(기본 24h, 최대 365일) 안의 데이터를 보관하므로, 컨슈머를 과거 위치(시퀀스/타임스탬프)부터 다시 읽게 해 재처리할 수 있다. 3일 재처리를 하려면 보존을 3일 이상으로 설정해 두었어야 한다. SQS와 달리 소비해도 데이터가 사라지지 않으며, 파티션 키 변경이나 리샤딩은 재처리와 무관하다.
