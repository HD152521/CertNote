# Day 4 - Amazon MSK(Kafka): 토픽, 파티션, 언제 무엇

스트리밍 수집 도구의 마지막 조각은 **Amazon MSK(Managed Streaming for Apache Kafka)** 다. Kinesis가 AWS 고유의 스트리밍 서비스라면, Kafka는 업계 표준 오픈소스 스트리밍 플랫폼이고 MSK는 그 Kafka를 AWS가 관리형으로 제공하는 서비스다.

핵심 질문은 어제와 같다: "Kinesis가 있는데 왜 MSK인가? 언제 무엇을 쓰나?" 오늘은 Kafka의 기본 개념(토픽·파티션·컨슈머 그룹)을 잡고, Kinesis와 정확히 어디서 갈리는지를 본다. DEA-C01에서 이 비교는 거의 반드시 나온다.

## Kafka의 구조: 토픽과 파티션

Kafka에서 데이터는 **토픽(topic)** 단위로 분류된다. 토픽은 "주제별 로그"라고 보면 된다(예: `orders`, `clicks`, `sensor-data`). 각 토픽은 다시 여러 **파티션(partition)** 으로 쪼개진다. 파티션이 Kafka의 병렬성·처리량 단위다.

```
토픽: orders
 ├─ 파티션 0:  [msg0][msg1][msg2] ...   ← append-only 로그, 순서 보장
 ├─ 파티션 1:  [msg0][msg1] ...
 └─ 파티션 2:  [msg0][msg1][msg2][msg3] ...
```

눈치챘겠지만 구조가 KDS와 거의 같다. **토픽 ≈ 스트림, 파티션 ≈ 샤드**다. 프로듀서가 메시지를 보낼 때 키를 지정하면 그 키로 어느 파티션에 갈지 결정되고, 한 파티션 안에서는 순서가 보장된다. KDS의 파티션 키 개념과 동일하다.

```python
from kafka import KafkaProducer
producer = KafkaProducer(bootstrap_servers="b-1.msk.amazonaws.com:9092")

# 키(user-8821)가 파티션을 결정 → 같은 사용자 메시지는 같은 파티션, 순서 보장
producer.send("orders", key=b"user-8821", value=b'{"item":"book","qty":2}')
producer.flush()
```

> 💡 **관련 이론**: Kafka와 Kinesis는 둘 다 "분산 append-only 로그" 모델을 공유한다. 메시지를 소비해도 사라지지 않고(retention 동안 보관), 여러 컨슈머 그룹이 각자의 오프셋(offset)에서 독립적으로 읽는다. 이 점에서 둘 다 SQS 같은 전통 큐와 근본적으로 다르다. 그래서 Kafka 경험자는 Kinesis를 빠르게 이해하고, 반대도 마찬가지다. 시험은 이 "개념적 1:1 대응"을 알고 있는지 확인한다.

## 컨슈머 그룹과 오프셋

컨슈머들은 **컨슈머 그룹(consumer group)** 으로 묶인다. 한 그룹 안에서는 파티션이 컨슈머들에게 분배되어, 각 파티션은 그룹 내 한 컨슈머만 읽는다(병렬 처리). 서로 다른 그룹은 같은 토픽을 독립적으로 전부 읽는다(팬아웃).

각 컨슈머 그룹은 자신이 어디까지 읽었는지를 **오프셋(offset)** 으로 기록한다. KDS의 체크포인트(KCL이 DynamoDB에 저장)와 같은 개념이다.

```
토픽 orders (파티션 3개)
 ├─ consumer-group-A (실시간 결제처리)  : 파티션0→C1, 파티션1→C2, 파티션2→C3
 └─ consumer-group-B (데이터레이크 적재) : 동일 토픽을 독립 오프셋으로 별도 소비
```

> 💡 **관련 이론**: 컨슈머 수가 파티션 수를 넘으면 초과 컨슈머는 놀게 된다(한 파티션은 그룹 내 한 컨슈머만 읽으므로). 따라서 처리량을 늘리려면 컨슈머만 늘리는 게 아니라 파티션 수를 충분히 잡아야 한다. 이는 KDS에서 컨슈머를 늘려도 샤드가 부족하면 병렬성이 제한되는 것과 같은 원리다. "병렬성의 상한 = 파티션(샤드) 수"라는 공식이 양쪽에 공통으로 적용된다.

## MSK: 관리형이지만 Kafka는 Kafka다

MSK는 Kafka 브로커·주키퍼(또는 KRaft)의 프로비저닝·패치·장애 복구를 AWS가 대신해준다. 하지만 여전히 **클러스터·브로커·파티션을 사용자가 인식하고 설계**해야 한다. 완전 서버리스가 필요하면 **MSK Serverless**가 용량을 자동 관리한다.

```
- MSK (Provisioned): 브로커 인스턴스 타입·수를 지정, 세밀한 제어
- MSK Serverless    : 용량 자동, 사용량 과금, 운영 부담 최소
- MSK Connect       : 관리형 Kafka Connect (소스/싱크 커넥터로 시스템 연동)
```

## Kinesis vs MSK: 언제 무엇을

이게 오늘의 핵심이다.

| 기준 | Kinesis (KDS/Firehose) | Amazon MSK |
|------|----------------------|-----------|
| 표준 | AWS 고유 | 오픈소스 Apache Kafka (이식성↑) |
| 운영 부담 | 최소(특히 Firehose/On-demand) | 상대적으로 큼(클러스터 인식 필요) |
| 기존 자산 | AWS 신규 구축에 적합 | 이미 Kafka 코드/팀/생태계 보유 시 |
| 생태계 | AWS 통합 빌트인 | Kafka Connect·Streams·서드파티 풍부 |
| 처리량 | 샤드 단위, On-demand 자동 | 브로커/파티션 튜닝으로 매우 높음 |

핵심 판단 기준은 단순하다.

- **이미 Kafka를 쓰고 있다(코드·커넥터·팀 역량) → MSK.** 기존 Kafka 애플리케이션을 코드 변경 거의 없이 그대로 옮길 수 있다(리프트 앤 시프트).
- **AWS에서 새로 시작하고 운영 부담을 최소화하고 싶다 → Kinesis.** 특히 단순 적재면 Firehose.
- **온프레미스/멀티클라우드 이식성이 중요하다 → Kafka(MSK).** Kinesis는 AWS에 종속된다.

> 💡 **관련 이론**: 시험에서 결정적 키워드는 "기존 Apache Kafka 워크로드/애플리케이션"이다. 이 표현이 나오면 거의 항상 MSK가 정답이다. Kafka 생태계(Kafka Connect, Kafka Streams, 기존 토픽 설계, 컨슈머 코드)를 재사용해야 하기 때문이다. 반대로 "최소 운영 부담", "서버리스", "AWS 네이티브 신규 구축", "단순 S3/Redshift 적재" 같은 표현이면 Kinesis 쪽이다. 두 서비스는 기능이 겹치므로, 정답은 기술적 우열이 아니라 "기존 자산과 운영 모델"로 갈린다는 점을 기억하자.

## 데이터 적재로 잇기

MSK에 들어온 데이터를 분석 스택으로 보내는 방법도 알아두자. **MSK Connect**의 싱크 커넥터(예: S3 Sink)로 토픽 데이터를 S3에 적재하거나, Kafka를 소비하는 Lambda·Flink(Amazon Managed Service for Apache Flink)로 실시간 처리 후 다운스트림에 보낸다. KDS와 마찬가지로 "수집 → 처리 → 적재"의 흐름은 동일하다.

## 정리

- Kafka 구조: 토픽 ≈ KDS 스트림, 파티션 ≈ 샤드, 오프셋 ≈ 체크포인트
- 컨슈머 그룹으로 병렬 소비 + 그룹별 독립 팬아웃, 병렬성 상한 = 파티션 수
- MSK = 관리형 Kafka(클러스터 인식 필요), MSK Serverless = 용량 자동
- 선택 기준: 기존 Kafka 자산·이식성 → MSK / 최소 운영·AWS 네이티브·단순 적재 → Kinesis

## 📝 연습 문제

**문제 1.** 한 기업이 온프레미스에서 수년간 Apache Kafka로 스트리밍 파이프라인을 운영해 왔고, 기존 컨슈머/프로듀서 코드와 Kafka Connect 커넥터를 거의 그대로 AWS로 옮기려 한다. 가장 적절한 서비스는?

A) Kinesis Data Streams  
B) Kinesis Data Firehose  
C) Amazon MSK  
D) SQS  

**정답: C**  
해설: "기존 Apache Kafka 워크로드를 코드 변경 없이 이전"은 MSK의 정석 시나리오다. MSK는 표준 Kafka API를 제공하므로 기존 클라이언트 코드·커넥터·토픽 설계를 그대로 재사용(리프트 앤 시프트)할 수 있다. Kinesis는 API가 달라 코드 재작성이 필요하고, SQS는 스트리밍 로그 모델이 아니다.

---

**문제 2.** Kafka의 파티션은 Kinesis Data Streams의 어떤 개념에 가장 가깝게 대응하는가?

A) 샤드  
B) 컨슈머 그룹  
C) 전달 스트림  
D) 보존 기간  

**정답: A**  
해설: Kafka의 파티션은 KDS의 샤드에 대응한다. 둘 다 병렬성·처리량의 단위이며 내부적으로 순서가 보장되는 append-only 로그다. 컨슈머 그룹은 KCL 애플리케이션/컨슈머 측 개념이고, 전달 스트림은 Firehose의 단위이며, 보존 기간은 데이터 보관 시간 설정이다.

---

**문제 3.** 파티션이 3개인 Kafka 토픽을 한 컨슈머 그룹에서 5개의 컨슈머로 소비하려 한다. 결과로 옳은 것은?

A) 5개 컨슈머가 모두 균등하게 일한다  
B) 파티션이 3개뿐이므로 최대 3개 컨슈머만 활성, 나머지 2개는 놀게 된다  
C) 자동으로 파티션이 5개로 늘어난다  
D) 순서 보장이 깨진다  

**정답: B**  
해설: 한 그룹 안에서 각 파티션은 한 컨슈머만 읽으므로, 컨슈머 수가 파티션 수를 넘으면 초과분은 할당받을 파티션이 없어 유휴 상태가 된다. 병렬성 상한은 파티션 수다. 파티션은 자동으로 늘지 않으며(수동 증설 필요), 순서 보장은 파티션 내에서 유지된다.

---

**문제 4.** AWS에서 새 스트리밍 파이프라인을 구축하는데, 운영 부담을 최소화하고 데이터를 단순히 S3와 Redshift에 적재만 하면 된다. Kafka 경험이나 기존 자산은 없다. 가장 적절한 선택은?

A) Amazon MSK Provisioned  
B) Amazon MSK Connect  
C) 자체 EC2에 Kafka 직접 설치  
D) Kinesis Data Firehose  

**정답: D**  
해설: 운영 부담 최소화 + 단순 S3/Redshift 적재 + 기존 Kafka 자산 없음 → 완전관리형 Firehose가 정답이다. 목적지가 빌트인이고 서버리스다. MSK는 클러스터 운영을 인식해야 해 부담이 크고, EC2 자체 설치는 운영 부담이 최대이며, MSK Connect는 Kafka 생태계가 전제다.

---

**문제 5.** Kafka와 Kinesis가 SQS 같은 전통적 메시지 큐와 근본적으로 다른 공통 특성은?

A) append-only 로그로 동작해, 보존 기간 동안 여러 컨슈머(그룹)가 각자 오프셋으로 독립 재소비할 수 있다  
B) 메시지를 소비하면 즉시 삭제된다  
C) 단일 컨슈머만 지원한다  
D) 순서를 전혀 보장하지 않는다  

**정답: A**  
해설: Kafka와 Kinesis는 모두 분산 append-only 로그 모델로, 소비해도 데이터가 사라지지 않고 보존 기간 동안 보관되며 여러 컨슈머 그룹이 독립 오프셋/체크포인트로 같은 데이터를 재소비·팬아웃할 수 있다. SQS는 소비 시 삭제되는 큐다. 단일 컨슈머 제한이나 순서 미보장은 둘의 특성과 반대다.
