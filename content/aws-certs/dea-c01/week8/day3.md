# Day 3 - 로깅·감사·트러블슈팅: CloudTrail과 실패 복구

## 📌 핵심 정리

- CloudTrail = "누가 어떤 API 를 호출했나"(감사), CloudWatch Logs = "애플리케이션이 무엇을 출력했나". 질문이 "누가"로 시작하면 CloudTrail 이다.
- 관리 이벤트는 기본으로 기록되고 이벤트 기록(Event history)에서 90일간 조회된다. S3 객체 접근 같은 **데이터 이벤트는 직접 켜야** 남는다.
- 디버깅은 오케스트레이터 → 실패 태스크 로그 → 입력 데이터 → 권한·리소스 → CloudTrail 순으로 위에서 아래로 좁힌다.
- 재시도는 일시적 오류에만, 지수 백오프와 지터를 붙여서 건다. 재시도는 멱등한 작업에서만 안전하고, 영구 실패는 Catch 로 격리한다.
- 반복 실패 메시지는 DLQ 로 빼서 큐가 막히지 않게 하고, 원인을 고친 뒤 redrive 로 다시 넣는다.

## CloudTrail: 누가·언제·무엇을

파이프라인이 멈췄을 때 "무슨 일이 있었는가"를 재구성하는 능력이 운영의 절반이다. 그 재료 가운데 "사람과 시스템이 AWS 에 무엇을 시켰는가"를 담는 것이 CloudTrail 이다.

| 이벤트 종류 | 담는 것 | 기본 기록 여부 |
|------|------|------|
| 관리 이벤트(Management) | 리소스 생성·수정·삭제, IAM 변경 등 제어 평면 작업 | 기록됨 |
| 데이터 이벤트(Data) | S3 객체 GET/PUT, Lambda Invoke, DynamoDB 항목 단위 작업 등 데이터 평면 작업 | 기록 안 됨(리소스 유형을 지정해 켠다) |
| 네트워크 활동 이벤트 | VPC 엔드포인트를 거친 API 호출 | 기록 안 됨 |
| 인사이트 이벤트(Insights) | 평소와 다른 API 호출량·오류율 | 기록 안 됨 |

- **이벤트 기록(Event history)** 은 아무 설정 없이 리전별로 지난 90일의 **관리 이벤트**를 보여 준다. 수정할 수 없는 기록이지만 90일이 지나면 볼 수 없고, 데이터 이벤트는 여기에 없다.
- 90일보다 길게 남기거나 데이터 이벤트를 남기려면 **추적(trail)** 을 만들어 S3 버킷으로 내보낸다. 추적은 CloudWatch Logs 와 EventBridge 로도 이벤트를 보낼 수 있다.
- S3 로의 전달은 즉시가 아니다. S3 문서 기준으로 데이터 이벤트는 5분, 관리 이벤트는 15분 간격으로 전달된다. "방금 일어난 일"을 실시간 알람으로 받으려면 EventBridge 규칙을 쓴다.
- **로그 파일 무결성 검증**을 켜면 전달된 로그 파일이 변조·삭제됐는지 해시와 서명으로 확인할 수 있다. S3 서버 액세스 로그에는 이 기능이 없다.
- 조직 전체의 로그는 조직 추적으로 중앙 계정의 버킷에 모으고, 그 버킷은 운영 계정과 분리해 변경하지 못하게 둔다.
- **CloudTrail Lake** 는 이벤트를 이벤트 데이터 스토어에 넣어 SQL 로 조회하게 해 준다. 보존은 요금 옵션에 따라 최대 약 7년 또는 약 10년까지다.

```text
질문: "어제 새벽 curated 테이블을 누가 DROP 했지?"
→ CloudTrail 에서 eventSource=glue.amazonaws.com, eventName=DeleteTable 을
  시간과 userIdentity 로 좁힌다
```

> 💡 **관련 이론**: CloudWatch Logs 는 애플리케이션이 쓴 로그, CloudTrail 은 AWS API 호출 기록이다. Athena 에서 실행된 `DROP TABLE` 문은 Athena 쿼리 이력에 남고, 그 결과로 호출된 `glue:DeleteTable` 은 CloudTrail 에 남는다. 한 사건이 두 곳에 다른 모습으로 남는다는 점을 기억하면 추적이 빨라진다.

## 닮은 로그 네 가지

| 로그 | 기록하는 것 | 기본 상태 | 고르는 단서 |
|------|------|------|------|
| CloudTrail 관리 이벤트 | 리소스·권한·설정 변경 API | 켜져 있음(90일 조회) | "누가 테이블·정책·키를 바꿨나" |
| CloudTrail 데이터 이벤트 | 객체·항목 단위 접근 | 꺼져 있음, 켜면 과금 | "누가 이 객체를 읽었나" |
| S3 서버 액세스 로그 | 버킷에 들어온 요청 | 꺼져 있음, 전달은 몇 시간 내(최선 노력) | 인증 실패 요청, 수명 주기 전환·만료까지 봐야 할 때 |
| CloudWatch Logs | 잡·함수가 출력한 텍스트 | 서비스·설정에 따라 다름 | "왜 실패했나(스택 트레이스)" |

- CloudTrail 은 자격 증명이 유효하지 않아 **인증에 실패한** 요청은 남기지 않는다. 권한 부족(`AccessDenied`)은 남긴다. 인증 실패까지 봐야 하면 서버 액세스 로그다.
- 수명 주기 규칙이 객체를 옮기거나 지운 기록은 서버 액세스 로그에만 남는다. "객체가 사라졌는데 CloudTrail 에 DeleteObject 가 없다"면 수명 주기 만료를 의심한다.

## CloudTrail 로그를 Athena 로 조회하기

추적이 S3 에 쌓은 JSON 로그는 Athena 테이블로 만들어 SQL 로 뒤진다.

```sql
-- 지난 이틀간 Glue 카탈로그 테이블을 지우거나 바꾼 호출
SELECT eventtime, useridentity.arn AS who, eventname, sourceipaddress, requestparameters
FROM cloudtrail_logs
WHERE eventsource = 'glue.amazonaws.com'
  AND eventname IN ('DeleteTable', 'UpdateTable', 'BatchDeleteTable')
  AND eventtime >= '2026-06-25T00:00:00Z'
ORDER BY eventtime DESC;
```

- 로그 양이 많으므로 날짜 기준 파티션(또는 파티션 프로젝션)을 걸어 스캔량을 줄인다.
- 역할을 넘겨받아(AssumeRole) 한 호출은 `userIdentity` 에 역할 세션이 찍힌다. 실제 사람을 찾으려면 그 세션을 만든 `AssumeRole` 이벤트를 한 번 더 거슬러 올라간다.

## 파이프라인 디버깅 워크플로우

장애가 났을 때 코드부터 열지 말고 위에서 아래로 좁힌다.

1. **오케스트레이터부터**: Step Functions 실행 그래프나 Airflow(MWAA) DAG 에서 어느 태스크가 실패했는지 본다.
2. **실패 태스크의 로그**: 해당 Glue·EMR·Lambda 의 CloudWatch Logs 에서 예외 스택을 본다.
3. **입력 데이터 점검**: 스키마 변경, 빈 파티션, 깨진 파일.
4. **권한·리소스 점검**: IAM·Lake Formation 거부, KMS 키 권한, 스로틀링, 메모리 부족.
5. **CloudTrail 로 변경 추적**: 최근 누군가 테이블·정책·설정을 바꿨는지.

```text
Step Functions 실행 → TransformJob 실패
  → CloudWatch Logs(Glue): "AnalysisException: cannot resolve 'email'"
  → 원인: 업스트림에서 email 컬럼명이 user_email 로 바뀜
  → 조치: 매핑 수정 + 스키마 검증 게이트 추가
```

- "어제까지 되던 잡이 코드 변경 없이 실패"하면 3번과 5번이다. 데이터가 바뀌었거나 누군가 설정을 바꿨다.

## 흔한 실패 유형: 증상 → 원인 → 조치

| 증상(로그·오류) | 원인 | 조치 |
|------|------|------|
| `ProvisionedThroughputExceededException`, `Rate exceeded`, `ThrottlingException` | API·처리량 한도 초과 | 백오프 재시도, 용량 증설, 호출 배치화 |
| Spark 익스큐터 OOM, 태스크가 반복해서 죽음 | 파티션이 너무 크거나 스큐 | 파티션 수 조정, 키 분산, 메모리가 큰 워커 |
| 일부 태스크만 유독 오래 걸림 | 데이터 스큐 | 셔플 지표 확인, 솔팅·브로드캐스트 조인 |
| `AccessDenied` | IAM 정책, Lake Formation 권한, KMS 키 정책 중 하나가 빠짐 | 세 층을 차례로 확인(Week 9) |
| 잡이 한참 돌다 강제 종료 | Glue 잡 타임아웃 | 타임아웃 값 확인. 비워 두면 Glue 4.0 이하는 2,880분, 5.0 이상은 480분 |
| 같은 잡을 동시에 시작하면 오류 | 최대 동시 실행 수 초과(기본값 1) | 동시 실행 수 상향 또는 잡 실행 큐잉 |
| VPC 안의 잡이 KMS 호출에서 타임아웃 | KMS 로 가는 경로 없음 | KMS VPC 엔드포인트 또는 NAT |
| 컬럼을 찾을 수 없음, 타입 불일치 | 업스트림 스키마 변경 | 매핑 수정, 스키마 검증 게이트 |

- Glue 잡의 자동 재시도 횟수는 0~10 으로 정한다. **타임아웃으로 끝난 잡은 재시작되지 않는다.** 타임아웃을 재시도로 해결하려는 설계는 동작하지 않는다.
- Glue 5.0 으로 올린 뒤 장시간 잡이 8시간에서 끊긴다면 기본 타임아웃이 바뀐 것이다. 시험 자료에는 옛 기본값(48시간)으로 나올 수 있다.

## 재시도와 실패 복구: Step Functions 의 Retry 와 Catch

분산 시스템에서 일시적 오류는 정상이다. 핵심은 **재시도할 오류와 영구 오류를 구분**하는 것이다.

```json
"Retry": [{
  "ErrorEquals": ["ThrottlingException", "Glue.ConcurrentRunsExceededException"],
  "IntervalSeconds": 5,
  "BackoffRate": 2.0,
  "MaxAttempts": 4,
  "MaxDelaySeconds": 60,
  "JitterStrategy": "FULL"
}],
"Catch": [{
  "ErrorEquals": ["States.ALL"],
  "ResultPath": "$.error",
  "Next": "QuarantineAndNotify"
}]
```

| 필드 | 기본값 | 의미 |
|------|------|------|
| `IntervalSeconds` | 1 | 첫 재시도까지 기다리는 시간 |
| `MaxAttempts` | 3 | 최대 재시도 횟수. 0 이면 재시도하지 않음 |
| `BackoffRate` | 2.0 | 재시도마다 간격에 곱하는 배수 |
| `MaxDelaySeconds` | 제한 없음 | 간격이 늘어나는 상한 |
| `JitterStrategy` | `NONE` | `FULL` 이면 0~계산된 간격 사이에서 무작위로 기다림 |

- 지터는 **기본으로 꺼져 있다.** 여러 실행이 같은 순간에 실패하면 같은 순간에 다시 몰려든다(thundering herd). `FULL` 을 직접 지정한다.
- `States.ALL` 은 모든 오류 이름과 맞지만, 배열에 단독으로, 그리고 마지막 항목에 와야 한다. `States.TaskFailed` 는 `States.Timeout` 을 뺀 모든 오류와 맞는다.
- `States.Runtime`(예: null 페이로드에 경로를 적용)은 재시도도 캐치도 되지 않고 실행을 실패시킨다. `States.DataLimitExceeded` 는 `States.ALL` 로는 안 잡히고 이름을 직접 적어야 잡힌다.
- 상태에 Retry 와 Catch 가 모두 있으면 **Retry 가 먼저**다. 재시도를 다 쓰고도 실패하면 Catch 로 넘어간다. 둘 다 없으면 상태 하나의 오류로 실행 전체가 실패한다.
- 재시도도 상태 전이로 계산된다. 표준 워크플로는 상태 전이 수로 과금되므로 무제한에 가까운 재시도는 비용이 된다.
- 실패한 실행을 고친 뒤에는 처음부터 다시 돌리지 않고 실패 지점부터 이어 가는 **redrive** 를 쓸 수 있다.

> 💡 **관련 이론**: 재시도는 멱등 작업에서만 안전하다. "잔액을 100 증가"처럼 비멱등한 작업을 무턱대고 재시도하면 두 번 적용된다. 멱등 키나 조건부 쓰기로 보호한다. 적재 잡이라면 append 대신 파티션 덮어쓰기·MERGE 가 같은 역할을 한다.

## 서비스마다 다른 재시도 기본 동작

| 실행 주체 | 기본 재시도 | 다 실패하면 |
|------|------|------|
| Step Functions Task | Retry 를 적지 않으면 재시도 없음 | Catch, 없으면 실행 실패 |
| Lambda 비동기 호출 | 함수 오류 시 2회 더(1분 뒤, 다시 2분 뒤). 스로틀·시스템 오류는 기본 최대 6시간 동안 재시도 | 이벤트 폐기. DLQ 나 실패 대상(destination)을 걸어야 남음 |
| Lambda 스트림 이벤트 소스 매핑(Kinesis) | 레코드가 만료될 때까지 같은 배치를 재시도 | 샤드가 막힘. 재시도 제한·배치 분할·실패 대상으로 격리 |
| SQS 컨슈머 | 가시성 타임아웃이 지나면 메시지가 다시 보임 | `maxReceiveCount` 초과 시 DLQ |
| Glue 잡 | 설정한 횟수(0~10)만큼 재시작 | 실패 상태로 종료 |

- 기본값이 "무한에 가까운 재시도"인 쪽(스트림 매핑)과 "재시도 없음"인 쪽(Step Functions)이 섞여 있다. 문제에서 어느 서비스가 호출하는지부터 확인한다.

## DLQ(데드레터 큐) 처리

처리에 계속 실패하는 메시지를 원래 큐에 두면 컨슈머가 같은 메시지를 받고 실패하기를 반복한다. **DLQ** 는 일정 횟수 넘게 실패한 메시지를 따로 빼 두는 큐다.

```text
정상 큐 → 컨슈머 처리 실패 N회(maxReceiveCount) → DLQ
DLQ → 원인 분석 → 수정 → 원본 큐로 재투입(redrive)
```

| 항목 | 내용 |
|------|------|
| 이동 조건 | 원본 큐의 redrive 정책에 적은 `maxReceiveCount` 만큼 수신됐는데 삭제되지 않음 |
| 위치 제약 | DLQ 는 원본 큐와 같은 계정·같은 리전에 있어야 한다 |
| 가시성 타임아웃 | 기본 30초, 메시지를 처음 받은 시점부터 최대 12시간. 처리 시간보다 짧으면 처리 중인 메시지가 다시 보여 중복 처리된다 |
| 보존 기간(표준 큐) | 만료는 **원래 큐에 들어온 시각** 기준이다. DLQ 로 옮겨도 시계가 다시 돌지 않는다 |
| 보존 기간(FIFO 큐) | DLQ 로 옮길 때 시각이 초기화된다 |
| redrive 허용 정책 | 어떤 원본 큐가 이 큐를 DLQ 로 쓸 수 있는지 제한 |

- 표준 큐에서는 DLQ 의 보존 기간을 **원본 큐보다 길게** 잡는다. 원본 큐에서 하루를 보낸 메시지는 보존 4일짜리 DLQ 에서 3일 뒤에 사라진다. 분석하기도 전에 증거가 없어지는 원인이다.
- `maxReceiveCount` 를 1 처럼 낮게 잡으면 일시적 오류 한 번에 메시지가 DLQ 로 간다. 충분한 재시도 횟수를 준다.
- FIFO 큐에 DLQ 를 붙이면 실패 메시지가 빠져나가면서 순서가 바뀐다. 순서가 깨지면 안 되는 작업에는 DLQ 를 쓰지 않는다.
- DLQ 에 메시지가 한 건이라도 쌓이면 알람이 울리게 한다. 알람 없는 DLQ 는 조용한 데이터 유실 창고다.
- Lambda 비동기 호출에서 **DLQ** 는 폐기된 이벤트 자체를 받고, **실패 대상(on-failure destination)** 은 실패한 호출의 기록을 받는다. 새 설계에서는 정보가 더 많은 대상 쪽을 쓴다.

## 📖 용어

- **관리 이벤트** : 리소스를 만들고 바꾸고 지우는 API 호출 기록. CloudTrail 이 기본으로 남긴다.
- **데이터 이벤트** : 객체를 읽고 쓰는 것처럼 리소스 안의 데이터를 다루는 호출 기록. 직접 켜야 남는다.
- **추적(trail)** : CloudTrail 이벤트를 S3 버킷 등으로 계속 내보내는 설정.
- **이벤트 기록** : 설정 없이 볼 수 있는 최근 90일의 관리 이벤트 목록.
- **지수 백오프** : 재시도할 때마다 기다리는 시간을 배수로 늘리는 방식.
- **지터(jitter)** : 재시도 간격에 섞는 무작위 값. 여러 클라이언트가 동시에 몰려드는 것을 막는다.
- **Catch** : 재시도로도 해결되지 않은 오류를 받아 다른 상태로 보내는 Step Functions 설정.
- **가시성 타임아웃** : 컨슈머가 받은 SQS 메시지가 다른 컨슈머에게 안 보이는 시간.
- **DLQ** : 여러 번 처리에 실패한 메시지를 따로 모아 두는 큐.
- **redrive** : 원인을 고친 뒤 DLQ 의 메시지나 실패한 실행을 다시 처리 경로로 돌려보내는 것.

## 📝 연습 문제

**문제 1.** "지난 밤 누가 Glue Data Catalog의 테이블을 삭제했는가"를 자격증명과 시각까지 추적하려면 어떤 서비스를 봐야 하는가?

A) CloudWatch Logs  
B) CloudTrail  
C) X-Ray  
D) Glue Data Quality  

**정답: B**  
해설: CloudTrail은 AWS API 호출을 자격증명(userIdentity)·시간과 함께 기록하므로 "누가 무엇을 했는가"를 감사할 수 있다. CloudWatch Logs는 애플리케이션 로그, X-Ray는 분산 추적, Glue Data Quality는 데이터 품질 평가로 API 감사 용도가 아니다.

---

**문제 2.** SQS 큐에서 컨슈머가 특정 메시지 처리를 반복적으로 실패해 큐 전체 처리가 막히는 것을 방지하기 위한 메커니즘은?

A) FIFO 큐 전환  
B) 가시성 타임아웃을 0으로 설정  
C) 메시지 보존 기간 단축  
D) 데드레터 큐(DLQ) + maxReceiveCount  

**정답: D**  
해설: maxReceiveCount를 초과해 반복 실패한 메시지를 DLQ로 이동시키면 정상 큐가 막히지 않고, 이후 원인 수정 후 redrive로 재처리할 수 있다. FIFO 전환·가시성 타임아웃 0·보존 기간 단축은 반복 실패 메시지 격리 문제를 해결하지 못한다.

---

**문제 3.** Step Functions에서 일시적 오류(예: ThrottlingException)에 대응할 때, 재시도 폭주(thundering herd)를 줄이기 위해 권장되는 전략은?

A) 즉시 무한 재시도  
B) 고정 간격 1초 재시도  
C) 지수 백오프 + 지터  
D) 재시도 없이 즉시 실패 처리  

**정답: C**  
해설: 지수 백오프는 재시도 간격을 점점 늘리고 지터(무작위성)는 여러 클라이언트의 동시 재시도를 분산시켜 폭주를 방지한다. 무한·고정 간격 재시도는 부하를 가중시키고, 재시도 없는 즉시 실패는 일시적 오류 복구 기회를 버린다.

---

**문제 4.** 비멱등 작업(예: "계좌 잔액을 100 증가")을 자동 재시도할 때 발생할 수 있는 가장 큰 위험은?

A) 동일 작업이 중복 적용되어 데이터가 잘못된다  
B) 작업이 느려진다  
C) 로그가 사라진다  
D) IAM 권한이 변경된다  

**정답: A**  
해설: 비멱등 작업을 재시도하면 같은 작업이 여러 번 적용되어(예: 잔액이 두 번 증가) 데이터 무결성이 깨진다. 멱등 키나 조건부 쓰기로 보호해야 재시도가 안전하다. 느려짐·로그 소실·권한 변경은 핵심 위험이 아니다.

**문제 5.** 파이프라인 장애를 디버깅할 때 가장 먼저 확인하기에 적절한 위치는?

A) 개별 익스큐터의 GC 로그  
B) S3 버킷의 요청 비용  
C) VPC 플로우 로그  
D) 오케스트레이터(Step Functions/MWAA)에서 어느 태스크가 실패했는지  

**정답: D**
