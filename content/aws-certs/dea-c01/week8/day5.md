# Day 5 - Week 8 종합: 데이터 운영 및 지원 복습

## 📌 핵심 정리

- 운영 문제는 네 질문으로 갈린다. **지금 정상인가**(CloudWatch) / **데이터가 맞는가**(Glue Data Quality) / **왜·누가 깨뜨렸나**(로그·CloudTrail) / **얼마를 쓰는가**(비용 도구).
- "누가 했나"는 CloudTrail, "시스템이 어떻게 동작했나"는 CloudWatch Logs·Metrics 다. 스트리밍 지연의 핵심 지표는 `IteratorAgeMilliseconds` 다.
- 품질 규칙 언어는 DQDL 이고, 양이 변하는 데이터에는 이상 탐지를 더한다. 기준 미달은 Step Functions Choice 로 막고 격리한다.
- 재시도는 멱등한 작업에만, 지수 백오프와 지터로 건다. 반복 실패는 DLQ 로 빼고 원인 수정 후 redrive 한다.
- 비용은 할당 태그로 보고, 변동은 자동 스케일링으로, 베이스라인은 사이징과 약정으로 다룬다. 순서는 사이징이 먼저다.

## 네 질문으로 보는 운영 지도

이번 주는 파이프라인이 "구축"된 뒤 "운영"되는 단계를 다뤘다. 나흘의 주제는 따로 떨어진 것이 아니라, 운영자가 장애 한 건을 겪으며 차례로 던지는 네 질문이다.

```
                     운영 중인 파이프라인
                            │
   ┌──────────────┬─────────┴────────┬───────────────┐
 지금 정상인가?   데이터가 맞는가?   왜·누가 깨뜨렸나?   얼마를 쓰는가?
   (Day 1)          (Day 2)            (Day 3)           (Day 4)
   │                │                  │                 │
 CloudWatch       Glue Data          CloudWatch Logs   비용 할당 태그
 지표·알람         Quality            CloudTrail        Cost Explorer
 EMF·복합 알람     DQDL·이상 탐지      Retry/Catch·DLQ   Budgets·이상 탐지
```

- 왼쪽 두 질문은 **탐지**, 셋째는 **진단과 복구**, 넷째는 **지속 가능성**이다. 문제를 읽을 때 지문이 넷 중 무엇을 묻는지 먼저 정하면 보기의 절반이 지워진다.
- 흔한 오답 구조는 "질문과 다른 칸의 도구"다. "누가 삭제했나"에 CloudWatch Logs, "비용 급증 탐지"에 CloudTrail 을 고르게 만든다.

## 신호 → 도구 매핑

| 알고 싶은 것 | 볼 곳 | 틀리기 쉬운 선택 |
|------|------|------|
| 컨슈머가 뒤처지는가 | `GetRecords.IteratorAgeMilliseconds`(Maximum) | `IncomingBytes`(유입량일 뿐) |
| 쓰기가 거부되는가 | `WriteProvisionedThroughputExceeded` | 이터레이터 에이지(읽는 쪽 지표) |
| Glue 잡이 왜 느린가 | 셔플·힙·익스큐터 지표, 드라이버·익스큐터 로그 | CloudTrail |
| EMR 이 놀고 있는가 | `IsIdle` 연속값, 자동 종료 정책 | `AppsRunning` 단일 시점 |
| 들어온 데이터가 믿을 만한가 | Glue Data Quality 점수·규칙 결과 | CloudWatch 지표(잡 성공 여부만 알려 줌) |
| 누가 테이블·정책을 바꿨나 | CloudTrail 관리 이벤트 | CloudWatch Logs |
| 누가 객체를 읽었나 | CloudTrail 데이터 이벤트(직접 켠다) | 관리 이벤트 |
| 어느 팀이 얼마를 썼나 | 활성화한 비용 할당 태그 + Cost Explorer | Budgets |
| 평소와 다른 비용 급증 | Cost Anomaly Detection | Budgets(정한 임계값만 본다) |

- "잡이 성공했다"와 "데이터가 맞다"는 다른 사실이다. 잡은 빈 파일을 읽고도 성공한다. 모니터링(Day 1)이 품질 검증(Day 2)을 대신하지 못하는 이유다.

**실패를 다루는 네 장치**

| 장치 | 대상 | 동작 |
|------|------|------|
| Retry | 일시적 오류 | 간격을 늘려 가며 다시 시도 |
| Catch | 재시도로 안 풀린 오류 | 다른 상태(격리·통보)로 분기 |
| DLQ | 반복 실패한 메시지 | 큐에서 빼서 따로 보관 |
| 검증 게이트 | 실행은 성공했지만 품질 미달 | 다음 단계 진행 차단 |

- 앞의 셋은 **실행이 실패**했을 때, 넷째는 **실행은 성공했는데 결과가 틀렸을** 때의 장치다.

**용량을 자동으로 맞추는 기능**

| 기능 | 무엇을 늘리나 | 사용자가 정하는 것 |
|------|------|------|
| Glue Auto Scaling | 잡 실행 중의 워커 | 최대 워커 수 |
| EMR Managed Scaling | 코어·태스크 노드 | 최소·최대, 온디맨드 상한, 코어 상한 |
| Kinesis 온디맨드 | 샤드 | 없음(모드 선택만) |
| Redshift Concurrency Scaling | 임시 쿼리 클러스터 | 큐의 모드, 클러스터 수 상한 |

## 통합 시나리오: 야간 주문 ETL 운영

```text
00:00 EventBridge 스케줄 → Step Functions 파이프라인 시작
  1) Glue 수집 잡 (실시간 로그 + Auto Scaling + 잡 지표)
  2) Glue Data Quality 평가 (DQDL + 이상 탐지)

  3) EMR 변환 (코어 온디맨드, 태스크 스팟, Managed Scaling)

비용 운영:
  - 모든 리소스에 Project/Environment 태그, 관리 계정에서 활성화
  - Budgets 80% 알림, Cost Anomaly Detection 으로 급증 감지
  - 월간 Cost Explorer 리뷰로 사이징 재조정
```

## 자주 틀리는 함정

- **알람이 조용한 것은 정상의 증거가 아니다.** 지표가 끊기면 기본 설정의 알람은 울리지 않는다.
- **품질 점수는 행 비율이 아니다.** 통과한 규칙의 비율이므로 치명 규칙은 점수와 따로 판정한다.
- **이상 탐지는 첫날부터 동작하지 않는다.** 통계가 쌓여야 하고, 한 번 잡힌 이상값은 제외하지 않으면 정상으로 학습된다.
- **CloudTrail 이 켜져 있어도 객체 접근은 안 남는다.** 데이터 이벤트는 별도 설정이다.
- **Step Functions 의 지터는 기본으로 꺼져 있다.** 백오프만으로는 동시 재시도가 흩어지지 않는다.
- **표준 큐의 DLQ 는 보존 기간이 새로 시작되지 않는다.** DLQ 보존을 원본 큐보다 길게 둔다.
- **태그는 달아도 활성화하지 않으면 비용에 안 보인다.** 조직에서는 관리 계정의 일이다.
- **Athena 워크그룹 알림은 쿼리를 멈추지 않는다.** 멈추는 것은 쿼리당 한도뿐이다.
- **스케일링 상한을 올려도 평소 비용은 줄지 않는다.** 베이스라인을 다시 잡는다.

| 지문 단서 | 정답 |
|------|------|

| "자동 재시도의 전제 조건" | 태스크가 멱등 |
| "자동 스케일링을 켰는데 평소 비용이 과도" | 베이스라인 사이징 점검 |
| "파이프라인이 멈췄는데 알림이 없었다" | 누락 데이터 처리, 하트비트성 지표 알람 |
| "실패 원인을 고친 뒤 큐의 실패 메시지 재처리" | DLQ redrive |
| "예산 임계값을 정하기 어려운 급증 탐지" | Cost Anomaly Detection |

다음 주는 데이터 보안과 거버넌스다. IAM 과 Lake Formation 의 접근 제어에서 시작한다.

## 📖 용어

- **관측성(observability)** : 지표·로그·추적으로 시스템 안에서 무슨 일이 벌어지는지 밖에서 알아낼 수 있는 정도.
- **증상 기반 알람** : CPU 같은 자원 수치가 아니라 지연·실패율처럼 사용자가 겪는 현상에 거는 알람.
- **검증 게이트** : 품질이 기준에 못 미친 데이터를 다음 단계로 넘기지 않는 지점.
- **격리 버킷** : 게이트를 통과하지 못한 데이터를 실패 사유와 함께 모아 두는 곳.
- **멱등 재처리** : 같은 구간을 몇 번 다시 돌려도 결과가 한 번 돌린 것과 같은 재처리.
- **redrive** : 실패한 메시지나 실행을 원인 수정 후 다시 처리 경로에 올리는 것.
- **베이스라인** : 평상시 부하에 맞춘 기본 용량. 스케일링이 흡수하는 변동분과 구분한다.
- **런북(runbook)** : 특정 장애가 났을 때 무엇을 어떤 순서로 확인하고 조치할지 적어 둔 절차서.

## 📝 연습 문제

**문제 1.** 다음 중 "어제 누가 prod Glue 테이블을 삭제했는지"와 "어젯밤 Kinesis 컨슈머가 얼마나 지연됐는지"를 각각 확인하기 위한 올바른 도구 조합은?

A) 둘 다 CloudWatch Logs  
B) 삭제는 CloudTrail, 지연은 CloudWatch IteratorAgeMilliseconds  
C) 삭제는 X-Ray, 지연은 CloudTrail  
D) 둘 다 Cost Explorer  

**정답: B**  
해설: API 호출 감사("누가 삭제")는 CloudTrail, 스트리밍 지연 측정은 CloudWatch의 IteratorAgeMilliseconds 지표입니다. CloudWatch Logs만으로는 감사가 부족하고, X-Ray는 추적, Cost Explorer는 비용 분석 도구입니다.

**문제 2.** 야간 ETL에서 Glue Data Quality 점수가 임계값 미만일 때 권장되는 파이프라인 동작은?

A) curated에 그대로 적재하고 나중에 정정  
B) 임계값을 자동으로 낮춰 통과시킴  
C) Step Functions Choice로 다운스트림을 막고 데이터를 격리 + 통보  
D) 잡을 즉시 삭제  

**정답: C**  
해설: 검증 게이트는 미달 데이터의 다운스트림 진행을 막고 격리 버킷으로 보낸 뒤 통보해 오염 전파를 차단합니다. 그대로 적재·임계값 하향은 품질 게이트를 무력화하고, 잡 삭제는 재처리 기회를 잃습니다.

**문제 3.** 비용을 절감하기 위해 EMR 태스크 노드를 Spot으로 전환할 때 함께 적용해야 하는 원칙으로 가장 적절한 것은?

A) HDFS 데이터를 보유하는 코어 노드는 안정적인 옵션으로 유지  
B) 코어 노드도 모두 Spot으로 전환  
C) 자동 스케일링을 비활성화  
D) 모든 데이터를 태스크 노드 로컬에 저장  

**정답: A**  
해설: 태스크 노드는 상태가 없어 Spot 회수에 견딜 수 있지만, HDFS 데이터를 보유한 코어 노드는 On-Demand/약정으로 유지해야 회수 시 데이터 손실을 막습니다. 코어 Spot 전환·로컬 저장은 데이터 손실 위험을 키웁니다.

**문제 4.** 일시적 오류가 잦은 외부 API 호출 태스크를 자동 재시도하도록 구성할 때, 안전성을 위해 반드시 전제되어야 하는 조건은?

A) 태스크가 비멱등이어야 한다  
B) 재시도 간격이 항상 0이어야 한다  
C) 로그를 비활성화해야 한다  
D) 태스크가 멱등(idempotent)이어야 한다  

**정답: D**  
해설: 재시도는 같은 작업이 여러 번 실행될 수 있으므로, 멱등 작업에서만 안전합니다. 비멱등 작업은 중복 적용으로 데이터가 오염되고, 재시도 간격 0은 폭주를 유발하며, 로그 비활성화는 디버깅을 어렵게 합니다.

**문제 5.** 자동 스케일링을 도입했는데도 평소 비용이 여전히 과도하다면 가장 먼저 점검해야 할 것은?

A) 더 많은 알람을 추가한다  
B) 모든 태그를 제거한다  
C) 베이스라인 리소스 사이징(워커/인스턴스/메모리)이 적정한지 점검한다  
D) 자동 스케일링 상한을 무한대로 올린다  

**정답: C**  
해설: 자동 스케일링은 변동을 흡수할 뿐 잘못된 베이스라인을 고치지 못하므로, 평상시 비용이 높으면 베이스라인 사이징을 먼저 재조정해야 합니다. 알람 추가·태그 제거·스케일링 상한 상향은 근본 원인인 과대 베이스라인을 해결하지 못합니다.
