# Day 1 - S3 데이터 레이크 레이아웃과 파티셔닝 전략

## 📌 핵심 정리

- 레이크는 **raw → clean → curated** 존으로 나눈다. 원본은 덮어쓰지 않고, 존마다 권한·포맷·스토리지 클래스를 다르게 가져간다.
- Hive 스타일(`key=value`) 파티션은 WHERE 절의 파티션 키로 **프루닝**된다. 키는 가장 흔한 쿼리의 필터에 맞추고, 드문 쿼리를 위해 잘게 쪼개지 않는다.
- 파티션을 과하게 나누면 **작은 파일 문제**가 생긴다. 파일은 128MB~1GB 로 맞추고, 쓰는 쪽에서 크게 쓰거나 컴팩션으로 합친다.
- 파티션이 수만 개면 카탈로그 조회가 병목이다. **파티션 프로젝션**은 Athena 가 규칙으로 파티션을 계산하게 하지만, Athena 전용이고 빈 파티션이 많으면 오히려 느려진다.
- 분석용 존은 **Parquet/ORC + 압축**이 기본이다. S3 는 프리픽스당 요청 한도가 자동 확장되므로 해시 프리픽스보다 읽기 쉬운 계층을 택한다.

## S3 가 데이터 레이크 스토리지로 적합한 이유

데이터 레이크의 핵심은 "원본은 손대지 않고, 단계별로 정제된 사본을 쌓아 간다"는 것이다. 그 바닥에 S3 가 놓이는 이유는 세 가지다.

- **용량과 내구성**: 사실상 무제한 용량, 99.999999999%(11 9's)로 설계된 내구성.
- **컴퓨팅과 스토리지의 분리**: 데이터는 S3 에 한 벌만 두고 Athena, EMR, Redshift Spectrum, Glue 가 같은 파일을 동시에 읽는다. 엔진을 바꿔도 데이터를 옮길 필요가 없다.
- **schema-on-read**: 먼저 저장하고 읽을 때 스키마를 입힌다. 테이블은 "이 S3 경로를 이런 컬럼으로 해석하라"는 Glue Data Catalog 의 메타데이터일 뿐이다.

> 💡 **관련 이론**: 데이터 레이크는 schema-on-read, 데이터웨어하우스는 schema-on-write 다. 레이크는 정형·반정형·비정형 데이터를 원본 그대로 저장하고 쿼리 시점에 스키마를 부여한다. 그래서 적재는 빠르고 유연하지만, 품질 검증이 적재 뒤로 밀린다. 존을 나누는 이유가 여기서 나온다.

## 존(Zone) 기반 레이아웃: raw → clean → curated

가공 단계별로 버킷 또는 프리픽스를 분리한다. 3계층이 일반적이고, 메달리온 아키텍처의 bronze/silver/gold 와 같은 개념이다.

```text
s3://company-datalake-raw/         # Raw(Bronze) — 원본 그대로, 불변
  └── source=salesforce/dt=2026-06-25/...

s3://company-datalake-clean/       # Clean(Silver) — 검증·중복제거·타입정규화
  └── domain=sales/orders/year=2026/month=06/day=25/...

s3://company-datalake-curated/     # Curated(Gold) — 비즈니스 집계, BI/ML 소비
  └── mart=revenue/daily_summary/year=2026/month=06/...
```

| 존 | 담는 것 | 포맷 | 쓰는 주체 | 읽는 주체 | 원칙 |
|------|------|------|------|------|------|
| Raw | 수집한 원본 그대로 | 원천 포맷(JSON·CSV·로그) | 수집 파이프라인 | 데이터 엔지니어, ETL | 덮어쓰지 않는다. 재처리의 단일 진실 공급원 |
| Clean | 스키마 검증·결측 처리·타입 정규화한 데이터 | Parquet/ORC | Glue ETL·Spark | ETL, 분석가 일부 | 원천 단위 구조 유지, 조인 전 단계 |
| Curated | 조인·집계가 끝난 분석용 데이터 | Parquet/ORC 또는 테이블 포맷 | 집계 잡 | Athena, QuickSight, ML | 소비 패턴에 맞춘 파티션·정렬 |

- 존을 **버킷으로** 나누면 버킷 정책·수명주기·암호화 키·복제를 존마다 다르게 걸기 쉽다. **프리픽스로** 나누면 버킷 수는 줄지만 정책이 프리픽스 조건으로 복잡해진다. 권한 경계가 다르면 버킷을 나누는 쪽이 단순하다.
- Raw 를 불변으로 두는 이유는 "로직 버그를 고친 뒤 처음부터 다시 만들 수 있게" 하기 위해서다. Clean·Curated 는 언제든 Raw 에서 재생성할 수 있어야 한다.
- 권한은 존을 따라 좁혀 준다. Raw 는 엔지니어만, Curated 는 분석가까지. 컬럼·행 단위 제어는 내일 다룰 Lake Formation 이 맡는다.

## 파티셔닝과 프루닝의 실제 동작

파티셔닝은 데이터를 키별 프리픽스로 나눠 쿼리의 스캔량을 줄이는 기법이다.

```text
s3://datalake-clean/orders/year=2026/month=06/day=25/region=us-east-1/file.parquet
```

`key=value` 형태를 **Hive 스타일 파티셔닝**이라 하고, Glue 크롤러와 Athena 의 `MSCK REPAIR TABLE` 이 이 형태를 파티션으로 인식한다.

```sql
-- 파티션 프루닝이 작동: year/month/day 프리픽스만 스캔
SELECT region, SUM(amount)
FROM orders
WHERE year = 2026 AND month = 6 AND day = 25
GROUP BY region;
```

Athena 가 이 쿼리를 처리하는 순서는 다음과 같다.

1. 테이블 메타데이터를 읽고, Glue Data Catalog 에 `GetPartitions` 를 호출해 파티션 목록을 가져온다.
2. WHERE 조건으로 목록을 걸러 낸다(프루닝). 남은 파티션의 S3 위치만 대상이 된다.
3. 남은 위치마다 S3 를 **나열(list)** 해 파일 목록을 만든다.
4. 파일을 읽는다. 컬럼형 포맷이면 필요한 컬럼, 통계상 걸리는 구간만 읽는다.

이 순서에서 세 가지 사실이 따라 나온다.

- **파티션 컬럼을 함수로 감싸면 프루닝이 약해진다.** 키 값을 그대로 비교하는 조건이 가장 잘 걸러진다. 모든 파티션 키에 등호 조건이 있으면 메타데이터를 직접 집어 올 수 있어 가장 빠르다.
- **카탈로그에 없는 파티션은 S3 에 파일이 있어도 조회되지 않는다.** "어제 데이터가 S3 에는 있는데 결과가 0행"이면 파티션 미등록이 첫 번째 용의자다.
- **파티션 키 타입은 STRING 이 유리하다.** Athena 가 파티션 필터를 Glue 로 내려보내려면 키가 문자열이어야 하고, 파티션이 많을 때 다른 타입은 느려질 수 있다. 날짜처럼 쓰려면 쿼리에서 캐스팅한다.

```sql
-- 실행 전에 어떤 파티션을 읽을지 확인
EXPLAIN SELECT COUNT(*) FROM orders WHERE dt BETWEEN '2026-06-23' AND '2026-06-25';
-- 출력의 dt:string:PARTITION_KEY 줄 아래에 [[2026-06-23], [2026-06-24], [2026-06-25]] 가 나오면 프루닝 성공
```

## 파티션 키를 고르는 법

- **가장 흔한 쿼리의 필터에 맞춘다.** 대부분 날짜 범위로 조회하면 날짜가 키다. 드문 쿼리를 위해 최적화하지 않는다.
- **일 단위로 조회하면 시간 단위로 쪼개지 않는다.** 가끔 있는 시간대 조회는 타임스탬프 컬럼 필터로 처리한다. 파일 안 데이터를 타임스탬프로 정렬해 두면 컬럼형 포맷의 최소·최대 통계로 필요 없는 구간을 건너뛰어, 시간 단위 파티션에 가까운 효과가 난다.
- **카디널리티가 높은 값(user_id 등)은 파티션 키로 쓰지 않는다.** 파티션마다 레코드가 몇 건뿐인 작은 파일이 쏟아진다. 특정 값 조회가 많으면 버킷팅(같은 값을 같은 파일로 모음)이 맞는 도구다.
- 날짜는 `year=/month=/day=` 계층 또는 `dt=2026-06-25` 단일 키로 둔다. 단일 키가 범위 조건을 쓰기 쉽고 프로젝션 설정도 단순하다.

| 선택 | 얻는 것 | 잃는 것 |
|------|------|------|
| 파티션 없음 | 관리할 것이 없음 | 모든 쿼리가 전체 스캔 |
| 날짜(일) | 날짜 조회의 스캔량 급감, 관리 쉬움 | 다른 축 필터는 그대로 스캔 |
| 날짜 + 리전 등 2~3단 | 두 축 모두 프루닝 | 파티션 수 = 각 키 값 수의 곱, 파일이 잘게 쪼개짐 |
| 시간 단위·고카디널리티 | 아주 좁은 조회만 빠름 | 작은 파일 폭증, 카탈로그·나열 오버헤드 |

작은 파일 문제(small files problem) — Athena 는 쿼리를 계획할 때 대상 파티션의 위치를 전부 나열하고, 파일마다 요청과 처리 오버헤드를 치른다. 같은 레코드라도 큰 파일 하나가 작은 파일 여러 개보다 빠르다. S3 나열은 한 번에 1,000개까지만 돌려주므로 파티션 하나에 파일이 1,000개를 넘으면 나열도 여러 번이다. 컬럼형 포맷은 파일이 작으면 포맷 자체의 오버헤드가 이점을 덮는다(Parquet 행 그룹의 기본 크기가 128MB 다).

## 작은 파일을 줄이는 방법

가장 좋은 시점은 **쓰기 전**이다. 이미 쌓였다면 합친다.

| 상황 | 조치 |
|------|------|
| 스트리밍 적재가 작은 파일을 쏟아냄 | 쓰는 쪽 버퍼를 키운다(Firehose 버퍼 크기·시간) |
| 파티션이 너무 잘게 나뉨 | 파티션 키를 줄인다 |
| Glue 잡이 작은 JSON/CSV 수십만 개를 읽느라 느림 | `groupFiles`/`groupSize` 로 읽을 때 묶는다 |
| 이미 쌓인 작은 Parquet | Glue/Spark 잡이나 Athena CTAS 로 다시 써서 병합 |
| Iceberg 테이블 | `OPTIMIZE ... REWRITE DATA USING BIN_PACK` 또는 Glue 자동 컴팩션 |

- Glue 의 `groupFiles` 는 **읽을 때** 여러 파일을 한 태스크로 묶는 옵션이다. csv·json·xml 같은 포맷에 적용되고 Parquet·ORC·Avro 입력에는 지원되지 않는다. 입력 파일이 50,000개를 넘으면 Glue 가 자동으로 켠다. 출력 파일을 키우는 것은 별개로, 쓰기 전 파티션 수를 줄여야 한다.

```python
# Glue: 작은 JSON 파일을 약 128MB 단위로 묶어 읽기
dyf = glueContext.create_dynamic_frame.from_options(
    "s3",
    {"paths": ["s3://acme-datalake-raw-prod/events/"], "recurse": True,
     "groupFiles": "inPartition", "groupSize": "134217728"},
    format="json",
)
```

## 파티션 메타데이터를 관리하는 네 가지 방법

| 방법 | 동작 | 맞는 경우 | 주의 |
|------|------|------|------|
| `MSCK REPAIR TABLE` | S3 를 훑어 Hive 스타일 파티션을 카탈로그에 추가 | 테이블을 처음 만들 때, 정합성이 의심될 때 | 추가만 하고 삭제는 안 한다. 파티션이 많으면 오래 걸리고 타임아웃 시 일부만 등록된다 |
| `ALTER TABLE ADD PARTITION` | 지정한 파티션만 등록 | 매일 새 파티션이 생기는 파이프라인, Hive 스타일이 아닌 경로 | 파이프라인이 직접 호출해야 한다 |
| Glue 크롤러 | 스키마와 파티션을 탐지해 등록 | 스키마도 함께 바뀌는 원천 | 실행 주기만큼 늦다. 크롤러 실행 비용 |
| 파티션 프로젝션 | 등록 없이 테이블 속성의 규칙으로 계산 | 파티션이 매우 많고 패턴이 규칙적 | Athena 에서만 동작 |

- 경로가 `2026/06/25/` 처럼 `key=value` 가 아니면 `MSCK REPAIR TABLE` 은 찾지 못한다. `ALTER TABLE ADD PARTITION ... LOCATION` 으로 위치를 직접 지정하거나 프로젝션의 경로 템플릿을 쓴다.
- S3 에서 파티션 데이터를 지웠다면(수명주기 만료 포함) 카탈로그의 파티션 항목도 `ALTER TABLE DROP PARTITION` 으로 지운다. 빈 파티션도 계획 단계에서 나열되므로 쌓이면 느려진다.
- 등록 방식을 유지하면서 조회만 빠르게 하려면 Glue Data Catalog 의 **파티션 인덱스**를 쓴다. 파티션 목록에 인덱스를 걸어 조건에 맞는 파티션을 빨리 찾는다.

## 파티션 프로젝션 (Partition Projection)

파티션이 많은 테이블에서 `GetPartitions` 호출이 병목이면, Athena 가 카탈로그를 조회하지 않고 **테이블 속성에 적은 규칙으로 파티션 값과 위치를 메모리에서 계산**하게 한다.

```sql
ALTER TABLE orders SET TBLPROPERTIES (
  'projection.enabled' = 'true',
  'projection.dt.type' = 'date',
  'projection.dt.range' = '2024-01-01,NOW',
  'projection.dt.format' = 'yyyy-MM-dd',
  'storage.location.template' = 's3://datalake-clean/orders/dt=${dt}/'
);
```

- 날짜가 지나도 `NOW` 까지 자동으로 범위에 들어오므로 파티션 등록 작업이 사라진다.
- 프로젝션을 켜면 Athena 는 그 테이블의 **카탈로그에 등록된 파티션 메타데이터를 무시**한다.
- 규칙이 가리키는 위치에 데이터가 없어도 오류 없이 0행이 나온다. 범위 밖 값을 조회해도 오류가 아니라 0행이다.
- **빈 파티션이 많은 희소한 테이블**에서는 계산된 위치를 전부 S3 에 나열하느라 오히려 느려진다. 프로젝션 대상의 절반 넘게 비어 있으면 일반 파티션이 낫다.
- **Athena 에서만 쓰인다.** 같은 테이블을 Redshift Spectrum, EMR, Athena for Spark 로 읽으면 카탈로그의 일반 파티션 메타데이터를 쓴다. 여러 엔진이 읽는 테이블이면 파티션 등록을 병행해야 한다.
- 파티션 키에 조건이 없으면 범위 전체를 계산해 나열한다. 값이 매우 많은 키는 범위 대신 `injected` 타입(쿼리의 등호 조건에서 값을 받음)을 쓴다.

> ⚠️ **함정**: 프루닝과 프로젝션은 다른 것이다. 프루닝은 "조건에 맞는 파티션만 읽는다"이고 파티션 테이블이면 항상 일어난다. 프로젝션은 "파티션 목록을 카탈로그에서 가져오지 않고 계산한다"다. "스캔량을 줄인다"가 정답이면 프루닝, "카탈로그 조회·파티션 등록 부담을 없앤다"가 정답이면 프로젝션이다.

## 네이밍 규칙과 요청 한도

- 버킷 이름은 전역에서 고유하고 소문자·숫자·하이픈을 쓴다. 환경과 존을 드러낸다: `acme-datalake-raw-prod`.
- 프리픽스는 `domain/entity/partition` 순으로 일관되게 둔다. 테이블마다 **서로 겹치지 않는 경로**를 준다. 한 테이블의 경로 아래에 다른 테이블 경로가 있으면 `MSCK REPAIR TABLE` 이 남의 파티션까지 끌어온다.
- 파티션 키 이름은 소문자로 쓴다. `userId=` 같은 낙타 표기 경로는 `MSCK REPAIR TABLE` 이 등록하지 못할 수 있다.
- 파티션 위치 아래에는 파일을 **평평하게** 둔다. 하위 디렉터리를 더 만들면 나열이 여러 번 일어난다.
- 파일명에 타임스탬프나 UUID 를 넣어 충돌을 막는다: `orders_20260625_a1b2.parquet`.

S3 는 프리픽스당 초당 최소 3,500건의 PUT/COPY/POST/DELETE, 5,500건의 GET/HEAD 를 처리하고 프리픽스 수에는 제한이 없다. 그래서 요청 분산용 해시 프리픽스는 더 이상 필수가 아니고, 의미 있는 계층 구조를 우선한다. 다만 이 확장은 **점진적**이라 요청이 급증하는 동안에는 `503 Slow Down` 이 날 수 있다. Athena 쿼리가 `SlowDown` 으로 실패하면 파일 수가 너무 많거나 같은 데이터에 동시 쿼리가 몰린 것이다.

## 컬럼형 포맷과 압축

| 축 | CSV/JSON(행 기반) | Parquet/ORC(컬럼형) |
|------|------|------|
| 읽는 범위 | 행 전체 | 필요한 컬럼만 |
| 건너뛰기 | 불가 | 구간별 최소·최대 통계로 조건 밖 구간을 건너뜀 |
| 압축 효율 | 낮음 | 같은 타입 값이 모여 있어 높음 |
| 분할 병렬 처리 | 압축하면 대부분 불가 | 압축 코덱과 무관하게 가능 |
| 맞는 존 | Raw | Clean, Curated |

- 텍스트 파일을 gzip 으로 압축하면 처음부터 읽어야 해서 파일 하나를 여러 워커가 나눠 처리하지 못한다. 압축한 텍스트는 파일 수가 곧 병렬도의 상한이다. Parquet/ORC 는 내부 단위(행 그룹·스트라이프)로 나뉘어 있어 이 문제가 없다.
- 압축은 저장량과 스캔량을 함께 줄인다. Athena 는 **압축된 크기** 기준으로 스캔량을 과금한다.

```bash
# Clean 존으로 Parquet 적재 예시 (AWS CLI)
aws s3 cp ./orders.parquet \
  s3://acme-datalake-clean-prod/sales/orders/year=2026/month=06/day=25/orders.parquet
```

## 증상 → 원인 → 조치

| 증상 | 원인 | 조치 |
|------|------|------|
| S3 에 파일이 있는데 결과가 0행 | 파티션 미등록 | `ALTER TABLE ADD PARTITION`, 크롤러, 또는 프로젝션 |
| 프로젝션 테이블에서 특정 날짜만 0행 | 범위 밖이거나 경로 템플릿 불일치 | `projection.*.range`, `storage.location.template` 확인 |
| WHERE 에 날짜를 줬는데 스캔량이 그대로 | 조건이 파티션 키가 아닌 일반 컬럼에 걸림 | 파티션 키로 필터, `EXPLAIN` 으로 확인 |
| 쿼리 계획 단계가 길다 | 파티션 수만 개, 빈 파티션 누적 | 프로젝션·파티션 인덱스, 오래된 파티션 메타데이터 정리 |
| `SlowDown` 오류 | 작은 파일 과다, 동시 쿼리 집중 | 파일 병합, 파티션 키 축소, 쿼리 분산 |
| `MSCK REPAIR TABLE` 이 파티션을 못 찾음 | Hive 스타일이 아니거나 대문자 포함 경로 | `ALTER TABLE ADD PARTITION ... LOCATION` |
| 스토리지 요금·요청 요금이 함께 증가 | 작은 파일 폭증 | 쓰는 쪽 버퍼 확대, 컴팩션 |

## 지문 단서 → 정답 판별표

| 지문 단서 | 정답 |
|------|------|
| "원본을 변경 없이 보관, 재처리의 기준" | Raw 존 |
| "특정 날짜만 조회하는데 전체를 스캔한다" | 날짜로 파티셔닝 후 파티션 키로 필터 |
| "파티션이 수만 개, 카탈로그 조회가 느리다 / 파티션 등록을 자동화" | 파티션 프로젝션 |
| "같은 테이블을 Athena 와 Redshift Spectrum 이 함께 읽는다" | 카탈로그에 파티션 등록(프로젝션만으로는 부족) |
| "작은 파일이 수십만 개라 쿼리가 느리다" | 컴팩션, 쓰는 쪽에서 큰 파일로 |
| "필요한 컬럼만 읽어 비용을 줄인다" | Parquet/ORC |
| "특정 user_id 조회가 대부분" | 파티션이 아니라 버킷팅 |
| "새 파티션을 매일 하나씩 추가" | `ALTER TABLE ADD PARTITION` 또는 프로젝션(`MSCK` 반복 실행은 비효율) |

내일은 이 레이크 위에서 "누가 어떤 테이블·컬럼·행을 볼 수 있는가"를 중앙에서 통제하는 Lake Formation 을 다룬다.

## 📖 용어

- **존(zone)** : 가공 단계별로 나눈 레이크의 구역. raw·clean·curated 3계층이 일반적이다.
- **schema-on-read** : 저장할 때가 아니라 읽을 때 스키마를 적용하는 방식.
- **Hive 스타일 파티셔닝** : 경로에 `key=value` 를 넣어 파티션을 표현하는 관례.
- **파티션 프루닝** : WHERE 조건에 맞는 파티션의 경로만 읽고 나머지를 건너뛰는 것.
- **파티션 프로젝션** : 파티션을 카탈로그에 등록하지 않고 테이블 속성의 규칙으로 계산하는 Athena 기능.
- **파티션 인덱스** : Glue Data Catalog 의 파티션 목록에 거는 인덱스. 조건에 맞는 파티션을 빨리 찾는다.
- **작은 파일 문제** : 파일이 지나치게 많고 작아 나열·요청·메타데이터 오버헤드가 커지는 현상.
- **컴팩션(compaction)** : 작은 파일 여러 개를 큰 파일로 다시 써서 합치는 작업.
- **버킷팅** : 특정 컬럼 값의 해시로 레코드를 정해진 수의 파일에 나눠 담는 기법. 같은 값은 같은 파일에 모인다.
- **컬럼형 포맷** : 데이터를 컬럼 단위로 저장하는 Parquet·ORC 같은 포맷.

## 📝 연습 문제

**문제 1.** 데이터레이크에서 수집한 원본 데이터를 절대 변경하지 않고 보관하며, 재처리의 단일 진실 공급원 역할을 하는 존은 무엇인가?

A) Curated 존  
B) Clean 존  
C) Raw 존  
D) Sandbox 존  

**정답: C**  
해설: Raw(Bronze) 존은 수집한 원본을 그대로 불변 보관하며 재처리의 source of truth입니다. Clean은 검증·정규화된 중간 단계, Curated는 비즈니스 집계 결과로 소비용입니다. Sandbox는 표준 3계층에 포함되지 않습니다.

---

**문제 2.** Athena 쿼리에서 `WHERE year=2026 AND month=6` 조건이 해당 프리픽스만 스캔하도록 만드는 기법은?

A) 파티션 프루닝  
B) 데이터 스큐  
C) 브로드캐스트 조인  
D) 버킷팅 셔플  

**정답: A**  
해설: 파티션 키가 WHERE 조건에 있으면 엔진이 관련 프리픽스만 읽는 파티션 프루닝이 작동해 스캔량과 비용을 줄입니다. 나머지는 파티션 기반 스캔 절감과 무관한 개념입니다.

---

**문제 3.** 데이터레이크에서 파일이 수만 개의 매우 작은 파일로 쪼개졌을 때 발생하는 문제로 가장 적절한 것은?

A) 데이터 내구성이 떨어진다  
B) 메타데이터 오버헤드와 S3 요청 비용이 증가한다  
C) 파티션 프루닝이 비활성화된다  
D) 스키마가 자동으로 변경된다  

**정답: B**  
해설: 작은 파일 문제는 파일별 메타데이터 처리 오버헤드와 다수의 S3 GET 요청으로 비용·지연이 증가합니다. 권장은 128MB~1GB이며 compaction으로 병합합니다. 내구성·스키마·프루닝과는 직접 관련이 없습니다.

---

**문제 4.** Glue Data Catalog에 파티션을 등록하지 않고 테이블 속성의 규칙으로 파티션을 계산해 카탈로그 병목을 줄이는 Athena 기능은?

A) 파티션 프로젝션  
B) 크롤러 스케줄링  
C) CTAS  
D) 워크그룹 격리  

**정답: A**  
해설: 파티션 프로젝션(Partition Projection)은 파티션을 카탈로그에 일일이 등록하지 않고 범위·포맷 규칙으로 계산해 대량 파티션 환경에서 조회 비용과 지연을 줄입니다. 크롤러는 등록 방식이고, CTAS는 결과 테이블 생성, 워크그룹은 비용·격리 관리입니다.

---

**문제 5.** 분석용 데이터레이크에서 컬럼 단위로 필요한 데이터만 읽어 스캔량을 줄이고 압축 효율이 높은 권장 파일 포맷은?

A) CSV  
B) JSON  
C) Parquet  
D) XML  

**정답: C**  
해설: Parquet(또는 ORC)은 컬럼형 포맷으로 필요한 컬럼만 읽어 스캔 비용을 줄이고 컬럼 단위 압축으로 저장 비용을 낮춥니다. CSV/JSON/XML은 행 기반 또는 비효율적이어서 분석 워크로드에 부적합합니다.
