# Day 5 - Week 1 종합 복습

## 📌 핵심 정리

- Week 1 의 결론: 데이터 엔지니어는 **수집 → 저장 → 처리 → 분석** 파이프라인을 만들고, **거버넌스**가 전 구간을 감싼다.
- 모든 선택(OLTP/OLAP, 배치/스트림, 레이크/웨어하우스, 행형/컬럼형)은 **"워크로드가 무엇을 요구하는가"** 에서 나온다.
- 지문은 네 가지 질문으로 분해한다: 원천이 무엇인가 → 얼마나 신선해야 하나 → 누가 어떻게 읽나 → 운영 부담·비용 조건은 무엇인가.
- 오답 보기는 "기능상 가능하지만 조건 하나를 어기는" 것이다. 운영 부담 최소·비용 최소·코드 변경 최소 같은 한정어가 정답을 가른다.
- 헷갈리는 8개 짝(Streams/Firehose, Glue/EMR, Athena/Redshift, IAM/Lake Formation 등)의 구분 축을 한 단어씩 말할 수 있으면 통과다.

## 한 장으로 보는 Week 1

지난 4일간 데이터 엔지니어링의 토대를 세웠다. Day 1에서 역할과 파이프라인, OLTP/OLAP, 레이크/웨어하우스를 봤고, Day 2에서 배치와 스트리밍을 갈랐으며, Day 3에서 AWS 데이터 서비스 지도를 펼쳤고, Day 4에서 데이터 포맷과 스키마 진화를 다뤘다. 흩어진 조각처럼 보이지만, 사실 이들은 **하나의 파이프라인**으로 꿰어진다.

오늘은 개별 개념을 다시 나열하는 대신, **하나의 시나리오를 처음부터 끝까지 따라가며** 네 날의 지식이 어떻게 맞물리는지 본다. 시험은 단편 암기가 아니라 "이 상황에서 무엇을 고를 것인가"를 묻기 때문에, 이렇게 연결해서 보는 것이 가장 효과적인 복습이다.

```
[Day1] 역할·개념          [Day2] 처리        [Day3] 서비스       [Day4] 포맷
 데이터 엔지니어           배치               수집 Kinesis/DMS    CSV/JSON (원시)
 = 파이프라인 책임         vs                 저장 S3/Redshift    Parquet/ORC (분석)
 OLTP vs OLAP             스트리밍            처리 Glue/EMR       Avro (스트리밍)
 레이크 vs 웨어하우스      (지연/처리량)       분석 Athena/QS      스키마 진화
                                              거버넌스 LakeFmt
```

네 날의 키워드가 결국 "데이터를 어떻게 수집·저장·처리·분석하고 통제하는가"라는 한 질문의 다른 측면들이다.

> 💡 **관련 이론**: 이 모든 판단을 관통하는 단일 원칙은 **"워크로드가 설계를 결정한다"**이다. OLTP냐 OLAP냐, 배치냐 스트림이냐, 행형이냐 컬럼형이냐 — 모두 "어떤 식으로 데이터를 읽고 쓰는가"라는 워크로드 특성에서 답이 나온다. 기술을 먼저 고르고 워크로드를 끼워맞추는 게 아니라, 워크로드를 분석해 기술을 고르는 것이 데이터 엔지니어링의 사고법이다.

## 시나리오로 꿰어보기

전자상거래 회사의 요구를 따라가 보자. 각 요구가 Week 1의 어느 개념에 닿는지 표시했다.

**요구 1.** "운영 주문 DB에 부하 주지 말고, 그 데이터를 분석할 수 있게 해줘."
- 운영 DB는 **OLTP**(Day1) → 무거운 집계를 직접 돌리면 안 됨
- **DMS의 CDC**(Day3)로 변경분만 분석 환경으로 복제
- 분석 환경은 **OLAP**(Day1) → Redshift 또는 S3+Athena

**요구 2.** "결제 순간 이상거래를 잡아내고 싶어."
- 즉시성이 필요 → **스트리밍**(Day2)
- **Kinesis Data Streams**(Day3)로 결제 이벤트 수집
- 스키마가 바뀔 수 있으니 **Avro + Schema Registry**(Day4)

**요구 3.** "매일 아침 어제 매출 리포트를 자동으로."
- 주기적·경계 있는 데이터 → **배치**(Day2)
- **Glue**(Day3)로 하루치 처리, **Parquet**(Day4)으로 적재
- **Athena/QuickSight**(Day3)로 조회·시각화

```sql
-- 요구 3의 분석 쿼리 — Parquet으로 저장돼 있어 빠르고 저렴
SELECT region, SUM(amount) AS revenue
FROM orders          -- S3의 Parquet, Glue Catalog에 등록됨
WHERE order_date = DATE '2026-06-25'   -- 파티션 프루닝
GROUP BY region;
```

하나의 회사가 세 요구를 동시에 가질 수 있고, 각각 다른 패러다임·서비스·포맷을 쓴다. "정답 하나"가 아니라 **요구마다 맞는 조합**이 있다는 것이 핵심이다.

> 💡 **관련 이론**: 요구 1~3을 한 그림에 합치면 자연스럽게 **레이크하우스**가 된다. 모든 원시 데이터(주문 CDC, 결제 스트림, 로그)가 S3 데이터레이크에 모이고, 배치·스트리밍 처리를 거쳐 Parquet으로 정제되며, 그 위에서 Athena·Redshift·QuickSight가 분석한다. Day1의 "레이크 vs 웨어하우스"가 현대에선 "레이크하우스로 통합"되는 이유다.

## 자주 헷갈리는 구분 정리

시험에서 함정으로 나오는 짝들이다.

| 헷갈리는 짝 | 핵심 구분 |
|------------|----------|
| OLTP vs OLAP | 거래(소수 행 빠르게) vs 분석(대량 행 집계) |
| 레이크 vs 웨어하우스 | schema-on-read(유연) vs schema-on-write(엄격) |
| 배치 vs 스트리밍 | 경계 있음·주기 vs 경계 없음·연속 |
| Kinesis Streams vs Firehose | 저지연·다중소비자 vs 자동적재 배달부 |
| Glue vs EMR | 관리형 서버리스 ETL vs 제어·대규모 클러스터 |
| 행형 vs 컬럼형 | 쓰기·전체행(Avro) vs 읽기·집계(Parquet) |
| Athena vs Redshift | 애드혹·서버리스·스캔과금 vs 상시·대규모·적재 |
| IAM vs Lake Formation | 리소스 단위 vs 데이터(테이블·컬럼·행) 단위 |

이 8개 짝의 구분 기준만 정확히 잡아도 Week 1 범위의 시나리오 문제 상당수를 풀 수 있다.

> 💡 **관련 이론**: 이 표의 거의 모든 짝은 "**유연성·범용성 vs 효율성·전문성**"이라는 같은 긴장 구조를 갖는다. 레이크는 유연하지만 관리가 필요하고, 웨어하우스는 효율적이지만 경직됐다. 서버리스(Glue/Athena)는 편하지만 세밀한 제어가 약하고, 클러스터(EMR/Redshift)는 강력하지만 운영 부담이 있다. 트레이드오프를 의식하면 암기가 이해로 바뀐다.

## 시험 관점 한 줄 정리

DEA-C01은 결국 이 4개 도메인을 묻는다(Day1 재확인).

```
1. 수집·변환 (34%)   ← Day2 배치/스트림 + Day3 Kinesis/Glue/EMR
2. 저장·관리 (26%)   ← Day1 레이크/웨어하우스 + Day3 S3/Redshift + Day4 포맷
3. 운영·지원 (22%)   ← (Week2 이후) 오케스트레이션·모니터링
4. 보안·거버넌스(18%)← Day3 LakeFormation/IAM/KMS
```

Week 1은 1·2번 도메인의 토대를 거의 다 깔았다. 다음 주부터 각 서비스의 깊은 디테일(파티셔닝 전략, Glue 잡 튜닝, Kinesis 샤드 등)로 들어가지만, 그 모든 것이 오늘 그린 이 큰 그림 위에 얹힌다는 점을 기억하자.

## 지문을 푸는 순서: 네 가지 질문

Week 1 의 개념은 따로 외우면 흩어지고, 질문 순서로 묶으면 판별 절차가 된다. 시나리오 지문을 만나면 아래 순서로 밑줄을 긋는다.

```
① 원천이 무엇인가?         DB / 파일 / 이벤트·로그 / SaaS
        ↓                  → 수집 서비스가 정해진다 (Day 3)
② 얼마나 신선해야 하나?    초 이내 / 분 / 시간 / 하루
        ↓                  → 배치·스트리밍·준실시간이 정해진다 (Day 2)
③ 누가 어떻게 읽나?        한 행 조회 / 대량 집계 / 검색 / 대시보드
        ↓                  → 저장소와 포맷이 정해진다 (Day 1, Day 4)
④ 붙은 조건은?             운영 부담 최소 / 비용 최소 / 코드 변경 최소 / 세밀한 권한
                           → 같은 단계의 후보 중 하나로 좁혀진다
```

| 질문 | 답 | 귀결 |
|------|------|------|
| ① 원천 | 운영 DB | DMS(CDC). 직접 집계 쿼리는 금지 |
| | 파일 서버 | DataSync(끌어옴) / Transfer Family(받음) / Snow(회선 부족) |
| | 이벤트·로그 | Kinesis Data Streams·MSK(스트림) / Firehose(적재) |
| | SaaS | AppFlow |
| ② 신선도 | 초 이내 | 스트림 + Flink/Lambda |
| | 수 초~분 | Firehose, Glue 스트리밍 |
| | 시간~하루 | 스케줄 배치(Glue/EMR) |
| ③ 읽는 방식 | 키로 한 건씩, 쓰기 많음 | OLTP — RDS/Aurora, DynamoDB |
| | 대량 집계·조인 | OLAP — Redshift, 또는 S3(Parquet)+Athena |
| | 형태가 제각각인 원본 보관 | S3 데이터 레이크 |
| ④ 조건 | 운영 부담 최소 | 서버리스 쪽(Firehose, Glue, Athena, Lambda) |
| | 기존 코드·도구 재사용 | 오픈소스 호환 쪽(MSK, EMR, MWAA) |
| | 컬럼·행 단위 권한 | Lake Formation |

- ④가 가장 자주 정답을 가른다. ①~③까지는 보기 두세 개가 살아남고, 마지막 한정어 하나가 승부를 낸다.

## 오답 보기가 만들어지는 다섯 가지 틀

출제자는 "틀린 기술"이 아니라 "이 상황에는 틀린 선택"을 보기로 만든다. 틀을 알면 소거가 빨라진다.

| 틀 | 예시 | 걸러내는 법 |
|------|------|------|
| 단계가 다르다 | "변경분 복제" 문제에 QuickSight, "권한" 문제에 KMS | 흐름의 어느 칸인지 먼저 확인 |
| 가능하지만 과하다 | S3 에 쌓기만 하면 되는데 KDS + KCL 직접 구현 | "최소 운영 부담" 한정어 확인 |
| 가능하지만 모자라다 | 여러 소비자·재처리가 필요한데 Firehose 단독 | 요구 기능을 전부 만족하는지 확인 |
| 워크로드가 반대다 | 대량 집계를 운영 RDS 에 직접, 한 건 조회를 Athena 로 | OLTP/OLAP 구분 |
| 원인을 잘못 짚는다 | Athena 가 느린데 "인스턴스를 키운다"(서버리스라 불가), 핫 샤드인데 "보존 기간을 늘린다" | 서비스가 실제로 가진 조절 손잡이인지 확인 |

- 특히 다섯 번째 틀: **서버리스 서비스에는 크기를 키우는 손잡이가 없다.** Athena 는 인스턴스가 없으므로 성능 개선은 데이터 쪽(포맷·압축·파티션·파일 크기)에서 한다.

## 시나리오 연습: 단서에서 정답까지

아래는 연습 문제와 겹치지 않는 새 상황이다. 단서 열을 가리고 정답을 말해 본 뒤 확인한다.

| 상황 | 결정적 단서 | 정답 구성 | 탈락하는 보기와 이유 |
|------|------|------|------|
| 웹 서버 로그를 S3 에 모아 한 달에 두세 번 장애 원인을 SQL 로 조사 | "가끔", "SQL" | Firehose → S3, Athena | Redshift — 상시 비용. EMR — 클러스터 운영 |
| 같은 로그로 키워드 검색과 초 단위 대시보드 | "검색", "초 단위" | Firehose → OpenSearch | Athena — 전문 검색·저지연 대시보드에 부적합 |
| IoT 센서 값이 임계치를 넘으면 2초 안에 경보 | "2초 안에" | KDS + Flink(또는 Lambda) | Firehose — 버퍼만큼 늦는다. 배치 — 불가 |
| 3년치 주문을 새 집계 규칙으로 다시 계산 | "3년치", "다시 계산" | S3 원본 + Glue/EMR 배치 | 스트림 재생 — 보존 기간 밖 데이터는 스트림에 없다 |
| 주문 이벤트에 필드가 계속 추가되는데 소비자 앱이 5개 | "스키마 변경", "여러 소비자" | Avro + Glue Schema Registry(BACKWARD) | JSON 그대로 — 깨지는 변경을 막을 장치가 없다 |
| 분석가가 매일 같은 3개 컬럼만 집계하는데 Athena 요금이 크다 | "3개 컬럼", "요금" | Parquet 변환 + 날짜 파티션 | 압축만 — 여전히 모든 컬럼을 읽는다 |
| 마케팅팀은 고객 테이블에서 이메일 컬럼을 보면 안 된다 | "컬럼을 숨긴다" | Lake Formation 컬럼 권한 | S3 버킷 정책 — 객체 단위라 컬럼을 못 가린다 |
| 온프레미스 PostgreSQL 을 멈추지 않고 Aurora 로 옮긴 뒤에도 분석용으로 계속 S3 에 흘린다 | "무중단", "계속" | DMS 전체 적재 + CDC | DataSync — 파일 도구. 덤프·복원 — 중단 발생 |
| 야간 배치가 끝나면 품질 검사 후 Redshift 적재, 실패 시 알림 | "순서", "실패 시" | Step Functions(또는 MWAA)로 Glue 잡 연결 | cron 만 — 앞 단계 성공 여부를 모른다 |
| 원시 JSON 을 손대지 않고 보관하면서 분석용 사본도 유지 | "원본 보존", "분석용" | S3 raw(JSON) → 처리 → S3 processed(Parquet) | 원본을 Parquet 으로 덮어쓰기 — 재처리 근거가 사라진다 |

## Week 1 숫자·기본값 한 장

숫자는 외울 양이 적을수록 좋다. Week 1 범위에서 지문 판별에 실제로 쓰이는 것만 추렸다.

| 항목 | 값 | 어디에 쓰이나 |
|------|------|------|
| 시험 도메인 비중 | 수집·변환 34% / 저장·관리 26% / 운영·지원 22% / 보안·거버넌스 18% | 학습 시간 배분 |
| Lambda 한 번 실행의 최대 시간 | 15분 | "긴 ETL 을 Lambda 로" 보기 소거 |
| Firehose S3 버퍼 | 크기 1~128MB(기본 5MB), 간격 0~900초(기본 300초), 먼저 찬 쪽에서 전달 | "준실시간"의 실제 지연 |
| Glue 스트리밍 기본 윈도우 | 100초 | 마이크로배치의 지연 수준 |
| KDS 보존 기간 | 기본 24시간, 최대 365일 | 재처리 가능 범위 |
| Parquet Row Group / ORC 스트라이프 기본 크기 | 128MB / 64MB | 작은 파일이 불리한 이유 |
| Athena 의 기본 컬럼 매칭 | Parquet 은 이름, ORC 는 위치 | 컬럼 이름 변경·중간 추가 시 동작 |
| Glue Schema Registry 권장 호환 모드 | BACKWARD | 새 소비자가 옛 데이터를 읽음 |

- 한도·요금 수치는 바뀐다. 시험은 정확한 숫자보다 "기본값이 있고 조정 가능하다", "먼저 도달한 조건에서 동작한다" 같은 **동작 방식**을 묻는다.

## 한 파이프라인에서 생기는 장애와 그 원인

개념을 "무엇이 잘못되면 어떤 증상이 나오는가"로 뒤집어 보면 Week 1 전체가 다시 연결된다.

| 증상 | Week 1 개념으로 본 원인 | 조치 |
|------|------|------|
| 분석 쿼리를 돌리면 서비스 응답이 느려진다 | OLTP DB 에 OLAP 쿼리를 직접 실행 | CDC 로 분석 환경 분리 |
| Athena 요금이 데이터 증가보다 빠르게 는다 | 행형 포맷 + 파티션 필터 없는 쿼리 | Parquet 변환, 파티션 설계, WHERE 에 파티션 컬럼 |
| 파일은 S3 에 있는데 Athena 결과가 비어 있다 | 카탈로그에 파티션 미등록 | 파티션 추가·크롤러·파티션 프로젝션 |
| 새벽 리포트 숫자가 실시간 대시보드와 다르다 | 스트리밍은 늦은 이벤트를 놓치고 배치는 다 모은 뒤 계산 | 기준 지표를 하나로 정하고 배치 결과로 보정 |
| 프로듀서 배포 직후 소비자가 역직렬화 오류 | 호환되지 않는 스키마 변경 | 스키마 레지스트리 호환 모드로 사전 차단 |
| 쿼리가 병렬로 돌지 않고 오래 걸린다 | 거대한 GZIP 텍스트 파일 하나 | 분할하거나 컬럼형으로 변환 |
| 쿼리 계획 단계부터 느리다 | 아주 작은 파일 수만 개 | 버퍼 확대, 주기적 병합 |
| 민감 컬럼이 전 직원에게 보인다 | 버킷 단위 권한만 설정 | Lake Formation 으로 컬럼·행 권한 |

> 🔍 **더 깊이**: 위 표의 조치는 대부분 "데이터를 어떻게 놓느냐"의 문제다. 클러스터를 키우는 것은 마지막 수단이고, 포맷·파티션·파일 크기·분리(운영과 분석, 원본과 가공본)를 먼저 바로잡는 것이 데이터 엔지니어의 일이다. DEA-C01 이 서비스 이름보다 설계 판단을 묻는 이유도 여기에 있다.

이 사고법을 손에 쥐었다면 Week 1은 성공이다. Week 2부터는 이 골격에 살을 붙여, 각 서비스를 실제로 다루는 법으로 들어간다.

## 📖 용어

- **워크로드** : 시스템이 처리해야 하는 일의 성격. 데이터를 어떤 식으로 읽고 쓰는가를 말한다.
- **OLTP / OLAP** : 소수 행을 빠르게 읽고 쓰는 거래 처리와, 대량 행을 모아 집계하는 분석 처리.
- **레이크하우스** : S3 데이터 레이크 위에 테이블 형식과 카탈로그를 얹어 웨어하우스처럼 쿼리하는 구조.
- **schema-on-read / schema-on-write** : 읽을 때 구조를 적용하는 방식과, 저장할 때 구조를 강제하는 방식.
- **한정어** : 지문의 "최소 운영 부담", "가장 비용 효율적" 같은 조건 문구. 후보 중 정답 하나를 가른다.
- **소거법** : 조건을 어기는 보기를 하나씩 지워 정답을 남기는 풀이법.
- **파티션 프루닝** : WHERE 조건에 맞는 파티션 폴더만 읽고 나머지는 건너뛰는 것.
- **작은 파일 문제** : 아주 작은 파일이 너무 많아 목록 조회·열기 비용이 커지고 쿼리가 느려지는 현상.

## 📝 연습 문제

**문제 1.** Week 1 전체를 관통하는 단일 설계 원칙으로, OLTP/OLAP·배치/스트림·행형/컬럼형 선택을 모두 결정짓는 것은?

A) 항상 가장 최신 기술을 먼저 고른다  
B) 워크로드(데이터를 어떻게 읽고 쓰는가)가 설계를 결정한다  
C) 항상 가장 저렴한 서비스를 고른다  
D) 항상 실시간 처리를 선택한다  

**정답: B**  
해설: OLTP냐 OLAP냐, 배치냐 스트림이냐, 행형이냐 컬럼형이냐는 모두 데이터를 어떻게 읽고 쓰는가라는 워크로드 특성에서 답이 나온다. 기술이나 비용을 먼저 정하고 끼워맞추는 것이 아니라 워크로드를 분석해 선택하며, 실시간이 항상 옳은 것도 아니다.

---

**문제 2.** "운영 주문 DB에 부하를 주지 않으면서 그 데이터를 대규모 집계 분석하고 싶다"는 요구를 충족하는 가장 적절한 조합은?

A) 운영 DB에 직접 집계 쿼리를 실행  
B) DMS의 CDC로 변경분을 OLAP 환경(Redshift/S3+Athena)으로 복제해 분석  
C) 운영 DB를 DynamoDB로 교체  
D) QuickSight를 운영 DB에 직접 연결해 매번 집계  

**정답: B**  
해설: OLTP인 운영 DB에 무거운 OLAP성 집계를 직접 돌리면 서비스에 부하를 준다. DMS의 CDC로 변경분만 분석 환경으로 흘려보내 OLAP에서 분석하는 것이 표준이다. DynamoDB로 교체해도 OLTP라 문제가 같고, BI 도구를 운영 DB에 직접 붙여 집계하는 것도 같은 부하 문제를 일으킨다.

---

**문제 3.** "결제가 일어나는 순간 이상거래를 탐지"하려는 요구에 가장 적합한 처리 패러다임·수집 서비스·포맷 조합은?

A) 배치 / Glue / CSV  
B) 스트리밍 / Kinesis Data Streams / Avro  
C) 배치 / DMS / Parquet  
D) 준실시간 / Firehose / ORC  

**정답: B**  
해설: 즉시성이 필요하므로 스트리밍이며, 낮은 지연·다중 소비자에 적합한 Kinesis Data Streams로 이벤트를 수집하고, 스키마 진화에 강한 행형 Avro가 이벤트 스트림에 적합하다. 배치 조합은 즉시성이 없고, Firehose는 자동 적재용 준실시간이라 즉각 탐지에는 Data Streams가 더 맞다.

**문제 4.** Kinesis Data Streams와 Kinesis Data Firehose의 핵심 차이를 가장 정확히 설명한 것은?

A) Streams는 배치 전용, Firehose는 스트리밍 전용이다  
B) Streams는 저지연·다중 소비자용이고, Firehose는 스트림을 S3/Redshift 등으로 자동 적재하는 준실시간 배달 서비스다  
C) Streams는 SQL을 지원하고 Firehose는 지원하지 않는다  
D) 둘은 기능이 완전히 동일하다  

**정답: B**  
해설: Data Streams는 낮은 지연과 여러 소비자가 동시에 읽어야 하는 진짜 스트리밍용이고, Firehose는 스트림을 받아 별도 소비자 코드 없이 S3·Redshift·OpenSearch로 자동 적재하는 관리형 준실시간 배달 서비스다. 둘 다 스트리밍 계열이며 기능이 동일하지 않다.

**문제 5.** 데이터레이크와 데이터 웨어하우스의 장점을 결합해, S3 데이터레이크 위에 테이블 형식과 카탈로그를 얹어 웨어하우스급 쿼리를 제공하는 현대 표준 패턴은?

A) 람다 아키텍처  
B) 레이크하우스(Lakehouse)  
C) OLTP 클러스터  
D) 마이크로배치  

**정답: B**  
해설: 레이크하우스는 schema-on-read의 유연한 S3 데이터레이크 위에 테이블 형식(Iceberg 등)과 카탈로그를 얹어, 웨어하우스급 쿼리·트랜잭션·거버넌스를 제공하는 통합 패턴이다. 람다 아키텍처는 배치/스피드 레이어 결합, OLTP 클러스터는 거래 처리, 마이크로배치는 준실시간 처리 기법으로 저장 패턴이 아니다.
