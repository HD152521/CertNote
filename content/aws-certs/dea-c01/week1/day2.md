# Day 2 - 배치 vs 스트리밍

## 📌 핵심 정리

- **배치**는 경계 있는 데이터를 주기적으로, **스트리밍**은 경계 없는 흐름을 연속적으로 처리한다. 스트리밍은 윈도우로 흐름을 잘라야 집계가 나온다.
- 선택 기준은 "얼마나 신선한 결과가 필요한가" 하나다. 실시간은 상시 가동 비용과 운영 복잡도를 치르므로, 필요한 지연을 숫자로 먼저 확정한다.
- 배치는 처리량·정확성에, 스트리밍은 낮은 지연에 강하다. 마이크로배치(Spark Structured Streaming, Glue 스트리밍)가 그 절충안이다.
- AWS 매핑: 배치 = Glue·EMR·AWS Batch, 스트리밍 = Kinesis Data Streams·MSK + Managed Service for Apache Flink·Lambda, 준실시간 적재 = Data Firehose.
- "실시간"이라는 단어만 보고 고르지 않는다. 목적지에 쌓기만 하면 Firehose, 여러 소비자·재처리·상태 있는 집계가 필요하면 스트림 + 처리 엔진이다.

## 두 패러다임의 본질

같은 데이터라도 "언제, 얼마씩" 처리하느냐에 따라 시스템 설계가 완전히 달라진다. 매일 밤 하루치 주문을 모아 정산 리포트를 만드는 것과, 결제가 일어나는 순간 이상거래를 잡아내는 것은 같은 결제 데이터를 다루지만 전혀 다른 기계가 필요하다. 전자가 **배치(batch)**, 후자가 **스트리밍(streaming)**이다.

오늘은 이 두 처리 패러다임의 본질, 각각이 적합한 사례, 그리고 둘을 가르는 핵심 트레이드오프인 지연(latency)과 처리량(throughput)을 본다. 데이터 엔지니어가 새 파이프라인을 설계할 때 가장 먼저 내리는 판단이 "이건 배치인가 스트림인가"다.

차이는 **데이터를 묶음으로 처리하느냐, 도착하는 대로 처리하느냐**다.

```
배치 (Batch)
  [····· 모은다 ·····] → 한 번에 처리 → 결과
  경계가 있는(bounded) 데이터, 정해진 주기로 실행

스트리밍 (Streaming)
  → 도착 → 처리 → 도착 → 처리 → 도착 → 처리 →
  경계가 없는(unbounded) 데이터, 끊임없이 흐름
```

배치는 "지난 한 시간/하루 동안 쌓인 것"이라는 **유한한 묶음**을 다룬다. 시작과 끝이 분명하다. 스트리밍은 "지금부터 영원히 들어오는 이벤트"라는 **무한한 흐름**을 다룬다. 끝이 없으므로, 결과를 내려면 "최근 5분"처럼 시간 창(window)으로 흐름을 잘라야 한다.

| 구분 | 배치 | 스트리밍 |
|------|------|---------|
| 데이터 | 경계 있음(bounded) | 경계 없음(unbounded) |
| 실행 | 주기적(시간/일 단위) | 연속적(상시) |
| 지연 | 분~시간 | 밀리초~초 |
| 처리량 | 매우 높음 | 건당 처리 |
| AWS 예시 | Glue, EMR, Batch | Kinesis, MSK, Flink |

> 💡 **관련 이론**: 스트리밍에서 가장 중요한 개념이 **윈도잉(windowing)**이다. 무한한 흐름에서 집계를 내려면 흐름을 시간 단위로 잘라야 한다. 텀블링 윈도우(겹치지 않는 고정 구간), 슬라이딩 윈도우(겹치며 이동), 세션 윈도우(활동 간격으로 구분)가 대표적이다. 또한 "이벤트가 발생한 시각(event time)"과 "시스템이 받은 시각(processing time)"의 차이를 다루는 것이 스트리밍 설계의 핵심 난제다.

## 각각 언제 쓰는가

선택의 기준은 단 하나, **얼마나 신선한 결과가 필요한가**다.

**배치가 적합한 경우:**
- 월말 정산, 일일 매출 리포트처럼 주기가 정해진 작업
- 대용량 과거 데이터 재처리(backfill)
- 결과가 몇 분~몇 시간 늦어도 무방한 분석
- 머신러닝 모델의 대규모 학습 데이터 준비

**스트리밍이 적합한 경우:**
- 실시간 이상거래·사기 탐지
- 라이브 대시보드, 실시간 모니터링·알람
- IoT 센서 데이터의 즉각적 처리
- 추천·개인화처럼 사용자 행동에 즉시 반응해야 하는 경우

```python
# 배치: 하루치 로그를 모아 한 번에 집계 (Glue/Spark)
df = spark.read.parquet("s3://logs/date=2026-06-25/")  # 하루치 전체
daily = df.groupBy("region").agg(sum("amount"))
daily.write.parquet("s3://reports/daily/2026-06-25/")

# 스트리밍: 5분 윈도우로 흐르는 이벤트를 집계 (Flink/KDA)
events.window(TumblingWindow.of(minutes=5)) \
      .key_by("region") \
      .aggregate(SumAggregator())  # 끝없이 5분마다 결과 방출
```

핵심은 **"실시간이 비싸다"**는 점이다. 스트리밍은 상시 가동되는 인프라와 더 복잡한 운영을 요구한다. 그래서 "정말 실시간이 필요한가, 5분 늦어도 되는가"를 따지는 것이 비용 최적화의 출발점이다. 막연히 "최신 데이터가 좋으니 다 스트리밍"으로 가면 비용과 복잡도가 폭증한다.

마이크로배치(micro-batch)는 둘의 중간 지점이다. Spark Structured Streaming처럼 아주 짧은 주기(수 초)로 작은 배치를 반복 실행해 "준실시간"을 만든다. 진짜 이벤트 단위 스트리밍보다 운영이 단순하면서 초 단위 지연을 달성하므로, 많은 현실 파이프라인이 이 절충안을 택한다.

## 지연과 처리량의 트레이드오프

배치와 스트리밍의 차이를 정량적으로 가르는 두 지표다.

- **지연(latency)**: 데이터가 발생한 뒤 결과가 나오기까지의 시간. 낮을수록 "실시간"에 가깝다.
- **처리량(throughput)**: 단위 시간당 처리할 수 있는 데이터의 양. 높을수록 "대용량"에 강하다.

```
배치    : 지연 높음 ↑   처리량 매우 높음 ↑↑↑
스트림  : 지연 낮음 ↓   건당 처리 → 누적 처리량은 낮음
```

배치는 데이터를 모아 한 번에 처리하므로 **건당 오버헤드가 분산되어 처리량이 압도적으로 높다**. 대신 모으는 시간만큼 지연이 생긴다. 스트리밍은 이벤트가 오는 즉시 처리하므로 **지연이 매우 낮지만**, 건마다 처리·전달 비용이 들어 같은 인프라로 낼 수 있는 누적 처리량은 배치보다 낮다.

여기에 **정확성(correctness)**이라는 축이 더해진다. 스트리밍은 늦게 도착하는 데이터(late-arriving data)나 순서가 뒤섞인 이벤트를 다뤄야 하므로, "정확한 최종 결과"와 "빠른 근사 결과" 사이에서 타협해야 한다. 배치는 모든 데이터가 도착한 뒤 처리하므로 이 문제에서 자유롭다.

```
        정확성 ↑
          │
   배치 ● │
          │      ● 마이크로배치
          │
          │            ● 스트리밍
          └──────────────────→ 신선도(낮은 지연) ↑
```

이 트레이드오프를 아키텍처 수준에서 푼 고전이 **람다 아키텍처(Lambda Architecture)**다. 배치 레이어(정확하지만 느림)와 스피드 레이어(빠르지만 근사)를 동시에 돌려 서빙 레이어에서 합친다. 코드를 두 벌 유지해야 하는 부담 때문에, 스트리밍 엔진 하나로 배치까지 처리하는 **카파 아키텍처(Kappa Architecture)**가 대안으로 등장했다. AWS에서는 Kinesis/MSK + Flink 조합이 카파에 해당한다.

## AWS에서의 매핑

시험에서 "이 시나리오에 어떤 서비스를 쓸 것인가"를 가르는 기준선이다.

| 패러다임 | 수집 | 처리 | 대표 시나리오 |
|---------|------|------|------------|
| 배치 | S3 적재, DataSync | Glue, EMR, AWS Batch | 일일 리포트, 대용량 ETL |
| 스트리밍 | Kinesis Data Streams, MSK | KDA(Flink), Lambda | 실시간 탐지, 라이브 대시보드 |
| 준실시간 | Kinesis Data Firehose | Firehose 변환, Lambda | 로그를 S3/Redshift로 거의 즉시 적재 |

특히 헷갈리기 쉬운 둘을 구분해야 한다. **Kinesis Data Streams**는 낮은 지연과 다중 소비자가 필요한 진짜 스트리밍용이고, **Kinesis Data Firehose**는 스트림을 받아 S3·Redshift 등으로 자동 적재하는 "관리형 준실시간 배달부"다. 직접 코드로 소비자를 운영할 필요 없이 목적지에 떨궈주길 원하면 Firehose다.

## 요구 지연을 숫자로 바꾸면 서비스가 정해진다

"실시간"은 사람마다 뜻이 다르다. 시험 지문도 `real-time`, `near real-time`, `within minutes`, `daily` 를 구분해서 쓴다. 지연 요구를 구간으로 나누면 후보가 좁혀진다.

| 요구되는 신선도 | 처리 형태 | AWS 구성 | 근거가 되는 동작 |
|------|------|------|------|
| 1초 안쪽 반응 | 이벤트 단위 스트리밍 | KDS/MSK + Managed Service for Apache Flink, 또는 Lambda(향상된 팬아웃) | 향상된 팬아웃은 레코드를 push 로 받아 전파 지연이 평균 70ms 수준, 공유 처리량은 소비자 1개일 때 평균 200ms 수준 |
| 수 초 ~ 1~2분 | 준실시간 적재 | Data Firehose | 버퍼(크기 또는 시간)가 차면 한 번에 전달. S3 목적지의 버퍼 간격은 0~900초, 기본 300초 |
| 1~수 분 | 마이크로배치 | Glue 스트리밍 ETL | Spark Structured Streaming 기반. 기본 100초 윈도우로 읽고 쓴다 |
| 수 분 ~ 시간 | 이벤트 기반 배치 | S3 이벤트 → Lambda/Glue 잡, EventBridge 스케줄 | 파일이 도착할 때 또는 정해진 간격으로 작은 배치를 실행 |
| 하루 단위 | 스케줄 배치 | Glue·EMR·AWS Batch + Step Functions/MWAA | 하루치 파티션을 통째로 읽어 한 번에 집계 |

- 표의 위로 갈수록 인프라가 **상시 가동**이고, 아래로 갈수록 **실행한 시간만큼만** 돈을 낸다.
- Lambda 를 KDS 소비자로 붙이면 표준 방식에서는 샤드마다 초당 1회 기본 주기로 폴링한다. "함수니까 즉시"가 아니라 폴링 주기와 배치 윈도우만큼 지연이 생긴다.
- Firehose 의 버퍼 간격을 60초 미만으로 낮추면 더 빨리 도착하지만 S3 에 작은 객체가 늘고 PUT 요청 비용이 오른다. 신선도와 파일 크기는 항상 맞바꾸는 관계다.

> ⚠️ **함정**: 지문에 "실시간으로 S3에 적재"라고 쓰여 있어도 요구가 "쌓기"뿐이면 정답은 Firehose 다. KDS 는 소비자 코드를 직접 운영해야 하므로 "운영 부담 최소" 조건과 충돌한다. 반대로 "여러 애플리케이션이 같은 이벤트를 각자 읽는다", "과거 구간을 다시 처리한다"가 나오면 Firehose 만으로는 안 된다.

## 스트리밍이 비싼 구조적 이유

"실시간이 비싸다"를 요금 구조로 풀면 이렇다.

| 구분 | 배치 | 스트리밍 |
|------|------|---------|
| 과금 시점 | 잡이 도는 동안만 | 데이터가 없어도 스트림·애플리케이션이 떠 있는 내내 |
| 수집 계층 | S3 저장·요청 요금 | KDS 프로비저닝 모드는 샤드 단위로, 온디맨드 모드는 쓰고 읽은 데이터량(GB)으로 과금 |
| 처리 계층 | Glue 는 잡 실행 시간, EMR 은 클러스터가 켜져 있는 시간 | Glue 스트리밍 잡은 실행 중인 시간만큼 계속 과금, Flink 애플리케이션도 상시 실행 |
| 운영 | 실패하면 그 날짜만 다시 실행 | 지연(lag) 모니터링, 체크포인트, 재시작 시 중복 처리 대비가 상시 필요 |
| 정확성 | 데이터가 다 모인 뒤 계산 | 늦게 온 데이터를 어디까지 기다릴지 정해야 함 |

- 하루에 한 번 5분 도는 배치와, 24시간 떠 있는 스트리밍 애플리케이션은 처리한 데이터량이 같아도 컴퓨팅 시간이 수백 배 차이 난다.
- 그래서 시험의 "가장 비용 효율적인(most cost-effective)" 지문에서, 요구 지연이 시간 단위 이상이면 스트리밍 보기는 대부분 오답이다.

## 이벤트 시간과 늦게 도착하는 데이터

배치에는 없고 스트리밍에만 있는 난제다.

- **이벤트 시간(event time)** : 사건이 실제로 일어난 시각. 프로듀서가 페이로드 안에 넣어 보내야 한다.
- **처리 시간(processing time)** : 시스템이 그 레코드를 받은 시각. KDS 레코드의 `ApproximateArrivalTimestamp` 가 이것이다. 스트림 도착 시각이지 사건 발생 시각이 아니다.
- 모바일 앱이 지하철에서 오프라인으로 쌓아둔 클릭을 20분 뒤 한꺼번에 보내면, 이벤트 시간은 10:00 인데 처리 시간은 10:20 이 된다. 처리 시간 기준으로 5분 윈도우를 자르면 이 클릭은 엉뚱한 윈도우에 들어간다.

```
이벤트 시간 기준 5분 텀블링 윈도우 [10:00~10:05)
  10:01 이벤트 A ─ 10:01 도착  → 정상 집계
  10:03 이벤트 B ─ 10:04 도착  → 정상 집계
  10:02 이벤트 C ─ 10:21 도착  → 윈도우가 이미 닫혔다면? (늦은 데이터)
```

- 스트리밍 엔진은 **워터마크(watermark)** 로 "이 시각 이전 이벤트는 다 왔다고 본다"는 기준선을 정하고, 허용 지연을 넘긴 이벤트는 버리거나 별도 출력으로 빼낸다.
- 배치는 이 문제를 **기다림**으로 해결한다. 자정 직후가 아니라 새벽 2시에 어제 파티션을 처리하면 늦은 이벤트 대부분이 이미 도착해 있다. 그래도 더 늦게 온 것은 해당 날짜 파티션을 통째로 다시 계산(backfill)해 덮어쓴다.
- Firehose 의 기본 S3 접두사(`YYYY/MM/dd/HH`, UTC)는 **Firehose 에 도착한 시각** 기준이다. 이벤트 시간 기준으로 폴더를 나누려면 동적 파티셔닝으로 레코드 안의 필드를 꺼내 써야 한다.

배치 재처리가 안전한 이유는 "같은 입력 파티션 → 같은 출력 파티션을 덮어쓰기"라는 멱등한 구조 덕분이다. 스트리밍은 장애 후 체크포인트 지점부터 다시 읽기 때문에 일부 레코드가 두 번 처리될 수 있고(at-least-once), 결과 저장소 쪽에서 중복을 흡수하도록 설계해야 한다.

## 윈도우 세 가지를 같은 데이터로 비교

같은 사용자의 클릭 시각이 `10:00, 10:02, 10:03, 10:11, 10:12` 일 때 건수를 세면 결과가 이렇게 달라진다.

| 윈도우 | 정의 | 결과 | 쓰는 곳 |
|------|------|------|------|
| 텀블링 5분 | 겹치지 않는 고정 구간 | [10:00~10:05) 3건, [10:10~10:15) 2건 | 5분마다 매출 합계, 분 단위 지표 |
| 슬라이딩 10분/5분 간격 | 길이 10분 창을 5분마다 이동, 서로 겹침 | [10:00~10:10) 3건, [10:05~10:15) 2건, 한 이벤트가 여러 창에 포함될 수 있음 | "최근 10분 이동 평균", 이상 급증 탐지 |
| 세션(간격 5분) | 활동이 5분 넘게 끊기면 세션 종료 | 세션1 10:00~10:03 3건, 세션2 10:11~10:12 2건 | 방문 세션 길이, 사용자 행동 묶음 |

- 텀블링은 모든 이벤트가 정확히 한 윈도우에만 속하므로 합계가 중복되지 않는다. 정산처럼 이중 계산이 금지된 집계에 맞다.
- 세션 윈도우는 길이가 데이터에 따라 달라져 상태를 오래 들고 있어야 한다. 그래서 상태 관리 기능이 있는 Flink 계열이 적합하고, 무상태로 도는 Lambda 에는 맞지 않는다.

## 스트림 처리 엔진 선택: Lambda vs Flink vs Glue 스트리밍

"스트리밍으로 처리한다"까지 정해졌을 때 다음 갈림길이다.

| 기준 | Lambda | Managed Service for Apache Flink | Glue 스트리밍 ETL |
|------|------|------|------|
| 처리 모델 | 배치 단위 함수 호출, 기본 무상태 | 이벤트 단위, 상태·체크포인트 내장 | 마이크로배치(Spark Structured Streaming) |
| 잘하는 일 | 레코드별 정제·필터·라우팅, 알림 | 윈도우 집계, 스트림 조인, 이벤트 시간·늦은 데이터 처리 | 스트림을 받아 변환 후 S3 데이터 레이크·JDBC 에 적재 |
| 소스 | KDS, MSK, DynamoDB Streams 등 이벤트 소스 매핑 | KDS, MSK 등 | KDS, Kafka, MSK |
| 운영 | 가장 가벼움 | 애플리케이션 병렬도·상태 크기를 신경 써야 함 | Glue 잡과 같은 방식으로 운영, 체크포인트로 읽은 위치 추적(잡 북마크 미지원) |
| 고르는 단서 | "간단한 변환", "이벤트마다 함수 실행" | "상태 있는(stateful)", "시간 윈도우", "정확한 집계" | "기존 Spark/Glue 코드 재사용", "분 단위면 충분" |

- 예전 자료의 **Kinesis Data Analytics(KDA)** 는 현재 **Amazon Managed Service for Apache Flink** 다. 본문 표의 `KDA(Flink)` 도 같은 서비스를 가리킨다.
- SQL 로만 작성하던 구버전 **Kinesis Data Analytics for SQL** 은 지원이 종료됐다(신규 생성 차단 후 2026년 1월 27일부터 애플리케이션 삭제). 스트림에 SQL 을 쓰려면 Flink SQL 이나 Managed Service for Apache Flink Studio 노트북을 쓴다.
- **Kinesis Data Firehose** 의 현재 이름은 **Amazon Data Firehose** 다. 시험 지문과 콘솔에 두 이름이 섞여 나오지만 같은 서비스다.

## 자주 만나는 안티패턴

- **배치로 충분한데 스트리밍**: 아침에 보는 리포트를 위해 24시간 Flink 를 띄운다. 요구 지연이 "다음 날 아침"이면 스케줄 배치가 정답이다.
- **스트리밍 결과를 초 단위로 S3 에 쓰기**: 작은 파일이 수만 개 생겨 Athena·Spark 조회가 느려진다. 버퍼를 키우거나 뒤에서 배치로 병합(compaction)한다.
- **스트리밍으로 과거 전체 재처리**: 스트림 보존 기간이 지난 데이터는 스트림에 없다. 원본을 S3 에 따로 보관해 두고 재처리는 배치로 한다(람다 아키텍처의 배치 레이어가 하는 일).
- **처리 시간으로 윈도우 자르기**: 프로듀서 지연·재시도가 있으면 집계가 틀어진다. 페이로드에 이벤트 시각을 넣고 이벤트 시간 기준으로 집계한다.
- **운영 DB 를 주기적으로 통째 덤프**: 배치라도 원천에 부하를 준다. 변경분만 필요하면 DMS 의 CDC 로 연속 복제한다.

## 지문 단서 → 정답 판별표

| 지문에 나오는 단서 | 고를 방향 | 이유 |
|------|------|------|
| "매일 밤", "일 단위 리포트", "전날 데이터" | 스케줄 배치(Glue/EMR) | 경계 있는 데이터, 지연 허용 |
| "수년치 과거 데이터를 다시 계산" | 배치(backfill) | 처리량이 중요, 스트림에는 과거가 없음 |
| "거래 발생 즉시 탐지", "초 이내 알림" | KDS/MSK + Flink 또는 Lambda | 이벤트 단위 저지연 |
| "최근 N분 이동 집계", "세션" | Managed Service for Apache Flink | 상태 있는 윈도우 연산 |
| "코드 없이 S3/Redshift 에 계속 적재" | Data Firehose | 관리형 준실시간 전달 |
| "기존 Spark 잡을 스트림에도 재사용, 1~2분 지연 허용" | Glue 스트리밍 ETL | 마이크로배치 |
| "실시간 결과와 정확한 최종 결과 둘 다" | 람다 아키텍처(스피드 + 배치 레이어) | 근사 결과를 배치가 나중에 보정 |
| "파이프라인 코드를 한 벌만 유지" | 카파 아키텍처(스트림 재생으로 재처리) | 배치 레이어 제거 |

다음 글에서는 이 처리 패러다임들을 실제로 구현하는 AWS 데이터 서비스 전체 지도를 수집·저장·처리·분석·거버넌스 카테고리로 펼쳐본다.

## 📖 용어

- **경계 있는/없는 데이터** : 시작과 끝이 정해진 묶음(bounded)과 끝없이 들어오는 흐름(unbounded). 배치와 스트리밍을 가르는 출발점이다.
- **지연(latency)** : 데이터가 생긴 뒤 결과가 나올 때까지 걸리는 시간. 짧을수록 실시간에 가깝다.
- **처리량(throughput)** : 같은 시간에 처리할 수 있는 데이터 양. 묶어서 처리하는 배치가 유리하다.
- **윈도우** : 끝없는 흐름을 집계하려고 시간 기준으로 잘라낸 구간. 텀블링·슬라이딩·세션이 대표적이다.
- **이벤트 시간 / 처리 시간** : 사건이 실제로 일어난 시각과 시스템이 그 데이터를 받은 시각. 둘의 차이가 늦은 데이터 문제를 만든다.
- **워터마크** : "이 시각까지의 이벤트는 다 도착했다"고 보는 기준선. 이보다 늦게 오면 늦은 데이터로 취급한다.
- **마이크로배치** : 몇 초~수십 초짜리 작은 배치를 계속 반복해 실시간처럼 보이게 하는 방식.
- **백필(backfill)** : 과거 구간을 다시 처리해 결과를 채우거나 고치는 작업. 보통 배치로 한다.
- **람다 / 카파 아키텍처** : 배치와 스트림 경로를 둘 다 두는 구조와, 스트림 하나로 통합하는 구조.
- **준실시간(near real-time)** : 초~분 단위로 조금 늦게 도착하는 수준. Firehose 가 대표적이다.

## 📝 연습 문제

**문제 1.** 경계가 없는(unbounded) 데이터 흐름을 다루는 스트리밍 처리에서, 무한한 흐름으로부터 집계 결과를 내기 위해 반드시 필요한 개념은?

A) 정규화(normalization)  
B) 윈도잉(windowing) — 흐름을 시간 단위로 잘라 집계  
C) 인덱싱(indexing)  
D) 샤딩(sharding)  

**정답: B**  
해설: 스트리밍 데이터는 끝이 없으므로 "최근 5분"처럼 시간 창(텀블링/슬라이딩/세션 윈도우)으로 흐름을 잘라야 집계 결과를 낼 수 있다. 정규화는 스키마 설계, 인덱싱은 조회 성능, 샤딩은 데이터 분산을 위한 개념으로 윈도잉과는 다른 문제를 다룬다.

**문제 2.** "매일 밤 하루치 거래를 모아 정산 리포트를 생성"하는 작업에 가장 적합한 처리 패러다임과 그 이유는?

A) 스트리밍 — 지연이 가장 낮으므로  
B) 배치 — 경계 있는 데이터를 정해진 주기로 처리하며, 결과가 다소 늦어도 무방하므로  
C) 스트리밍 — 처리량이 가장 높으므로  
D) 배치 — 늦게 도착하는 데이터를 실시간으로 보정하므로  

**정답: B**  
해설: "하루치를 모아 정해진 시각에"는 경계 있는 데이터를 주기적으로 처리하는 전형적 배치 작업이며, 리포트는 즉시성이 필요 없다. 스트리밍은 낮은 지연이 강점이고 누적 처리량은 오히려 배치가 더 높으며, 늦게 도착하는 데이터 보정은 스트리밍의 과제다.

**문제 3.** 배치 처리가 스트리밍보다 단위 시간당 처리량(throughput)이 높은 근본적인 이유는?

A) 배치는 데이터를 압축하기 때문  
B) 데이터를 묶음으로 한 번에 처리해 건당 오버헤드가 분산되기 때문  
C) 배치는 더 비싼 인스턴스를 쓰기 때문  
D) 스트리밍은 SQL을 쓸 수 없기 때문  

**정답: B**  
해설: 배치는 많은 레코드를 하나의 작업으로 묶어 처리하므로 건당 처리·전달 오버헤드가 분산되어 처리량이 높다. 대신 모으는 시간만큼 지연이 생긴다. 압축이나 인스턴스 종류 때문이 아니며, 스트리밍도 SQL 기반 처리(예: Flink SQL)가 가능하다.

**문제 4.** 스트림 데이터를 받아 별도 소비자 코드 운영 없이 S3나 Redshift로 거의 즉시 자동 적재하길 원할 때 가장 적합한 AWS 서비스는?

A) Kinesis Data Streams  
B) Kinesis Data Firehose  
C) AWS Glue  
D) Amazon EMR  

**정답: B**  
해설: Firehose는 스트림을 받아 S3·Redshift·OpenSearch 등으로 자동 적재하는 관리형 준실시간 배달 서비스로, 소비자 코드를 직접 운영할 필요가 없다. Data Streams는 낮은 지연·다중 소비자가 필요한 진짜 스트리밍용이고, Glue·EMR은 배치 ETL 처리 엔진이다.

**문제 5.** 배치 레이어(정확하지만 느림)와 스피드 레이어(빠르지만 근사)를 함께 운영해 지연과 정확성의 트레이드오프를 푸는 고전적 아키텍처는?

A) 카파 아키텍처(Kappa)  
B) 람다 아키텍처(Lambda)  
C) 마이크로서비스 아키텍처  
D) 서버리스 아키텍처  

**정답: B**  
해설: 람다 아키텍처는 배치 레이어와 스피드 레이어를 동시에 돌려 서빙 레이어에서 합치는 방식이다. 코드 이중 유지 부담 때문에 스트리밍 엔진 하나로 통합하는 카파 아키텍처가 대안으로 나왔다. 마이크로서비스·서버리스는 데이터 처리 패러다임이 아니라 일반적인 시스템 구조 개념이다.
