# Day 3 - AWS 데이터 서비스 조감도

## 📌 핵심 정리

- AWS 데이터 서비스는 **수집 → 저장 → 처리 → 분석** 흐름에 배치되고, **거버넌스**(카탈로그·권한·암호화)가 전 구간을 감싼다.
- 시나리오 문제는 "이건 흐름의 어느 단계인가"를 먼저 묻고, 그 단계 후보를 **원천 종류·신선도·운영 부담**으로 좁힌다.
- 수집은 원천이 결정한다: 이벤트 = Kinesis/MSK, 데이터베이스 변경분 = DMS(CDC), 파일 = DataSync, SaaS = AppFlow.
- S3 가 저장의 기본값이고 Glue Data Catalog 가 Athena·Redshift Spectrum·EMR 이 함께 보는 공통 메타데이터다.
- 권한은 층이 다르다: IAM 은 리소스(버킷·API), Lake Formation 은 테이블·컬럼·행, KMS 는 암호화 키를 맡는다.

## 데이터 흐름이 곧 서비스 지도

AWS의 데이터 관련 서비스는 수십 개다. 처음 콘솔을 열면 Kinesis, Glue, EMR, Redshift, Athena, Lake Formation… 비슷해 보이는 이름들이 쏟아져 막막하다. 하지만 이들을 **데이터가 흐르는 순서**대로 줄 세우면 지도가 그려진다. 데이터는 항상 **수집 → 저장 → 처리 → 분석**의 흐름을 따르고, 그 전체를 가로질러 **거버넌스(보안·카탈로그)**가 감싼다.

오늘은 이 5개 카테고리에 어떤 서비스가 어디에 속하는지 지도를 그린다. 개별 서비스의 깊은 디테일은 이후 주차에서 다루고, 오늘은 "이 서비스가 파이프라인의 어느 단계에 있는가"를 머릿속에 배치하는 것이 목표다. 시험 문제의 절반은 "이 시나리오에 맞는 서비스는?"이고, 그 답은 이 지도에서 나온다.

![수집·저장·처리·분석 네 단계별 AWS 서비스 지도와 이를 관통하는 거버넌스](/diagrams/data-pipeline-map.svg)

이 한 장이 DEA-C01 서비스 지식의 뼈대다. 데이터는 왼쪽(수집)에서 오른쪽(분석)으로 흐르고, 아래의 거버넌스 계층이 전 구간의 권한·카탈로그·암호화를 관장한다.

> 💡 **관련 이론**: 이 흐름을 산업 표준 용어로 "데이터 파이프라인의 단계"라 한다. 각 단계는 느슨하게 결합(loosely coupled)되어야 한다. 예를 들어 수집(Kinesis)과 처리(Lambda) 사이에 S3나 스트림 버퍼를 두면, 처리 단계가 느려도 수집이 막히지 않는다. 이 "버퍼로 단계를 분리"하는 패턴이 견고한 파이프라인 설계의 핵심이다.

## 수집(Ingestion): 데이터를 들여오기

원천에서 AWS로 데이터를 가져오는 입구다. 원천의 성격에 따라 도구가 갈린다.

| 서비스 | 용도 | 언제 |
|--------|------|------|
| Kinesis Data Streams | 실시간 스트림 수집 | 낮은 지연, 다중 소비자 |
| Kinesis Data Firehose | 스트림 → S3/Redshift 적재 | 준실시간 자동 배달 |
| Amazon MSK | 관리형 Apache Kafka | 기존 Kafka 생태계 |
| AWS DMS | DB 마이그레이션/복제 | RDS·온프렘 DB를 S3/Redshift로 |
| AWS DataSync | 대용량 파일 전송 | 온프렘 NFS/SMB → S3 |

핵심 구분: **실시간 이벤트 스트림은 Kinesis/MSK**, **기존 데이터베이스의 변경을 가져오려면 DMS(CDC 포함)**, **온프렘 파일 덩어리는 DataSync**다.

> 💡 **관련 이론**: DMS의 진가는 CDC(Change Data Capture)에 있다. 운영 DB의 트랜잭션 로그를 읽어 "변경분만" 지속적으로 복제하므로, 전체를 매번 덤프하지 않고도 분석 환경을 최신으로 유지한다. OLTP에 부하를 거의 주지 않으면서 OLAP로 데이터를 흘려보내는 표준 방식이다.

## 저장(Storage): 데이터를 담기

수집한 데이터가 머무는 곳. Day 1의 OLTP/OLAP, 레이크/웨어하우스 구분이 그대로 적용된다.

| 서비스 | 유형 | 역할 |
|--------|------|------|
| Amazon S3 | 객체 스토리지 | 데이터레이크의 토대, 모든 원시 데이터 |
| Amazon Redshift | 데이터 웨어하우스(OLAP) | 정제된 정형 데이터 대규모 분석 |
| Amazon DynamoDB | NoSQL(OLTP) | 키-값, 저지연 대량 읽기/쓰기 |
| Amazon RDS/Aurora | 관계형(OLTP) | 트랜잭션 운영 DB |

**S3가 모든 것의 중심**이다. 데이터레이크의 토대이자, 거의 모든 처리·분석 서비스의 입출력 지점이다. "어디에 저장할까"가 막연하면 일단 S3가 기본값이다.

```bash
# S3는 데이터레이크의 토대 — 파티션 구조로 저장
aws s3 cp orders.parquet \
  s3://datalake/raw/orders/year=2026/month=06/day=25/

# Athena가 이 S3 위에서 바로 SQL 조회 (별도 적재 불필요)
# Glue Catalog가 스키마를 알고 있으면 즉시 쿼리 가능
```

> 💡 **관련 이론**: S3 스토리지 클래스(Standard, Intelligent-Tiering, Glacier 등)와 수명주기 정책은 비용 최적화의 핵심이다. 자주 안 쓰는 과거 데이터를 자동으로 저렴한 계층으로 옮기는 것이 데이터 엔지니어의 일상 업무이며, 시험에서도 비중 있게 다뤄진다.

## 처리(Processing): 데이터를 변환하기

원시 데이터를 분석 가능한 형태로 정제·변환하는 엔진들이다. 데이터 양과 작업 성격으로 고른다.

| 서비스 | 엔진 | 적합한 작업 |
|--------|------|------------|
| AWS Glue | 서버리스 Spark | 관리형 ETL, 카탈로그 통합 |
| Amazon EMR | Hadoop/Spark 클러스터 | 대규모·커스텀 빅데이터 처리 |
| AWS Lambda | 함수 | 가벼운 이벤트 기반 변환 |
| Glue / EMR Serverless | 서버리스 | 클러스터 관리 없이 Spark |

**Glue는 "관리형 ETL의 기본값"**이다. 서버 관리 없이 Spark 기반 변환을 돌리고, 데이터 카탈로그·크롤러·스케줄러가 통합돼 있다. **EMR은 더 큰 제어와 규모**가 필요하거나 기존 Hadoop/Spark 코드를 그대로 옮길 때 쓴다. **Lambda는 작은 단위의 이벤트 기반 변환**(파일 하나 도착 시 가공 등)에 적합하다.

> 💡 **관련 이론**: Glue Crawler는 S3 데이터를 스캔해 스키마를 자동 추론하고 Glue Data Catalog에 테이블로 등록한다. 이 카탈로그가 Athena·Redshift Spectrum·EMR이 공유하는 "공통 메타데이터 사전"이 된다. 즉 한 번 카탈로그에 등록하면 여러 분석 엔진이 같은 정의로 같은 데이터를 본다.

## 분석(Analytics): 데이터에서 답 얻기

정제된 데이터에 질문을 던지는 소비 계층이다.

| 서비스 | 용도 |
|--------|------|
| Amazon Athena | S3 위 서버리스 SQL 쿼리 |
| Amazon Redshift | 대규모 웨어하우스 쿼리 |
| Amazon QuickSight | BI 대시보드·시각화 |
| Amazon OpenSearch | 로그·텍스트 검색, 실시간 분석 |

**Athena는 S3에 적재된 데이터를 옮기지 않고 그 자리에서 SQL로 조회**하는 서버리스 도구다. 인프라가 없고 스캔한 데이터량만큼 과금돼, 가끔 하는 애드혹 분석에 이상적이다. 자주·빠르게 대규모로 조회한다면 데이터를 Redshift에 적재한다. 최종 결과를 사람이 보는 대시보드로 만들려면 QuickSight다.

## 거버넌스(Governance): 전 구간을 통제하기

수집부터 분석까지 모든 단계를 가로지르는 보안·카탈로그·권한 계층이다.

| 서비스 | 역할 |
|--------|------|
| AWS Lake Formation | 데이터레이크 중앙 권한·거버넌스 |
| AWS Glue Data Catalog | 통합 메타데이터 카탈로그 |
| AWS IAM | 신원·접근 권한 |
| AWS KMS | 암호화 키 관리 |

**Lake Formation은 S3 데이터레이크에 "테이블·컬럼·행 단위"의 세밀한 권한**을 부여한다. IAM이 "이 사람이 이 S3 버킷에 접근 가능한가"라면, Lake Formation은 "이 사람이 이 테이블의 이 컬럼까지 볼 수 있는가"를 통제한다.

> 💡 **관련 이론**: 거버넌스가 별도 카테고리인 이유는, 데이터 파이프라인에서 보안·권한·계보(lineage)는 한 단계의 문제가 아니라 전 구간을 관통하는 횡단 관심사(cross-cutting concern)이기 때문이다. 누가 어떤 데이터에 접근했고, 그 데이터가 어디서 와서 어디로 갔는지(data lineage)를 추적하는 것이 거버넌스의 본질이다.

## 지도에 아직 없는 조각들

위 표는 뼈대만 담았다. DEA-C01 범위에는 단계 사이를 잇거나 틈을 메우는 서비스가 더 있다. 이름을 봤을 때 "어느 칸의 무엇"인지 바로 떠올라야 한다.

| 서비스 | 지도상 위치 | 한 줄 역할 | 지문 단서 |
|------|------|------|------|
| Amazon AppFlow | 수집 | Salesforce 같은 SaaS 와 AWS 사이 데이터 흐름을 코드 없이 구성 | "SaaS 애플리케이션 데이터", "코드 없이" |
| AWS Transfer Family | 수집 | 외부가 SFTP/FTPS 로 올리는 파일을 S3·EFS 로 받는다 | "파트너가 SFTP 로 전송" |
| AWS Snow 패밀리 | 수집 | 장비에 담아 물리 배송 | "회선이 느리다", "일회성 대용량 이전" |
| AWS SCT | 수집(DMS 와 한 쌍) | 이기종 DB 의 스키마·코드를 변환 | "Oracle → PostgreSQL/Redshift" |
| Amazon Managed Service for Apache Flink | 처리(스트림) | 상태 있는 실시간 집계·조인 | "윈도우 집계", "실시간 이상 탐지" |
| AWS Glue DataBrew | 처리(준비) | 시각적 화면에서 정제·프로파일링 | "코드를 쓰지 않는 분석가", "데이터 프로파일" |
| AWS Glue Data Quality | 처리·거버넌스 | 규칙으로 데이터 품질 검사 | "완전성·유일성 규칙", "품질 점수" |
| Redshift Spectrum | 분석 | Redshift 에서 S3 데이터를 외부 테이블로 조회 | "적재하지 않고 Redshift SQL 로 S3 조회·조인" |
| AWS Step Functions | 오케스트레이션 | 서버리스 상태 기계로 단계 연결·재시도·분기 | "서버리스 워크플로", "AWS 서비스 여러 개를 순서대로" |
| Amazon MWAA | 오케스트레이션 | 관리형 Apache Airflow | "기존 Airflow DAG", "오픈소스 호환" |
| Amazon EventBridge | 오케스트레이션·트리거 | 이벤트 규칙·스케줄로 실행 시작 | "이벤트가 발생하면", "cron 스케줄" |
| Amazon Macie | 거버넌스 | S3 안의 민감정보(PII)를 찾아낸다 | "S3 에 개인정보가 있는지 탐지" |
| AWS CloudTrail | 거버넌스 | 누가 어떤 API 를 호출했는지 기록 | "감사", "누가 접근했는가" |

- **오케스트레이션**은 수집·처리 단계 자체가 아니라 그 단계들을 **언제 어떤 순서로** 돌릴지 정하는 층이다. Glue 워크플로·트리거도 여기에 속하지만 Glue 작업끼리만 엮을 때 쓴다.
- 본문 표의 `Kinesis Data Firehose` 는 현재 이름이 **Amazon Data Firehose** 다. 시험 지문에는 두 표기가 모두 나온다.

## 닮은 서비스 판별표

이 트랙에서 가장 자주 틀리는 것은 "둘 다 될 것 같은" 보기다. 갈리는 축을 하나씩만 기억한다.

**수집: 원천이 무엇인가**

| 원천 | 서비스 | 핵심 |
|------|------|------|
| 관계형·NoSQL 데이터베이스 | DMS | 전체 적재 + CDC 로 변경분 지속 복제. 이기종이면 SCT 로 스키마 변환 |
| NFS·SMB 파일 서버, 다른 오브젝트 스토리지 | DataSync | 에이전트가 파일을 전송·검증. 스케줄 증분 동기화 |
| 외부 파트너가 밀어 넣는 파일 | Transfer Family | SFTP/FTPS 엔드포인트를 AWS 가 운영 |
| SaaS 애플리케이션 | AppFlow | 커넥터 선택 후 매핑·스케줄 설정 |
| 애플리케이션 이벤트·로그·IoT | KDS·MSK·Firehose | 끊임없이 들어오는 작은 레코드 |

- DMS 는 **행**을 옮기고 DataSync 는 **파일**을 옮긴다. "데이터베이스 백업 파일을 S3 로 복사"는 파일 전송이라 DataSync 쪽이고, "데이터베이스의 테이블을 계속 동기화"는 DMS 다.

**처리: 얼마나 크고 얼마나 제어해야 하나**

| 서비스 | 고르는 조건 | 고르면 안 되는 조건 |
|------|------|------|
| Lambda | 파일 하나·이벤트 하나 단위의 가벼운 변환 | 한 번 실행이 15분을 넘는 작업(함수 제한 시간 상한), 대용량 조인 |
| Glue ETL | 서버리스 Spark, 카탈로그·크롤러·북마크와 통합 | 클러스터 설정을 세밀하게 손대야 하는 경우, Spark 외 프레임워크 |
| EMR | Spark·Hive·Presto·HBase 등 여러 프레임워크, 인스턴스·설정 직접 제어, 기존 Hadoop 코드 이전 | "운영 부담 최소"가 조건일 때(단, EMR Serverless 는 예외) |
| Athena(CTAS/INSERT INTO) | SQL 만으로 끝나는 변환, 포맷 변환 | 복잡한 절차형 로직, 외부 시스템 호출 |

**분석: 데이터가 어디에 있고 얼마나 자주 묻는가**

| 서비스 | 데이터 위치 | 과금 구조 | 맞는 상황 |
|------|------|------|------|
| Athena | S3 그대로 | 쿼리가 스캔한 데이터량(용량을 미리 사 두는 방식도 있음) | 가끔 하는 애드혹, 로그 조사 |
| Redshift Spectrum | S3 그대로(외부 테이블) | 스캔한 데이터량 + Redshift 클러스터 | 웨어하우스 테이블과 S3 데이터를 한 쿼리로 조인 |
| Redshift | Redshift 내부 스토리지에 적재 | 노드 시간 또는 서버리스 사용량 | 복잡한 조인을 자주·빠르게, 다수 동시 사용자 |
| OpenSearch | 인덱스에 색인 | 도메인 인스턴스·스토리지 | 전문 검색, 로그 탐색, 초 단위 대시보드 |

**거버넌스: 무엇을 통제하나**

| 서비스 | 통제 단위 | 질문 |
|------|------|------|
| IAM | 리소스·API 호출 | "이 역할이 이 버킷/잡/쿼리 API 를 쓸 수 있나" |
| Lake Formation | 데이터베이스·테이블·컬럼·행·셀 | "이 분석가가 이 테이블의 급여 컬럼을 볼 수 있나" |
| KMS | 암호화 키 | "이 데이터를 누가 복호화할 수 있나" |
| Macie | S3 객체 내용 | "어디에 민감정보가 들어 있나" |
| CloudTrail | API 호출 이력 | "누가 언제 무엇을 했나" |

> ⚠️ **함정**: "컬럼 수준 접근 제어"를 S3 버킷 정책이나 IAM 정책만으로 풀려는 보기는 오답이다. S3 는 객체 단위까지만 안다. 객체 안의 컬럼·행을 가려 주는 것은 카탈로그 테이블에 권한을 거는 Lake Formation 이다.

## Glue Data Catalog 가 실제로 하는 일

카탈로그는 데이터를 **담지 않는다.** "이 테이블의 데이터는 S3 의 어느 경로에 있고, 컬럼과 타입은 무엇이며, 어떤 포맷으로 읽어야 하는가"라는 설명서만 가진다.

```sql
-- Athena DDL: 데이터는 S3 에 그대로, 카탈로그에 설명서만 등록된다
CREATE EXTERNAL TABLE orders (
  order_id   string,
  amount     double,
  region     string
)
PARTITIONED BY (dt string)
STORED AS PARQUET
LOCATION 's3://datalake/processed/orders/';

-- 새 날짜 폴더가 생기면 파티션을 카탈로그에 알려야 조회된다
ALTER TABLE orders ADD IF NOT EXISTS
  PARTITION (dt = '2026-06-25')
  LOCATION 's3://datalake/processed/orders/dt=2026-06-25/';
```

- 계층은 **데이터베이스 → 테이블 → 파티션**이다. 테이블은 S3 경로·포맷(SerDe)·컬럼을, 파티션은 하위 경로를 가리킨다.
- `DROP TABLE` 로 외부 테이블을 지워도 S3 의 파일은 남는다. 반대로 S3 파일을 지워도 카탈로그 항목은 남아 빈 결과가 나온다.
- 카탈로그를 채우는 방법은 세 가지다.

| 방법 | 동작 | 맞는 상황 |
|------|------|------|
| Glue 크롤러 | S3·JDBC 를 훑어 스키마를 추론하고 테이블·파티션을 등록 | 스키마를 모르는 원시 데이터, 주기적으로 파티션이 늘어나는 경로 |
| DDL / API 직접 등록 | `CREATE EXTERNAL TABLE`, `ALTER TABLE ADD PARTITION` | 스키마가 이미 확정된 정제 영역, 파이프라인이 파티션을 직접 추가 |
| 파티션 프로젝션(Athena) | 파티션 목록을 카탈로그에 저장하지 않고 테이블 속성의 규칙으로 계산 | 날짜처럼 규칙적인 파티션이 아주 많을 때 |

- 크롤러는 실행할 때마다 비용과 시간이 든다. "새 파일이 들어왔는데 Athena 에서 안 보인다"의 원인은 대개 파티션이 등록되지 않은 것이다.
- `MSCK REPAIR TABLE` 은 새 파티션을 추가만 하고 오래 걸리며 지워진 파티션을 정리하지 못한다. 파티션 관리는 `ALTER TABLE ADD PARTITION`·크롤러·파티션 프로젝션이 낫다.

> 🔍 **더 깊이**: 카탈로그 하나를 여러 엔진이 공유한다는 것은 장점이자 책임이다. 누군가 테이블의 컬럼 타입을 바꾸면 Athena 쿼리뿐 아니라 그 테이블을 읽는 Glue 잡·EMR 잡·Redshift Spectrum 외부 스키마가 한꺼번에 영향을 받는다. 그래서 Lake Formation 권한은 데이터 조회 권한뿐 아니라 카탈로그 메타데이터를 고칠 권한도 따로 관리한다.

## 과금 방식이 서비스 성격을 말해준다

시험은 금액을 묻지 않고 **구조**를 묻는다. "무엇에 비례해 돈이 나가는가"를 알면 "가장 비용 효율적인" 보기가 가려진다.

| 서비스 | 무엇에 비례하나 | 그래서 줄이는 방법 |
|------|------|------|
| S3 | 저장량 × 스토리지 클래스, 요청 수 | 수명주기로 클래스 전환, 작은 객체 줄이기 |
| Athena | 스캔한 데이터량 | 컬럼형 포맷, 압축, 파티션 필터 |
| Glue ETL | 잡이 쓴 처리 용량 × 실행 시간 | 필요한 파티션만 읽기, 북마크로 증분 처리 |
| EMR | 클러스터 인스턴스가 켜져 있는 시간 | 작업 끝나면 종료하는 일시 클러스터, 스팟 인스턴스 |
| Redshift | 노드가 켜져 있는 시간(프로비저닝) 또는 사용한 용량(서버리스) | 사용 패턴이 간헐적이면 서버리스 |
| KDS | 샤드 수 × 시간(프로비저닝) 또는 쓰고 읽은 데이터량(온디맨드) | 트래픽이 일정하면 프로비저닝 |
| Data Firehose | 수집한 데이터량 | Direct PUT·KDS 소스는 레코드 크기를 5KB 단위로 올림해 계산하므로 아주 작은 레코드는 묶어서 보낸다 |
| Lambda | 호출 수 × 실행 시간 × 메모리 | 배치 크기 키우기 |

- **가끔 쓰면 사용량 과금**(Athena, Lambda, 온디맨드/서버리스)이 유리하고, **계속 꽉 채워 쓰면 용량 과금**(프로비저닝 클러스터·샤드)이 유리하다. 이 한 줄이 "서버리스 vs 프로비저닝" 문제의 기준이다.

## 시나리오 → 서비스 판별표

| 시나리오 | 정답 | 헷갈리는 오답과 이유 |
|------|------|------|
| 온프레미스 Oracle 의 변경을 Redshift 에 계속 반영 | DMS(CDC) + SCT | DataSync — 파일 전송 도구라 테이블 변경을 못 따라간다 |
| Salesforce 데이터를 매시간 S3 로 | AppFlow | Glue 커스텀 잡 — 가능하지만 "코드 없이"에 어긋난다 |
| S3 의 JSON 로그를 한 달에 몇 번 SQL 로 조사 | Athena | Redshift 적재 — 상시 클러스터 비용이 든다 |
| 수백 명이 매일 보는 대시보드의 복잡한 조인 | Redshift (+ QuickSight) | Athena — 가능하지만 동시성·응답 일관성에서 불리 |
| 비개발자가 클릭으로 데이터 정제 | Glue DataBrew | Glue ETL — 코드를 작성해야 한다 |
| 기존 Airflow DAG 를 그대로 옮겨 운영 | MWAA | Step Functions — DAG 를 다시 작성해야 한다 |
| S3 버킷에 주민번호 같은 민감정보가 섞였는지 점검 | Macie | Lake Formation — 권한 통제이지 탐지 도구가 아니다 |
| 분석가별로 볼 수 있는 컬럼을 다르게 | Lake Formation | IAM/S3 버킷 정책 — 객체 단위까지만 통제 |

다음 글에서는 이 파이프라인을 흐르는 데이터가 어떤 "형태"로 저장되는지 — CSV·JSON·Parquet·ORC·Avro와 컬럼형 vs 행형, 스키마 진화 — 를 본다.

## 📖 용어

- **수집(ingestion)** : 원천 시스템의 데이터를 AWS 안으로 들여오는 단계. 원천 종류에 따라 도구가 달라진다.
- **CDC(Change Data Capture)** : 데이터베이스의 변경 로그를 읽어 바뀐 행만 계속 복제하는 방식.
- **데이터 카탈로그** : 데이터가 어디에 있고 어떤 컬럼·포맷인지 적어 둔 설명서. 데이터 자체는 담지 않는다.
- **크롤러** : 저장소를 훑어 스키마와 파티션을 추론하고 카탈로그에 테이블로 등록해 주는 Glue 기능.
- **외부 테이블** : 데이터는 S3 에 두고 정의만 등록한 테이블. 테이블을 지워도 파일은 남는다.
- **파티션** : S3 경로를 날짜 같은 값으로 나눈 단위. 조건에 맞는 폴더만 읽게 해 스캔량을 줄인다.
- **서버리스** : 서버나 클러스터를 직접 띄우지 않고 쓴 만큼만 내는 방식. Athena·Glue·Lambda 가 해당한다.
- **오케스트레이션** : 여러 작업을 순서·조건·재시도 규칙에 맞춰 자동으로 이어 실행하는 것.
- **데이터 계보(lineage)** : 데이터가 어디서 와서 어떤 가공을 거쳐 어디로 갔는지의 이력.
- **애드혹(ad hoc) 쿼리** : 미리 정해 두지 않고 필요할 때 즉석에서 던지는 조회.

## 📝 연습 문제

**문제 1.** AWS 데이터 파이프라인을 이해하는 기본 골격인 4단계 흐름을 순서대로 올바르게 나열한 것은?

A) 분석 → 처리 → 저장 → 수집  
B) 수집 → 저장 → 처리 → 분석  
C) 저장 → 수집 → 분석 → 처리  
D) 처리 → 수집 → 분석 → 저장  

**정답: B**  
해설: 데이터는 원천에서 들여오는 수집(Kinesis/DMS 등) → 담아두는 저장(S3/Redshift) → 변환하는 처리(Glue/EMR) → 답을 얻는 분석(Athena/QuickSight)의 순서로 흐른다. 거버넌스(Lake Formation/IAM/KMS)는 이 전 구간을 가로질러 감싼다. 나머지 보기는 흐름의 순서가 뒤바뀌어 있다.

---

**문제 2.** 운영 중인 RDS 데이터베이스의 변경분(CDC)을 운영 부하 없이 지속적으로 분석 환경(S3/Redshift)으로 복제하려 한다. 가장 적합한 수집 서비스는?

A) AWS DataSync  
B) AWS DMS  
C) Kinesis Data Streams  
D) Amazon QuickSight  

**정답: B**  
해설: DMS는 데이터베이스 마이그레이션·복제 서비스로, CDC를 통해 트랜잭션 로그에서 변경분만 읽어 OLTP에 거의 부하를 주지 않고 분석 환경으로 흘려보낸다. DataSync는 온프렘 파일 전송, Kinesis는 실시간 이벤트 스트림, QuickSight는 BI 시각화 도구다.

---

**문제 3.** S3에 적재된 데이터를 별도 인프라 없이, 데이터를 옮기지 않고 그 자리에서 SQL로 애드혹 조회하며 스캔량만큼 과금받는 서비스는?

A) Amazon Redshift  
B) Amazon Athena  
C) Amazon EMR  
D) AWS Glue  

**정답: B**  
해설: Athena는 S3 위에서 동작하는 서버리스 SQL 쿼리 엔진으로, 데이터를 적재·이동하지 않고 그 자리에서 조회하며 스캔한 데이터량만큼 과금한다. Redshift는 데이터를 적재해야 하는 웨어하우스, EMR은 빅데이터 클러스터, Glue는 ETL 처리 엔진이다.

---

**문제 4.** 여러 분석 엔진(Athena, Redshift Spectrum, EMR)이 같은 데이터를 동일한 스키마 정의로 공유하도록 메타데이터를 중앙 관리하는 서비스는?

A) AWS Glue Data Catalog  
B) Amazon S3  
C) AWS KMS  
D) Amazon DynamoDB  

**정답: A**  
해설: Glue Data Catalog는 통합 메타데이터 카탈로그로, Crawler가 등록한 테이블 정의를 Athena·Redshift Spectrum·EMR 등이 공통으로 참조한다. S3는 데이터 저장소, KMS는 암호화 키 관리, DynamoDB는 NoSQL 데이터베이스다.

---

**문제 5.** IAM이 "버킷 접근 가능 여부"를 통제한다면, S3 데이터레이크에서 테이블·컬럼·행 단위의 세밀한 접근 권한을 중앙에서 부여하는 거버넌스 서비스는?

A) AWS KMS  
B) AWS Lake Formation  
C) Amazon OpenSearch  
D) AWS DataSync  

**정답: B**  
해설: Lake Formation은 데이터레이크에 테이블·컬럼·행 수준의 세밀한 권한을 중앙에서 부여하는 거버넌스 서비스다. IAM이 리소스(버킷) 단위 접근을 다룬다면 Lake Formation은 그 안의 데이터 단위를 통제한다. KMS는 암호화 키, OpenSearch는 검색 분석, DataSync는 파일 전송 도구다.
