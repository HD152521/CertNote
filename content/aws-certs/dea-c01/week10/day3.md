# Day 3 - 전체 모의고사 페이스: 4개 도메인 종합 시나리오

오늘은 실전 모드입니다. 4개 도메인이 섞인 종합 시나리오 8문항을 풀며 **시험 페이스**를 체감합니다. 실제 시험은 65문항/130분이므로 한 문항당 약 2분입니다. 오늘 8문항을 16분 안에 푸는 것을 목표로 하고, 푼 뒤 해설로 사고 과정을 점검하세요. 핵심은 정답을 맞히는 것보다 "요구사항 키워드 → 서비스 매핑" 반사신경을 다듬는 것입니다.

## 시나리오 풀이 전략

긴 문제는 다음 순서로 분해합니다.

1. **마지막 문장(질문)**을 먼저 읽어 "무엇을 묻는지" 파악.
2. 본문에서 **제약 키워드** 추출: 서버리스/최소 운영, 실시간/배치, 비용 최소, 최소 코드, 보안·암호화.
3. 보기에서 **명백한 오답 2개**를 먼저 제거(서비스 목적 불일치).
4. 남은 2개 중 **제약을 가장 잘 만족**하는 것을 선택.

> 💡 **관련 이론**: 대부분의 오답은 "기술적으로 가능은 하지만 운영 부담·비용·실시간성에서 요구사항을 위반"합니다. "할 수 있다"가 아니라 "가장 적합하다"를 고르는 것이 Associate 시험의 핵심입니다.

## 자주 등장하는 종합 패턴

| 시나리오 신호 | 전형적 정답 조합 |
|--------------|-----------------|
| 실시간 클릭스트림 → 무관리 적재 → SQL 분석 | Kinesis Firehose → S3 → Athena |
| 매시간 증분 ETL → DW 적재 | Glue(북마크) → Redshift |
| DB 변경분 실시간 복제 | DMS(CDC) → S3/Redshift |
| 이기종 단계 조율 + 재시도 | Step Functions |
| 민감정보 탐지 + 컬럼 접근 통제 | Macie + Lake Formation |

## 핵심 정리

- 한 문항 약 2분 페이스를 몸에 익힌다.
- 질문부터 읽고 제약 키워드로 오답을 소거한다.
- "가능"이 아니라 "가장 적합/최소 운영/최저 비용"을 고른다.
- 도메인이 섞여도 결국 키워드→서비스 매핑이 승부를 가른다.

## 📝 연습 문제

**문제 1.** 모바일 앱의 클릭스트림을 실시간으로 받아 추가 서버 관리 없이 S3에 Parquet로 적재하고, 분석가가 즉석 SQL로 조회해야 한다. 가장 적합한 조합은?

A) Kinesis Data Firehose → S3(Parquet) → Athena  
B) RDS → EC2 cron → 수동 CSV 다운로드  
C) DynamoDB → DAX → QuickSight 직접  
D) EMR 상시 클러스터 → HDFS → 로컬 Presto  

**정답: A**  
해설: Firehose는 완전관리형으로 스트리밍을 버퍼링·Parquet 변환 후 S3에 적재하고, Athena는 서버리스 SQL로 즉석 조회합니다. RDS·EC2·EMR 상시 클러스터는 운영 부담이 크고 실시간 적재에 부적합하며, DynamoDB는 분석 SQL 용도가 아닙니다.

**문제 2.** 온프레미스 PostgreSQL의 변경분을 거의 실시간으로 AWS 분석 환경에 지속 복제해야 한다. 초기 전체 적재 후 지속적인 CDC가 필요하다. 가장 적합한 서비스는?

A) AWS Glue 크롤러  
B) AWS DMS(전체 적재 + CDC)  
C) S3 배치 업로드 스크립트  
D) Amazon Athena 페더레이션 쿼리만  

**정답: B**  
해설: AWS DMS는 초기 전체 적재(full load)에 이어 변경 데이터 캡처(CDC)로 소스 DB 변경분을 지속 복제할 수 있습니다. Glue 크롤러는 스키마 추론, S3 배치는 실시간 CDC가 아니며, 페더레이션 쿼리는 복제가 아니라 즉석 조회입니다.

**문제 3.** 여러 Lambda·Glue 잡을 순서대로 실행하되, 단계별 분기와 자동 재시도, 시각적 실행 추적이 필요하다. 서버리스로 운영 부담을 최소화하려 한다. 가장 적합한 서비스는?

A) AWS Step Functions  
B) cron이 설정된 단일 EC2  
C) S3 이벤트 알림만  
D) DynamoDB 스트림 트리거 하나  

**정답: A**  
해설: Step Functions는 서버리스 상태 기계로 단계 조율, 분기, 자동 재시도, 시각적 실행 추적을 제공합니다. EC2 cron은 운영 부담이 크고, S3 이벤트·DynamoDB 스트림 단독으로는 다단계 분기·재시도 오케스트레이션을 구성하기 어렵습니다.

---

**문제 4.** 데이터레이크의 여러 부서가 같은 테이블을 쓰는데, 인사팀만 급여 컬럼을 볼 수 있고 다른 팀은 마스킹되어야 한다. 권한을 중앙에서 컬럼 단위로 통제하려 한다. 가장 적합한 서비스는?

A) S3 버킷 ACL  
B) AWS Lake Formation 컬럼 수준 권한  
C) Security Group 규칙  
D) CloudFront 지오 제한  

**정답: B**  
해설: Lake Formation은 테이블·컬럼·행·셀 수준 권한을 중앙에서 관리하므로 컬럼 단위 접근 통제에 적합합니다. S3 ACL은 객체 수준까지만, Security Group은 네트워크, CloudFront 지오 제한은 콘텐츠 배포용으로 데이터 컬럼 통제와 무관합니다.

---

**문제 5.** Redshift 대시보드 쿼리가 최근 30일 데이터에만 자주 접근하고, 1년 이전 콜드 데이터는 가끔만 조회된다. 비용을 줄이면서 콜드 데이터도 필요 시 SQL로 조회하려 한다. 가장 적합한 접근은?

A) 모든 데이터를 Redshift 노드에 영구 보관  
B) 콜드 데이터를 삭제한다  
C) 콜드 데이터는 S3에 두고 Redshift Spectrum으로 조회  
D) 콜드 데이터를 DynamoDB로 옮긴다  

**정답: C**  
해설: 핫 데이터는 Redshift 클러스터에, 콜드 데이터는 저렴한 S3에 두고 Redshift Spectrum으로 로드 없이 SQL 조회하면 스토리지 비용을 줄이면서 접근성을 유지합니다. 전량 보관은 비용 증가, 삭제는 조회 불가, DynamoDB는 분석 SQL에 부적합합니다.

**문제 6.** Glue ETL 잡이 가끔 실패해 재실행되는데, 동일 데이터가 타깃에 중복 적재되는 문제가 있다. 재시도 시 안전하게 만들려면 가장 우선해야 할 설계 원칙은?

A) 잡 재시도를 완전히 비활성화한다  
B) 로그 레벨을 낮춘다  
C) 잡을 멱등(idempotent)하게 설계해 재실행해도 중복이 생기지 않게 한다  
D) 매번 타깃 테이블을 수동으로 비운다  

**정답: C**  
해설: 분산·재시도 환경에서는 잡을 멱등하게 설계(예: 업서트/MERGE, 결정적 키 기반 덮어쓰기)해 재실행해도 결과가 동일하도록 해야 합니다. 재시도 비활성화는 복원력을 해치고, 수동 정리·로그 조정은 근본 해결이 아닙니다.

**문제 7.** 매시간 S3 raw 존에 도착하는 신규 로그만 처리해 curated 존(Parquet)으로 변환하는 서버리스 ETL을 구성한다. 이미 처리한 파일은 다시 읽지 않아야 한다. 가장 적합한 조합은?

A) Glue 잡 + 잡 북마크  
B) EMR 상시 클러스터 + 전체 재처리  
C) Athena CTAS로 매번 전체 재생성  
D) Lambda로 전체 버킷을 매번 스캔  

**정답: A**  
해설: 서버리스 ETL은 Glue가 기본이며, 잡 북마크가 이미 처리한 데이터를 추적해 신규 데이터만 증분 처리합니다. EMR 상시 클러스터·전체 재처리·전체 스캔은 증분 요구와 비용·운영 효율을 위반합니다.

**문제 8.** 스트리밍 주문 이벤트를 받아 5분 윈도로 매장별 매출 합계를 실시간 집계해야 한다. SQL 기반으로 윈도 집계를 처리하려 한다. 가장 적합한 서비스는?

A) Amazon Athena 단발 쿼리  
B) AWS Glue 배치 잡  
C) Amazon QuickSight  
D) Amazon Managed Service for Apache Flink(Kinesis Data Analytics)  

**정답: D**  
해설: Managed Service for Apache Flink는 스트리밍 데이터에 대해 텀블링/슬라이딩 윈도 집계를 SQL/Flink로 실시간 처리합니다. Athena·Glue는 배치 지향이라 5분 윈도 실시간 집계에 부적합하고, QuickSight는 시각화 도구입니다.
