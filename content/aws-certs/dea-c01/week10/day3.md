# Day 3 - 전체 모의고사 페이스: 4개 도메인 종합 시나리오

## 📌 핵심 정리

- 실제 시험은 65문항 130분, 문항당 평균 2분이다. 오늘은 종합 시나리오 8문항을 16분 안에 푸는 것이 목표다.
- 질문(마지막 문장)부터 읽고, 제약 키워드를 뽑고, 목적이 어긋난 보기 2개를 지운 뒤, 남은 둘 중 제약을 더 잘 만족하는 쪽을 고른다.
- "가능한 답"이 아니라 "가장 적합한 답"을 고른다. 정답을 가르는 것은 대개 최소 운영·최저 비용·실시간 같은 한정어 하나다.
- 도메인이 섞여도 문장마다 묻는 칸(수집·저장·운영·보안)은 하나씩이다. 문장을 칸에 배정하면 키워드 → 서비스 매핑으로 돌아온다.
- 채점 뒤에는 틀린 이유를 분류한다. 지식 공백인지, 한정어를 놓쳤는지, 닮은 서비스를 혼동했는지에 따라 처방이 다르다.

## 65문항 130분을 숫자로 쪼개기

오늘은 실전 모드다. 4개 도메인이 섞인 종합 시나리오를 풀며 **시험 페이스**를 체감한다. 핵심은 정답을 맞히는 것보다 "요구사항 키워드 → 서비스 매핑" 반사신경을 다듬는 것이다. 먼저 시간을 숫자로 바꿔 둔다.

| 구간 | 배정 시간 | 문항당 | 중간 점검 |
|------|------|------|------|
| 1차 통과(65문항 전부 한 번씩) | 약 90분 | 약 83초 | 30분에 22번 근처, 60분에 43번 근처 |
| 2차 검토(표시한 문항) | 약 30분 | 표시 문항 수에 따라 | 15문항을 표시했다면 문항당 2분 |
| 3차 확인 | 약 10분 | — | 복수 응답 개수, 빈 답 |

- 평균 2분은 "모든 문항에 2분"이 아니다. 한 줄짜리 매핑 문항을 30~60초에 끝내야 긴 시나리오에 3분을 쓸 수 있다.
- 중간 점검 시각에 번호가 5문항 이상 뒤처져 있으면, 다음 구간에서는 막히는 문항에 잠정 답을 고르고 표시한 뒤 즉시 넘어간다.
- 65문항 가운데 채점되는 것은 50문항이고 15문항은 비채점이다. 어느 것이 비채점인지는 표시되지 않으므로 모든 문항을 같은 무게로 푼다.

도메인 비중을 채점 문항 50개에 곱하면 대략의 문항 수가 나온다. 비중은 "채점 문항 중 비율"이므로 근사치로만 본다.

| 도메인 | 비중 | 채점 50문항 중 근사 |
|------|------|------|
| 1. 수집·변환 | 34% | 17문항 |
| 2. 스토어 관리 | 26% | 13문항 |
| 3. 운영·지원 | 22% | 11문항 |
| 4. 보안·거버넌스 | 18% | 9문항 |

- 합격선 720점은 전체 점수에만 적용된다. 도메인별 합격선은 없으므로(보상 채점) 약한 도메인을 강한 도메인이 메울 수 있다. 그렇다고 30문항에 해당하는 도메인 1·2 를 흘리고 합격하기는 어렵다.

## 시나리오 풀이 전략

긴 문제는 다음 순서로 분해한다.

1. **마지막 문장(질문)** 을 먼저 읽어 "무엇을 묻는지" 파악.
2. 본문에서 **제약 키워드** 추출: 서버리스/최소 운영, 실시간/배치, 비용 최소, 최소 코드, 보안·암호화.
3. 보기에서 **명백한 오답 2개**를 먼저 제거(서비스 목적 불일치).
4. 남은 2개 중 **제약을 가장 잘 만족**하는 것을 선택.

> 💡 **관련 이론**: 대부분의 오답은 "기술적으로 가능은 하지만 운영 부담·비용·실시간성에서 요구사항을 위반"한다. "할 수 있다"가 아니라 "가장 적합하다"를 고르는 것이 Associate 시험의 핵심이다.

## 한정어가 지우는 보기

질문 문장의 한정어는 정답을 고르는 기준이기 전에 **보기를 지우는 도구**다. 한정어마다 먼저 탈락하는 보기의 모양이 정해져 있다.

| 한정어 | 먼저 지우는 보기 | 살아남는 쪽 |
|------|------|------|
| 운영 부담 최소 | EC2 에 직접 설치, 상시 클러스터, 직접 짠 컨슈머·스케줄러 | Firehose, Glue, Athena, Lambda, Step Functions |
| 비용 최소(간헐적 사용) | 종일 떠 있는 프로비저닝 자원 | 쓴 만큼 내는 서버리스, S3 계층화 |
| 비용 최소(상시·대량 사용) | 스캔량·요청 수 과금이 무한히 느는 구성 | 프로비저닝 용량, 포맷·파티션 최적화 |
| 실시간(초 이내) | 배치 스케줄, 버퍼가 큰 적재 | 스트림 + Flink/Lambda |
| 준실시간(분 단위 허용) | 직접 구현한 스트림 처리 | Firehose, 마이크로배치 |
| 코드 변경 최소 | 다른 엔진으로 재작성 | 호환 서비스(MSK, EMR, MWAA) |
| 기존 데이터 유지·무중단 | 덤프 후 복원, 일회성 복사 | DMS 전체 적재 + CDC |
| 최소 권한 | 와일드카드 정책, 장기 액세스 키 | 역할, 범위를 좁힌 정책, Lake Formation |

- "비용 최소"는 방향이 둘이다. 가끔 쓰면 서버리스가, 종일 쓰면 프로비저닝이 싸다. 지문의 사용 빈도 단서(가끔·임시·종일·수백 명)를 함께 읽어야 한다.

## 종합 패턴

| 시나리오 신호 | 전형적 정답 조합 |
|--------------|-----------------|
| 실시간 클릭스트림 → 무관리 적재 → SQL 분석 | Kinesis Firehose → S3 → Athena |
| 매시간 증분 ETL → DW 적재 | Glue(북마크) → Redshift |
| DB 변경분 실시간 복제 | DMS(CDC) → S3/Redshift |
| 이기종 단계 조율 + 재시도 | Step Functions |
| 민감정보 탐지 + 컬럼 접근 통제 | Macie + Lake Formation |

같은 패턴도 조건 하나가 더 붙으면 조합이 바뀐다. 종합 문항은 이 "한 칸 교체"를 묻는다.

| 기본 조합 | 추가된 조건 | 바뀌는 칸 |
|------|------|------|
| Firehose → S3 → Athena | 같은 이벤트를 다른 앱도 실시간으로 읽는다 | 앞에 Kinesis Data Streams 를 두고 Firehose 는 그 소비자가 된다 |
| Firehose → S3 → Athena | 키워드 검색과 초 단위 대시보드가 필요하다 | 목적지를 OpenSearch Service 로 |
| Glue(북마크) → Redshift | 원본 행이 수정·삭제된다 | 북마크 대신 DMS CDC |
| Glue(북마크) → Redshift | 수십 TB 를 기존 Hive 스크립트로 처리한다 | Glue 대신 EMR |
| DMS(CDC) → S3 | 5분 창으로 실시간 집계도 한다 | DMS → Kinesis Data Streams → Managed Service for Apache Flink |
| Step Functions 로 Glue 잡 연결 | 이미 Airflow DAG 수백 개가 있다 | MWAA |
| Athena 로 S3 조회 | 수백 명이 종일 같은 대시보드를 본다 | Redshift(콜드 데이터는 Spectrum) |
| Lake Formation 컬럼 권한 | 어디에 PII 가 있는지부터 모른다 | 앞에 Macie 를 둔다 |
| SSE-S3 | 키 사용을 감사하고 역할별로 복호화를 막는다 | SSE-KMS 고객 관리 키 |

## 풀이 시연: 네 단계를 실제로 밟아 보기

아래는 연습 문제와 겹치지 않는 지문 세 개를 네 단계로 분해한 것이다. 눈으로 읽지 말고 단계마다 가리고 먼저 답해 본다.

```text
지문 A) 유통사가 매장 POS 에서 발생하는 판매 이벤트를 수집한다. 재고 알림 앱과
        가격 분석 앱이 각각 독립적으로 이벤트를 읽어야 하고, 처리 로직에 버그가
        있으면 지난 3일치를 다시 처리해야 한다. 가장 적합한 수집 서비스는?

  ① 질문    → 수집 서비스 하나
  ② 키워드  → 독립적으로 읽는 소비자 둘 / 3일치 재처리
  ③ 소거    → SQS(한 메시지는 한 소비자, 재생 불가), Firehose(재처리 없음)
  ④ 선택    → Kinesis Data Streams + 보존 기간을 3일 이상으로 연장
              (기본 24시간으로는 "3일치"를 만족하지 못한다)
```

```text
지문 B) 분석팀이 매일 새벽 S3 의 전일 주문(CSV)을 Parquet 으로 바꿔 Redshift 에
        적재한다. 변환이 실패하면 적재를 건너뛰고 담당자에게 알려야 한다.
        서버를 운영하고 싶지 않다. 가장 운영 부담이 적은 구성은?

  ① 질문    → 운영 부담이 가장 적은 구성
  ② 키워드  → 매일 배치 / 순서(변환 → 적재) / 실패 시 알림 / 서버 없음
  ③ 소거    → EC2 cron(서버 운영, 앞 단계 성공 여부를 모른다),
              MWAA(상시 환경 비용, 기존 Airflow 자산 언급 없음)
  ④ 선택    → EventBridge 스케줄 → Step Functions 가 Glue 잡 → COPY 순서로 실행,
              Catch 에서 SNS 알림
```

```text
지문 C) 의료 데이터 레이크를 여러 연구팀이 Athena 로 조회한다. 환자 식별 컬럼은
        승인된 팀만 볼 수 있어야 하고, 누가 어떤 키로 데이터를 복호화했는지
        감사할 수 있어야 한다. 요구를 충족하는 조합은? (두 가지 선택)

  ① 질문    → 조합, 두 개
  ② 키워드  → 컬럼 단위 접근 통제 / 복호화 감사
  ③ 소거    → S3 버킷 정책(컬럼을 가리지 못한다), SSE-S3(키 사용 감사 불가),
              GuardDuty(위협 탐지)
  ④ 선택    → Lake Formation 컬럼 권한 + SSE-KMS 고객 관리 키(CloudTrail 로 키 사용 기록)
```

- 지문 A 의 교훈: 정답 서비스를 맞혀도 **기본값이 요구를 채우지 못하면** 보기에 설정이 함께 붙어 있다. "보존 기간 연장"처럼 설정까지 포함한 보기를 고른다.
- 지문 C 의 교훈: 복수 응답은 요구 두 개에 정답 두 개가 하나씩 대응하는 경우가 많다. 요구를 먼저 세고 보기에 배정한다.

## 도메인이 섞인 문항 읽는 법

종합 시나리오는 길어 보이지만 문장 하나가 묻는 칸은 하나다. 문장마다 칸을 적어 넣으면 네 개의 짧은 문제로 바뀐다.

| 지문의 문장 | 칸 | 좁혀지는 후보 |
|------|------|------|
| "초당 수천 건의 센서 이벤트가 들어온다" | 수집(도메인 1) | Kinesis Data Streams, Firehose, MSK |
| "S3 에 Parquet 으로 저장하고 날짜별로 조회한다" | 저장(도메인 2) | 날짜 파티션, Glue Data Catalog, Athena |
| "적재가 한 시간 넘게 멈추면 알림을 받아야 한다" | 운영(도메인 3) | CloudWatch 알람, SNS |
| "장비 위치 컬럼은 운영팀만 볼 수 있다" | 보안(도메인 4) | Lake Formation 컬럼 권한 |

- 질문 문장이 네 칸 가운데 **어느 칸을 묻는지** 확인한다. 나머지 세 칸은 보기를 지우는 배경일 뿐이다. 질문이 "알림"을 묻는데 수집 서비스가 그럴듯한 보기를 고르는 실수가 가장 흔하다.
- 보기가 모두 여러 서비스의 조합이면, 조합에서 **서로 다른 칸만** 비교한다. 네 보기 모두 S3 를 쓴다면 S3 는 판단 재료가 아니다.

## 문항 유형별 목표 시간

| 유형 | 생김새 | 목표 시간 | 푸는 법 |
|------|------|------|------|
| 단순 매핑 | 한두 문장, "가장 적합한 서비스는?" | 30~60초 | 키워드 하나로 결정 |
| 닮은 서비스 비교 | 보기에 같은 범주 서비스가 둘 이상 | 1~2분 | 구분 축 하나(재처리 여부, 운영 주체 등)로 가른다 |
| 장애 진단 | "이런 증상이 나타난다. 원인/조치는?" | 2분 | 증상 → 원인 → 조치 순으로 역추적. 서비스에 없는 조절 수단을 말하는 보기부터 지운다 |
| 설계 조합 | 긴 지문, 보기가 여러 서비스의 조합 | 2~3분 | 문장을 칸에 배정하고 다른 칸만 비교 |
| 복수 응답 | "두 가지/세 가지를 고르시오" | 2~3분 | 요구 개수를 세고 보기를 하나씩 참·거짓 판정 |

## 채점 후 복기: 틀린 이유를 다섯 가지로 나눈다

오늘 8문항을 채점한 뒤 틀린 문항을 "다시 읽어 본다"로 끝내면 같은 실수가 시험장에서 반복된다. 이유를 분류해야 처방이 나온다.

| 틀린 이유 | 판별 질문 | 처방 |
|------|------|------|
| 지식 공백 | 해설을 봐도 그 기능을 처음 듣는가 | 해당 주차 본문으로 되돌아간다 |
| 한정어 놓침 | 고른 답이 기능상 가능하긴 했는가 | 질문 문장을 먼저 읽는 순서를 지킨다 |
| 닮은 서비스 혼동 | 정답과 내 답이 같은 범주의 짝이었는가 | Day 4 의 서비스 쌍 표에서 구분 축을 한 단어로 말해 본다 |
| 과잉 설계 선택 | 더 강력한 서비스를 골랐는가 | "단순 적재에 Flink", "가끔 조회에 Redshift"를 의심한다 |
| 시간 압박 | 시간이 남았다면 맞혔을 문항인가 | 중간 점검 시각을 정하고 표시 후 넘기는 연습을 한다 |

- 맞힌 문항도 "나머지 보기 세 개가 왜 틀렸는지"를 한 줄씩 말해 본다. 소거 근거를 댈 수 없는 정답은 다음에 틀린다.
- 16분을 넘겼다면 어느 유형에서 시간을 썼는지 표의 목표 시간과 비교한다. 대개 단순 매핑 문항에서 시간을 아끼지 못한 것이 원인이다.

내일은 시험 직전에 볼 "요구사항 → 서비스" 번역표와 자주 틀리는 함정을 정리한다.

## 📖 용어

- **한정어** : "운영 부담 최소", "가장 비용 효율적" 같은 질문 문장의 조건. 살아남은 보기 가운데 하나를 가른다.
- **소거법** : 목적이 어긋나거나 조건을 어기는 보기를 먼저 지워 정답을 남기는 풀이법.
- **검토 표시(flag)** : 나중에 다시 보려고 문항에 붙여 두는 표시. 잠정 답을 고른 뒤에 붙인다.
- **비채점 문항** : 점수에 반영되지 않고 향후 출제를 위해 통계만 수집하는 문항. 어느 문항인지는 알 수 없다.
- **보상 채점** : 도메인별 합격선 없이 전체 점수로만 합격을 가르는 방식. 약한 영역을 강한 영역이 메울 수 있다.
- **과잉 설계** : 요구보다 강력하고 복잡한 서비스를 고르는 것. 기능은 되지만 운영 부담·비용 조건을 어긴다.
- **종합 패턴** : 수집·저장·운영·보안 칸을 채운 전형적인 서비스 조합. 조건이 하나 바뀌면 한 칸이 교체된다.

## 📝 연습 문제

**문제 1.** 모바일 앱의 클릭스트림을 실시간으로 받아 추가 서버 관리 없이 S3에 Parquet로 적재하고, 분석가가 즉석 SQL로 조회해야 한다. 가장 적합한 조합은?

A) Kinesis Data Firehose → S3(Parquet) → Athena  
B) RDS → EC2 cron → 수동 CSV 다운로드  
C) DynamoDB → DAX → QuickSight 직접  
D) EMR 상시 클러스터 → HDFS → 로컬 Presto  

**정답: A**  
해설: Firehose는 완전관리형으로 스트리밍을 버퍼링·Parquet 변환 후 S3에 적재하고, Athena는 서버리스 SQL로 즉석 조회한다. RDS·EC2·EMR 상시 클러스터는 운영 부담이 크고 실시간 적재에 부적합하며, DynamoDB는 분석 SQL 용도가 아니다.

**문제 2.** 온프레미스 PostgreSQL의 변경분을 거의 실시간으로 AWS 분석 환경에 지속 복제해야 한다. 초기 전체 적재 후 지속적인 CDC가 필요하다. 가장 적합한 서비스는?

A) AWS Glue 크롤러  
B) AWS DMS(전체 적재 + CDC)  
C) S3 배치 업로드 스크립트  
D) Amazon Athena 페더레이션 쿼리만  

**정답: B**  
해설: AWS DMS는 초기 전체 적재(full load)에 이어 변경 데이터 캡처(CDC)로 소스 DB 변경분을 지속 복제할 수 있다. Glue 크롤러는 스키마 추론, S3 배치는 실시간 CDC가 아니며, 페더레이션 쿼리는 복제가 아니라 즉석 조회이다.

---

**문제 3.** 여러 Lambda·Glue 잡을 순서대로 실행하되, 단계별 분기와 자동 재시도, 시각적 실행 추적이 필요하다. 서버리스로 운영 부담을 최소화하려 한다. 가장 적합한 서비스는?

A) AWS Step Functions  
B) cron이 설정된 단일 EC2  
C) S3 이벤트 알림만  
D) DynamoDB 스트림 트리거 하나  

**정답: A**  
해설: Step Functions는 서버리스 상태 기계로 단계 조율, 분기, 자동 재시도, 시각적 실행 추적을 제공한다. EC2 cron은 운영 부담이 크고, S3 이벤트·DynamoDB 스트림 단독으로는 다단계 분기·재시도 오케스트레이션을 구성하기 어렵다.

---

**문제 4.** 데이터레이크의 여러 부서가 같은 테이블을 쓰는데, 인사팀만 급여 컬럼을 볼 수 있고 다른 팀은 마스킹되어야 한다. 권한을 중앙에서 컬럼 단위로 통제하려 한다. 가장 적합한 서비스는?

A) S3 버킷 ACL  
B) AWS Lake Formation 컬럼 수준 권한  
C) Security Group 규칙  
D) CloudFront 지오 제한  

**정답: B**  
해설: Lake Formation은 테이블·컬럼·행·셀 수준 권한을 중앙에서 관리하므로 컬럼 단위 접근 통제에 적합하다. S3 ACL은 객체 수준까지만, Security Group은 네트워크, CloudFront 지오 제한은 콘텐츠 배포용으로 데이터 컬럼 통제와 무관하다.

---

**문제 5.** Redshift 대시보드 쿼리가 최근 30일 데이터에만 자주 접근하고, 1년 이전 콜드 데이터는 가끔만 조회된다. 비용을 줄이면서 콜드 데이터도 필요 시 SQL로 조회하려 한다. 가장 적합한 접근은?

A) 모든 데이터를 Redshift 노드에 영구 보관  
B) 콜드 데이터를 삭제한다  
C) 콜드 데이터는 S3에 두고 Redshift Spectrum으로 조회  
D) 콜드 데이터를 DynamoDB로 옮긴다  

**정답: C**  
해설: 핫 데이터는 Redshift 클러스터에, 콜드 데이터는 저렴한 S3에 두고 Redshift Spectrum으로 로드 없이 SQL 조회하면 스토리지 비용을 줄이면서 접근성을 유지한다. 전량 보관은 비용 증가, 삭제는 조회 불가, DynamoDB는 분석 SQL에 부적합하다.

**문제 6.** Glue ETL 잡이 가끔 실패해 재실행되는데, 동일 데이터가 타깃에 중복 적재되는 문제가 있다. 재시도 시 안전하게 만들려면 가장 우선해야 할 설계 원칙은?

A) 잡 재시도를 완전히 비활성화한다  
B) 로그 레벨을 낮춘다  
C) 잡을 멱등(idempotent)하게 설계해 재실행해도 중복이 생기지 않게 한다  
D) 매번 타깃 테이블을 수동으로 비운다  

**정답: C**  
해설: 분산·재시도 환경에서는 잡을 멱등하게 설계(예: 업서트/MERGE, 결정적 키 기반 덮어쓰기)해 재실행해도 결과가 동일하도록 해야 한다. 재시도 비활성화는 복원력을 해치고, 수동 정리·로그 조정은 근본 해결이 아니다.

**문제 7.** 매시간 S3 raw 존에 도착하는 신규 로그만 처리해 curated 존(Parquet)으로 변환하는 서버리스 ETL을 구성한다. 이미 처리한 파일은 다시 읽지 않아야 한다. 가장 적합한 조합은?

A) Glue 잡 + 잡 북마크  
B) EMR 상시 클러스터 + 전체 재처리  
C) Athena CTAS로 매번 전체 재생성  
D) Lambda로 전체 버킷을 매번 스캔  

**정답: A**  
해설: 서버리스 ETL은 Glue가 기본이며, 잡 북마크가 이미 처리한 데이터를 추적해 신규 데이터만 증분 처리한다. EMR 상시 클러스터·전체 재처리·전체 스캔은 증분 요구와 비용·운영 효율을 위반한다.

**문제 8.** 스트리밍 주문 이벤트를 받아 5분 윈도로 매장별 매출 합계를 실시간 집계해야 한다. SQL 기반으로 윈도 집계를 처리하려 한다. 가장 적합한 서비스는?

A) Amazon Athena 단발 쿼리  
B) AWS Glue 배치 잡  
C) Amazon QuickSight  
D) Amazon Managed Service for Apache Flink(Kinesis Data Analytics)  

**정답: D**  
해설: Managed Service for Apache Flink는 스트리밍 데이터에 대해 텀블링/슬라이딩 윈도 집계를 SQL/Flink로 실시간 처리한다. Athena·Glue는 배치 지향이라 5분 윈도 실시간 집계에 부적합하고, QuickSight는 시각화 도구이다.
