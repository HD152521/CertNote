# Day 4 - 데이터 저장·접근 최적화: Pipe vs File mode, FSx for Lustre, 분산 학습

데이터를 잘 준비해도, 학습 작업이 그 데이터를 **느리게 읽으면** GPU는 데이터를 기다리며 놀게 된다. 비싼 GPU 인스턴스가 I/O 병목 때문에 유휴 상태가 되는 것은 실무에서 가장 흔하고 값비싼 낭비다. 그래서 "데이터를 어떤 방식으로 학습 컨테이너에 흘려보내는가"는 성능과 비용에 직결된다.

오늘은 SageMaker의 **입력 모드(Pipe vs File vs FastFile)**, 고성능 파일 시스템 **FSx for Lustre**, 그리고 분산 학습을 위한 **데이터 샤딩** 개념을 다룬다.

## SageMaker 입력 모드

SageMaker 학습 작업이 S3의 데이터를 컨테이너로 가져오는 방식에는 여러 모드가 있다.

### File mode (기본)

학습이 시작되기 전에 **S3의 데이터 전체를 컨테이너의 EBS 볼륨으로 먼저 다운로드**한 뒤 학습을 시작한다.

- 장점: 단순하고 안정적. 데이터를 로컬 파일처럼 다룬다. 여러 epoch 반복 읽기에 유리.
- 단점: 데이터가 크면 **다운로드 완료까지 학습이 시작되지 못한다**(시작 지연). EBS 용량도 데이터셋 크기 이상이어야 한다.

### Pipe mode

데이터를 미리 다운로드하지 않고, S3에서 **스트리밍으로 직접 흘려보내며** 학습한다.

- 장점: 다운로드 대기가 없어 **학습이 즉시 시작**된다. 디스크 용량 제약에서 자유롭고, 데이터셋이 디스크보다 커도 된다. 대규모 데이터에서 처리량(throughput)이 높다.
- 단점: 데이터를 순차 스트림으로 받으므로 임의 접근(random access)이 어렵고, 보통 RecordIO/protobuf 등 특정 포맷이 필요하다.

> 💡 **관련 이론**: File mode는 "다 받아 놓고 시작", Pipe mode는 "받으면서 학습"이다. 핵심 트레이드오프는 **시작 지연 vs 임의 접근 유연성**이다. 데이터셋이 수백 GB~TB로 크고 시작 지연·디스크 비용이 부담이면 Pipe mode가, 데이터가 작고 여러 번 자유롭게 읽어야 하면 File mode가 유리하다.

### FastFile mode

비교적 최신 모드로, **File mode의 사용 편의성(POSIX 파일처럼 접근)과 Pipe mode의 즉시 시작**을 절충한다. 파일을 필요할 때 스트리밍으로 가져오되 로컬 파일처럼 다룬다. 전체 다운로드를 기다리지 않으면서 임의 접근도 가능해, 큰 데이터셋에서 자주 권장된다.

```python
# SageMaker Estimator에서 입력 모드 지정 (개념 예시)
from sagemaker.estimator import Estimator
from sagemaker.inputs import TrainingInput

estimator = Estimator(
    image_uri=image,
    role=role,
    instance_count=1,
    instance_type="ml.p3.2xlarge",
    input_mode="Pipe",   # "File" | "Pipe" | "FastFile"
)

train_input = TrainingInput(
    s3_data="s3://ml-train/clicks/",
    input_mode="FastFile",   # 입력별로 모드 재지정도 가능
)
estimator.fit({"train": train_input})
```

> ⚠️ **함정**: "무조건 Pipe mode가 빠르다"는 단순화는 위험하다. Pipe mode는 순차 스트림이라 임의 접근·셔플이 까다롭고 특정 포맷을 요구한다. 작은 데이터셋이거나 임의 접근이 필요하면 오히려 File/FastFile이 적합하다. 데이터 크기·접근 패턴·포맷을 함께 고려해야 한다.

## FSx for Lustre — 초고성능 학습 파일 시스템

대규모·반복 학습에서 S3 직접 접근의 지연을 더 줄이고 싶을 때 **Amazon FSx for Lustre**를 쓴다. Lustre는 HPC(고성능 컴퓨팅)용 병렬 파일 시스템으로, **수백 GB/s급 처리량과 밀리초 이하 지연**을 제공한다.

핵심 특징:
- **S3와 연동**: FSx for Lustre를 S3 버킷에 연결하면 데이터를 자동으로 로드·동기화한다. S3가 영구 저장소, FSx가 고속 캐시·작업 공간 역할.
- **반복 학습에 강함**: 같은 데이터를 여러 epoch·여러 작업에서 반복 읽을 때, 매번 S3에서 가져오는 대신 FSx에서 빠르게 읽는다.
- **분산 학습 공유 스토리지**: 여러 학습 노드가 같은 파일 시스템을 동시에 고속으로 읽는다.

> 💡 **관련 이론**: FSx for Lustre가 빛나는 전형적 상황은 (1) 데이터셋이 크고 (2) 여러 학습 작업·여러 epoch에서 **반복적으로** 읽으며 (3) 낮은 지연이 중요한 경우다. 단발성·소규모 학습이라면 S3 직접 접근(File/FastFile)으로 충분하고, FSx의 추가 비용·설정이 정당화되지 않는다.

| 옵션 | 특징 | 적합 상황 |
|------|------|----------|
| File mode | 전체 다운로드 후 시작 | 작은 데이터, 반복 읽기, 단순함 우선 |
| Pipe mode | S3 스트리밍, 즉시 시작 | 매우 큰 데이터, 순차 처리, 디스크 절약 |
| FastFile mode | 스트리밍 + POSIX 접근 | 큰 데이터 + 임의 접근 편의 |
| FSx for Lustre | 초고속 병렬 FS, S3 연동 | 대규모 + 반복 + 저지연 + 분산 |

## 데이터 샤딩과 분산 학습

데이터나 모델이 한 대의 머신으로 감당 안 될 만큼 크면 **분산 학습**을 한다. 이때 데이터를 여러 노드에 어떻게 나눠 줄지가 핵심이다.

### 데이터 병렬 vs 모델 병렬

- **데이터 병렬(data parallelism)**: 모델 복제본을 여러 GPU/노드에 두고, **데이터를 쪼개(shard)** 각자 다른 배치를 학습한 뒤 그래디언트를 동기화한다. 가장 흔한 방식.
- **모델 병렬(model parallelism)**: 모델 자체가 한 GPU 메모리에 안 들어갈 때, **모델을 여러 GPU에 나눠** 올린다(거대 언어 모델 등).

### 샤딩(ShardedByS3Key)

데이터 병렬 학습에서 각 노드가 **데이터셋의 서로 다른 부분만** 읽게 하는 것이 효율적이다. SageMaker는 `S3DataDistributionType`으로 이를 제어한다.

- **FullyReplicated(기본)**: 모든 인스턴스가 전체 데이터를 받는다.
- **ShardedByS3Key**: S3 객체(파일)들을 인스턴스 수만큼 나눠 각 인스턴스가 **자기 몫만** 받는다. 데이터 병렬 학습에서 중복 다운로드·중복 처리를 막아 효율을 높인다.

```python
# 분산 데이터 병렬 학습에서 샤딩 지정 (개념 예시)
train_input = TrainingInput(
    s3_data="s3://ml-train/clicks/",
    distribution="ShardedByS3Key",   # 각 인스턴스가 데이터의 일부만 받음
)
estimator = Estimator(
    image_uri=image, role=role,
    instance_count=4,                # 4개 노드로 분산
    instance_type="ml.p3.16xlarge",
)
estimator.fit({"train": train_input})
```

> 💡 **관련 이론**: ShardedByS3Key가 효과를 보려면 데이터가 **여러 개의 S3 객체(파일)**로 나뉘어 있어야 한다. 거대한 단일 파일 하나라면 객체 단위로 쪼갤 수 없어 샤딩 효과가 없다. 그래서 대규모 데이터는 적당한 크기의 여러 파일(예: 수백 개의 Parquet/RecordIO 샤드)로 미리 분할해 두는 것이 분산 학습 친화적이다.

> 🎯 **시나리오**: "수 TB 학습 데이터를 8개 GPU 노드로 데이터 병렬 학습한다. 각 노드가 전체 데이터를 다 받아 시작이 너무 느리다." → 데이터를 여러 파일로 분할하고 `ShardedByS3Key`로 각 노드가 자기 몫만 받게 하면 다운로드·처리 중복이 사라진다. 반복 읽기가 많다면 FSx for Lustre를 공유 스토리지로 붙여 지연을 더 줄인다.

## 정리하며

오늘은 데이터를 학습에 효율적으로 공급하는 방법을 배웠다. **File mode는 전체 다운로드 후 시작(작은 데이터·단순함), Pipe mode는 스트리밍 즉시 시작(매우 큰 데이터·순차), FastFile mode는 둘의 절충(스트리밍+POSIX 접근)**이다. 대규모·반복·저지연·분산 학습에는 **FSx for Lustre**가 S3와 연동된 고속 캐시로 강력하다. 분산 데이터 병렬 학습에서는 데이터를 여러 파일로 나누고 **ShardedByS3Key**로 각 노드에 분배해 중복을 없앤다. 핵심은 비싼 GPU가 I/O를 기다리며 놀지 않게 하는 것이다.

## 📝 연습 문제

**문제 1.** 수백 GB의 학습 데이터를 사용하는데, 학습 시작 전 전체 다운로드 대기 시간과 EBS 디스크 비용을 줄이고 싶다. 임의 접근은 크게 필요 없다. 가장 적합한 입력 모드는?

A) Pipe mode  
B) File mode  
C) 로컬 노트북 업로드  
D) DynamoDB 직접 읽기  

**정답: A**  
해설: Pipe mode는 S3에서 데이터를 스트리밍으로 흘려보내 다운로드 대기 없이 즉시 학습을 시작하고 디스크 용량 제약에서 자유로우므로, 매우 큰 데이터를 순차 처리할 때 적합하다. File mode(A)는 전체 다운로드를 기다려 시작 지연·디스크 비용이 크고, C·D는 대규모 학습 데이터 공급 방식으로 부적절하다.

---

**문제 2.** File mode의 POSIX 파일 접근 편의성과 Pipe mode의 즉시 시작 장점을 절충하여, 큰 데이터셋을 스트리밍하면서도 로컬 파일처럼 임의 접근하려는 경우 적합한 모드는?

A) File mode  
B) Pipe mode  
C) FastFile mode  
D) Batch mode  

**정답: C**  
해설: FastFile mode는 파일을 필요할 때 스트리밍으로 가져오되 로컬 파일처럼 POSIX 접근이 가능해, 전체 다운로드를 기다리지 않으면서 임의 접근도 지원하므로 큰 데이터셋에 자주 권장된다. File(A)은 전체 다운로드가 필요하고 Pipe(B)는 임의 접근이 어려우며, Batch mode(D)는 SageMaker 학습 입력 모드가 아니다.

---

**문제 3.** Amazon FSx for Lustre가 학습 데이터 접근에 특히 유리한 상황으로 가장 옳은 것은?

A) 한 번만 읽는 소규모 단발성 학습  
B) 텍스트 한 줄을 읽는 단순 함수  
C) 데이터를 전혀 읽지 않는 추론  
D) 대규모 데이터를 여러 epoch·여러 작업에서 반복 읽으며 저지연이 중요한 분산 학습  

**정답: D**  
해설: FSx for Lustre는 수백 GB/s급 처리량과 밀리초 이하 지연의 병렬 파일 시스템으로, 대규모 데이터를 반복적으로 읽고 여러 노드가 공유하며 저지연이 중요한 분산 학습에서 가치를 발한다. 단발성·소규모 학습(A)은 S3 직접 접근으로 충분하고, C·D는 데이터 접근 자체가 미미해 FSx가 정당화되지 않는다.

**문제 4.** 4개 노드로 데이터 병렬 학습을 하면서 각 노드가 전체 데이터를 중복 다운로드하지 않고 자기 몫만 받게 하려면 SageMaker에서 사용하는 분배 설정은?

A) FullyReplicated  
B) ShardedByS3Key  
C) FileMode only  
D) SingleRecord  

**정답: B**  
해설: ShardedByS3Key는 S3 객체들을 인스턴스 수만큼 나눠 각 인스턴스가 데이터의 일부만 받게 하므로, 데이터 병렬 학습에서 중복 다운로드·중복 처리를 막는다. FullyReplicated(A)는 모든 인스턴스가 전체 데이터를 받아 중복이 발생하고, C·D는 데이터 분배 방식과 무관하다.

**문제 5.** ShardedByS3Key 샤딩이 실제로 효과를 내기 위한 전제 조건으로 가장 옳은 것은?

A) 데이터가 하나의 거대한 단일 파일이어야 한다  
B) 데이터가 여러 개의 S3 객체(파일)로 분할되어 있어야 한다  
C) 모델 병렬만 사용해야 한다  
D) 입력 모드가 반드시 File mode여야 한다  

**정답: B**  
해설: ShardedByS3Key는 S3 객체 단위로 나누므로, 데이터가 여러 파일로 분할되어 있어야 인스턴스별로 분배되어 효과를 낸다. 단일 거대 파일(A)은 객체 단위로 쪼갤 수 없어 샤딩 효과가 없다. 샤딩은 데이터 병렬에서 쓰이므로 모델 병렬 전용(C)이 아니고, 특정 입력 모드(D)에 종속되지도 않는다.
