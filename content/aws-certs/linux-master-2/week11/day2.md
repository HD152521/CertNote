# Day 2 - 가상화

## 📌 핵심 정리

- 가상화는 **한 대의 물리 컴퓨터에서 여러 운영체제를 동시에** 돌리는 기술이다.
- **전가상화는 게스트 OS를 고치지 않아도 되고**, **반가상화는 게스트 OS를 수정해야** 한다.
- 하이퍼바이저는 둘로 나뉜다 — **Type 1(하드웨어 위에 바로)** 과 **Type 2(운영체제 위에)**.
- **VirtualBox는 오라클의 Type 2 제품**이며 **GPL** 로 공개되어 있고 **전가상화**를 쓴다.
- **VirtualBox는 VMware의 VMDK와 마이크로소프트의 VHD 이미지를 지원**한다.

## 가상화란

![가상화가 없을 때와 하이퍼바이저를 둘 때의 구조 비교](/diagrams/virtualization-compare.svg)

- **하이퍼바이저(hypervisor)** 가 하드웨어를 나눠 각 가상 머신에 배분한다.
- 물리 컴퓨터를 **호스트**, 그 위의 가상 컴퓨터를 **게스트**라 한다.
- 하이퍼바이저는 **VMM**(Virtual Machine Monitor, 가상 머신 모니터)이라고도 부른다. 같은 것의 다른 이름이다.

| 이름 | 가리키는 것 | 예 |
|------|-----------|-----|
| **호스트 OS** | 물리 컴퓨터에 **직접 설치된** 운영체제 | 내 노트북의 윈도 |
| **게스트 OS** | 가상 머신 **안에** 설치한 운영체제 | 그 안에 설치한 리눅스 |
| **가상 머신(VM)** | 하이퍼바이저가 만들어 준 **가짜 하드웨어 한 벌** | CPU 2개·메모리 4GB·디스크 20GB짜리 한 대 |
| **디스크 이미지** | 게스트의 하드디스크 노릇을 하는 **호스트의 파일 하나** | `rocky9.vdi` |

- 게스트의 디스크는 결국 **호스트에 있는 파일**이다. 그래서 가상 머신은 복사·백업·이동이 쉽고, 이 파일의 **형식(VDI·VMDK·VHD)** 이 제품마다 달라 시험에 나온다.

| 가상화로 얻는 것 | 설명 |
|---------------|------|
| **서버 통합** | 한가한 서버 여러 대를 한 대의 물리 장비에 모아 **자원 낭비를 줄인다** |
| **격리** | 게스트 하나가 망가져도 다른 게스트와 호스트는 영향이 없다 |
| **스냅샷** | 어느 시점의 상태를 저장해 두었다가 **그때로 되돌린다** |
| **이식성** | 이미지 파일만 옮기면 다른 장비에서 그대로 켠다 |

- 2주차에 "학습용이라면 가상 머신에 설치하라"고 권한 이유가 이 스냅샷이다. 파티션을 잘못 나눠도 되돌리면 그만이다.

## 하이퍼바이저의 두 종류

| 구분 | **Type 1 (네이티브·베어메탈)** | **Type 2 (호스트형)** |
|------|---------------------------|---------------------|
| 위치 | **하드웨어 위에 바로** | **운영체제 위에** |
| 성능 | **좋다** | 상대적으로 낮다 |
| 용도 | **서버·데이터센터** | **개인 PC·테스트** |
| 예 | **Xen, KVM, VMware ESXi, Hyper-V** | **VirtualBox, VMware Workstation** |

- **Type 1은 그 자체가 운영체제 역할**을 한다. 그래서 빠르다.
- **Type 2는 이미 깔린 운영체제 위에 프로그램처럼 설치**한다. 설치가 간단해 개인용으로 쓴다.

```text
      Type 1 (네이티브)                 Type 2 (호스트형)

   게스트 OS   게스트 OS             게스트 OS   게스트 OS
   ─────────────────────             ─────────────────────
       하이퍼바이저                      하이퍼바이저      ← 프로그램의 하나
   ─────────────────────             ─────────────────────
         하드웨어                          호스트 OS       ← 한 층이 더 있다
                                     ─────────────────────
                                           하드웨어
```

- 가르는 질문은 **"하이퍼바이저 밑에 무엇이 있나"** 다. **하드웨어면 Type 1, 운영체제면 Type 2** 다.
- Type 2가 느린 이유는 그림의 **한 층**이다. 게스트의 요청이 하이퍼바이저를 거친 뒤 호스트 OS를 한 번 더 거쳐야 하드웨어에 닿는다.
- **KVM이 헷갈리는 지점**이다. 리눅스를 먼저 설치하고 쓰니 Type 2처럼 보이지만, 모듈이 올라가면 **리눅스 커널 자체가 하이퍼바이저로 동작**하므로 **Type 1로 분류**한다. 시험도 이 분류를 따른다.
- 같은 회사 제품이 양쪽에 다 있다 — **VMware ESXi는 Type 1, VMware Workstation은 Type 2**. "VMware"라는 이름만으로 고르면 틀린다.

## 전가상화와 반가상화

| 구분 | **전가상화 (Full)** | **반가상화 (Para)** |
|------|------------------|------------------|
| 게스트 OS 수정 | **필요 없다** | **필요하다** |
| 방식 | 하드웨어를 **그대로 흉내** | 게스트가 하이퍼바이저에 **직접 요청** |
| 성능 | 보통 (하드웨어 지원 시 개선) | **좋다** |
| 하드웨어 지원 | **Intel VT-x / AMD-V** 활용 | — |
| 대표 | **VirtualBox, VMware, KVM** | **Xen**(초기) |

> **가르는 기준은 "게스트 OS를 고쳐야 하는가"** 다. **전가상화는 수정 없이 그대로**, **반가상화는 수정이 필요**하다. 대신 반가상화가 더 빠르다.

- **Intel VT-x와 AMD-V**는 CPU가 가상화를 도와주는 기능이다. 이 덕분에 전가상화도 성능이 크게 좋아졌고, 지금은 전가상화가 주류다.
- Xen은 반가상화로 시작했지만 지금은 전가상화도 지원한다.

### 왜 게스트를 고쳐야 하나

운영체제는 하드웨어를 **자기 혼자 독점한다**고 믿고 만들어졌다. 한 컴퓨터에 그런 운영체제가 여럿 올라가면 누군가 교통정리를 해야 한다.

```text
   전가상화                              반가상화

   게스트 OS : "디스크에 직접 쓴다"       게스트 OS : "하이퍼바이저야, 써 줘"
        │  (자기가 가상 머신인 줄 모른다)       │  (자기가 가상 머신인 줄 안다)
        ▼                                    ▼
   하이퍼바이저가 그 명령을 가로채         하이퍼콜(hypercall)로 바로 요청
   진짜 하드웨어 대신 흉내 내어 처리        → 가로채고 흉내 내는 과정이 없다
```

| 질문 | 전가상화 | 반가상화 |
|------|--------|--------|
| 게스트는 자신이 가상 머신임을 아는가 | **모른다** | **안다** |
| 하이퍼바이저에 일을 시키는 방법 | 평소처럼 명령 → 하이퍼바이저가 **가로챈다** | **하이퍼콜**로 직접 요청 |
| 수정할 수 없는 OS(윈도 등)를 올릴 수 있나 | **있다** | 어렵다 (커널을 고쳐야 하므로) |
| 느린 이유 / 빠른 이유 | 가로채고 흉내 내는 비용 | 그 과정을 건너뛴다 |

- 반가상화가 빠른데도 주류가 되지 못한 이유가 셋째 줄이다. **소스를 고칠 수 없는 운영체제는 올릴 수 없다.**
- CPU가 가로채는 일을 직접 도와주면서(**Intel VT-x, AMD-V**) 전가상화의 약점이 줄었다. 이렇게 CPU의 도움을 받는 방식을 **하드웨어 지원 가상화**라 한다.

리눅스에서는 CPU가 이 기능을 갖췄는지 `/proc/cpuinfo` 로 확인한다.

```bash
grep -E -c 'vmx|svm' /proc/cpuinfo
# 4
```

| 플래그 | 뜻 |
|-------|-----|
| **`vmx`** | **Intel VT-x** 지원 |
| **`svm`** | **AMD-V** 지원 |

- 출력된 숫자는 플래그가 보이는 **논리 CPU의 개수**다. 위 예는 코어 4개 모두 지원한다는 뜻이고, **0이면 그 환경에서는 하드웨어 지원 가상화를 쓸 수 없다.**
- 플래그 이름과 회사를 바꿔 묻는다. **vmx가 인텔, svm이 AMD** 다.

## 제품별 특징

| 제품 | 만든 곳 | 종류 | 특징 |
|------|--------|------|------|
| **VirtualBox** | **오라클** | **Type 2** | **GPL 공개**. 무료. **전가상화** |
| **VMware Workstation** | VMware | Type 2 | 상용. 개인용 |
| **VMware ESXi** | VMware | **Type 1** | 서버용 |
| **KVM** | 오픈소스 | **Type 1** | **리눅스 커널에 내장**됨 |
| **Xen** | 오픈소스 | **Type 1** | **반가상화의 대표** |
| **Hyper-V** | 마이크로소프트 | Type 1 | 윈도 서버용 |
| QEMU | 오픈소스 | 에뮬레이터 | 다른 CPU도 흉내 낸다. KVM과 함께 쓴다 |

### VirtualBox

시험에 **제품 스펙 그대로** 나오는 항목이다.

| 항목 | 내용 |
|------|------|
| 개발 | **오라클**(원래 이노테크 → 썬 → 오라클) |
| 라이선스 | **GPL** (기본 패키지) |
| 종류 | **Type 2 호스트형** |
| 가상화 방식 | **전가상화** (Intel VT-x / AMD-V 활용) |
| 기본 이미지 | **VDI** |
| **지원 이미지** | **VMDK(VMware)**, **VHD(마이크로소프트)**, HDD(Parallels) |

> ⚠️ **"VirtualBox는 반가상화를 지원한다"는 설명은 틀린 것**으로 출제된다. VirtualBox는 Intel VT-x·AMD-V를 이용한 **전가상화** 제품이다. 반면 **VMDK와 VHD 이미지를 지원한다는 설명은 맞다.**

| 더 알아 둘 것 | 내용 |
|------------|------|
| 설치할 수 있는 호스트 | **윈도 · 리눅스 · macOS · 솔라리스** — 여러 운영체제에서 돈다 |
| **게스트 확장**(Guest Additions) | 게스트 안에 설치하는 드라이버 묶음. **공유 폴더, 클립보드 공유, 화면 해상도 자동 조절**을 쓸 수 있게 된다 |
| **확장 팩**(Extension Pack) | 일부 추가 기능을 담은 별도 묶음. 기본 패키지와 달리 **GPL이 아닌 별도 라이선스**다 |
| 스냅샷 | 가상 머신의 현재 상태를 저장하고 되돌린다 |
| `VBoxManage` | 창 없이 가상 머신을 다루는 **명령줄 도구** |

- 보기에 **"VirtualBox 전체가 GPL"** 이 아니라 **"기본 패키지가 GPL"** 이라고 적히는 이유가 확장 팩이다.
- 실제 VirtualBox 설정 창에는 "반가상화 인터페이스"라는 항목이 있어 혼란스러울 수 있다. 이것은 게스트에 시각 정보 등을 알려 주는 **보조 기능**이고, 제품의 가상화 방식 분류는 **전가상화**다. 시험에서는 분류대로 답한다.

### 가상 디스크 이미지 형식

제품과 형식을 짝짓는 문제의 재료다.

| 형식 | 풀네임 | 만든 쪽 |
|------|-------|--------|
| **VDI** | Virtual Disk Image | **VirtualBox** 기본 |
| **VMDK** | Virtual Machine Disk | **VMware** |
| **VHD** | Virtual Hard Disk | **마이크로소프트** (후속 형식은 VHDX) |
| HDD | — | Parallels |
| qcow2 | QEMU Copy On Write | **QEMU·KVM** |

- VirtualBox는 **자기 형식(VDI)만 쓰는 것이 아니라 남의 형식(VMDK·VHD)도 읽는다.** "다른 회사의 이미지는 지원하지 않는다"는 보기는 틀린 설명이다.
- **VDI는 뜻이 둘**이다. VirtualBox 맥락에서는 디스크 이미지 형식이고, 기술 동향 맥락에서는 **데스크톱 가상화**(Virtual Desktop Infrastructure — 서버에 둔 데스크톱 화면을 원격으로 받아 쓰는 방식)다. 지문의 앞뒤로 가린다.

### VMware

| 제품 | 종류 | 쓰는 곳 |
|------|------|--------|
| **VMware ESXi** | **Type 1** | 서버·데이터센터 |
| **VMware Workstation** | **Type 2** | 윈도·리눅스 PC |
| VMware Fusion | Type 2 | macOS |

- VMware는 **상용 제품**이라는 점이 오픈소스인 VirtualBox(기본 패키지)·KVM·Xen과 갈린다.

### Xen

| 항목 | 내용 |
|------|------|
| 시작 | 영국 **케임브리지 대학**의 연구 프로젝트 |
| 종류 | **Type 1** |
| 방식 | **반가상화**로 출발, 이후 전가상화(HVM)도 지원 |
| **Dom0** | 하드웨어를 직접 다루며 다른 게스트를 **관리하는 특별한 도메인** |
| **DomU** | 일반 **게스트** 도메인 |

- Xen은 가상 머신을 **도메인(domain)** 이라 부른다. **Dom0이 관리용, DomU가 일반 게스트**다.
- "반가상화의 대표"로 묻지만 "전가상화를 전혀 못 한다"는 설명은 틀리다.

### KVM

| 항목 | 내용 |
|------|------|
| 풀네임 | **Kernel-based Virtual Machine** |
| 특징 | **리눅스 커널 자체가 하이퍼바이저**가 된다 |
| 종류 | **Type 1** |
| 함께 쓰는 것 | **QEMU**(장치 흉내), libvirt·`virsh`(관리) |

- 별도 하이퍼바이저를 설치하는 것이 아니라 **커널 모듈을 올리면 리눅스가 곧 하이퍼바이저**가 된다. 이 점이 KVM의 정의다.

```bash
lsmod | grep kvm
# kvm_intel             368640  0
# kvm                  1028096  1 kvm_intel
virsh list --all
#  Id   Name    State
# ------------------------
#  1    web01   running
#  -    db01    shut off
```

- `kvm` 이 공통 모듈이고 **`kvm_intel`(인텔) 또는 `kvm_amd`(AMD)** 가 CPU에 맞춰 함께 올라간다. `kvm` 줄 끝의 `1 kvm_intel` 은 "이 모듈을 `kvm_intel` 하나가 쓰고 있다"는 뜻이다.
- `virsh list --all` 은 꺼진 가상 머신까지 보여 준다. 실행 중인 것만 `Id` 번호를 받고 꺼진 것은 `-` 다.
- KVM은 CPU의 **VT-x / AMD-V가 있어야** 동작하는 **전가상화** 방식이다. 리눅스 커널 **2.6.20**부터 커널에 포함되었다.

| 도구 | 맡는 일 |
|------|--------|
| **KVM** | CPU·메모리 가상화 (커널 모듈) |
| **QEMU** | 디스크·네트워크 카드 같은 **장치 흉내** |
| **libvirt** | 여러 가상화 기술을 **같은 방법으로 다루게** 해 주는 관리 계층 |
| **`virsh`** | libvirt의 **명령줄** 도구 |
| `virt-manager` | libvirt의 **그래픽** 관리 도구 |

- **QEMU만 쓰면** 다른 CPU 구조까지 흉내 내는 **에뮬레이터**라 느리다. **KVM과 함께 쓰면** CPU 명령을 진짜 CPU가 직접 처리해 빨라진다. 그래서 둘은 늘 붙어 다닌다.

## 컨테이너 — 가상화와 다르다

| 구분 | **가상 머신** | **컨테이너** |
|------|------------|------------|
| 게스트 OS | **각각 따로** 있다 | **호스트 커널을 공유**한다 |
| 크기 | 무겁다(GB) | **가볍다(MB)** |
| 시작 속도 | 느리다 | **빠르다** |
| 격리 수준 | **강하다** | 상대적으로 약하다 |
| 예 | VirtualBox, KVM | **Docker**, LXC |

- **컨테이너는 운영체제를 따로 올리지 않는다.** 커널을 공유하고 프로세스만 격리한다. 그래서 가볍고 빠르다.
- **Docker는 가상 머신이 아니다.** 이 구분을 묻는 문제가 나온다.

```text
      가상 머신                          컨테이너

   앱        앱                       앱        앱
   게스트 OS  게스트 OS                 ─────────────────
   ─────────────────                   컨테이너 엔진(Docker)
     하이퍼바이저                       ─────────────────
   ─────────────────                    호스트 OS (커널 하나를 함께 쓴다)
       하드웨어                         ─────────────────
                                           하드웨어
```

- 그림에서 **게스트 OS 층이 통째로 없다.** 컨테이너가 가볍고 빨리 뜨는 이유의 전부다.
- 컨테이너는 리눅스 커널의 두 기능으로 만든다 — 프로세스가 **볼 수 있는 범위를 가르는** 네임스페이스(namespace)와 **쓸 수 있는 자원을 제한하는** cgroups다.
- 커널을 공유하므로 **호스트와 다른 커널의 운영체제는 올릴 수 없다.** 리눅스 호스트의 컨테이너 안은 언제나 리눅스다. 윈도를 올리려면 가상 머신이 필요하다.

## 지문으로 가려내기

| 지문에 나온 표현 | 답 |
|---------------|-----|
| "게스트 OS의 **수정 없이**" | 전가상화 |
| "게스트 OS의 **커널을 수정**해", "하이퍼콜" | 반가상화 |
| "**하드웨어 위에서 직접** 동작" | Type 1 (Xen·KVM·ESXi·Hyper-V) |
| "**호스트 운영체제 위에** 설치" | Type 2 (VirtualBox·VMware Workstation) |
| "**리눅스 커널에 포함**되어 커널이 하이퍼바이저 역할" | KVM |
| "**Dom0**", "케임브리지 대학" | Xen |
| "오라클", "**VDI** 기본, VMDK·VHD 지원", "기본 패키지 GPL" | VirtualBox |
| "**다른 CPU 구조**까지 흉내" | QEMU (에뮬레이터) |
| "**호스트의 커널을 공유**", "프로세스 격리" | 컨테이너 (Docker·LXC) |

## 자주 틀리는 지점

1. **반가상화가 게스트를 고치지 않는 쪽이다** → 반대다. **고치지 않는 쪽이 전가상화**다. "전(全)"은 하드웨어를 **전부** 흉내 낸다는 뜻으로 기억한다.
2. **전가상화가 언제나 더 빠르다** → 원리상으로는 **반가상화가 빠르다.** 전가상화는 CPU 지원으로 그 차이를 줄였을 뿐이다.
3. **VirtualBox는 Type 1이다** → 운영체제 위에 설치하는 **Type 2** 다.
4. **KVM은 Type 2다** → 커널 자체가 하이퍼바이저가 되므로 **Type 1** 이다.
5. **VMware 제품은 모두 Type 2다** → **ESXi는 Type 1** 이다.
6. **VirtualBox는 VDI 형식만 쓴다** → **VMDK·VHD도 지원**한다.
7. **VHD는 VMware의 형식이다** → VHD는 **마이크로소프트**, VMware는 **VMDK** 다.
8. **vmx가 AMD의 플래그다** → **vmx는 인텔, svm이 AMD** 다.
9. **Docker는 Type 2 하이퍼바이저다** → 하이퍼바이저가 아니라 **컨테이너** 기술이다.
10. **컨테이너마다 커널이 따로 있다** → **호스트 커널 하나를 공유**한다. 따로 있는 쪽이 가상 머신이다.

> 내일은 임베디드 시스템과 기술 동향을 다룬다.

## 📖 용어

- **가상화** : 한 대의 물리 컴퓨터에서 여러 운영체제를 동시에 실행하는 기술.
- **하이퍼바이저** : 가상 머신에 하드웨어 자원을 나누어 주는 소프트웨어.
- **Type 1 / Type 2** : 하드웨어 위에서 바로 동작하는 방식 / 운영체제 위에 설치하는 방식.
- **전가상화** : 게스트 OS를 수정하지 않고 하드웨어를 흉내 내는 방식.
- **반가상화** : 게스트 OS를 수정해 하이퍼바이저에 직접 요청하는 방식.
- **VirtualBox** : 오라클의 Type 2 가상화 제품. GPL로 공개되어 있고 전가상화를 사용한다.
- **KVM** : 리눅스 커널 자체를 하이퍼바이저로 만드는 가상화 기술.
- **컨테이너** : 호스트 커널을 공유하며 프로세스만 격리하는 경량 방식. Docker가 대표적이다.

## 📝 연습 문제

**문제 1.** 다음 중 게스트 운영체제의 커널을 수정해야 하는 가상화 방식으로 알맞은 것은?

A) 전가상화  
B) 컨테이너  
C) 반가상화  
D) 에뮬레이션  

**정답: C**  
해설: 반가상화는 게스트 운영체제가 하이퍼바이저에 직접 요청을 보내도록 커널을 수정해야 하며 그 대신 성능이 좋습니다. 전가상화는 하드웨어를 그대로 흉내 내므로 게스트 운영체제를 수정할 필요가 없습니다.

---

**문제 2.** 다음 중 VirtualBox에 대한 설명으로 알맞지 **않은** 것은?

A) 인텔과 AMD 기반의 반가상화를 지원한다  
B) 기본 패키지가 GPL 라이선스로 공개되어 있다  
C) VMware의 VMDK 이미지 형식을 지원한다  
D) 마이크로소프트의 VHD 이미지 형식을 지원한다  

**정답: A**  
해설: VirtualBox는 Intel VT-x와 AMD-V 같은 하드웨어 지원 기능을 활용한 전가상화 제품이며 반가상화 방식을 사용하지 않습니다. 기본 패키지가 GPL로 공개되어 있고 자체 형식인 VDI 외에 VMDK와 VHD 이미지도 지원한다는 설명은 모두 맞습니다.

---

**문제 3.** 다음 중 하드웨어 위에서 직접 동작하는 Type 1 하이퍼바이저에 해당하는 것으로 알맞은 것은?

A) VirtualBox  
B) VMware Workstation  
C) Docker  
D) KVM  

**정답: D**  
해설: KVM은 리눅스 커널 자체가 하이퍼바이저 역할을 하므로 하드웨어 위에서 직접 동작하는 Type 1에 해당하며 Xen과 VMware ESXi도 같은 유형입니다. VirtualBox와 VMware Workstation은 운영체제 위에 설치하는 Type 2이고, Docker는 가상화가 아닌 컨테이너 기술입니다.

---

**문제 4.** 다음 중 KVM에 대한 설명으로 알맞은 것은?

A) 게스트 운영체제 없이 애플리케이션만 격리한다  
B) 리눅스 커널 자체가 하이퍼바이저 역할을 한다  
C) 마이크로소프트가 개발한 윈도 전용 가상화 기술이다  
D) 반가상화만 지원하며 게스트 커널 수정이 필수다  

**정답: B**  
해설: KVM은 Kernel-based Virtual Machine의 줄임말로 커널 모듈을 적재하면 리눅스 자체가 하이퍼바이저가 됩니다. 장치 흉내는 QEMU가 맡고 관리에는 libvirt와 `virsh`를 사용합니다. 애플리케이션만 격리하는 것은 컨테이너 방식입니다.

---

**문제 5.** 다음 중 컨테이너 기술의 특징으로 알맞은 것은?

A) 게스트 운영체제를 각각 따로 설치한다  
B) 가상 머신보다 이미지 크기가 크고 무겁다  
C) 호스트의 커널을 공유하므로 가볍고 시작이 빠르다  
D) 서로 다른 CPU 구조를 흉내 낼 수 있다  

**정답: C**  
해설: 컨테이너는 별도의 게스트 운영체제를 올리지 않고 호스트 커널을 공유하면서 프로세스만 격리하므로 크기가 작고 실행이 빠릅니다. 다른 CPU 구조를 흉내 내는 것은 QEMU 같은 에뮬레이터의 기능입니다.
