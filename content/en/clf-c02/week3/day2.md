# Day 2 - Application Integration: Connecting Systems Loosely

Up through yesterday we looked at "where data is stored." Today we look at "how systems talk to each other." In a small app, a function can just call another function directly within a single program. But in a large service with separate order, payment, and notification systems, wiring them together directly means that when one dies, the whole thing collapses with it.

That's why in the cloud we connect systems loosely using **asynchronous messaging**. Today we'll distinguish, at a conceptual level, the three core services for this — SQS, SNS, and EventBridge.

## Why Not Connect Directly: The Story of Coupling

Suppose the order service calls the payment service directly (a synchronous call). If the payment service slows down or dies for a moment, the order service also stalls, waiting for a response. The two systems are strongly bound together — tightly coupled.

Instead, what if the order service tosses a **message** saying "an order came in" into an intermediate queue, and the payment service pulls it out and processes it when it's ready? Even if payment goes down for a while, the message sits safely in the queue, and orders are unaffected. This is **loose coupling**.

> 💡 **Related theory**: Loose coupling is a core principle of the **Reliability** pillar of the Well-Architected Framework. To keep the failure of a single component from spreading across the whole system, you break the middle with messages/events instead of direct calls.

```
[Tight coupling]  Order ──direct call──▶ Payment   (if Payment dies, Order stalls too)

[Loose coupling]  Order ──message──▶ [Queue] ──▶ Payment  (if Payment dies, it's held in the queue)
```

## Amazon SQS: A Queue That Safely Holds Messages

**Amazon SQS (Simple Queue Service)** is a fully managed **message queue**. When one side (the producer) puts a message into the queue, the other side (the consumer) pulls it out and processes it when it's ready. The key is **1:1 delivery and buffering**.

- The producer and consumer don't need to be alive at the same time (asynchronous).
- When traffic surges, it piles up in the queue and the consumer processes it at its own pace (buffering).
- Messages are retained until the consumer signals completion, so they aren't lost.

A classic analogy is a **café's order queue**. Even when customers pour in, the order tickets line up, and the barista works through them one at a time.

> 💡 **Related theory**: When you see keywords like "messages must not be lost," "buffer a traffic spike," or "pile up work in a queue for sequential processing," it's SQS. The decisive difference from SNS is that a single message is usually taken and processed by just one consumer.

## Amazon SNS: Notifying Many Places at Once with One Message

**Amazon SNS (Simple Notification Service)** is a **publish/subscribe (pub/sub)** notification service. When a publisher sends a message once to a single **topic**, it's **delivered simultaneously to the many targets** subscribed to that topic (1:many, fan-out).

Subscribers can be email, SMS, HTTP endpoints, Lambda functions, and SQS queues. For example, a single "order complete" message can, at the same time, send the customer an email, record it in an analytics system, and wake up the shipping system.

| Item | SQS | SNS |
|------|-----|-----|
| Model | Queue (1:1, pull) | Topic (1:many, push) |
| Core analogy | Order queue | Broadcast/notification dispatch |
| Delivery method | Consumer polls and pulls | Pushed to subscribers immediately |
| Typical use | Work buffering, async processing | Multi-recipient notifications, fan-out |

> 💡 **Related theory**: When you see "notify multiple systems of one event at once," "email/SMS notifications," or "fan-out," it's SNS. In practice, the **SNS + SQS combination** is common (subscribe multiple SQS queues to an SNS topic to fan out while each queue still buffers safely).

## Amazon EventBridge: Wiring Flows Together Based on Events

**Amazon EventBridge** is an **event bus** service. It receives **events** generated by AWS services, your own apps, and external SaaS (e.g., Zendesk, Datadog), and routes them to the appropriate targets according to rules.

It may look similar to SNS, but EventBridge is strong at **filtering and routing based on the content of the event**. For example, you can build conditional flows without code as rules — "when a file lands in a specific folder in S3 → run this Lambda," or "when an EC2 state changes → send this notification." It also provides a **schedule (cron)** feature to run tasks at fixed intervals.

```
[Various event sources]         [EventBridge rules]        [Targets]
 AWS services ──┐                Content filter + routing    Lambda
 My app       ──┼──▶ [Event bus] ──────────────▶            SQS/SNS
 SaaS apps    ──┘                                            Step Functions ...
```

> 💡 **Related theory**: When you see "react to AWS service state changes," "integrate SaaS events," "conditionally route by event content," or "run automatically at a set time," it's EventBridge. It acts as the glue that lets you build event-driven architecture without code.

## Distinguishing the Three on One Page

| Signal (keywords) | Service |
|--------------|--------|
| Work queue, buffering, loss prevention, sequential processing | SQS |
| Multi-recipient notifications, email/SMS, fan-out | SNS |
| Event routing, reacting to service/SaaS events, scheduling | EventBridge |

The CLF exam asks not about deep configuration but about the ability to split scenarios apart using these **three one-line identities**. "Notify many people" → SNS, "safely pile up and process work" → SQS, "react to events and wire flows together" → EventBridge.

## Wrapping Up

Today we looked at three integration services that connect systems loosely. SQS is a queue that safely holds messages, SNS is publish/subscribe that notifies many places at once, and EventBridge is an event bus that routes events by rule. All three share a single goal — keeping components from being bound directly to one another, so that when one wobbles, the whole holds up.

## 📝 연습 문제

**문제 1.** You want to decouple an order system and a payment system so that no messages are lost during a traffic spike and the payment system processes them one at a time at its own pace. Which service is most appropriate?

A) Amazon SNS  
B) Amazon SQS  
C) Amazon EventBridge  
D) Amazon ElastiCache  

**정답: B**  
해설: SQS safely piles messages into a queue to decouple producer and consumer (buffering), so it cushions traffic spikes and prevents loss. SNS is for multi-recipient notifications, EventBridge is for event routing, and ElastiCache is a cache — none are meant for a work queue.

---

**문제 2.** With a single "order complete" event, you want to send the customer an email, record it in an analytics system, and wake up the shipping system all at once. Which service is most appropriate?

A) Amazon SQS  
B) Amazon RDS  
C) Amazon SNS  
D) Amazon Redshift  

**정답: C**  
해설: SNS uses the publish/subscribe (pub/sub) model to deliver a single message to multiple subscribers simultaneously (fan-out). SQS is typically a 1:1 queue where one consumer takes the message, and RDS/Redshift are databases, not notification-dispatch services.

---

**문제 3.** What is the main benefit of connecting system components with messages instead of direct calls?

A) Tight coupling between components improves speed  
B) Loose coupling prevents a single component's failure from spreading across the whole  
C) Reduced database cost  
D) Automatic IAM permission configuration  

**정답: B**  
해설: Breaking the middle with messaging creates loose coupling, so even if one component dies, the message is retained and other components are unaffected. Direct calls instead create tight coupling, and cost reduction or IAM configuration is not the direct purpose of messaging.

---

**문제 4.** You want to conditionally route work based on the content of AWS service or SaaS events — for example, automatically running a Lambda when a specific file is uploaded to S3. Which service is most appropriate?

A) Amazon SQS  
B) Amazon EventBridge  
C) Amazon ElastiCache  
D) Amazon Aurora  

**정답: B**  
해설: EventBridge is an event bus that receives events from various sources and routes them to targets by rules (content filters), and it also supports scheduled execution. SQS is a simple queue, ElastiCache is a cache, and Aurora is a database, so none have event-routing capability.

---

**문제 5.** Which is the most accurate description of the difference between SQS and SNS?

A) SQS pushes to multiple recipients, and SNS is polled by a single consumer  
B) SQS is a message queue (usually 1:1, consumer pulls), and SNS is publish/subscribe (1:many, pushed to subscribers)  
C) Both are database services  
D) SQS is exclusively for sending notifications, and SNS is exclusively for buffering work  

**정답: B**  
해설: SQS is a message queue the consumer polls and pulls from (usually 1:1, buffering), while SNS is publish/subscribe that pushes one message to multiple subscribers (1:many). A swaps the two, both are not databases, and their purposes are also the reverse of D.
