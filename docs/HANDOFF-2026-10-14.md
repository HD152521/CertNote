## 4. 작업 방식 (이번에 쓴 방법과 함정)

### 단계별 검수 게이트

각 단계를 `구현 에이전트 → 총괄 검수 에이전트 → (FAIL 이면 지적만 재작업) → 재검수` 로 돌렸다.
검수 에이전트는 구현 보고를 믿지 않고 직접 실행한다: `tsc`, `vitest`, `npm run build`, `test:e2e:only`,
`test:e2e:seo:only`, 그리고 **가드를 일부러 망가뜨려 테스트가 죽는지(뮤테이션)** 확인한다. 콘텐츠(문제은행)는
정답을 가린 채 전부 풀고 대조했다. 이 방식에서 테스트가 다 초록인데도 실제 결함이 여러 번 잡혔다
(검색창 15초 멈춤, 자정 경계 환불 오류, 캐시된 소프트 404 등).

### 환경

- 레포는 여러 세션이 공유한다. 메인 체크아웃(`CertNote-repo`)에서 브랜치를 바꾸지 말고 `git worktree add` 로 분리.
- 로컬 `.env` 는 **개발 DB(`certnote_dev`)만** 가리키게 둔다. E2E 의 `e2e/db.ts` 가 DB 이름을 검사한다.
- 새 워크트리는 `npm ci` 필요(약 5~6분). 낡은 `.next` 가 남아 있으면 `tsc` 가 `.next/types` 오류를 낸다 — 지우고 다시.
- `npm run build` 는 `src/data/questions.json`·`exam-questions.json` 을 다시 쓴다. CRLF 만 다르면 `git checkout --`.
- 이 PC 는 메모리가 빠듯하다(여유 1GB 수준일 때가 있음). 빌드는 한 번에 하나, 다른 세션이 테스트를 돌리면 빌드가 죽을 수 있다.
- 전체 vitest 실행 시 무거운 import 테스트가 느려진다(`cacheContract.test.ts` 는 180초 제한으로 올림). 단독 실행은 빠르다.
- E2E 로그인은 분당 5회 제한이 있어 `auth.setup.ts` 의 storageState 를 재사용한다.
- AI 튜터 E2E 는 가짜 스트림(`E2E_FAKE_TUTOR`, `x-e2e-fake-tutor` 헤더)을 쓴다. `VERCEL` 환경에서는 켜지지 않는다.

### 운영 DB 마이그레이션 절차

`npm run db:migrate` 는 `.env` 를 읽어 **개발 DB 에 적용된다.** 운영에는 PowerShell 에서:

```powershell
$env:DATABASE_URL = '운영_DB_주소'   # 작은따옴표 필수. 주소 끝 DB 이름이 certnote_dev 가 아닌 것
node scripts/db-migrate.mjs
Remove-Item Env:DATABASE_URL
```

마이그레이션은 항상 배포(머지)보다 먼저. 스크립트는 멱등이다.
